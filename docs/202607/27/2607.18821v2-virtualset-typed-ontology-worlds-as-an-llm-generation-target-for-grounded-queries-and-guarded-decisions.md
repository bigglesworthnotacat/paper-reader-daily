## 摘要
大语言模型越来越多地读取和处理企业数据，但SQL会给出延迟的错误信号：幻觉字段或关系可以执行并返回看似合理的错误答案，而错误的写入在事后无法安全评估。我们提出VirtualSet，一个实时、接收者类型化的本体世界接口和大语言模型生成目标。与SQL不同，模型在实体-边世界之上发出集合表达式。通用约束投影（GCP）在执行前检查表达式，同时未来通过集合链保留具体的接收者类型，将无效字段、边、接收者和动作转化为基于令牌锚定的类型错误。类型清洁的读取使用SQL快速路径或有限流解释，并有一个奇偶校验预言在已执行的操作空间上检查两条路径。相同的底层支持守卫决策：动作首先在模拟世界中运行，而世界变更事件在实现前需要外部批准。在BIRD上，我们将关系模式提升为类型化世界，并比较VirtualSet与直接SQL，同时尽可能保持模型、证据、值、零样本设置、超时、词汇表、修复/投票和评分器不变。在一个冻结的1,072个问题划分上，VirtualSet达到67.5%的准确率，而使用词汇表匹配的直接SQL（带修复和投票）为63.5%（+4.0个百分点；McNemar精确p=0.00117），使用deepseek-reasoner。全语料分析未发现引擎对类型清洁表达式的计算错误；剩余错误源于模型语义或黄金缺陷。在一个30体守卫语料中，写入链拦截了20/20个幻觉动作体，零误报。因此，VirtualSet在SQL的主场基准上保持竞争力，同时为守卫决策提供执行前语义。

## Abstract
Large language models increasingly read and act on enterprise data, but SQL gives a late error signal: hallucinated fields or relations can execute and return plausible wrong answers, while incorrect writes cannot be safely assessed after execution. We present VirtualSet, a live, receiver-typed ontology-world interface and generation target for LLMs. Instead of SQL, the model emits set expressions over entity-edge worlds. Generic Constraint Projection (GCP) checks expressions before execution, while future this preserves concrete receiver types through collection chains, turning invalid fields, edges, receivers, and actions into token-anchored type errors. Type-clean reads use a SQL fast path or bounded stream interpretation, with a parity oracle checking both paths over the exercised operator space. The same substrate supports guarded decisions: actions run first in a simulated world, and world-change events require external approval before actualization. On BIRD, we lift relational schemas into typed worlds and compare VirtualSet with direct SQL while holding the model, evidence, values, zero-shot setting, timeout, glossary, repair/voting, and grader constant where possible. On a frozen 1,072-question split, VirtualSet achieves 67.5% accuracy versus 63.5% for glossary-matched direct SQL with repair and voting (+4.0 points; McNemar exact p = 0.00117) using deepseek-reasoner. Full-corpus analysis finds no engine mis-computation of a type-clean expression; remaining errors arise from model semantics or gold defects. In a 30-body guard corpus, the write chain intercepts 20/20 hallucinated action bodies with zero false positives. VirtualSet thus remains competitive on SQL's home benchmark while providing pre-execution semantics for guarded decisions.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：大语言模型（LLM）在直接使用SQL查询企业数据时，存在两类严重失效模式：
  - **读错误**：LLM编造不存在的字段或关系，生成的SQL仍能解析并执行，返回一个看似合理但实际错误的结果，且没有警告。
  - **写错误**：LLM执行错误的UPDATE等写操作，由于执行本身就是伤害，无法在事后通过执行结果来评估错误。
- **背景**：现有文本到SQL（text-to-SQL）方法依赖执行后比较答案来发现错误，这对写操作完全无效。需要一种在**执行前**就能提供语义错误信号的生成目标。
- **整体含义**：本文提出一种替代SQL的、类型安全的生成目标——VirtualSet，使LLM输出的是类型化本体世界上的集合表达式，通过执行前的类型检查（GCP）即时捕获无效字段/关系，并支持在模拟世界中守卫决策，从而从根本上改变LLM与企业数据交互的安全范式。

## 2. 论文提出的方法论

### 2.1 核心思想
- 将企业数据抽象为**实时运行的、接收者类型化的本体世界**（typed ontology world），其中实体、字段、边（关系）和动作均具有显式类型。
- LLM不再生成SQL字符串，而是生成**VirtualSet表达式**——一种基于集合导航的表达式语言，支持filter、map、group_by、count等操作。
- 利用**通用约束投影（GCP）** 在表达式真正执行前进行类型检查：任何不存在的字段、边、接收者或动作都会被报告为“令牌锚定的类型错误”，并附上合法成员的闭包，供LLM修复。
- 引入 **“future this”** 规则：集合操作（如filter）返回的仍然是具名实体集合（而非泛型流），从而在表达式链的每个步骤都能保留具体的接收者类型，防止类型丢失。

### 2.2 关键技术细节
- **表达式结构**：实体集合继承通用`VirtualSet<a>`参数化类型，包含`filter: (a -> Bool) -> this`等操作，其中`this`保持接收者具体类型。
- **双模式执行**（Dual-Mode Execution）：
  - **GCP2SQL**：将可翻译的VirtualSet链编译为单个SQL语句（通过SQLite快速路径），适用于简单过滤、投影、聚合和边导航。
  - **GCP2Stream**：当lambda包含无法翻译的操作（如UDF、捕获变量）时，在内存中逐行解释执行，配有安全行数限制（默认10,000行），超限则报`STREAMING_OVERFLOW`而不静默截断。
  - **奇偶校验预言**：在开发过程中对两种执行路径的结果进行一致性和正确性验证。
- **生成与修复循环**：
  - 提供系统大纲（System Outline）、世界大纲（World Outline）、全局配方（Global Recipe）和世界配方（World Recipe）作为提示上下文。
  - LLM一次性生成完整VirtualSet表达式，GCP检查，若通过则执行；若类型错误则提供令牌锚定的错误信息和合法成员闭包，允许最多两次重新生成。
  - 当首次结果可疑（空、错误、类型拒绝或修复后）时，启用延迟投票（Lazy Voting）：最多再采样2个表达式，取两个一致的结果执行。
- **守卫决策写入链**：
  - 所有持久写入操作归约为三个原语：`collection.create(...)`、`entity.update(...)`、`entity.delete()`，并在实体大纲中通过能力标记控制。
  - 领域动作（domain action）是大纲代码，使用上述原语和VirtualSet读/导航操作。
  - 动作体在执行前先由GCP进行类型检查；通过后先在本体世界的**模拟版本**（通过GCP2Stream）中执行，产生类型化事件；外部监听器（策略引擎、审批队列等）决定是否批准实际化。LLM的因果影响止于模拟世界边界。

## 3. 实验设计

### 3.1 数据集与基准
- **主基准**：BIRD dev（1,534个问题，覆盖11个关系数据库）。划分为462问题开发集和1,072问题评估集。
  - BIRD是文本到SQL的“主场”基准，包含外部知识证据（evidence）和官方词汇表（glossary）。
- **辅助基准**：Spider dev（1,034个问题），用于稳健性检验。

### 3.2 对比方法
- **VirtualSet arm**：将BIRD关系模式机械提升为类型化本体世界，使用VirtualSet表达式+ GCP检查+修复/投票循环。
- **Direct-SQL arm**：对照方法，使用相同模型、相同证据、相同词汇表（以SQL原生表/列描述形式提供）、相同值词典、相同零样本条件、相同超时、相同执行评分器（EX@1）、相同修复/投票机制（SQL端执行反馈）。
- **关键差异**：VirtualSet使用执行前类型诊断进行修复，SQL只能从执行后数据库反馈修复。

### 3.3 实验数量与充分性
- **主实验**：在1,072问题评估集上，使用deepseek-reasoner进行单次运行，报告STRICT执行准确率（逐行与黄金SQL结果比较）。
- **复现实验**：使用deepseek-chat模型在同一评估集上进行检查点复现（同一模型家族，不同版本）。
- **消融实验**：

  - 测试了少样本示例（few-shot exemplars），发现脆弱且不跨数据库泛化，最终两臂均为零样本。
- **执行基板审计**：对全部11个数据库的失败进行逐条分析，检查生成表达式、下推SQL和黄金SQL，确认零项引擎错误计算了类型清洁表达式。

## 5. 论文的主要结论与发现

- **读性能**：VirtualSet在BIRD上达到67.5%准确率，优于词汇表匹配的直接SQL（63.5%），差距+4.0个百分点（p=0.00117）。优势主要来自首次生成清洁的子集（+51题），修复/投票尾基本持平（-1题）。
- **执行可靠性**：对类型清洁表达式，引擎零误计算。
- **守卫决策**：在30体语料上，完美拦截20/20幻觉动作体，零误报（10/10合法体均通过）。
- **关键洞察**：类型系统不解决语义误解（如退休年龄的边界规则），但能有效拦截结构级错误（幻字段、幻边）。语义错误仍需依赖领域证据或元数据。
- **架构意义**：VirtualSet作为生成IR，使底层SQL后端可插拔（GCP2SQL插件），无需重写提示示例。

## 6. 优点

- **读/写不对称性的解决思路新颖**：识别出“读错误可事后审计，写错误不可”的关键问题，并设计执行前语义检查的生成目标。
- **接收者类型检查与future this机制**：在动态运行时保持类型精度，使链式操作不丢失实体上下文，避免泛型流的类型擦除。
- **双模式执行与奇偶校验**：既高效（SQL下推）又安全（流解释器限制行数），且通过预言验证一致性。
- **守卫写入链设计简洁而有效**：类型检查→模拟世界执行→事件门控实际化，清晰划分LLM的因果边界。
- **实验控制严谨**：在BIRD上对模型、证据、词汇表等变量进行严格控制，使比较公正，统计检验支持结论。

## 7. 不足与局限

- **模型家族偏差**：仅使用DeepSeek系列模型进行复现（两个版本），未使用GPT、Claude等其他主流模型，无法排除vendor-family效应。
- **基准局限**：BIRD本体是机械提升自关系模式，并非原生设计为类型化本体世界；Spider仅作为方向性稳健性检验，非原生本体测量。
- **守卫语料规模小**：30体语料属于小规模概念验证，未在真实世界的多样化场景中充分测试。
- **语义错误仍无法解决**：类型检查仅针对结构级幻觉（字段/边不存在），对聚合粒度、边选择错误、投影形状等语义问题无直接帮助，这些问题仍是主要的残余失败原因（如论文所述“错误聚合粒度”等）。

- **未提供算力开销分析**：缺少VirtualSet生成、GCP检查、修复循环等环节的延迟和计算资源对比。
- **写入端无端到端决策精度基准**：论文声明“不声称动作基准或端到端决策准确率”，守卫测试仅为“拦截幻觉”的单点测试，缺少在复杂决策场景下的系统性评估。
