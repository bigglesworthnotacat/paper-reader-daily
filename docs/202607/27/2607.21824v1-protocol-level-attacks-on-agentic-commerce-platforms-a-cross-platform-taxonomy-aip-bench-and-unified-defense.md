## 摘要
智能体商务平台让AI智能体自主发现服务、移动支付并代表用户使用用户凭证，它们已在处理真实资金。迄今为止，其安全性几乎完全在AI模型层面通过提示注入和不对齐进行研究。我们表明，更具后果性的风险位于下一层，即智能体与商务服务之间的协议中。在那里，漏洞是结构性的：利用是确定性的，且独立于智能体运行的模型，因此任何模型改进都无法消除它们。在三个领先平台上，我们识别出33个此类漏洞，每个都无论部署何种模型都能确定性成功，在实时测量时攻击成功率达到100%。相同故障模式在独立构建的代码库中重复出现，这是系统性模式而非孤立漏洞。其中三个可链式组合成端到端支付劫持。我们贡献了一个分类体系，将这些结构性攻击与模型依赖的语义攻击区分开来。我们还构建了两个工具：AIP-Bench（智能体交互协议基准测试），据我们所知是首个用于智能体商务安全确定的基准测试；以及PCAT（协议级商务智能体信任），一种平台无关的防御，将五种结构性类别中的四种（RC-1、RC-2、RC-4、RC-5）的结构性攻击成功率降至零，RC-3（可观察凭证通道）降至仅警告，而无需修改任何平台。智能体商务必须在协议层而非仅模型层确保安全。

## Abstract
Agentic commerce platforms let AI agents autonomously discover services, move payments, and wield user credentials on their users' behalf, and they already handle real money. Their security has so far been studied almost entirely at the level of the AI model, through prompt injection and misalignment. We show that the more consequential risks lie one layer down, in the protocol between agents and commerce services. There, vulnerabilities are structural : exploitation is deterministic and ndependent of which model an agent runs, so no model improvement removes them. Across three leading platforms we identify 33 such vulnerabilities, each succeeding deterministically regardless of the deployed model, at a 100% attack-success rate (ASR) wherever live-measured. The same failure modes recur across independently built codebases, a systemic pattern rather than isolated bugs. Three of them chain into an end-to-end payment hijack. We contribute a taxonomy separating these structural attacks from model-dependent semantic ones. We also build two artifacts: AIP-Bench (Agent Interaction Protocol Benchmark), to our knowledge the first deterministic benchmark for agentic commerce security, and PCAT (Protocol-level Commerce Agent Trust), a platform-agnostic defense that drives the structural attack-success rate to zero for four of the five structural classes (RC-1, RC-2, RC-4, RC-5), with RC-3 (observable credential channels) reduced to warn-only, without modifying any platform. Agentic commerce must be secured at the protocol layer, not only the model.

- **研究动机**：现有对智能体商务平台（如 CoralOS、Fetch.ai、Google AP2）的安全研究几乎全部集中在 AI 模型层，即提示注入和模型不对齐导致的语义攻击。然而，这些平台的真正风险在于更底层的**协议层**——智能体与商务服务之间的交互协议。协议层漏洞是结构性的（structural），与部署的 AI 模型无关，因此不能通过模型改进来修复。
- **核心问题**：当前主流智能体商务平台存在大量协议级结构性漏洞，这些漏洞可被攻击者确定性利用（攻击成功率为 100%），且跨平台复现，构成系统性风险，而非孤立软件缺陷。三个漏洞可链式组合实现端到端支付劫持。
- **整体含义**：必须将安全关注点从模型层转向协议层，构建平台无关的协议级防御，否则即使最强模型也无法阻止这些攻击。

### 2. 论文提出的方法论：核心思想、关键技术细节

- **核心思想**：
  - 区分 **结构性攻击**（protocol-level, deterministic, model-independent）和 **语义攻击**（reasoning-level, probabilistic, model-dependent）。结构性攻击不依赖模型推理，而是利用协议认证、支付原子性、会话隔离等层面的设计缺陷，因此成功率恒为 100%。
  - 提出六类根因分类（RC-1 至 RC-6），其中 RC-1 至 RC-5 为结构性，RC-6 为语义性。
- **关键技术细节**：
  1. **系统审计**：对三个代表性平台（CoralOS、Fetch.ai uAgents、Google AP2 v0.2.0）进行代码级与运行级安全分析，识别 33 个结构性漏洞。
  2. **AIP-Bench 基准**：首个确定性智能体商务安全基准，使用非 LLM 的确定性评判器（如 HTTP 状态码、钱包地址字符串匹配、日志模式正则等），避免 LLM 评判器的偏见和可注入性。
  3. **PCAT 防御框架**：平台无关的 HTTP sidecar，实现五条原理：
     - P1（响应完整性验证，RC-1）：使用 ECDSA P-256 签名，防伪造注册表响应。
     - P2（调用者身份绑定，RC-2）：基于 DID 的调用者证明，验证身份和授权范围。
     - P3（安全通道强化，RC-3/RC-5）：检测 URL 中的凭证、CSRF 令牌验证、重定向白名单。
     - P4（支付状态原子性，RC-4）：使用 asyncio.Lock 和 compare-and-swap 串行化支付检查-执行操作。
     - P5（MCP 工具调用授权，RC-5）：要求敏感工具调用携带预注册身份令牌。
     - 形式化安全定理：如 P1 下伪造签名概率可忽略（基于 ECDLP 假设），P3 下 CSRF 被 HTTP 403 阻断，P4 下单进程内并发双倍扣除概率为 0。

### 6. 论文的主要结论与发现

- **核心发现**：智能体商务平台存在大量结构性（模型无关）协议级漏洞，攻击成功率恒为 100%。这些漏洞在不同平台重复出现，表明是架构性失败模式而非孤立错误。
- **分类有效性**：将攻击分为结构性（RC-1～RC-5）和语义性（RC-6）两类，前者需协议层修复，后者需模型层防御，两者互补。
- **PCAT 有效性**：平台无关的 HTTP sidecar 可将 RC-1、RC-2、RC-4、RC-5 的 ASR 降为 0%，RC-3 降为仅警告，零假阳性，且延迟开销微小（P1 最慢约 0.21 ms）。
- **模型行为梯度**：语义攻击（V5 的 IPI 影响）成功率在便宜模型（GPT-4o-mini、Gemini Flash）为 99-100%，主流模型 GPT-4o 为 68%，而对齐训练的模型（Claude、Gemini Pro）为 0%，说明对齐训练而非模型规模是抵抗关键。
- **链式攻击**：三个漏洞可组合成端到端支付劫持，从市场注入到凭证窃取再到钱包重定向。
- **安全含义**：仅靠模型改进无法防御协议层漏洞，必须同时强化协议层安全；PCAT 提供现成的平台无关解决方案。

### 7. 优点

- **系统性**：首次跨平台系统分类结构性攻击，覆盖三个不同架构的主流平台，发现 33 个漏洞，揭示共有根因。
- **理论与实践结合**：不仅识别漏洞，还构建了确定性基准 AIP-Bench 和可部署的防御框架 PCAT，形式化证明了防御属性。
- **方法创新性**：将攻击分为结构性与语义性，提供正式定义；使用确定性评判器避免 LLM 偏差；PCAT 设计为 sidecar 无需修改平台代码。
- **实验严谨**：实时运行系统验证（live）、代码级证明、大规模 LLM 行为实验（1440 次）、统计置信区间、分布式验证（4 实例）等，全面且有复现性。
- **实用性**：PCAT 延迟极低（<0.21 ms/请求），吞吐量高（>5100 req/s），假阳性 0%，可直接部署。
- **伦理透明**：负责任披露，90 天封锁期，仅发布非敏感信息。

### 8. 不足与局限

- **实验覆盖**：仅覆盖三个平台（CoralOS、Fetch.ai、AP2），可能未涵盖所有架构类型（如全链上、全加密注册表）。作者建议后续扩展。
- **LLM 行为研究规模**：1,440 次试验中，某些模型显示温度依赖性，且仅用了 3 种 IPI 变体。更多变体和更大样本量可进一步提升边界精度。
- **PCAT 局限**：
  - P2 依赖 DID 解析器，无解析器时回退为记录和允许，不完全防护。
  - P4 的原子性证明仅适用于单进程，多进程场景通过实验验证但无形式化证明。
  - 14 个漏洞位于 PCAT 层之外（如内部 LLM 代理调用、文件系统竞态、WebSocket 事件等），PCAT 无法覆盖，需其他层修复。
- **安全审查自我认可**：PCAT 自身发现并修复了 4 个实施漏洞，但未经过独立外部审计。
- **真实资金未涉及**：支付劫持证明停留在协议层（生成 Devnet 密钥对但未链上结算），符合标准实践，但实际攻击链可能需要进一步验证。
- **道德限制**：实时攻击仅针对测试环境，未消耗真实资金。
