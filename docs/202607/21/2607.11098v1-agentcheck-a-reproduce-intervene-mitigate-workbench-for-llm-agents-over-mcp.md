## 摘要
使用工具的LLM代理大多在假设所有工具都正常工作的条件下进行评估。当工具超时、返回过时值或在部署过程中其描述被投毒时，开发者需要一种可控的方式来复现故障、测试修复方案，并在部署前确认修复有效。我们提出AgentCheck，一个开源网络工作台，它将MCP服务器转变为干预界面。AgentCheck让代理与其实工具交互并记录每个工具响应，然后通过故障注入器（12种类型）扰动响应后重新运行代理。匹配的工具调用从缓存重放，后续工具调用在代理偏离后实时进行。这形成了一个复现-干预-确认循环：开发者切换缓解措施，针对相同故障重新运行，并观察故障是否消失。评分分为两部分：确定性通过/失败规则，以及用于解释性标签的LLM评判器（根据人工标注进行验证）。在五个代理中，最好的代理通过了105/120个场景，最弱的仅通过77个。故障通常是静默的，即自信地使用错误的工具输出而非崩溃。在最弱的代理上，重试缓解措施将超时错误故障的成功率从仅30%的案例提升到100%，而过时数据故障无论采取何种缓解措施，成功率仍接近每10个中有3-4个。AgentCheck使得这些故障模式在部署前可复现、可比较且可验证。

## Abstract
Tool-using LLM agents are mostly evaluated assuming all tools work. When a tool times out, returns a week-stale value, or has its description poisoned in deployment, the developer needs a controlled way to reproduce the failure, test a fix, and confirm the fix worked before deployment. We present AgentCheck, an open-source web workbench that turns an MCP server into an intervention surface. AgentCheck runs an agent against its real tools and records every tool response, then re-runs the agent with the response perturbed by a fault (12 types) injector. Matching tool calls are replayed from cache, and later tool calls go live after the agent diverges. This yields a reproduce-intervene-confirm loop: the developer toggles a mitigation, re-runs against the identical fault, and sees if the failure goes away. Scoring has two parts: deterministic pass/fail rules, plus an LLM judge for interpretive labels, validated against human annotations. Across five agents, the best passes 105/120 scenarios and the weakest only 77. The failures are usually silent, confident use of incorrect tool outputs rather than crashes. On the weakest agent, a retry mitigation raises success on timeout error faults from as few as 30% of cases to 100%, whereas stale-data faults remain near 3-4 of 10 regardless of the mitigation. AgentCheck makes these failure modes reproducible, comparable, and verifiable before deployment.

## 1. 核心问题与整体含义（研究动机和背景）

- **现有评估范式缺陷**：当前 LLM Agent 基准（如 GAIA、SWE-bench、ToolBench）均假设工具工作正常，无法反映部署中常见的工具异常（超时、错误码、过时数据、描述投毒等）。
- **实际部署痛点**：当工具超时、返回过时值或描述被投毒时，开发者缺乏可控手段来复现故障、测试修复方案并确认修复有效。现有方法或为离线基准（只打分不干预），或为监控工具（只观测不注入），均无法形成闭环验证。
- **研究目标**：提出 AgentCheck，将 MCP 服务器转变为干预面，实现工具的**复现‑干预‑确认**闭环，使 Agent 故障模式在部署前可重现、可比较、可验证。

## 2. 方法论：核心思想、关键技术细节、算法流程

- **核心思想**：通过**受控比较**（clean run vs. faulted run vs. mitigated run）归因故障，确保差异仅源于注入的故障。
- **关键技术细节**：
  - **MCP 代理运行器**：Agent 与真实工具交互时，AgentCheck 记录每个工具响应（缓存）；在故障运行中，通过 `Replay` 函数重放缓存响应，但将指定调用点 `p` 的响应替换为故障注入器 `g` 的输出。后续不匹配的调用实时执行。
  - **故障注入引擎**：12 种故障类型，分为三类：A-工具执行（超时、API 错误、权限拒绝、模式漂移）；B-数据质量（过时数据、矛盾、错误答案、空结果）；C-安全（提示注入、描述投毒、虚假事实、数据泄露）。每个故障类型有具体的通过标准（如超时需承认错误而非捏造）。
  - **算法流程（Algorithm 1）**：
    1. Clean run：正常执行任务，缓存所有工具响应。
    2. Faulted run：复用缓存，仅对注入点 `(tool, args, i)` 应用故障变换 `g(r)`。
    3. 计算失败的主要检查集合 `F`。
    4. Mitigated run（可选）：对 Agent 应用缓解措施 `m`，针对相同故障 `(p, g)` 重放，验证所有失败检查是否通过。
    5. 返回轨迹分歧点、失败的检查、修复确认状态。
  - **评分**：双重评分体系。主要检查为**确定性规则**（如检查是否捏造值、是否调用非法域）；辅助为**LLM 评判器**（Claude 4.5 Haiku）给出的诊断标签（故障检测、恢复行为、不确定性沟通），与人工标注对齐验证。
- **交互式仪表盘**：浏览器界面支持选择场景、配置故障、对比轨迹、应用缓解并验证结果。

## 6. 主要结论与发现

- **故障检测能力差异大**：最佳 DeepSeek 通过 105/120，最弱 Llama 仅 77/120。这种差异在无故障基准中不会显现（所有 Agent 均“成功”）。
- **主要弱点在于数据质量故障（B 类）**：所有 Agent 在 B 类（过时、矛盾、错误答案、空结果）上表现最弱，DeepSeek 仅 29/40，Llama 仅 13/40。这些故障无错误码，容易滑过 happy‑path 基准。
- **缓解效果因故障类型而异**：
  - 重试显著提升工具执行故障（A1/A2/A3）：Llama 的 A1 从 3/10 升至 10/10，A2 从 5/10 升至 10/10，A3 从 3/10 升至 10/10。
  - 数据质量故障（B1/B2/B3）几乎不受缓解影响，需要更复杂的时序推理或跨调用一致性检查。
  - 安全故障（C1–C3）原本已较高，缓解提升有限；C4（数据泄露）未改进，因为缓解未针对其攻击向量。
- **静默故障为主**：Agent 倾向于自信地使用错误输出而非崩溃，导致更危险的误用。

## 7. 优点

- **创新的受控比较方法**：通过缓存重放和故障注入，实现精确归因（差异仅来自注入故障），比离线基准或生产监控更具诊断能力。
- **完整的闭环工作流**：重现 → 干预 → 确认，支持开发者在部署前验证缓解措施是否实际修复了特定故障，这是现有工具缺失的。
- **双层评分体系**：确定性检查提供可重复的通过/失败判定，LLM 评判器提供解释性标签，并经过人工验证，降低单一信号偏差。
- **开源且支持自有 Agent**：提供预建场景库，也允许开发者连接自己的 MCP 服务器和 Agent，灵活实用。
- **广泛的故障覆盖**：12 种现实故障类型，涵盖工具执行、数据质量和安全三方面，基于已有基准和新编写场景。

## 8. 不足与局限

- **只支持单故障注入**：未评估复合或级联故障，实际部署中可能同时出现多个异常。
- **故障库有限**：12 种故障未覆盖所有可能的故障模式（如长时间延迟、多步逻辑错误等），B 类场景为新编写，结论外推需谨慎。
- **缓解实验仅在一个 Agent（Llama）上进行**：未验证在其他 Agent 上的泛化性，且缓解措施仅三种简单策略，未探索更复杂的方案。
- **评分器可靠性问题**：确定性检查可能被模式绕过；LLM 评判器（Claude 4.5 Haiku）与人工标注的一致性中等（Cohen’s κ 0.66–0.87），且可能过度预测“传播”标签（论文将其视为上界）。作者承认这是“fallible signals”。
- **计算成本未详细量化**：虽然提及“modest”，但未提供具体 token 或时间消耗。
- **未评估对真实部署的长期影响**：工作台聚焦部署前验证，但未说明修复后在实际生产中是否能保持鲁棒性。
