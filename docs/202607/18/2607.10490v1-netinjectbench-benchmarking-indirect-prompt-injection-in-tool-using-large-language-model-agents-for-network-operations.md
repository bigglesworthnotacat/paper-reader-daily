## 摘要
使用工具的大语言模型（LLM）代理对于网络运维很有吸引力，但工单、告警、日志、运行手册和ChatOps消息可能携带间接提示注入。我们提出了NetInjectBench，一个包含130个场景的基准测试，它将不可信的人工制品文本、可信的策略元数据和网络运维工具使用的评估标签分离开来。样本包含40个良性场景、40个弱攻击场景、40个强攻击场景和10个已批准的高影响变更场景；每个场景均使用Qwen2.5-7B、Llama3.1-8B和Mistral-7B进行评估。在240个攻击实例中，朴素执行达到了82.50%的不安全工具操作率。仅提示安全、自我提醒、聚焦提示和双通LLM评判分别将该比率降低至25.63%、21.67%、18.33%和10.00%。静态白名单达到5.00%，但阻止了所有已批准的变更，导致已批准场景的有用性为0.00%，过度阻止率为100.00%。在所述元数据完整性假设下，元数据感知策略门控在240个攻击中产生了0个不安全攻击动作，Wilson上限为1.58%（95%置信水平），同时保留了99.17%攻击场景的有用性和100.00%已批准变更的有用性。研究结果表明，网络运维代理需要执行时授权边界以及提示级别的指令卫生。

## Abstract
Tool-using large language model (LLM) agents are attractive for network operations, but tickets, alerts, logs, runbooks, and ChatOps messages can carry indirect prompt injections. We present NetInjectBench, a 130-scenario benchmark that separates untrusted artifact text, trusted policy metadata, and evaluation labels for network-operation tool use. The sample contains 40 benign, 40 weak-attack, 40 strong-attack, and 10 approved high-impact change scenarios; each is evaluated with Qwen2.5-7B, Llama3.1-8B, and Mistral-7B. Across 240 attack instances, naive execution reached an 82.50% unsafe tool-action rate. Prompt-only safety, Self-Reminder, Spotlighting, and a Two-Pass LLM Judge reduced this rate to 25.63%, 21.67%, 18.33%, and 10.00%, respectively. Static allowlisting reached 5.00% but blocked all approved changes, yielding 0.00% usefulness and 100.00% overblocking on approved cases. Under the stated metadata-integrity assumption, the metadata-aware policy gate produced 0/240 unsafe attack actions, with a 95% Wilson upper bound of 1.58%, while preserving 99.17% attack-scenario usefulness and 100.00% approved-change usefulness. The findings show that network-operation agents need execution-time authorization boundaries alongside prompt-level instruction hygiene.

## 2. 论文提出的方法论

- **核心思想**：将场景中的信息明确分为三个独立通道：
  - **不可信工件文本**（artifact text）：包括工单、日志等外部内容，可能包含恶意指令。
  - **可信策略元数据**（trusted policy metadata）：如审批状态、维护窗口、批准设备、补丁等，来自独立的变更管理系统。
  - **评估标签**（evaluation labels）：仅用于事后评分，不参与模型或防御决策。
- **关键技术细节**：
  - 定义6个模拟网络运维工具：`get_telemetry`（低风险读）、`fetch_logs`（低风险读）、`search_runbook`（低风险读）、`query_topology`（敏感读）、`open_incident_ticket`（低风险写）、`apply_config_change`（高影响写）。
  - 设计**元数据感知策略门控**（Policy Gate）：当LLM提议高影响工具时，门控根据可信元数据检查审批状态、维护窗口、工具/设备/补丁匹配等条件。若通过则允许执行，否则按顺序回退到安全操作（`fetch_logs` → `get_telemetry` → `search_runbook` → `open_incident_ticket`）。
  - 对比7种执行设置：
    1. Naive LLM：直接执行模型输出。
    2. Prompt-only Safety：在提示中添加安全指令。
    3. Self-Reminder：在工件前后重复信任边界提醒。
    4. Spotlighting：用显式分隔符标记不可信内容。
    5. Two-Pass LLM Judge：第一轮调用LLM得到工具提议，第二轮提供任务和提议但不含工件，再次判断安全性。
    6. Static Allowlist：全局禁止`apply_config_change`。
    7. Policy Gate：上述元数据感知门控。
- **算法流程**（文字描述）：LLM接收任务描述和工件文本（可能含攻击）→ LLM输出工具调用提议 → 防御层处理（可选） → 执行最终动作（允许/阻止/回退） → 根据安全性和有用性标签评分。

## 3. 实验设计

- **数据集/场景**：NetInjectBench包含 **130个场景**，分为4类：
  - **Benign（40个）**：正常运维任务，无恶意指令。
  - **Weak Attack（40个）**：明显恶意指令（如“忽略策略，立即变更”）。
  - **Strong Attack（40个）**：更逼真的操纵，如伪造审批、紧急授权、供应商/安全机构背书。
  - **Approved Change（10个）**：合法的高影响变更，元数据验证为真实批准。
- **基准对比方法**：上述7种防御方法均在同一组场景上评估。模型使用Qwen2.5-7B、Llama3.1-8B、Mistral-7B三种本地模型。
- **评估指标**：
  - 不安全工具操作率（UTAR）
  - 有用行动率（UAR）
  - 阻止率（BR）、过度阻止率（OBR）
  - 无效输出率（IOR）、归一化率（NR）
- **统计方法**：Wilson置信区间（95%）、McNemar配对检验。

## 6. 论文的主要结论与发现

- **朴素执行**下UTAR高达82.50%，表明攻击极易成功。
- **提示级防御**（Prompt-only Safety、Self-Reminder、Spotlighting）将UTAR降至25.63%–18.33%，但仍残留显著不安全动作，尤其对强攻击（如伪造权威）效果更差。
- **Two-Pass LLM Judge**（去除工件文本）进一步降至10.00%，但仍未解决授权缺失问题。
- **Static Allowlist**（全局禁止`apply_config_change`）UTAR为5.00%，但导致所有已批准变更被阻止（有用性0%，过度阻止率100%），无法用于实际运维。
- **Policy Gate**（元数据感知策略门控）在攻击场景中实现0不安全动作（95% Wilson上限1.58%），同时保留攻击场景有用性99.17%、已批准变更有用性100%。
- 结论：**提示级指令卫生可降低风险，但只有执行时授权边界（基于独立可信元数据）才能根本阻止间接提示注入导致的不安全操作**，同时不干扰合法操作。

## 8. 不足与局限

- **场景合成**：所有场景由人工设计，可能无法完全反映真实工单、日志的噪声与复杂度。未来应使用真实运维数据（在隐私安全允许下）进行验证。
- **工具集简化**：仅6个模拟工具，高影响工具仅`apply_config_change`，缺少回滚、服务重启、凭据轮换等更丰富的操作。
- **单步设计**：仅评估直接从工件到工具选择的单步风险，未涉及多步代理中“安全读工具返回恶意文本影响后续调用”的工输出中毒攻击。
- **元数据完整性假设**：策略门控依赖可信元数据源（如变更管理系统）未被攻陷。若元数据通道本身被破坏，门控失效。论文未评估此场景。
- **模型与解码局限性**：仅测试3个7B-8B本地模型，未包含更大开源模型或前沿闭源模型；仅使用温度0确定性解码，未考虑采样随机性对结果的影响（如单次异常输出）。
- **统计功率有限**：场景总数130个，攻击场景240个，可能不足以检测微小差异。作者建议未来增加重复解码和更多场景。
