## 摘要
使用工具的LLM智能体大多在假设所有工具正常工作的条件下进行评估。当工具超时、返回过时值或部署中其描述被篡改时，开发者需要一种可控的方式复现故障、测试修复并确认修复在部署前有效。我们提出AgentCheck，一个开源Web工作台，将MCP服务器转变为干预平面。AgentCheck让智能体在其真实工具上运行并记录每次工具响应，然后通过故障注入器（12种类型）扰动响应后重新运行智能体。匹配的工具调用从缓存中重放，后续在智能体偏离后实时进行工具调用。这形成了一个复现-干预-确认循环：开发者切换缓解措施，对同一故障重新运行，并观察故障是否消失。评分包含两部分：确定性通过/失败规则，以及用于解释性标签的LLM评判（经人工标注验证）。在五个智能体上，最佳通过105/120场景，最弱仅通过77个。故障通常是无声的，即自信地使用不正确工具输出而非崩溃。在最弱的智能体上，重试缓解措施将超时错误故障的成功率从仅30%提升至100%，而过时数据故障无论采取何种缓解措施仍维持在每10个中约3-4个。AgentCheck使这些故障模式在部署前可复现、可比较、可验证。

## Abstract
Tool-using LLM agents are mostly evaluated assuming all tools work. When a tool times out, returns a week-stale value, or has its description poisoned in deployment, the developer needs a controlled way to reproduce the failure, test a fix, and confirm the fix worked before deployment. We present AgentCheck, an open-source web workbench that turns an MCP server into an intervention surface. AgentCheck runs an agent against its real tools and records every tool response, then re-runs the agent with the response perturbed by a fault (12 types) injector. Matching tool calls are replayed from cache, and later tool calls go live after the agent diverges. This yields a reproduce-intervene-confirm loop: the developer toggles a mitigation, re-runs against the identical fault, and sees if the failure goes away. Scoring has two parts: deterministic pass/fail rules, plus an LLM judge for interpretive labels, validated against human annotations. Across five agents, the best passes 105/120 scenarios and the weakest only 77. The failures are usually silent, confident use of incorrect tool outputs rather than crashes. On the weakest agent, a retry mitigation raises success on timeout error faults from as few as 30% of cases to 100%, whereas stale-data faults remain near 3-4 of 10 regardless of the mitigation. AgentCheck makes these failure modes reproducible, comparable, and verifiable before deployment.

# AgentCheck: 详细总结

## 1. 核心问题与整体含义（研究动机和背景）

- **研究动机**：现有LLM智能体评估基准（如GAIA、SWE-bench、ToolBench）均假设工具正常工作，但在实际部署中，工具可能出现超时、HTTP错误、返回过时或语义损坏的数据、工具描述被投毒等故障。这些故障会导致智能体无声地失败（自信地使用错误输出而非崩溃），但缺乏可控复现、测试修复和验证修复效果的工具。
- **整体含义**：开发者需要一种系统化的方法，在部署前能够注入真实故障、观察智能体行为、施加缓解措施并确认修复是否有效。AgentCheck通过将MCP服务器转化为干预平面，实现了“复现-干预-确认”闭环，填补了离线基准测试与线上监控之间的空白。

## 2. 方法论：核心思想、关键技术细节

### 核心思想
- 基于**可控比较**：一次干净运行记录所有工具响应；故障运行重放除注入点外所有响应，仅改变一个工具响应为故障版本；缓解运行应用包装后的智能体并重放同一故障，验证修复是否消除故障。
- 将MCP服务器作为**干预表面**：AgentCheck位于智能体与工具之间，拦截工具调用，记录响应，并在重放时注入12种故障。

### 关键技术细节
- **故障注入引擎**：支持12种故障类型，分为三类：
  - **A类（工具执行）**：超时、API错误、权限拒绝、模式漂移。
  - **B类（数据质量）**：过时数据、矛盾、错误答案、无声空结果。
  - **C类（安全）**：提示注入、描述投毒、虚假声明、数据外泄。
- **缓存重放机制**：首次运行缓存所有工具响应；故障运行重放除指定注入点外的所有响应，匹配调用从缓存返回，后续实时执行。
- **评分系统**：双输出：
  - **主要确定性子检查**：基于规则，检查智能体是否传播错误、执行隐藏指令等。
  - **诊断标签（LLM评判器）**：使用Claude 4.5 Haiku作为LLM评判器，输出故障检测、恢复行为、不确定性沟通等标签，经人工标注验证。
- **缓解措施验证**：开发者可在界面中选择缓解包装（如重试、模式检查、注入过滤），对同一故障重新运行，输出`fix_confirmed`状态。

### 算法流程（文字描述）
1. 干净运行：给定智能体、任务、工具集，执行并缓存所有工具响应。
2. 故障运行：使用重放函数，仅改变指定注入点`(tool, call_index)`处的响应为`g(r)`（注入器），其余从缓存获取。
3. 对故障运行轨迹运行主要检查，得到失败检查集F。
4. 若应用缓解措施，对包装后的智能体以同一故障重放，得到缓解轨迹，检查F中的所有检查是否通过，输出`fix_confirmed`。
5. 返回干净与故障轨迹的差异点、失败检查集、修复确认状态。

## 6. 主要结论与发现

- **智能体表现差异大**：DeepSeek最好（105/120），Llama最弱（77/120）。这种差异在理想基准测试中不会显现。
- **弱点集中在无声数据质量故障（B类）**：所有智能体在B类（过时、矛盾、错误、空结果）上表现最差，即使是DeepSeek也仅29/40。这些故障无错误代码，易被忽视。
- **缓解措施效果因故障类型而异**：
  - 重试显著提升A类（工具执行）成功率（如A1从30%升至100%）。
  - B1（过时数据）无论何种缓解效果甚微（约30-40%），需要更高级的时序推理或跨调用一致性检查。
  - C4（数据外泄）不变（7/10），因为现有缓解未针对外泄。
- **LLM评判器的局限性**：评判标签是上限估计（可能过度触发），确定性检查作为主要判据更可靠。

## 8. 不足与局限
