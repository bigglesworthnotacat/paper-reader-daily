## 摘要
LLM代理越来越依赖迭代执行，通过规划、工具使用、状态更新和代理协作来解决问题。虽然这种设计实现了灵活的自动化，但它也带来了一类新的故障：当反馈路径没有被有效约束时，代理可能会重复执行模型调用、工具操作、工作流转换或代理交接。我们将此问题称为无限代理循环（Infinite Agentic Loops，IALs）。IALs不是普通的编程循环；它们源于代理逻辑、框架语义、运行时观察和终止机制之间的交互。此类故障可能将单个请求放大为长时间运行的模型和工具执行，导致成本耗尽、模型拒绝服务、上下文增长以及重复的外部副作用。我们提出了IAL-Scan，一种用于检测真实世界LLM代理项目中IAL故障的静态分析工具。IAL-Scan将异构代理代码抽象为与框架无关的代理中间表示（Agent IR），构建代理循环依赖图（Agentic Loop Dependence Graph，ALDG）以恢复显式以及框架引入的反馈路径，并检查这些路径是否可能在没有有效约束的情况下重复到达成本高昂或状态增长的操作。我们在6,549个LLM代理仓库上评估了IAL-Scan。它报告了74个潜在发现，其中人工审查确认了47个项目中的68个IAL故障，达到了91.9%的精确率。

## Abstract
LLM agents increasingly rely on iterative execution to solve tasks through planning, tool use, state updates, and agent collaboration. While this design enables flexible automation, it also creates a new class of failures: an agent may repeatedly execute model calls, tools, workflow transitions, or agent handoffs when the feedback path is not effectively bounded. We call this problem Infinite Agentic Loops (IALs). IALs are not ordinary programming loops; they arise from the interaction between agent logic, framework semantics, runtime observations, and termination mechanisms. Such failures can amplify a single request into long running model and tool execution, causing cost exhaustion, model denial of service, context growth, and repeated external side effects. We propose IAL-Scan, a static analysis tool for detecting IAL failures in real-world LLM agent projects. IAL-Scan abstracts heterogeneous agent code into a framework independent Agent IR, builds an Agentic Loop Dependence Graph (ALDG) to recover explicit and framework induced feedback paths, and checks whether these paths can repeatedly reach costly or state growing operations without an effective bound. We evaluate IAL-Scan on 6,549 LLM agent repositories. It reports 74 potential findings, among which manual review confirms 68 IAL failures across 47 projects, achieving 91.9% precision.

## 1. 核心问题与整体含义（研究动机和背景）
- **问题定义**：LLM（Large Language Model）代理通过迭代执行（感知-推理-行动循环）完成任务，但反馈路径（如模型调用、工具调用、状态更新、代理切换）若未被有效终止条件约束，会导致**无限代理循环（Infinite Agentic Loops, IALs）**。
- **严重性**：IALs不是普通的编程循环，而是由代理逻辑、框架语义、运行时观察和终止机制交互引发的新型结构化失效。一个请求可能被放大为长时间的模型和工具执行，造成：
  - API 成本耗尽
  - 模型拒绝服务（DoS）
  - 上下文窗口持续增长（状态膨胀）
  - 重复的外部副作用（如重复发送邮件、创建工单）
- **现有方法缺失**：通用静态分析工具（CodeQL、Semgrep）无法捕捉代理执行语义；已有的代理安全研究（AgentProof、Agent Audit等）关注拓扑、信息流等，未专门检测无界反馈路径。
- **研究目标**：定义IALs，并提出自动化的静态检测工具，帮助开发者在部署前发现此类故障。

## 2. 方法论：核心思想、关键技术细节、算法流程
### 核心思想
- **IAL-Scan** 通过将异构的代理代码抽象为框架无关的中间表示（Agent IR），进而构建 **Agentic Loop Dependence Graph (ALDG)**，在该图上检查反馈路径是否无有效边界地重复触发代价高昂或状态增长的操作。

### 关键技术细节
1. **Agent IR 构建**
   - 对每个项目进行索引（模块、导入、装饰器、自定义运行时类、可调用代理）。
   - 解析 AST，提取五种事实：**ExecutionUnit**（执行作用域）、**Controller**（循环/路由器/重试）、**Invocation**（模型调用、工具调用、子代理执行）、**StateUpdate**（状态更新）、**Bound** 和 **ExitRecord**（终止机制）。
   - 对主流框架进行行为建模，将框架特有 API（如 LangGraph 的 `add_edge`、AutoGen 的 `GroupChat`）映射为通用 Agent IR。

2. **ALDG 构建**
   - **节点**：从 Agent IR 中保留控制器、代价高昂调用（`LLM_CALL`、`TOOL_CALL`）、状态增长更新（`STATE_APPEND`）、执行作用域，共 12 种节点类型。
   - **边**：从 Agent IR 关系中导出控制流、调用、工作流转换、工具分发、反馈（循环回退、递归、重试）、退出等 10 种边类型。
   - **循环属性标注**：对每个控制器节点，标注是否到达昂贵操作、是否状态增长、是否有出口、守卫依赖来源（模型输出/工具结果/异常）。

3. **IAL 故障检测**
   - **SCC 候选发现**：将 ALDG 中的循环相关边（排除退出边和边界属性）提取子图，计算强连通分量（SCC），保留非平凡 SCC（含自环）。筛选出可达、含反馈路径且涉及代价/增长操作的候选。
   - **控制器与边界验证**：对每个候选，基于控制器类型（确定性、模型控制、工具控制等）和边界状态（覆盖、缺失、弱、禁用、可绕过）判断是否有效。
   - **IAL 识别**：当满足三条条件时报告为故障：存在代理反馈路径、路径到达代价/增长操作、无有效边界覆盖。
   - **LLM 辅助剪枝**：对模糊候选，构建包含反馈证据、控制器条件、守卫定义、候选边界的切片，让 LLM 作为负向过滤器（排除有限边界、非代理循环、测试代码等）。

### 算法流程（文字说明）
1. 输入：ALDG `G_A`，循环边类型 `K_cycle`。
2. 提取循环相关子图 `G_cycle`。
3. 计算 `G_cycle` 的 SCC，保留非平凡 SCC。
4. 对每个 SCC `L`：
   - 收集属性 `Π_L` 和拓扑 `Θ_L`。
   - 检查是否为合格候选（可达、反馈到达代价/增长操作）。
   - 选择控制器，检查边界覆盖。
   - 若未覆盖，构建发现并报告。

## 3. 实验设计
### 数据集
- **来源**：GitHub 上收集的 6,549 个 Python LLM 代理仓库（含至少一个 star）。
- **筛选**：包含下游代理应用，排除框架实现、教程、独立示例。最终包含 246,748 个 Python 文件，33.41M 行代码。
- **框架覆盖**：LangChain、LangGraph、CrewAI、AutoGen、LlamaIndex、OpenAI Agents SDK、Google ADK、Semantic Kernel，共 8 个主流框架。

### 评测指标
- **精确率（Precision）**：报告发现中手工确认的 IAL 比例。
- **True Positives (TP)**、**False Positives (FP)**、**False Negatives (FN)**。
- **平均 Token 使用量**（每项目）。
- **平均分析时间**（每项目）。

### 对比基线
- **消融实验**：逐一移除以下组件：框架建模、代理门控（agentic gate）、边界覆盖、良性循环过滤、LLM 剪枝。比较静态候选数、告警数、TP/FP、Token、时间。
- **LLM 基线**：
  - **编码助手（Coding Assistant）**：使用 Codex（gpt-5.5）对整个仓库进行分析。
  - **纯 LLM API**：使用相同模型逐文件分析（限制最大 80 文件，每文件 ≤3000 字符）。

### 人工审查协议
- 前两位作者独立审查每个报告，标记为确认的 IAL、假阳性或漏报。超过 94.6% 初始一致，分歧通过讨论解决。

## 4. 资源与算力
- **硬件环境**：单台 Ubuntu 24.04.3 LTS 服务器，搭载 2× AMD EPYC 9554 处理器（共 256 逻辑核），6× NVIDIA A100 GPU (80 GB 显存)。
- **LLM 模型**：默认使用 gpt-5.5（OpenAI API）进行辅助剪枝。实验中也使用了 gpt-5.4-mini、deepseek-v4-pro、gemini-2.5-flash 测试敏感性。
- **分析时间**：完整 IAL-Scan 平均每项目 31.2 秒，平均 token 消耗 4.2K。未说明训练时长（因为工具是静态分析，无需训练）。

## 5. 实验数量与充分性
- **主实验**：在 6,549 个仓库上运行，报告 74 个候选，手动确认 68 个 IAL 故障（47 个项目），精确率 91.9%。
- **消融实验**：6 种变体（依次去除框架建模、代理门控、边界覆盖、良性循环过滤、LLM 剪枝），全部在 264 个项目子集上（对应全部 340 个静态候选的项目）。每种变体对比 TP、FP、Token、时间。
- **基线对比**：编码助手和纯 LLM API 在相同子集上对比，报告覆盖率和成本。
- **稳定性实验**：
  - 端到端重复性：相同设置重复 3 次，静态候选相同（340），LLM 剪枝导致告警从 74 到 70，TP 从 68 到 60，验证了静态部分的确定性。
  - LLM 敏感性：固定 340 个静态候选，使用 4 种不同 LLM 剪枝，结果差异明显。
- **FP/FN 分析**：人工检查 6 个 FP 原因（主要是间接边界），估计 7 个 FN。
- **评价**：实验设计较为充分，覆盖大规模真实数据，消融和基线对比合理，稳定性测试透明。但基线方法受限于 token 和时间预算，可能未完全展示 LLM 潜力。

## 6. 主要结论与发现
- **IAL 是真实且广泛的问题**：在 47 个真实开源代理项目中确认 68 个故障，涵盖所有 8 个框架。
- **最常见模式**：
  - 重试反馈无边界（25.0%）
  - 工具调用迭代无边界（23.5%）
  - 多智能体对话无轮次限制（20.6%）
- **主要影响**：95.6% 的故障可导致 API 成本耗尽和模型 DoS；27.9% 可耗尽上下文窗口。
- **根本原因**：所有故障均因缺少有效边界（边界缺失、弱、可绕过或被模型/工具输出控制）。41.2% 涉及工具控制的重试，38.2% 涉及模型控制的终止。
- **工具有效性**：IAL-Scan 端到端精确率 91.9%，优于所有对比基线。消融表明每个组件均有贡献，尤其是代理门控和边界覆盖。

## 7. 优点
- **新问题定义**：首次系统定义 LLM 代理中的无限循环故障（IALs），并分析其成因和影响。
- **框架无关性**：通过 Agent IR 抽象和 ALDG，统一处理 8 个主流框架，具有较强泛化能力。
- **高精度与覆盖**：在 6,549 个项目中达到 91.9% 精确率，发现大量真实故障。
- **全面的实验评估**：包括大规模真实数据、消融、基线对比、稳定性测试，结果客观可靠。
- **合理的设计权衡**：静态阶段追求召回，LLM 辅助剪枝降低误报，且仅作为负向过滤器，避免关键判断完全依赖不稳定的 LLM。
- **开放与可复现性**：工具开源，人工审查协议透明。

## 8. 不足与局限
- **静态分析的固有过近似**：可能报告假阳性（实验中 6 个 FP），部分边界很难静态分辨（如跨作用域深度绑定）。
- **语言与框架限制**：仅支持 Python 和 8 个主流框架，未覆盖其他语言或定制框架，可能存在假阴性。
- **对高度自定义语义支持弱**：用户自定义调度器、基于外部状态的停止逻辑、自然语言条件等难以建模。
- **LLM 辅助剪枝不稳定**：不同 LLM 模型、甚至相同模型多次运行结果有差异（TP 从 60 到 68），对模型选择有一定依赖。
- **未评估运行时影响**：静态检测无法捕捉仅在特定输入下触发的 IAL，也无法完全确认实际资源消耗。
- **基线对比的资源约束**：给 LLM 基线的 token 和时间预算有限，可能未能展现其全部能力。
