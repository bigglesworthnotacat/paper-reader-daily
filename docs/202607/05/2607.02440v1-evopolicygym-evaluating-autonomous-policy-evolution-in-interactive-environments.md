## 摘要
自主智能体越来越期望通过反馈来改进可执行策略，然而现有评估常常将此过程简化为最终得分，或将其与开放式的软件工程进展混为一谈。我们引入了自主策略进化（Autonomous Policy Evolution），这是一种受控评估设置，其中搭载模型的智能体在固定的交互预算下反复编辑可执行策略系统。我们在EvoPolicyGym中实例化了该设置，这是一个基于紧凑交互式强化学习环境构建的基准，用于评估智能体如何迭代改进探索策略。在EvoPolicyGym套件上，GPT-5.5在所有16个环境中取得了最强的综合排名分数和前两名表现。除了排行榜结果，EvoPolicyGym还提供了轨迹级别的诊断，以区分智能体如何分配预算、将反馈转化为参数调整。这些分析表明，强大的自主策略进化不仅依赖于孤立的任务胜利，还依赖于发现适合任务的机制并在有限反馈下优化策略。

## Abstract
Autonomous agents are increasingly expected to improve executable policies through feedback, yet existing evaluations often collapse this process into a final score or confound it with open-ended software-engineering progress. We introduce Autonomous Policy Evolution, a controlled evaluation setting in which a harness-model agent repeatedly edits an executable policy system under a fixed interaction budget. We instantiate this setting in EvoPolicyGym, a benchmark built from compact interactive RL environments that evaluates how agents iteratively improve explored policies. On the EvoPolicyGym suite, GPT-5.5 achieves the strongest aggregate rank score and top-two performance on all 16 environments. Beyond leaderboard results, EvoPolicyGym also provides trajectory-level diagnostics that distinguish how agents allocate budget, convert feedback into parametric tuning. These analyses show that strong autonomous policy evolution depends not only on isolated task wins, but on discovering task-appropriate mechanisms and refining policies under bounded feedback.

## 2. 方法论

### 核心思想
- **形式化定义**：智能体在工作区维护一个可执行策略系统，在固定 episode 预算下反复提交候选策略，服务器运行训练 rollouts 并返回反馈（摘要+轨迹），智能体根据反馈修订代码。服务器在训练结束后通过**隐藏的验证集**选择最佳检查点，并在**隐藏的 held-out 集**上评估最终泛化性能。
- **关键概念**：
  - **策略系统**：包含 policy.py 及可达模块的整个可执行包，可以有内部状态、辅助模块、参数等。
  - **episode 预算**：每次提交消耗一定数量的训练 episode，总预算固定（Core16 中为 128 episodes）。
  - **可见性边界**：训练反馈（摘要、轨迹、错误）对智能体可见；验证和 held-out 数据始终隐藏，防止过拟合。
- **评估对象**：不是最终策略性能本身，而是**智能体在有限预算下转化反馈、发现机制、迭代优化的能力**。

### 关键技术细节
- **交互协议**：智能体通过 `/info`, `/task`, `/submit` 接口与环境交互。每次提交服务器对当前策略系统快照，运行请求的训练 episodes，写入反馈到 `feedback/submit_NNN/` 目录。
- **工作区语义**：智能体可随时覆写 `system/` 下的文件，无回滚保护，服务器仅保留提交的快照。
- **选择与评分**：训练结束后，对所有状态为 `ok` 的检查点在隐藏验证集上评估，选择验证均值最高的检查点，然后在 held-out 集上报告最终均值。跨环境聚合使用**排名得分**（rank score）来归一化不同奖励尺度。

### 算法流程（文字说明）
1. 初始化：智能体获得环境、初始策略代码、episode 预算。
2. 循环（直到预算耗尽或主动停止）：
   - 智能体查看当前工作区、历史反馈和剩余预算。
   - 智能体编辑代码（修改参数、添加模块、重写控制逻辑等）。
   - 可选择提交候选策略（指定要运行的训练 case 数量）。
   - 服务器接受提交后，消耗相应预算，运行 rollouts，生成反馈（摘要、轨迹、错误等）。
   - 智能体阅读反馈，决定下一轮编辑。
3. 训练结束后，服务器自动执行隐藏验证选择最佳检查点，并在隐藏 held-out 集上评估，报告最终得分。

## 6. 主要结论与发现

1. **GPT-5.5 综合最强**：在 Core16 聚合排名得分 0.891，在所有 16 个环境中均进入前二，获得 9 个第一。
2. **Claude Opus 4.7 在 MiniGrid 家族领先**，但在 BipedalWalker 上表现较差（-15.8 vs GPT-5.5 的 248.9）。
3. **MiniMax-M3 和 DeepSeek-V4-Pro 只有孤立任务胜利**，但综合覆盖率低（Core16 得分 0.531 和 0.359）。
4. **合成 vs 调优差异显著**：在高信息需求的合成任务（如 CarRacing、MiniGrid）上，强模型（GPT-5.5、Claude Opus 4.7）能高效构建新机制（结构编辑成功率 41%-48%），弱模型则几乎零成功率（3%-10%）；在调优任务上所有模型相对接近。
5. **编辑类型与成功概率有关**：结构编辑在合成任务上更可能带来验证最佳；参数编辑在已有合理控制框架时有效。
6. **轨迹诊断揭示不同行为模式**：强模型能较早发现高验证得分候选并有效利用反馈定位失败原因；弱模型消耗大量预算在无效结构切换或机械重试上。

1. **问题形式化清晰**：首次将自主策略进化定义为**受控的预算约束下的策略迭代优化问题**，并给出完整形式化描述。

## 8. 不足与局限

1. **实验规模有限**：仅 4 个闭源模型，无开源模型或小模型对比；每个环境仅一次运行，缺乏统计重复性。
2. **预算单一**：仅使用 128 episodes 一种预算，无法考察预算对优化行为的影响；实际应用中可能需要适应不同预算水平。
3. **缺乏标准基线**：未与传统 RL 方法（如 PPO、模拟退火等）进行对比，使得难以判断智能体在代码空间中搜索的效率是否优于传统优化方法。
4. **引擎依赖与混淆**：不同模型使用不同 harness（Codex vs Claude Code），harness 本身的差异（如工具使用方式、上下文管理）可能显著影响结果，论文将其作为评估维度的一部分，但无法单独归因于模型能力。
5. **诊断指标的局限性**：
   - AST 拓扑变化并不总是对应有意义的行为变化（相同拓扑可不同行为，不同拓扑也可相似行为）。
   - “合成/调优”分类是粗略的，部分任务（如 BipedalWalker）也需要先合成步态再调优，类似混合需求。
6. **泛化风险**：结论可能过度依赖当前 16 个任务和特定预算，如需推广到更复杂环境（如 Atari、MetaWorld）或更长预算，需进一步验证。
