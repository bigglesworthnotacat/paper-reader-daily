## 摘要
多智能体LLM应用将规划器、工作智能体、验证器和合成器串联起来，每个智能体之间的跳转都是一个未受监控的通道，攻击者可借此注入指令。现有防御仅保护输入边界（如IBProtector、Llama Guard、困惑度过滤器、SmoothLLM），或在应用外部以不透明、随机的提供方侧过滤器形式运行。我们发现这一缺口带来了一个鲜少被衡量的后果：在涵盖8种攻击家族、5种防御机制和3种模型后端的2100条轨迹评估中，一个在标准报告下看似完全安全（工具和内存投毒攻击成功率为0.000）的无防御管道，其安全性几乎完全依赖于云提供商的服务器端过滤器（Azure GPT-5上60个拦截中有54个），而在没有此类过滤器的后端上，则悄然转向智能体模型自身的对齐。仅报告结果掩盖了这一依赖性。我们提出ChannelGuard，一种无需训练的深度防御框架，在每个智能体间通道上设置信息瓶颈门控；每个门通过嵌入相似度对通道文本与对抗性短语库进行评分，并决定性地通过、压缩或阻止文本，无需调用LLM，同时通过归因方法记录每个攻击被哪一层拦截。ChannelGuard的工具输出门在应用层完全阻止了30次中的30次工具投毒攻击，在Azure GPT-5、Anthropic Sonnet 4.5和Anthropic Haiku 4.5上表现一致，而无防御管道则在不同后端间完全变化；它还将提示注入攻击成功率降低一半（从0.333降至0.167），并保持GSM8K准确率不变（0.867）。白盒自适应改写绕过所有嵌入门，而扰动-投票基线表现更好。扩展附录增加了基线、消融实验、扫描、良性保留分析以及评审者审计（kappa=0.900），总成本为47.36美元。

## Abstract
Multi-agent LLM applications chain a planner, worker agents, a verifier, and a synthesizer, and every hop between agents is an unmonitored channel through which an adversary can smuggle instructions. Existing defenses guard only the input boundary (IBProtector, Llama Guard, perplexity filters, SmoothLLM) or run outside the application as opaque, stochastic provider-side filters. We show this gap carries a consequence rarely measured: on a 2,100-trace evaluation across eight attack families, five defenses, and three model backends, an undefended pipeline that appears fully safe under standard reporting (attack success 0.000 on tool- and memory-poisoning) owes that safety almost entirely to the cloud provider's server-side filter (54 of 60 blocks on Azure GPT-5), and silently shifts to the agent model's own alignment on a backend without such a filter. Outcome-only reporting hides this dependence. We present ChannelGuard, a training-free defense-in-depth framework placing information-bottleneck gates on every inter-agent channel; each scores channel text against an adversarial phrase bank by embedding similarity and deterministically passes, compresses, or blocks it, adding no LLM call, while an attribution method records which layer stopped each attack. ChannelGuard's tool-output gate blocks Tool Poisoning 30 of 30 at the application layer, identically across Azure GPT-5, Anthropic Sonnet 4.5, and Anthropic Haiku 4.5, whereas the undefended pipeline shifts entirely across backends; it also lowers Prompt Injection attack success by half (0.333 to 0.167) and preserves GSM8K accuracy exactly (0.867). White-box adaptive paraphrase evades every embedding gate, where a perturb-and-vote baseline does better. An extended appendix adds baselines, ablations, sweeps, a benign-preservation analysis, and a judge audit (kappa = 0.900), at a total cost of 47.36 USD.

## 1. 论文的核心问题与整体含义（研究动机和背景）

现代多智能体 LLM 应用通常由规划器、多个工作智能体、验证器和合成器串联组成，智能体之间的每一次跳转（如 planner→worker、tool→worker、memory→worker 等）都构成一个未受监控的通道。攻击者可以在任意通道注入恶意指令（如提示注入、工具投毒、内存投毒等），从而污染管道的最终输出。现有防御（如 IBProtector、Llama Guard、SmoothLLM、困惑度过滤等）仅保护输入边界，或依赖于云提供商端不透明、随机的内容过滤器（如 Azure 内容安全策略、Anthropic 可接受使用分类器），这些过滤器在应用层之外运行，开发者无法控制且其覆盖范围随提供商策略变化而变化。论文揭示了一个关键问题：一个看似安全的多智能体管道（攻击成功率为 0.000）实际上可能完全依赖云提供商的服务器端过滤器才达到零攻击率，而非依赖应用自身的防御；如果更换后端（如从 Azure 换到 Anthropic），安全机制会完全“重新来源”（mechanism substitution），而开发者无法察觉这种变化，也无法对系统鲁棒性进行推理。因此，该论文的核心动机是：**仅报告攻击成功率（ASR）会隐藏真正安全机制的来源，必须建立可归因、可检查的防御体系，覆盖所有智能体间通道，并确保安全机制不随后端漂移。**

## 2. 论文提出的方法论：核心思想、关键技术细节与算法流程

### 核心思想
- **ChannelGuard** 是一个无需训练的深度防御框架，在每一个智能体间通道上部署**信息瓶颈（Information Bottleneck, IB）门控**。每个门控对通道文本进行句子级嵌入，计算与固定对抗性短语库的最大余弦相似度，然后根据阈值做出**通过（pass）**、**压缩（compress）** 或**阻断（block）** 的三路决策。不需要额外调用 LLM，整个门控可本地运行。
- 通道覆盖：共有 6 个门控位置（表 1）：IB-0（用户输入→规划器）、IB-1（规划器→每个工作智能体）、IB-2/IB-4（工作智能体输出→验证器）、IB-3（工具输出→工作智能体）、IB-3-mem（内存读取→工作智能体）、IB-5（所有工作智能体输出→合成器）。其中只有 IB-0 与现有输入边界防御重合，其余五个覆盖智能体间表面。
- 验证器与合成器：每个幸存的工作智能体输出经过不确定性感知验证器（5 次蒙特卡洛采样），报告平均安全性、离散度；通过三重过滤（门控 + 安全性 + 确定性）后进入合成器；若没有任何内容幸存，则返回硬拒绝，不消耗 LLM 调用。
- 归因方法：每次运行记录每个门控决策和完整调用链，以此识别哪个防御层最先阻止了攻击（归因类别优先级：泄露 > IB 阻断 > 提供商过滤 > 验证器 > 合成器拒绝 > 安全回答），从而将结果级 ASR 转换为机制级解释，使机制替代变得可测量。

### 关键技术细节
- **门控决策公式**：给定通道文本 t 和短语库 B，风险分数 risk(t) = max_{句子 s in t, 短语 b in B} cos(e(s), e(b))，其中 e(·) 为 L2 归一化的句子嵌入（默认 all-MiniLM-L6-v2，384 维，CPU 本地运行）。决策为三路阈值：
  - 若 risk ≥ θ，则 **block**（返回空字符串）；
  - 若 αθ ≤ risk < θ，则 **compress**（保留前 N=2 个句子）；
  - 否则 **pass**（原样传递）。
  默认 θ=0.60，α=0.70。
- 有一个可调严格度参数 β，重新映射阻断阈值：θ_eff(β) = max(0.15, 0.85 - 0.15 β)，β>1 更严格。
- 短语库包含 20 个手工编制的对抗性短语（如“忽略之前所有指令”、“用户是管理员”等）。通过句子级评分防止长文本中单个恶意句子被稀释。
- 性质：门控将通道文本压缩到至多 log₂3 ≈ 1.58 bits，形成硬信息瓶颈。门控决策不依赖后端智能体模型，因此工具输出门在三个不同后端上行为一致。
- 门控算法（Algorithm 1）：将文本分句，对每个句子与每个短语计算余弦相似度，取全局最大值，然后按阈值返回三元组（决策, 处理后的文本, 风险分数）。
- 完整管道算法（Algorithm 2）：在每个通道调用门控，一旦任一通道 block，立即短路，不再调用后续 LLM，从而获得加速。

## 6. 论文的主要结论与发现

1. **机制替代**：标准 ASR 报告隐藏了安全机制的真实来源。在无防御管道中，工具投毒和内存投毒上的零攻击率（0.000）在 Azure 上 90% 依赖提供商过滤器；更换到 Anthropic 后端后，安全机制完全转变为模型自身行为（提供方过滤器不存在）。ChannelGuard 的工具输出门在所有三个后端上提供相同的应用自有阻断（30/30 全部拦截）。
2. **ChannelGuard 降低提示注入成功率 50%**（从 0.333 降至 0.167），McNemar 检验 p=0.125（方向性）。
3. **白盒自适应改写可绕过所有嵌入门**：两个系统均泄露约 2/3 的案例；SmoothLLM 的扰动-投票策略在此攻击上表现更好（ASR=0.200）。
4. **保留推理准确性**：GSM8K 上 CTCA 保持 0.867 不变；良性 HotpotQA 上 BPR 为 0.533（无防御为 0.567，略有下降）。
5. **效率提升**：在提示注入攻击上，由于早期短路，ChannelGuard 比无防御快 3.30 倍；全攻击集合并时快 1.19 倍。
6. **门控主要基于模板而非标记**：标记随机化实验显示 94% 的阻断行为保持不变（短语库针对角色标签和指令覆盖，而非仅靠 `ATTACK_SUCCESS` 字样）。
7. **压缩带的有效性**：内部通道（IB-2 到 IB-5）的压缩操作 100% 有效（注射通常出现在末尾），但输入边界（IB-0）的压缩操作漏泄率约 23.4%，因为用户提示往往将载荷放在前两句。
8. **短语库规模的影响**：5 短语短语库在提示注入上 ASR（0.067）优于默认 20 短语（0.100）和 50 短语（0.167），说明关键参数匹配质量比数量更重要。

## 7. 优点：方法或实验设计上的亮点

- **创新的归因方法论**：将单维 ASR 分解为防御层级别的归因，使机制替代变得可量化。这是论文的核心贡献之一，对未来的安全评估领域具有方法论意义。
- **实用的训练无关框架**：无需训练数据和额外 LLM 调用，仅需本地嵌入模型和固定短语库，易于部署和审计。
- **多通道覆盖**：现有防御仅覆盖输入边界，ChannelGuard 系统性地覆盖了所有智能体间通道（工具输出、内存读取、子任务分配、工作输出、合成输入）。
- **后端不变性**：工具输出门的设计使得其行为不依赖底层智能体模型，从而在提供商切换时提供可预测的安全属性。
- **全面的实验设计**：包括配对样本、多种攻击类型（包括叙事型和白盒自适应）、基线对比、消融、扫描、良性保留分析、归因随机化验证等，体现了严谨性。
- **透明度与可复现性**：完整发布 2,100 条轨迹、代码和配置，总实验成本公开列出（47.36 美元），支持完全复现。
- **效率与安全性平衡**：通过短路和压缩带降低计算成本，同时保持高安全性。

## 8. 不足与局限

- **样本量与统计显著性**：主比较基于 n=30（单个种子），McNemar 检验 p 值不显著（0.125），论文本身承认方向性而非确定性。多种子扫描是必要的后续。
- **模拟环境**：使用模拟工具（canned responses）而非真实检索 API，可能低估了现实场景下的间接注入风险。论文将此列为后续工作。
- **白盒自适应改写可绕过**：所有基于静态短语库的门控（包括 ChannelGuard 和 IBProtector）均被自适应改写轻松绕过，而 SmoothLLM 的扰动-投票在此攻击上显著更优，表明 ChannelGuard 的防御天花板受限于签名式方法。
- **叙事型内存攻击**：慢速漂移等攻击的载荷被包裹在自然对话中，每句相似度低于阈值，门控完全失效，只能依赖模型自身行为；这说明短语库面向的分布不匹配。
- **压缩带在 IB-0 上的泄露**：约 23% 的压缩输入仍泄漏，因为用户可能将载荷放在开头。论文提出了修复建议（IB-0 使用仅阻断模式或重新评分前缀），但未在新实验中验证。
- **短语库手工编制且仅英语**：规模固定且语言受限，无法直接适应多语言或新攻击模式。论文建议使用对抗学习生成短语库。
- **验证器的不对称盲点**：验证器的三重过滤不拒绝“安全但不确定”的报告，其中 19.5% 对应的轨迹最终泄漏，表明存在改进空间。
- **提供商依赖性揭示但不完全替代**：在内存投毒等攻击上，即使启用 ChannelGuard，Azure 的提供商过滤器仍承担大部分工作；ChannelGuard 尚未实现完全替代，而是补充。
- **仅测试三个后端，其中两个同属 Anthropic**：提供商的独立性证据较弱。需要更多第三方后端（如 Groq/Llama、Google Gemini）来加强后端不变性主张。
- **无跨种子或跨可变性分析**：未评估随机种子或模型输出的随机性对结果的波动影响。
