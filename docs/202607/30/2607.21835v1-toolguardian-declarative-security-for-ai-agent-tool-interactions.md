## 摘要
LLM代理越来越依赖外部工具，在扩展能力的同时也创建了一个新的安全边界：第三方工具可能在接口层面看似良性，但在实现中嵌入不安全行为。现有防御措施依赖于弱元数据，将特征描述和策略判断合并为单一决策，或使用启发式/LLM强制执行，缺乏对任务上下文和多种工具组合的确定性、可审计推理。本文提出ToolGuardian，一个策略驱动的框架，通过准入前审查和任务感知的运行时授权来保护智能体-工具交互。ToolGuardian使用渐进式特征化将证据转换为结构化事实：描述捕获声明意图，系统调用跟踪暴露粗粒度行为，模拟执行揭示观察到的影响，源码分析识别潜在行为。ToolGuardian的核心贡献是基于回答集编程（ASP）的声明式策略层，该策略层明确推理能力、影响、任务上下文和组合。我们使用相同的输入和输出契约比较ASP与基于启发式和LLM的策略实现。我们在16个MCP风格的工具上评估ToolGuardian，包括8个源自真实开源工具的恶意变体，以及20个运行时场景。对于审查，ASP使用描述、系统调用和观察到的影响证据达到拒绝类F1为0.86和88%的准确率。对于运行时授权，完全指定的实现正确分类所有场景，而消融实验表明删除组合和一致性规则会显著降低性能。

## Abstract
LLM agents increasingly rely on external tools, expanding capability while creating a new security boundary: third-party tools may appear benign at the interface level while embedding unsafe behavior in implementation. Existing defenses rely on weak metadata, collapse characterization and policy judgment into a single decision, or use heuristic/LLM enforcement that lacks deterministic, auditable reasoning over task context and multi-tool composition.   This paper presents ToolGuardian, a policy-driven framework for securing agent-tool interactions through pre-admission vetting and task-aware runtime authorization. ToolGuardian uses progressive characterization to convert evidence into structured facts: descriptions capture declared intent, system-call traces expose coarse behavior, mock execution reveals observed effects, and source analysis identifies latent behavior. ToolGuardian's core contribution is an Answer Set Programming (ASP)-based declarative policy layer that reasons explicitly over capabilities, effects, task context, and composition. We compare ASP against heuristic and LLM-based policy realizations using identical inputs and output contracts.   We evaluate ToolGuardian on 16 MCP-style tools, including 8 malicious variants derived from real open-source tools, and 20 runtime scenarios. For vetting, ASP reaches a deny-class F1 of 0.86 and 88% accuracy using description, syscall, and observed-effect evidence. For runtime authorization, fully specified realizations classify all scenarios correctly, while ablations show that removing compositional and conformance rules substantially degrades performance.

## 1. 核心问题与整体含义（研究动机和背景）

- **核心问题**：大型语言模型（LLM）智能体越来越多地通过外部工具（如MCP服务器）执行文件读写、API调用、命令执行等操作，从而扩展能力。然而，第三方工具可能在接口层面看似良性，但在实现中嵌入恶意行为（如数据泄露、状态篡改、资源消耗），构成新的安全边界。现有防御方法存在三大缺陷：
  - 依赖弱元数据（如工具描述），缺乏对实现行为的可见性；
  - 将特征提取与策略判断合并为单一决策（如扫描器），难以研究不同证据层对安全-效用权衡的影响；
  - 仅关注预使用检测或运行时调用控制，忽略了预准入审查与任务感知运行时授权两阶段协同的需求。
- **研究意义**：该工作旨在为LLM智能体工具生态系统提供一种结构化、可审计、确定性推理的安全框架，解决多工具组合场景下的复杂安全风险，推动声明式策略在AI系统中的应用。

## 2. 方法论：核心思想、关键技术细节

- **核心思想**：将工具安全分为两个独立阶段：**预准入审查**（vetting，独立于任务判断工具是否可被引入）和**任务感知运行时授权**（runtime authorization，在任务上下文中判断具体调用是否允许）。通过渐进式特征化（progressive characterization）将不同层次证据转化为结构化事实，再交由策略层进行确定性推理。
- **关键技术细节**：
  - **渐进式特征化**：共四个证据级别，累积递增：
    - L0：基于描述的特征化（提取声明功能，但不可信）
    - L1：系统调用跟踪（暴露文件、网络、进程等粗粒度行为）
    - L2：模拟执行与观察效应（在受控环境中运行工具，记录HTTP请求、状态变更等）
    - L3：静态源码分析（AST分析，识别未执行的潜在代码路径）
  - **特征化层级（P0-P3）**：P0仅含L0，P1含L0+L1，P2含L0+L1+L2，P3含所有四级。每个层级产出结构化事实，如 `capability(T,network_access)`, `data_access(T,env_vars)`, `observed_http_post(T,Endpoint)`, `effect_mismatch(T,undeclared_network_access)`。
  - **策略层**：基于**回答集编程（Answer Set Programming, ASP）** 构建声明式策略，使用Clingo求解器。ASP规则可表达：
    - 拒绝条件：`deny(Tool) :- capability(Tool,shell_exec), network_access(Tool).`
    - 异常：`admit_restricted(Tool) :- ...`
    - 组合约束：`compositional_risk(C, sensitive_externalization) :- source_class(I, sensitive_read), sink_class(J, external_project_update), ...`
  - 策略分为审查策略和运行时策略，运行时额外考虑任务授权、效果一致性和组合工作流风险。
  - 三种策略实现（基于相同输入和输出契约）：
    - **ASP实现**：确定性逻辑推理
    - **LLM实现**：使用openai/gpt-oss-120b模型（通过OpenRouter），温度0，通过提示解释事实输出决策
    - **启发式实现**：基于风险评分、阈值和手工编码条件
  - **输出契约**：统一决策（allow/deny）+ 解释标签 + 可选限制注解。

## 6. 论文的主要结论与发现

1. **结构化特征化提升策略可见性，但安全-效用存在权衡**：中间层级（P2）达到最佳性能（ASP F1=0.86，准确率88%）；增加静态分析（P3）可暴露更多风险，但也会导致对良性高权限工具过度拒绝。
2. **运行时授权完全正确需要明确策略规则**：在所有完全指定的实现（ASP、启发式、LLM）下，20个运行时场景均正确分类；但消融实验表明，去除组合规则或弱化LLM提示会导致性能显著下降（LLM消融后准确率降至75%，启发式消融后降至60%）。
3. **组合工作流是运行时安全的主要难点**：原子授权相对容易处理；组合（如数据流从敏感源到外部槽）需要显式策略约束，ASP的声明式规则天然适合这种多条件依赖推理。
4. **三种策略实现各有利弊**：
   - ASP提供确定性、可审计、可测试的推理，但需要专家设计规则。
   - 启发式基线可在无AI成本下实现较好效果，但组合逻辑手工编码复杂。
   - LLM在结构化输入和显式提示下表现良好，但依赖提示质量，不可复现且成本高。
5. **部分干预（如 `restricted_admit`）是必要的安全-效用调节手段**：在P3下，没有工具被完全“admit”，多数被限制准入，反映高可见性特征化下策略的保守倾向。

## 7. 优点

- **体系结构分离**：将特征化与策略执行解耦，允许不同证据源和不同策略实现相互替换，便于研究比较。

- **全面对比实验**：在相同输入和输出契约下对比ASP、启发式、LLM三种策略，并进行了多组消融实验，结论有说服力。

- **可审计性**：ASP规则提供明确的审查路径，解释标签可追溯决策原因。

## 8. 不足与局限

- **基准规模有限**：仅16个工具和20个场景，作者承认需扩展到更多MCP服务器、独立开发的良性工具以及真实世界恶意工具。
- **领域特定**：评估聚焦于MCP协议，其他智能体-工具生态系统（如浏览器代理、代码执行代理、云API代理）可能具有不同元数据和授权模型，泛化性未验证。
- **组合深度不足**：组合场景仅考虑短工作流（2-3步），实际智能体可能执行更长、间接依赖的任务链，风险累积方式未覆盖。
- **ASP规则设计负担**：需要专家手动编码策略规则，可能遗漏例外或产生错误；规则正确性依赖测试，未提供形式化安全不变式。
- **LLM实现依赖结构输入**：LLM在无显式策略指导（消融）时性能大幅下降，证明其不可作为独立安全权威；且推理成本随决策次数线性增长。
- **未覆盖所有攻击面**：如侧信道攻击、内核级妥协、分布式拒绝服务等超出工具调用边界的行为不在考虑范围内。
