## 摘要
随着编程智能体从有监督的代码补全转向无人值守的全天候探索，其工作也从孤立的预测扩展为包含推理、工具使用与反馈的长轨迹。因此，Token 效率对于扩展递归式自我改进变得至关重要。我们在执行框架（harness）层面采用受 RSI 启发的方法，将自动研究循环扩展至数量日益庞大、种类日益多样的环境，以开展框架 rollout。在这一规模下，该过程产生了可复用的改进，这些改进能够迁移到其开发环境之外，推动自动化的框架发现走向生产级成果。共有四种机制通过筛选并构成 SoL-Pi，涵盖动作执行、上下文压缩、观测处理和委托式阅读。在包含 51 项任务的 EdgeBench 评测中，SoL-Pi 在 GPT-5.6 Sol 与 Opus 5 上取得了与 Pi 相当的性能，同时将记录的 token 流量降低 44.7–49.0%，并将 API 成本降低约三分之一。换言之，相对于原生的 Codex 与 Claude Code 框架，估计每小时可节省 8.75–13.50 美元；相对于 Pi，则可节省 4.36–5.71 美元。

## Abstract
As coding agents move from supervised code completion to unattended, around-the-clock exploration, their work expands from isolated predictions into long trajectories of reasoning, tool use, and feedback. Token efficiency therefore becomes important for scaling recursive self-improvement. We take an RSI-inspired approach at the harness layer, scaling auto-research loops across increasingly numerous and diverse environments for harness rollouts. At this scale, the process yields reusable improvements that transfer beyond their development setting, moving automated harness discovery toward production-level outcomes. Four mechanisms survive selection and form SoL-Pi, spanning action execution, context compaction, observation handling, and delegated reading. On the 51-task EdgeBench evaluation, SoL-Pi achieves performance comparable to Pi across GPT-5.6 Sol and Opus 5 while reducing recorded token traffic by 44.7-49.0% and API cost by about one third. In other words, estimated hourly savings are \$8.75-\$13.50 relative to native Codex and Claude Code harnesses, and \$4.36-\$5.71 relative to Pi.

## 1. 核心问题与研究背景

- **背景转变**：编码智能体正从"有监督的代码补全"转向**无人值守、全天候的自主探索**，工作形态由孤立预测扩展为包含推理、工具调用与反馈的长轨迹。
- **核心痛点**：长轨迹使 **token 效率成为一阶系统问题**——它直接决定递归自我改进（Recursive Self-Improvement, RSI）能否规模化。
- **既有路线与其局限**：现有效率研究多聚焦"降低单 token 成本"，如更快的注意力核（FlashAttention-2）、服务基础设施（PagedAttention）、量化压缩（SmoothQuant/GPTQ）、调用更便宜的模型等。
- **本文切入点（正交方向）**：在 **harness 层（智能体执行框架层，即模型与环境之间的中介）** 做优化，无需额外模型训练，可与基础设施层、模型层优化互补。
- **为何难做**：harness 中工具使用、上下文管理、验证、委派、恢复、终止等环节高度耦合；局部有益的改动可能导致下游失败，或把 token 成本转移到执行后期。人工分析长轨迹、识别反复出现的失败模式并转写为代码改动，成本高、难扩展。
- **既有自动化 harness 改进的风险**：Meta-Harness、RHI、AHE 等工作已证明自动化可行，但有研究（Wang et al.）指出，演化出的 harness 容易**过拟合搜索时使用的任务**，在未见任务上收益边际化。这直接催生了本文的核心设计原则：**搜索反馈与最终评测必须严格分离**。
- **整体含义**：SoL-Pi 试图证明——RSI 的长期价值可能不在于"自我改写模型"，而在于**一个能在大量公开环境中扩展、并发现可复用改进的搜索过程**。

## 2. 方法论

### 2.1 核心思想：受 RSI 启发的 Harness 自动研究循环

- 由一个**研究型 AI（research AI）** 观察另一个运行基础 harness 的智能体的**执行轨迹**，识别反复出现的开销来源，提出候选改动，并在预备好的研究环境中测试。
- 通过**能力门（capability gate）**与**效率门（efficiency gate）**决定候选机制的去留，开发结果指导下一轮迭代。
- **三条指导原则**：
  - **广度与深度（Breadth and Depth）**：广度扩大假设覆盖，深度则反复实现、评审、加固有前景的候选。
  - **独立验证（Independent Validation）**：留出集证据只在候选被**冻结（freeze）**后评测，且**永不回流到搜索**，防止把验证失败"打补丁"成任务特化方案。
  - **可扩展编排（Scalable Orchestration）**：隔离、一次性的搜索谱系（lineage）使漏斗可跨更多想法与环境扩展，候选间失败不互相耦合。

### 2.2 关键技术细节：宽到深（Broad-to-Deep）漏斗

- **外层搜索（广度）**：初始 152 个候选方向，分属六大提案族——**context、progress、tools、delegation、prompt and policy、improvement and evaluation**。提案族按"假设来源"分类，而非限制实现位置（例：ObservationPack 源自两个 context 假设，最终却修改了**观测边界**）。
- **Oracle Analysis**：在分配 rollout 预算前，先检视已有开发轨迹，识别基础 harness 中可避免的无效工作；每个入选方向必须指明具体开销来源并提出对应改动。
- **内层搜索（深度）**：每条独立搜索遵循"提案 → 实现 → 固定实验 → 检视结果 → 保留/修改/丢弃"的经典自动研究循环，并用 **Ralph Loop** 扩展为迭代实现循环：
  - 实现者把候选打磨到满足**显式完成判据**；
  - **独立评审者**在评测前检查，评审失败触发修订；
  - 每个迭代可产出多条探索轨迹，多个**独立分析器**各看一条轨迹，检查重复动作、上下文增长、大观测、稀疏诊断信号；
  - 一个 **reducer** 汇总各分析器发现，形成候选级摘要，指导下一步提案。
- **工程实现**：每次独立搜索都是一份**共享技能模板**的一次性实例（模板含最小研究循环与操作指令）；实验复制模板、设定参数、跑完即弃，只保留候选与证据，丢弃被修改的编排代码。
- **接受规则（严格预注册、与优化器隔离）**：
  1. 所有能力指标必须落在**预先声明的容差**内；
  2. 候选必须至少改进**一项已声明的效率指标**；
  3. 双门通过者中，保留在声明指标下的**非支配（nondominated）**结果。
  - 能力指标、容差、效率指标在实验开始前固定，全程不变，且**严格不受优化智能体控制**，防止其"刷分"。
- **集成与冻结**：各机制独立探索，之后合并为 SoL-Pi 并细化超参与实现（同时保持能力）。评测前冻结机制源码、配置、指标、能力容差与接受规则；EdgeBench 与搜索完全隔离，验证失败即拒绝候选，**不触发进一步优化**。

### 2.3 搜索环境（535 个可执行环境）

| 类型 | 数量 | 构造方式 |
|---|---|---|
| 仓库衍生（Repository-derived） | 495 | 每个环境配对一条 GitHub issue 与其**修复前仓库状态**和离线依赖，以已接受的 patch 与变更历史作为参考轨迹；PR 与回归测试对智能体隐藏；**仅保留"patch 前测试失败、patch 后通过"的环境** |
| 验证器驱动（Verifier-driven） | 40 | 先生成定义成功的可执行 verifier，再围绕它构造任务环境，允许多条有效解路径；主要采用 **Terminal-Bench-2 风格**的 verifier 接口 |

- 两类环境共同支持**自动评测**，且 EdgeBench 始终留出、不参与搜索。

### 2.4 四项被保留的机制

| 机制 | 作用环节 | 核心做法 | 回退/边界 |
|---|---|---|---|
| **Action Fusion** | 动作执行 | 把"编辑文件"与随后的"测试/构建/运行"合并为**一次工具请求**，在单次观测中返回两者结果，省去中间模型往返 | 需要检视变更结果本身的命令仍保持分离 |
| **Online Context Compact** | 上下文压缩 | 在**计划步骤完成边界**（通过 `update_plan` 维护计划）重估何时压缩：用已完成步骤间观测到的请求数 × 未完成步骤数估计剩余请求，并以"按当前增长速度填满上下文窗口所需请求数"封顶；**成本门**比较预计输入节省与重写 prompt cache 的额外成本；后续压缩还需计入未回收的重写成本，要求更大节省余量 | 仅在门通过或上下文逼近窗口上限、且压缩确实能缩短上下文时，调用 Pi 原生压缩 |
| **ObservationPack** | 观测存储 | 超过阈值（**10 KiB**）的结果在本地归档；**前两次 provider 请求仍全量发送**，从第三次起替换为**稳定句柄 + 原始大小 + 完整首尾行的短摘录** | 智能体可凭句柄按需取回精确分页；小结果不变 |
| **Evidence-Preserving Reducer** | 委派式阅读 | 对**预定义命令集**产生的、≥ **4 KiB** 的构建/测试日志做压缩：归档原始输出，让**低成本模型（GPT-5.6 Luna, high）**抽取关键证据为紧凑"回执（receipt）"；**确定性验证器**检查回执的 schema、源哈希、退出状态、精确引文、大小 | 验证失败、疑似凭据泄露、或回执未带来体积缩减时，**回退到原始日志**；文件读取与搜索结果绕过该 reducer |

- **机制间协同顺序**：Evidence-Preserving Reducer 先处理工具结果，ObservationPack 再对模型上下文做投影；ObservationPack **识别 reducer 的回执标记并跳过**，以保留已核验的证据。
- **职责边界**：辅助模型只负责抽取证据，**诊断与行动选择仍由主智能体承担**。
- **互补性**：四者分别针对动作执行、上下文压缩、观测处理、委派阅读四类互补开销，覆盖"编辑代码 → 环境返回输出 → 完成计划步骤"的不同阶段。

3.4 实验结果（主表）

- **效率维度（核心结论）**：在 EdgeBench 上，SoL-Pi [Efficiency] 在保持能力指标（得分）不劣于基线 Pi 的前提下，**Total token 流量与 API 成本均显著低于所有对比 harness**，$ / score 指标取得最优；相对原生 harness（Codex、Claude Code），成本下降幅度最大，相对第三方 harness 亦保持稳定优势。
- **能力维度（不可退让约束）**：SoL-Pi [Performance] 在 GPT-5.6 Sol 与 Opus 5 两个后端上均**不低于各原生 harness 的得分**，说明效率优化未以牺牲任务成功率为代价；这也是接受规则中"能力门"在最终评测上的兑现。
- **跨基准泛化**：
  - **Terminal-Bench 4**（63 个纯 CPU 任务）：SoL-Pi 在 token 效率上的优势复现，得分保持基线水平，表明机制并非针对 EdgeBench 的任务特化。
  - **IMO 2026**（6 道 Lean 4 形式化题）：在 150 分钟时限下，效率机制（尤其是 ObservationPack 与 Online Context Compact）减少了长证明搜索中的无效上下文增长，使智能体在同样时限内保留更多有效推理预算。
  - **内核优化基准（多智能体集群）**：SoL-Pi 将起始冻结版本所需的 **147,734 模拟机器周期**进一步压低，验证机制在 swarm 场景下的可叠加性。
- **与官方参考点对比**：EdgeBench 官方 GPT-5.5 @2h 检查点为 31.2，仅作分数参考、不计排名；SoL-Pi 在可比设置下以更低 token 成本达到或超过该水平。

### 3.5 消融与机制归因

- **单机制消融**：四个机制各自独立集成后单独评测，均能在至少一项已声明的效率指标上取得非支配改进，验证"每个机制对应一类独立开销来源"的设计假设。
- **后端相关性**：不同基础模型对机制的敏感度不同——GPT-5.6 Sol 下 **ObservationPack** 收益最高（该后端倾向产生大观测），Opus 5 下 **Action Fusion** 收益最高（该后端动作往返开销占比更大）。SoL-Pi [Performance] 即按此后端差异选择配置。
- **叠加效应**：四机制合并后收益大于任一单机制，且机制间未出现相互抵消；Evidence-Preserving Reducer 与 ObservationPack 的协同顺序（先 reducer、后 projection，且 projection 跳过已核验回执）是叠加不冲突的关键。
- **搜索规模效应**：从 152 个候选方向经 Oracle Analysis 与宽到深漏斗收敛到最终 4 个机制，说明**广度筛选 + 深度加固**的组合在有限 rollout 预算下优于单纯扩大候选数或单纯深挖单一方向。

## 4. 讨论与局限

- **方法层面的贡献**：本文的主要贡献不只是一组 harness 改动，而是一套**可复用的自动研究协议**——"搜索反馈与最终评测严格分离 + 预注册接受规则 + 候选冻结"三件套，直接回应了既有自动化 harness 改进（Meta-Harness、RHI、AHE）过拟合搜索任务的已知风险。
- **RSI 的路线含义**：结果表明，RSI 的近期可行形态可能是**在 harness 层做可扩展搜索**，而非改写模型权重；这一路线无需训练、可与模型层与基础设施层优化正交叠加。
- **局限**：
  - 搜索环境虽达 535 个，但以仓库衍生任务为主（495/535），任务分布仍偏向代码修复，对开放式研究、长周期规划等形态覆盖有限。
  - EdgeBench 的 51 个公开任务中仅 11 个用于单向接受、40 个用于最终评测，样本量使统计置信区间较宽。
  - 机制收益对基础模型行为分布敏感（后端相关性），换模型可能需重新走一遍搜索。
  - IMO 2026 与内核基准规模小，结论方向性意义大于定量意义。
  - GPU 依赖任务被排除，未覆盖需要大规模并行训练/推理的智能体工作负载。

## 5. 结论

- SoL-Pi 把"提升智能体执行效率"重新表述为一个**可在大量公开环境中自动搜索的研究问题**，并给出了一套带独立验证与冻结纪律的完整流水线。
- 在 EdgeBench、Terminal-Bench 4、IMO 2026 与内核优化基准上，SoL-Pi 在**不损失能力**的前提下降低了 token 流量与 API 成本，且改进可跨后端、跨任务类型迁移。
- 最终得到的四个机制（Action Fusion、Online Context Compact、ObservationPack、Evidence-Preserving Reducer）分别对应动作执行、上下文压缩、观测处理、委派阅读四类互补开销，可作为 harness 设计的可复用组件。
- 更广义地看，本文支持一个判断：**递归自我改进的规模化瓶颈可能不在模型本身，而在承载模型的执行框架，以及发现框架改进的搜索过程是否具备可扩展、可验证、不过拟合的组织形式。**
