## 摘要
自进化方法允许使用工具的智能体生成自身的训练数据，从而减少了对人工标注轨迹的需求。然而，现有方法通常将轨迹生成与评估分离，依赖无法适应新出现失败模式的静态验证器，或依赖可能强化轨迹间共有错误的自洽性信号。联合调整规划、执行与评估提供了一种有前景的替代方案，但引入了根本性的协调挑战：每个组件都会持续改变用于训练其他组件的数据或反馈。我们通过 UnifiedPlayers 来应对这一挑战；这是一个协作框架，包含生成任务的规划玩家（Planning Player）、生成带 Python 工具调用的多轮轨迹的执行玩家（Execution Player），以及构建可执行验证器的评估玩家（Evaluation Player）。我们设计了角色特定的奖励，在 GRPO 下将三个玩家协调至共享学习目标。在两个模型骨干和十二个推理基准上，UnifiedPlayers 在数学推理和通用推理任务上分别至少高出最强先前基线 3.5% 和 3.9%。此外，学习到的验证器实现了 84.2% 的对抗检测准确率，而其奖励信号的逐题方差比自洽性基线高 2.03 倍，从而提供更具判别力的验证。这些结果凸显了专门化玩家之间的合作是迈向自我增强的工具集成智能体的一条有前景路径。

## Abstract
Self-evolving methods reduce the need for human-annotated trajectories by allowing tool-using agents to generate their own training data. Yet existing methods typically separate trajectory generation from evaluation, relying on static verifiers that cannot adapt to emerging failure modes or self-consistency signals that may reinforce errors shared across trajectories. Jointly adapting planning, execution, and evaluation offers a promising alternative, but introduces a fundamental coordination challenge: each component continuously changes the data or feedback used to train the others. We address this challenge with \textbf{UnifiedPlayers}, a cooperative framework comprising a Planning Player that generates tasks, an Execution Player that produces multi-turn trajectories with Python tool calls, and an Evaluation Player that constructs executable verifiers. We design role-specific rewards that coordinate the three players toward a shared learning objective under GRPO. Across two model backbones and twelve reasoning benchmarks, UnifiedPlayers outperforms the strongest prior baseline by at least 3.5\% on mathematical reasoning and 3.9\% on general reasoning tasks. Moreover, the learned verifier achieves 84.2\% adversarial detection accuracy, while its reward signal exhibits 2.03$\times$ higher per-question variance than a self-consistency baseline, providing more discriminative verifications. These results highlight cooperation among specialized players as a promising path toward self-enhanced tool-integrated agents.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景痛点**：训练工具使用型智能体（tool-using agent）需要大量包含工具调用、观测、错误恢复与最终决策的执行轨迹，但人工标注（如 Humanity's Last Exam 级别的评估数据）成本极高；Self-Instruct、UltraChat 等语料偏向指令跟随与对话，而非可执行工具交互。
- **自进化路线的现状**：Absolute Zero、R-Zero、Socratic-Zero、TaskCraft、AReaL-SEA、Agent0 等让模型自造任务/轨迹/验证器，减少人工依赖。但 Agent0 等两玩家系统存在两个根本缺陷：
  - **监督自指**：Curriculum 奖励依赖 Executor 自洽性（majority vote）与工具调用频率，Executor 又从同一批样本的多数投票伪标签学习，**"一致地错"会被当成正确标签**，产生错误优势更新。
  - **评估静态/不可训练**：评估信号来自 Executor 输出或 LLM 裁判，无法适应新出现的失败模式。
- **核心科学问题——循环相互依赖（cyclic interdependence）**：一旦规划、执行、评估三方同时可训练，每一方都会改变另外两方的学习环境（规划改变任务分布、执行改变轨迹与失败模式、评估改变奖励）。若无显式协调，会诱发**退化学习环**：
  - 规划偏向简单、重复或不可验证的任务；
  - 执行强化被评估器"放行"的自信错误轨迹；
  - 评估坍缩为平凡规则（全接受、全拒绝、模板重复），内部奖励升高但工具集成推理能力不提升。
- **整体含义**：论文主张以"**共享可执行证据**"而非共享标量奖励来耦合三个专门化玩家，是通往自我增强工具集成智能体的可行路径。

## 2. 方法论

### 2.1 核心思想

- 三个可训练策略（同一骨干初始化、**参数与奖励各自独立**）：
  - **Planning Player（Task-Setter）**：生成多步、可验证的工具使用任务 q；
  - **Execution Player（Solver）**：以自然语言推理与 Python 工具调用交替，产出多轮轨迹 τ，以 `\boxed{}` 作答；
  - **Evaluation Player（Critic-Coder）**：为任务编写可执行 Python 验证器 `check(trajectory)`，返回 `(passed, fail_step)`。
- 三者通过**共享判决矩阵 Z(q)** 协调：固定扰动引擎生成对抗变体，沙箱执行每个有效验证器 → 证据同时刻画任务可验证性、轨迹正确性、验证器判别力，再由各方按不同方式汇总为角色专属奖励。
- 形式化为随机博弈 G=(P, π, X, J)，P={T,S,C}，**不要求共享标量奖励或共享参数**，仅共享可执行证据。

### 2.2 关键构造与公式

- **交互记录**：ξ(q) = (q, T(q), V(q), T_adv(q), Z(q), ρ_red(q))，其中 T 为原始轨迹、V 为有效验证器、T_adv 为扰动轨迹、ρ_red 为验证器源码冗余度。
- **判决矩阵**：Z(q) = [Z_orig | Z_adv] ∈ {0,1}^{M_q × K(1+P)}；K=8 条原始轨迹、M=4 个验证器候选、P=5 个扰动变体，每任务沙箱执行 K·M·(1+P)=192 次。列 = 某轨迹被验证器池如何判定（执行反馈），行 = 某验证器的行为（评估反馈）。
- **执行玩家奖励**：r_S(τ_k) = (1/M_q) Σ_{i∈I_valid} v_i(τ_k)，即 Z_orig 对应列均值——用**真实执行的检查**取代多数投票伪标签，因此样本间一致并不保证高奖励。
- **评估玩家奖励**：r_C(v_i) = α·ρ_gold_i + β·ρ_adv_i − γ·ρ_red_i，其中 ρ_gold 为原始轨迹通过率、ρ_adv 为对抗变体拒绝率、ρ_red 为与其他有效验证器的最大源码相似度；α=0.4、β=0.5、γ=0.1。全接受者无对抗奖励，全拒绝者无原始通过奖励，模板重复者受冗余惩罚。
- **规划玩家奖励**：r_T(q) = w_unc·U(q) + w_ver·V(q) − w_rep·R(q)（w=1.0/1.0/0.5）
  - U(q) = min(p̂, 1−p̂)：K 条执行轨迹多数答案占比 p̂ 的不确定性，奖励"贴近执行能力边界"的任务；
  - V(q) = m(q)·(1/M_q)Σρ_adv_i（m 为有效验证器比例）：验证器可写性，无有效验证器或无拒绝则置 0；
  - R(q)：基于 BLEU 的历史问题重复惩罚。
- **扰动引擎（固定、5 条规则，每条独立施加）**：
  - 局部编辑：`arg mutation`（数值参数 ±1/±2 或浮点 ±5%）、`step drop`（删一条 reason 步）、`step swap`（交换相邻步，代码-输出绑定整体搬移）；
  - 全局编辑：`early terminate`（截断并注入错误终答）、`tool substitute`（改语言标识符 python→bash，代码体与输出不变）。
- **沙箱**：基于 VeRL-Tool，子进程隔离、无网络、仅标准库、10 秒超时、512MB 内存上限，返回 stdout/stderr/exit status 作为下一步观测。
