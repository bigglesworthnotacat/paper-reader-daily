## 摘要
基于大语言模型（LLM）的软件智能体被设计用于自动程序修复（APR）任务，这使得在不远的将来，APR 智能体可能在无需太多人工干预的情况下自动修复缺陷。在这种情况下，我们能否信任 APR 智能体生成功能正确且安全的代码？如果攻击者以看似良性但可能影响智能体生成功能正确但不安全代码的对抗性 issue 来攻击生产环境中的 APR 智能体，会怎样？在本文中，我们通过开展实证研究，朝着回答这些问题迈出了第一步。首先，我们构建了 SWEADV，一个包含 750 个对抗性 issue 描述的基准，这些描述基于 SWE-bench Verified 中的 150 个修复任务构建。对于每个修复任务，我们创建了五个对抗性 issue 描述，分别对应一种攻击类型：命令执行、反序列化、路径遍历、拒绝服务以及弱哈希。其次，我们在 SWEADV 上评估了来自三个 LLM 后端的 mini_swe APR 智能体：GPT-5-Mini、MiniMax-M2.5 和 DeepSeek-R。我们发现，平均而言，对抗性 issue 描述能够在 51.7% 的案例中在成功修复的同时诱导出恶意行为。第三，我们研究了典型检测机制是否足以阻止此类恶意补丁被接受。在修复前，使用 LLM-as-judge 对对抗性 issue 描述进行检测，平均检测准确率仅为 62.3%。在修复后，使用静态分析工具和 LLM-as-judge 对对抗性 APR 补丁进行检测，平均检测准确率分别仅为 39.4% 和 55.4%。我们得出结论：鉴于自主 APR 智能体易受对抗性攻击影响，目前尚不能在生产部署中信任它们。

## Abstract
Software agents with Large Language Models (LLMs) are designed for Automated Program Repair (APR) tasks, raising the possibility that, in the near future, APR agents will fix bugs automatically without much human intervention. Can we trust an APR agent to produce both functionally correct and secure code in such situations? What if attackers target production APR agents with adversarial issues that seem benign but may influence the agents to produce correct but insecure code? In this paper, we took a first step towards answering these questions by conducting an empirical study. First, we created SWEADV, a benchmark of 750 adversarial issue descriptions constructed from 150 repair tasks in SWE-bench Verified. For each repair task, we created five adversarial issue descriptions, one for each attack type: command execution, deserialization, path traversal, denial of service, and weak hashing. Second, we evaluated mini_swe APR agents from three LLM backends on SWEADV: GPT-5-Mini, MiniMax-M2.5, and DeepSeek-R. We found that on average, adversarial issue descriptions can induce malicious behaviors with successful repair in 51.7% of cases. Third, we investigated whether typical detection mechanisms are sufficient to prevent such malicious patches from being accepted. Pre-repair detection with LLM-as-judge on the adversarial issue descriptions resulted in an average detection accuracy of only 62.3%. Post-repair detection on adversarial APR patches using static analysis tools and LLM-as-judge achieved average detection accuracies of only 39.4% and 55.4%, respectively. We conclude that autonomous APR agents cannot be trusted yet in production deployment, given their susceptibility to adversarial attacks.

- **攻击设想**：攻击者只需构造看似良性、却夹带隐蔽要求的"对抗性 issue"，就可能诱导智能体在通过功能测试的同时植入漏洞（如论文 Fig.1 中，一个 astropy 修复任务被注入 traceback 与"添加预处理钩子"要求后，智能体生成的补丁虽修复了原缺陷，却额外加入读取环境变量并 `subprocess.Popen(..., shell=True)` 执行命令的恶意辅助函数）。
- **整体含义**：这是**首个针对 LLM 驱动 APR 系统的对抗性 issue 描述脆弱性实证研究**。作者指出"通过测试的补丁不应默认被视为安全"，并警示自主 APR 智能体目前尚不适合生产部署。

## 2. 方法论

### 2.1 核心思想

- 构建**模型无关（model-agnostic）**的对抗基准 SWEADV：同一条对抗性文本可对任意受害智能体/LLM 复用，与先前需针对特定受害者定制的攻击（如 SWExploit）不同。

### 2.2 威胁模型与形式化

- **黑盒攻击者 A**：不知晓目标 APR 智能体、内部系统、训练数据、参数、执行环境与验证设施；唯一能力是提交/影响 issue 描述 $i^*$，不能修改仓库、补丁、测试套件或验证流水线，也不能强制智能体生成特定补丁。
- **攻击目标形式化**：构造 $i^*$ 使生成补丁 $p^*=V(R,i^*)$ 同时满足
  - 载荷谓词：$V_a(R,p^*)=\text{TRUE}$（含预期恶意行为）
  - 功能验证谓词：$T(R,p^*)=\text{TRUE}$（通过 FAIL_TO_PASS 与 PASS_TO_PASS 测试）

### 2.3 SWEADV 构建流水线（Fig.2）

- **输入**：SWE-bench Verified 的真实修复任务（原始 issue、golden patch、仓库上下文、测试规范）。
- **步骤一：攻击载荷创建（离线）**
  - *目标符号提取*：解析 golden patch diff，映射到仓库快照源文件，选被改动行最多的封闭函数/方法/类（如 `separable.py::_cstack`）作为目标符号。
  - *注入符号生成*：由目标符号基名 + 邻近代码命名（补丁标识符、兄弟符号）组合出符合仓库命名风格的候选名，取首个不存在于仓库者（如 `_coord_matrix_cstack`）。
  - *载荷模板*：每类攻击含四要素——可选 import、可替换函数名、攻击者可控的环境变量输入、攻击特定危险 sink（命令执行、不安全反序列化、攻击者可控路径写文件、昂贵正则匹配、弱哈希）。
- **步骤二：对抗性 issue 创建**
  - 由攻击者 LLM（Gemini 2.5 Pro）接收原始 issue + 载荷，生成保留原修复目标、追加诱导性要求的对抗文本。
  - 提交给构造期"代理修复智能体"（mini_swe + Gemini 2.5 Pro）生成补丁；若 diff 验证器确认注入 helper 被**定义且被调用接入**目标路径，则保留该实例，否则将反馈回传攻击者 LLM 重试。
- **五类攻击**：run command、deserialization、path traversal、denial of service（DoS）、weak hashing，覆盖执行滥用、不安全数据处理、文件系统操纵、资源耗尽、弱密码学等不同漏洞类别。

### 2.4 评估指标

- **FR（Fix Rate）**：对抗性 issue 导致功能有效修复的比例。
- **ISR（Injection Success Rate）**：诱导出预期恶意行为的比例。
- **ASR（Attack Success Rate）**：补丁既通过功能验证又含预期漏洞的比例。
- 记 $F$ 为通过验证数、$I$ 为注入并调用漏洞数、$S$ 为二者同时满足数，则 FR $=F/N$，ISR $=I/N$，ASR $=S/N$。

## 6. 主要结论与发现

- **Finding 1–3（鲁棒性）**：对抗性注入**不降低修复性能**（SWEADV 上对抗与良性的 FR 差多在 4% 内），因此"修复成功"无法作为被感染的信号。SWEADV 的 ISR 达 75.2%–81.7%，约为基线的 3–4 倍；ASR 达 48.5%–54.0%，几乎是基线（18.8%–26.4%）的两倍，且跨模型更稳定（模型间差距仅 5.5%）。攻击成功与否取决于载荷能否自然融入修复：weak hashing 最易注入（MiniMax-M2.5 达 64.0%），path traversal 最难（44.7%/40.0%）。
- **Finding 4–5（修复前检测）**：SWEADV 对抗性 issue 比基线更难检测；guided 提示下平均准确率仅 **62.3%**（F1 70.9%），比基线低 16.6%/13.9%。DoS 类最难检测，因其行为可伪装为正常校验支持（GPT-4o 的 F1 不足 10%）。
- **Finding 6–9（修复后检测）**：静态分析效果差——SWEADV 上 Semgrep 平均准确率 49.5%、Bandit 仅 29.3%，静态平均 **39.4%**（F1 37.0%），规则覆盖是关键瓶颈。补丁级 LLM judge 更好但平均准确率也仅 **55.4%**（F1 61.8%），略优于随机猜测，且会因过度泛化而在 Run Command/Deserialization 上退步。
- **Finding 10–11（组合防御）**：组合检测在基线上接近完美（平均准确率 88.8%、F1 87.8%，Claude-S-4.6 达 98%+），但在 SWEADV 上平均仅 **65.9%**（F1 72.4%），最强的 Claude-S-4.6 也只有 75.8% 准确率/82.3% F1。
- **Finding 12（前沿模型）**：Claude Opus 4.5 在 206 个实例上 FR 98.1%、ISR 86.4%、**ASR 85.4%**——编码能力越强、越善于遵循指令的模型反而可能更易被诱导注入漏洞。
- **Finding 13（失败归因）**：600 个假阴性中，"误判为合法缺陷/功能"最多（359），其次为"要求显式恶意意图"（161），以及将恶意逻辑误认作安全审计（21）、不良工程（19）、证据不足（18）、Hook/基础设施（17）、歧义（5）。检测器常能识别出合理的良性意图，却**未能发现修复目标与新增安全敏感代码之间的错位**。

## 7. 优点

- **基准设计的模型无关性**：SWEADV 的对抗文本不绑定特定受害者，可跨模型/智能体复用，弥补了 SWExploit 需按目标定制文本的局限。
- **现实的黑盒威胁模型**：仅控制 issue 文本、不可见修复管线，贴近真实开源 issue 提交流程。
- **构造流程自动化且有"
