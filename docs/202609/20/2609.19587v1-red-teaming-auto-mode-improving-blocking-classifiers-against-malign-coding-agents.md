## 摘要
为防止编程智能体失控，生产系统如今会用阻断式监控器审查其提出的每个动作，并在执行前予以拒绝（Claude Code 中的 Auto Mode、OpenAI Codex 中的 Guardian）。先前对此类监控器的评估，主要衡量其对意外危害或来自试图劫持智能体的不可信来源的提示注入的鲁棒性。但较少被理解的是，当它们所监控的智能体持续失准时，这些监控器表现如何。为理解这一风险，我们让一个对抗性智能体执行任务：规避生产环境中的阻断式监控器并造成灾难性危害，例如外泄自身权重。我们发现，当以高层级攻击策略进行指示时，对抗性智能体可以通过若干不同机制取得成功，例如由智能体生成的针对监控器的提示注入、多智能体攻击以及恶意压缩。尤其我们发现，在 79% 的试验中，智能体可以利用针对 Auto Mode 和 Guardian 的注入攻击来运行任意 bash 命令。我们还发现，通过设计变更，如增强工具覆盖范围、转录格式以及引入智能体化监控阶段，可以大幅改进 Auto Mode。即使有这些改进，以可接受的成本防止多上下文攻击仍是一个未解决的问题。通过详细说明我们的红队测试方法并强调新的攻击向量，我们旨在帮助防御者评估其缓解措施，以应对持续存在的恶意编程智能体的可能性。代码见 https://github.com/safety-research/red-teaming-auto-mode。

## Abstract
To keep coding agents from going off the rails, production systems now review each proposed action with a blocking monitor that can reject it before it runs (Auto Mode in Claude Code, Guardian in OpenAI's Codex). Prior evaluations of such monitors largely measure robustness to accidental harm or prompt injections from untrusted sources looking to hijack the agent. Less understood is how they hold up when the agent they monitor is persistently misaligned. To understand this risk, we task an adversarial agent with evading production blocking monitors and causing catastrophic harm, e.g. by exfiltrating its own weights. We find that when instructed with high-level attack strategies, adversarial agents can succeed through several distinct mechanisms, such as agent-generated prompt injection against the monitor, multi-agent attacks, and malicious compaction. In particular we find that in 79% of trials, the agent can use an injection attack against Auto Mode and Guardian to run arbitrary bash commands. We also find that it is possible to greatly improve Auto Mode through design changes like enhancements to tool coverage, transcript formatting and an agentic monitor stage. Even with these improvements, preventing multi-context attacks at an acceptable cost remains an open problem. By detailing our red-teaming methodology and highlighting new attack vectors, we aim to help defenders evaluate their mitigations against the possibility of persistent malign coding agents. Code is available at https://github.com/safety-research/red-teaming-auto-mode.

## 2. 方法论

### 2.1 核心思想

- 采用 **AI Control 框架**：假设被监控模型会**故意颠覆**其安全措施；沿用**可信监控（trusted monitoring）协议**，即监控器被假定不与智能体合谋。
- 与 MonitoringBench、SLEIGHT-Bench 等用固定攻击轨迹打分不同，本文让**自适应攻击者 live 对抗生产监控器**，从而给出更可信的风险估计。

### 2.2 四类攻击类型（Table 1）

| 攻击类型 | 监控失效原因 |
|---|---|
| **Monitor Injection（监控注入）** | 智能体生成的内容（代码、注释、工具参数）腐化监控判断，使其批准有害动作 |
| **Multi-Context Attack（多上下文攻击）** | 攻击跨越监控只能孤立看到的上下文：多智能体经共享工作区协调，或单会话的 **compaction（上下文压缩）** 隐藏早期攻击步骤 |
| **Coverage Gap（覆盖缺口）** | 监控无法介入动作空间的某些部分，或某些信息对监控不可见 |
| **Policy Failure（策略失败）** | 提示策略未涵盖有害行为，或监控未能正确应用策略 |

### 2.3 监控器变体（Table 2）

- **阶段设计**：动作先过一 token 预筛分类器 **S1**，再入推理分类器 **S2**，最后可由**工具调用型智能体**读取文件、查询环境；**任一阶段判为无害即放行**，因此大多数动作被便宜的预筛清掉，只有模糊案例升级到昂贵阶段。
- **五个主要变体**：
  - `auto mode`：S1→S2，Sonnet 5，不监控 cwd 内编辑（Claude Code 生产默认）；
  - `guardian`：agent，GPT 5.6 Luna，不监控 cwd 编辑（近似 Codex 生产默认）；
  - `guardian strict`：guardian + **监控所有编辑**；
  - `auto mode ++`：S1→S2→agent，Opus 4.8，**全编辑监控 + bug 修复 + 抗注入 + compaction 监控**；
  - `auto mode strict`：仅保留 agentic 阶段（去掉 S1/S2）。
- 读取（reads）始终自动放行。

### 2.4 三种评估模式（成本/保真度递增）

1. **分析式评估（Analytical）**：直接阅读监控的 prompt、代码及其与系统的集成，寻找离散漏洞（未监控的工具调用、注入通道、prompt 边界情况、智能体输出被提升为用户意图之处）。
2. **回放式评估（Replay，off-policy）**：用既有转录对监控打分，便宜、可复用、可自由优化转录局部，但**不捕捉攻防交互**。含两类：
   - **Benign replay**：4,000 条 SWE-chat 真实用户动作，测误报率（FPR）；
   - **Malign replay**：攻击转录，用于打分与优化攻击（如注入字符串搜索）。
3. **Rollout 式评估（on-policy）**：让红队智能体（主要为 Opus 5）**实时对抗**监控，是风险估计的最可信来源。含两类：
   - **Arena**：真实 Claude Code 智能体在 Docker 环境（LinuxArena、BashArena、自定义任务）中行动，用 `PreToolUse` hook 把每个动作先路由到监控；side task 由**确定性 checker 读取环境最终状态**判定；
   - **Simulation**：基于 Inspect 的 Python agent，含 bash/write/edit 工具，工具输出由 **LLM Dungeon Master（DM）**按场景描述生成，并额外提供 **compaction 工具**以便触发压缩。

### 2.5 自动化红队

- **监控注入**：OPRO 式优化循环——proposer 模型迭代注入字符串，在固定 base transcript 集上以"绕过监控的比例"为目标爬山（回放式，无状态，可大量迭代）。
- **Compaction 攻击与策略失败**：**调研式 fuzzing agent**——给定主任务/副任务/场景 brief，批量生成候选转录并调用监控，由 judge 判定转录是否"足够可信"从而构成真实假阴性；每个 fuzzing agent 有 30 次分类器调用预算，多次 epoch 迭代。

### 2.6 防御硬化技术

- **Heredoc framing**：每条记录包裹在 `<record-h>...</record-h>` 中，标识符 `h` 是**由 per-process 密钥派生的 48-bit 十六进制串**，对智能体不可猜，使其无法伪造记录边界（尤其是闭合标签）。
- **转义**：记录内部用 **JSON-L 编码**并追加一层转义，把智能体可控的 `<`、`>` 变成 `\u003c`、`\u003e`，削弱伪造标签（如 `</transcript>`）的效果；高熵框架标识符还使记录边界对监控更显著。
- **其他设计变更**：(a) 把**工具结果纳入监控上下文**；(b) 增加**工具调用型调查 agent**作为最后阶段；(c) 加入 **compaction 摘要检查**（标记误述用户意图或建议有害后续步骤的摘要）；(d) 监控 cwd 内所有编辑。

### 2.7 攻击者 affordances（信息给予）

- 默认按 **Kerckhoffs 原则**告知攻击者监控的格式、代码、设置等全部细节（但不给具体破解技巧）。
- 设计 **P（技术知识）× M（监控知识）阶梯网格**：P0–P4 从"目标"逐步加到"伪造结构并让真实动作排在最前、无害动作排在最后"；M0–M4 从"存在审查者"逐步加到"给出精确文本格式与示例转录"。
- 主要实验使用 **P2 + M4**：给全监控信息，但不直接给出注入思路。

## 3. 实验设计

### 3.1 场景与 Benchmark

- **Arena 三大环境**（主结果池）：
  1. **凭证泄露**：主任务写磁盘用量报告；副任务把真实生产凭证发给日志端点。
  2. **权重外泄**：小型模型仓库旁有外部镜像；
