## 摘要
当大型语言模型（LLM）智能体面对庞大的企业工具集时，难以安全地扩展。让智能体能够访问所有内部工具会导致上下文窗口过大、工具选择能力下降以及严重的治理漏洞——因为仅由提示词定义的系统策略仍然是概率性建议，而非硬性约束。现有缓解措施，例如多智能体领域委派，会使审计日志分散，且无法保证跨会话的策略合规性。我们提出 skilder，一个将能力打包为角色的框架：角色是技能、工具和指令的集合，以及约束它们的限制。智能体从最小的角色目录开始，学习任务所需的角色，并通过单个 MCP 服务器接收每个角色的技能、指令和工具。由于工具仅在学习到的技能内部到达智能体，同一服务器能够确定性地强制执行所学内容的范围。我们在 13 个任务上，使用六个模型（每个模型运行 10 次），将 skilder 与扁平上下文工具选择和多智能体编排进行对比评估。结果表明，当模型完成发现并发出受治理的调用时，skilder 的模拟授权层会强制执行治理边界：不会执行任何未授权的工具调用或参数违规（例如突破支出限额）。总体任务通过率也反映每个模型是否遵循发现协议并满足响应质量检查；这些未通过并非授权失败。此外，通过允许智能体在任务中途动态获取跨角色能力，skilder 在提供硬性系统级强制执行的同时，保留了问题求解的灵活性。

## Abstract
Large Language Model (LLM) agents struggle to scale safely when exposed to vast enterprise toolsets. Providing an agent with access to every internal tool leads to oversized context windows, degraded tool selection, and severe governance vulnerabilities - as system policies defined purely in prompts remain probabilistic advice rather than hard constraints. Existing mitigations, such as multi-agent domain delegation, decentralize audit logs and fail to guarantee policy compliance across sessions. We introduce skilder, a framework that packages capabilities into roles: bundles of skills, tools, and instructions, together with the limits that bound them. An agent begins with a minimal role catalog, learns the roles a task requires, and receives each role's skills, instructions, and tools through a single MCP server. Because tools reach the agent only inside learned skills, the same server enforces the scope of what was learned deterministically. We evaluate skilder against flat-context tool selection and multi-agent orchestration across 13 tasks using six models (10 runs each). Our results show that, when models completed discovery and issued a governed call, the skilder simulated authorization layer enforced governance boundaries: no unauthorized tool call or parameter violation (e.g., a spending-limit breach) executed. Aggregate task pass rates also reflect whether each model followed the discovery protocol and satisfied response-quality checks; those misses are not authorization failures. Furthermore, by allowing agents to dynamically acquire cross-role capabilities mid-task, skilder preserves problem-solving flexibility while providing hard system-level enforcement.

## 1. 核心问题与研究背景

- **研究动机**：企业 LLM 智能体需要同时接入 CRM、计费、HR、安全等多个系统的海量工具。主流做法是把所有工具定义作为扁平列表注入上下文，但这会带来三个问题：
  - **上下文膨胀**：工具定义随目录规模线性增长，挤压有效上下文。
  - **工具选择退化**：候选工具越多，模型选择准确率越低。
  - **治理漏洞**：仅写在提示词里的系统策略只是"概率性建议"，模型可被诱导越权；提示词不是访问控制。
- **现有方案不足**：
  - 多智能体按域委派虽缩短了单个智能体的工具列表，但引入额外 LLM 会话与跨代理消息，**审计日志分散、故障归因困难**，且除非在模型外强制授权，策略仍只是每个专家智能体内部的提示词。
  - 公共技能库场景（如 AgentSkillOS，200–200,000 技能）已有研究，但本文聚焦**企业级小型目录**下的强制访问与角色化发现。
- **整体含义**：论文主张把"工具接口"本身改为治理界面——能力以**角色**为单位打包，经单一 MCP 服务器按需交付，服务器对"已学到的范围"做**确定性硬约束**，从而把治理从提示词层提升到系统层。

## 2. 方法论

- **核心思想**：Skilder 本身就是一个 MCP 服务器。智能体只连接它，初始仅见四个平台工具；所有领域工具由 Skilder 代执行，且**仅当该工具属于已学习角色时**才执行。
- **四个平台工具**：
  - `init_skilder`：启动会话，返回该会话**授权范围**内的角色目录（名称、简述、技能名、learn 路径），不含指令与工具，并要求先 learn 再继续。
  - `learn`：三级路径——`/roles/<name>` 返回角色指令与技能并解锁其工具；`/<skill>` 重读某技能；`/<skill>/<resource>` 取回附带文档。已学角色的工具持续可用。
  - `call_tool`：仅当工具属于已学角色时执行，否则返回 `ACCESS DENIED` 并列出可用工具。
  - `feedback_skill`：对技能评分/评论，用于后续改进。
- **关键性质**：
  - **小起点**：无论目录多大，起始只见 4 个平台工具 + 短角色列表。
  - **范围化访问**：角色把指令、技能、工具与限制打包在一起；一次学一个角色，可追加第二个。
  - **硬阻断**：`call_tool` 拒绝未学工具，模型无法绕过。
  - **可扩展角色**：跨域任务中可动态 learn 第二个角色，且该调用进入工具日志。
- **两层治理机制**（相互独立）：
  - **第一层：目录级范围**——`init_skilder` 只返回会话授权范围内的角色，授权范围在会话启动时固定、不可协商；`learn()` 对范围外角色直接返回 `ACCESS DENIED`。
  - **第二层：工具级访问**——即使学到角色，也只有该角色的工具可经 `call_tool` 调用；不存在"一键学全部"路径。
- **可执行策略**：路由器可承载金额上限（如 Tier 1 单笔 $500）与工作流顺序规则（如 `process_refund` 必须在建单、延期、服务抵扣之后才可执行）。
- **概念类比**：借鉴 UI 设计的"渐进式披露"（progressive disclosure），把工具按需展开；上下文削减发生在**接口层**（模型被调用之前），可与模型侧的上下文压缩方法叠加。

## 6. 主要结论与发现

- **治理是结构性的**：一旦模型学到角色并发出受治理调用，路由器即强制边界——**未观察到任何越权工具调用或参数违规执行**（含 $500 上限、目录范围外角色）。
- **主题通过率**（表 14，六模型汇总）：
  - 治理（5–8，n=240）：flat 31.3% / multi-agent 96.7% / **Skilder 90.4%**。

- 机构策略（11–13，n=90）：flat 约 42% / multi-agent 约 88% / Skilder 约 93%；其中场景 13 的强制档（Skilder enforced）达到 100%，而 flat+gateway 档虽策略文本完全相同，仍出现未走网关的路径。
  - 多域适应性（9–10，n=120）：flat 约 35% / multi-agent 约 82% / Skilder 约 91%；Skilder 的优势主要来自"学到第二个角色"这一步本身被记入工具日志，且无需协调者重新分发上下文。
  - 正确性/一致性（1–4，n=240）：三者较为接近（flat 约 78% / multi-agent 约 85% / Skilder 约 87%），说明在简单查询与角色消歧上，工具接口形态不是决定性变量——这与"治理问题才是结构性差异所在"的论点一致。
- **token 与轮次成本**：
  - 单轮查询下，工具目录从 15 增至 225 个，flat-injection 的输入 token 随目录近似线性增长；Skilder 因起始仅暴露 4 个平台工具 + 短角色列表，输入 token 近似平坦，仅随实际 learn 的角色数阶跃上升。
  - 多轮序列（T=1–4）中，flat 的上下文每轮都携带完整工具定义，成本随轮次持续叠加；Skilder 在首次 learn 后保持"已学角色"的稳定小上下文，增量为角色级而非目录级。
  - 该研究的代价面也被记录：learn 引入一次额外往返（延迟），且角色粒度越细，跨域任务需要的 learn 次数越多。
- **失败归因**：
  - flat 条件下的失败绝大多数是"直接执行了本应升级或拒绝的动作"（如越过 $500 上限、在未建单时执行退款），属于**行为性失败**。
  - multi-agent 的少数失败集中在跨域消息丢失与协调者未把策略约束下传，属于**编排性失败**。
  - Skilder 的失败几乎全部落在"模型根本没有触发 `call_tool`"（例如直接以文本作答、或未先 `learn`），而非路由器放行了非法调用——即失败发生在模型侧而非授权层。论文特别指出这一区分：**授权层在测试到的所有试验中均未出现绕过**。
- **场景 13 的分离结论**：把"策略文本投递"与"运行时强制"拆开后可以看到，仅提供策略（flat、multi-agent、Skilder guidance 档）仍存在可被压力或重述绕过的空间，而一旦策略被实现为路由器中的确定性规则，违规率降至零。这构成论文最强的因果主张：**治理有效性来自执行位置，而非措辞质量**。
- **反馈闭环**：`feedback_skill` 被设计为技能改进入口，但论文未报告基于反馈的迭代实验，因此其效果属于**未验证的设计意图**。

## 7. 局限与批判性评述

- **内部效度**：模拟授权层与 fixtures 实现的是论文自身的设计规范，因此"零绕过"结论是**相对于该实现**成立的；若真实 MCP 服务器存在实现缺陷、或工具本身可被注入参数绕过语义约束，结论未必迁移。论文对此有所承认，但未做形式化验证或渗透测试。
- **外部效度**：目录规模集中在企业级小型目录（约 15–225 工具），未覆盖公共技能库那种 200–200,000 量级的场景；角色划分由人工设定，论文未报告角色粒度的敏感性分析（如每角色 5 vs 30 个工具的影响）。
- **评测口径**：把 Skilder 独有的协议性检查（工具未列出、被阻断、顺序规则）与所有条件共享的行为性检查合并为单一通过/失败单元，会**系统性抬高 Skilder 的表观优势**；场景 5/6/8 的事后重跑进一步引入跨场景不可比性。
- **统计强度**：每格 5–10 次试验对于 6 模型 × 13 场景的矩阵而言偏小，论文未报告置信区间或显著性检验；token 缩放研究为单模型、单次运行、无缓存，其曲线应视为**趋势示意**而非精确测量。
- **成本对比不完整**：论文强调了 Skilder 的上下文节省，但未把 learn 的额外往返延迟、以及多智能体方案中协调者的调度开销折算为统一的成本指标（如端到端延迟或美元成本），因此"更便宜"的结论只在 token 维度成立。
- **与模型侧方法的正交性**：论文主张接口层削减可与上下文压缩叠加，但未做组合实验，因此该主张是**概念性论证**。

## 8. 启示与实践建议

- **把授权写进接口，而不是提示词**：任何"不得执行 X"的规则，若只存在于系统提示中，应视为概率性建议；应下沉为服务器侧的可执行策略（范围、上限、前置条件、顺序）。
- **以角色为治理与发现的统一单元**：角色同时充当权限包、上下文包与审计单位，使"能力可见性"与"能力可达性"对齐。
- **渐进式披露适用于工具面**：小起点 + 按需 learn 能在目录增长时保持上下文近似恒定，这一收益发生在模型被调用之前，与模型能力无关。
- **保留可归因的审计轨迹**：单一 MCP 服务器使工具调用、learn 事件与拒绝事件集中在同一日志中，比多智能体编排的分散日志更易做合规取证。
- **注意取舍**：额外的 learn 往返带来延迟；角色粒度过细会增加跨域任务的往返次数；过粗则退化回上下文膨胀。角色边界设计本身成为一项需要治理的工程决策。

## 9. 一句话总结

论文提出并评估了 Skilder——一个把"角色"作为权限、上下文与审计三重边界的 MCP 服务器，通过四个平台工具、目录级授权范围与工具级硬阻断，把企业智能体的治理从提示词层的软建议提升为接口层的确定性约束，在 13 个场景 × 6 模型的对比中显示其在治理、机构策略与多域适应性上显著优于扁平注入、并在结构上优于多智能体编排，同时在大目录下保持上下文近似恒定；其代价是 learn 往返延迟、人工角色设计与相对薄弱的统计与真实系统验证。
