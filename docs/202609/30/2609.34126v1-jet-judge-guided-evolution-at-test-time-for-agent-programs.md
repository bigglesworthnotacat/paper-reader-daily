## 摘要
智能体的可执行程序决定了它如何使用工具、处理观测以及应对失败。在测试时进化该程序有助于适应，但当真实奖励不可用时，决定保留哪些变化是困难的。执行轨迹提供了智能体行为的证据，但解释这些证据需要一个在任务和候选程序变化时仍然有用的裁判。我们提出测试时裁判引导进化（Judge-Guided Evolution at Test Time, JET），它在带标注的源轨迹上进化一个可执行裁判，然后将其冻结并迁移，以引导目标侧的程序进化。该裁判提供分数和诊断反馈，而无需访问目标评估器，也无需更新模型权重。在未见过的 WebShop 任务上，当进化从未经进化的程序开始（冷启动）时，JET 的平均奖励比固定评分标准引导高约 13%；当从已在源任务上优化过的程序开始（热启动）时，高 4%，并且冷启动精确成功率相对提升 36%。在 PushT 上的精确裁判对照实验中，裁判从观测中重建评分规则，结果表明在没有裁判误差的情况下，程序搜索成为瓶颈。分析识别出进化代码中有用的奖励预测逻辑，并表明仅靠更好的最终选择无法解释这些增益。这些结果支持在保持评估器的任务偏移下，通过可执行裁判迁移来实现程序适应。

## Abstract
An agent's executable program governs how it uses tools, processes observations, and responds to failures. Evolving this program at test time can help adaptation, but deciding which changes to retain is difficult when true rewards are unavailable. Execution traces provide evidence of agent behavior, yet interpreting that evidence requires a judge that remains useful as tasks and candidate programs change. We introduce Judge-Guided Evolution at Test Time (JET), which evolves an executable judge on labeled source trajectories, then freezes and transfers it to guide target-side program evolution. The judge supplies scores and diagnostic feedback without target evaluator access or model-weight updates. On unseen WebShop tasks, JET achieves approximately 13% higher mean reward than fixed-rubric guidance when evolution begins from an unevolved program (cold start) and 4% higher when it begins from one already optimized on source tasks (warm start), with a 36% relative improvement in cold-start exact success. An exact-judge control on PushT, where the judge reconstructs the scoring rule from observations, shows that without judge error, program search becomes the bottleneck. Analyses identify useful reward-prediction logic in the evolved code and show that better final selection alone cannot explain the gains. These results support executable judge transfer for program adaptation under evaluator-preserving task shifts.

## 2. 方法论

### 2.1 问题设定

- 任务空间为 \(\mathcal{T}\)，轨迹空间为 \(\mathcal{X}\)。
- 智能体程序 \(\pi\) 将任务 \(\tau\) 映射为可观测轨迹 \(x=\pi(\tau)\)。
- 评估器给出真实奖励 \(R(\tau,x)\)。
- 源任务 \(\mathcal{T}_{src}\) 上评估器输出可用，用于开发裁判；目标任务 \(\mathcal{T}_{adapt}\) 上评估器输出被隐藏，仅可用于事后审计。
- 目标是在不查询目标评估器的条件下，最大化目标任务的真实平均奖励。

### 2.2 阶段一：源监督的裁判进化

- 裁判 \(J\) 是可执行程序，输入轨迹 \(x\)，输出标量估计 \(\hat r=J_{score}(x)\)，并可输出结构化诊断 \(J_{diag}(x)\)。
- 可修订部分包括：提示词、轨迹预处理、确定性计算、校准逻辑、输出解析等；底层推理模型权重固定。
- 在源轨迹数据 \(D=\{(x_i,r_i)\}\) 上，以预测分数与源奖励之间的平均绝对误差（MAE）为目标进化裁判。
- 每轮由 proposer 基于当前裁判代码和源任务反馈生成候选裁判；训练损失决定进化父代，私有验证集损失决定最终选择，固定搜索预算后冻结裁判。
- 源 holdout 仅用于最终报告，不参与开发。

### 2.3 阶段二：冻结裁判并进化智能体程序

- 设 \(\pi^\star_{t}\) 为截至第 \(t\) 轮最高分合格程序。
- 每轮 proposer 接收：当前最佳程序代码、其裁判分数、部署可见轨迹、最近候选的冻结裁判反馈（包括被拒候选反馈）。
- proposer 生成候选程序集合 \(C_t\)，每个候选在所有目标任务上执行，并由裁判打分：

\[
S_J(\pi)=\frac{1}{n}\sum_{i=1}^{n}J_{score}(\pi(\tau_i))
\]

- 合格候选集合 \(C^{elig}_t\) 中最高分候选 \(\bar\pi_t\) 仅在其裁判分数高于当前最佳时，才更新当前最佳程序。
- 选择过程不使用任何目标评估器输出；裁判分数决定晋升，文本诊断和轨迹反馈用于后续改写。
- 可选“源约束”：候选还需在固定源检查集上满足 \(Q_G(\pi)\ge b-\epsilon\)，以保留源能力，但核心方法不要求源评估器查询。

### 2.4 从奖励预测到搜索引导

- 裁判的平均预测误差只是有用性的一个指标；程序晋升取决于候选平均裁判分数的排序。
- 因此，即使整体 MAE 不大，裁判在“哪个候选更好”这一关键决策上的排序一致性更重要。

## 3. 实验设计

### 3.1 数据集 / 场景与 Benchmark

- **WebShop**：主测试场景，检验从服装类任务到非服装类任务的迁移。
  - 源数据：500 个服装训练任务、300 个验证任务、300 个 holdout 任务。
  - 适配集：500 个非服装任务，包括 300 个 garden、81 个 beauty、71 个 electronics、48 个 grocery。
  - held-out 目标集：500 个同目标分布但 session 不相交的未见任务，不参与进化、选择或模型开发。
  - 使用完整目录 1,181,436 个产品与 11,674,685 个目标构成的合成属性生成宇宙。
- **PushT**：精确裁判对照场景，连续控制推 T 形块到目标。
  - 源任务：起始接近目标且无阻尼。
  - 目标任务：更大初始位移并带阻尼 0.2。
  - 评估规则不变且可由可见位姿精确重建：最终覆盖率 \(C_T=\frac{\text{Area}(B_T\cap G)}{\text{Area}(G)}\)。
