## 摘要
多智能体LLM系统正越来越多地被部署于复杂、长时程任务，或者作为智能体在开放环境中交互的自然结果而涌现。然而，它们也带来了显著的安全与安全性风险：使任务泛化成为可能的灵活协议同样暴露了新型威胁，从级联提示注入到智能体间合谋。由于缺乏共享的实证基础设施，针对这些威胁的防御进展一直缓慢，这迫使每项新防御都需要定制化环境开发，并使标准化比较无法实现。现有评估针对的是孤立威胁模型或单智能体设置，但没有一个能在现实多智能体环境中联合变化攻击、防御和架构。为填补这一空白，我们提出ORBIT，一个用于实证多智能体安全与安全性研究的可配置评估框架，构建于英国AISI的Inspect之上。ORBIT允许研究人员配置通信拓扑、记忆、调度和智能体角色。它支持四种威胁类型和四种防御策略，以及非对抗性失败，并提供一个基准测试套件，涵盖五个场景族：浏览器使用、计算机使用、智能体编码、客户服务和协作分配。我们的核心发现是防御在不同威胁之间的可迁移性存在差距：在多问题编码任务中，将受损智能体的攻击成功率降低60个百分点的逐动作防御，对合谋智能体没有可测量的保护作用，而且我们测试的防御均未在所有测试攻击上实现泛化。我们进一步展示了安全-性能权衡，以及架构与防御有效性之间的交互作用。ORBIT已开源，地址为：https://github.com/wlanderson0/orbit。

## Abstract
Multi-agent LLM systems are increasingly deployed for complex, long-horizon tasks or emerge as a natural consequence of agents interacting in the wild. Yet they give rise to significant safety and security risks: the flexible protocols that enable task generalization also expose novel threats, from cascading prompt injection to inter-agent collusion. Progress in defending against these threats has been slowed by a lack of shared empirical infrastructure, which forces bespoke environment development for every new defense and makes standardized comparison impossible. Existing evaluations address isolated threat models or single-agent settings, but none jointly vary attack, defense, and architecture across realistic multi-agent environments. To address this gap, we introduce ORBIT, a configurable evaluation framework for empirical multi-agent safety and security research, built on UK AISI's Inspect. ORBIT lets researchers configure communication topologies, memory, scheduling, and agent roles. It supports four threat types and four defense strategies, as well as non-adversarial failures, with a benchmark suite spanning five scenario families covering browser use, computer use, agentic coding, customer service, and cooperative allocation. Our central finding is a gap in defense transferability across threats: per-action defenses that cut a compromised agent's attack success by 60 points on multi-issue coding give no measurable protection against colluding agents, and none of the defenses we tested generalized over all attacks tested. We further demonstrate security-performance tradeoffs and interactions between architecture and defense effectiveness. We make ORBIT available open-source at https://github.com/wlanderson0/orbit.

## 1. 核心问题与整体含义（研究动机与背景）

- **研究背景**：前沿 LLM 智能体正朝自主化、长时程、多智能体系统（MAS）方向发展，被用于软件工程、计算机使用、科研等复杂任务。MAS 既可能由设计刻意构建，也可能由独立部署的智能体在开放网络中自发组合而成。
- **核心问题**：多智能体系统带来了单智能体系统不具备或会被放大的安全风险，包括：
  - 任务分解把有害目标拆成看似无害的子任务，绕过安全过滤；
  - 内部受损智能体利用可信位置攻击同伴；
  - 智能体间合谋（collusion），通过隐蔽信道或私密黑板协调损害系统目标；
  - 级联式提示注入、记忆投毒、工具使用失败、传染式攻击等。
- **基础设施缺口**：现有防御研究大多是“单一机制 + 单一攻击 + 自建环境”，结果难以横向比较。已有 MAS 框架缺乏可配置拓扑、威胁模型参数化和防御集成；单智能体安全基准（如 ASB）不涉及多智能体编排，安全导向的 MAS 框架（如 Terrarium、MASTER、MASpi）则分别受限于黑板通信、攻击演示或单一威胁模型。
- **整体含义**：论文提出 ORBIT，旨在为多智能体安全与安全性研究提供共享、可配置、可扩展的实证评估基础设施，使“新防御可只改一个配置文件即可与现有攻击、场景、拓扑进行基准比较”，从而缓解防御研究相对攻击研究的基础设施成本不对称。

## 2. 方法论：核心思想、关键技术与流程

- **总体定位**：ORBIT 构建于英国 AISI 的 Inspect AI 之上，是一个集评估框架、编排器和基准套件于一体的系统，支持在真实智能体环境中联合变化攻击、防御与架构。
- **三项设计原则**：
  1. **可配置评估**：拓扑、攻击、防御等维度均可用 YAML 配置，便于控制变量做消融；
  2. **真实智能体环境**：浏览器、真实开源代码库、桌面 GUI 等，每个场景运行在 Docker 隔离沙箱中；
  3. **可插拔威胁模型**：新增攻击/防御只需实现短协议并注册，无需改动编排器或评分管线。
- **六层可组合实验层**（实验 = 每层选一个配置的笛卡尔积）：
  1. **Setup**：定义智能体角色、模型、系统提示、工具，声明有向通信拓扑（star、mesh、chain、flat 等），以及记忆可见性策略；
  2. **Scenario**：任务与执行环境，覆盖五类场景族；
  3. **Attacks**：指定攻击类型、威胁模型（知识水平、预算、持久性、受损智能体数量）、注入时机和成功判据；
  4. **Defenses**：指定防御类型、调用模式、作用范围和失败模式，可组合叠加；
  5. **Execution**：ORBIT 引入 `turn_react()`（每次只执行一个工具调用）和 `AgentScheduler`（维护每智能体隔离状态并选择每轮由谁运行），支持任意执行顺序；
  6. **Evaluation**：对完成日志做 LLM 驱动评分、指标计算和自动有效性检查。
- **编排流程**（Orchestrator，Inspect `@solver`）分三阶段：
  - 组件装配（从注册表组装）；
  - 部署前修改（受损智能体注入、提示疫苗等）；
  - 逐轮循环：注入攻击 → 防御前置钩子 → 执行智能体 → 监控输出 → 评估成功 → 停止检查。
- **度量体系（三层指标）**：
  - **逐智能体妥协分数**：judge 给出 \(C_i \in \{0, 0.5, 1\}\)，分别表示拒绝攻击、计划但未执行、执行有害动作；
  - **逐样本传播深度与攻击成功**：
    \[
    PD_j = \frac{1}{n}\sum_{i=1}^{n} C_i,\quad AS_j = \mathbb{1}[\max_i C_i = 1]
    \]
  - **逐实验聚合率**：攻击成功率 \(ASR = \frac{1}{N}\sum_j AS_j\)，平均传播深度 \(PD\)；
  - **安全–效用权衡**：用良性任务完成率 BTCR 及其变化 \(\Delta BTCR = BTCR_{\text{undefended}} - BTCR_{\text{defended}}\)，与 \(\Delta ASR\) 共同刻画；
  - **合作分配场景的真值指标**：regret \(= (R^* - R_{\text{actual}})/R^*\)，coalition advantage \(= \bar{r}_{\text{coalition}} - \bar{r}_{\text{non-coalition}}\)。
- **内置威胁与防御**：
  - 四类威胁：间接提示注入、误用、受损智能体、合谋；另支持非对抗失败（智能体不当行为、协调失败）；
  - 四种防御：安全系统提示、无状态逐动作 LLM 监控器、有状态历史感知守护智能体、Dual-LLM 隔离架构（Q-LLM 总结不可信内容后再交给有工具的 P-LLM）。
- **记忆可见性控制**：通过 `AgentMemoryAccess` 六个布尔标志（目标可见、自身动作、自身思维链、他人动作、他人思维链、累积自然语言指令）实现，由 `MemoryInjectionFilter` 在每次 `generate()` 时拦截并注入允许内容。

## 3. 实验设计：数据集/场景、Benchmark 与对比方法

- **五个场景族**（共约 90 个实验条件）：
  - **Browser（浏览器自动化）**：基于 BrowserART，100 个有害行为 + 52 个良性任务，攻击以误用为主；
  - **Coding（智能体编码）**：SWE-Bench 单议题、SWE-Bench 多议题（同仓库多智能体并发）、RedCode-Gen（160 个恶意函数签名，8 类恶意软件）、BigCodeBench（约 1000 个良性函数补全）；
  - **Desktop（桌面计算机使用）**：OSWorld 与 OS-Harm，150 个安全关键任务，含误用、提示注入、不当行为；
  - **Customer service（客户服务）**：τ²-Bench 航空域，引入 7 种拓扑预设（solo、双控制、主管–专员、分层升级、网状委员会、起草–审查、跨域交接）；
  - **Cooperative allocation（合作分配）**：hospital、jira_ticket、meeting_scheduling，属 DCOP，支持合谋和受损智能体攻击，有真值最优分配。
- **Benchmark 性质**：将既有单智能体基准适配为多智能体配置，适配路线包括功能分解（F）、多目标重构（M）和原生多智能体（N）；每个场景都提供有害任务和良性任务，以便直接测量安全–性能权衡。
- **对比的防御**：系统提示、LLM 监控器、守护智能体、Dual-LLM；比较的威胁类型为误用、受损智能体、合谋。
- **模型与拓扑**：GPT-5.4、Claude Sonnet 4.6、Qwen3-235B、Llama 70B，以及 GPT-4o 和两个 mini 模型；拓扑包括 standalone、star、mesh，可选共享记忆。
- **统计报告**：所有比率给 95% Wilson 区间，连续指标给 95% 百分位 bootstrap 区间（10,000 次重采样）；同任务实例比较采用配对 bootstrap；LLM judge 自一致率 95.4%，与第二 judge 一致率 92.5%，与人类评分一致率 91%（约 1,300 个判断、100 样本分层子集）。

## 5. 实验数量与充分性

- **实验规模**：总实验矩阵约 90 个不同条件，覆盖 4 种防御、3 类威胁、4 个场景族、多种拓扑和模型；每个条件通常配对一个有害评估和一个良性评估；单格样本量多为 N=50 或 N=100（BrowserART 为 100 有害 / 52 良性；RedCode-Gen 为 160 恶意 / 50 良性；OS-Harm 为 44 有害 / 50 良性）。
- **主要实验组**：
  - BrowserART 防御头对头（3 模型 × 5 防御配置）；
  - JiraTicket 合谋（2 个 mini 模型 × 3 拓扑 × 5 防御；另有前沿模型无防御/双 LLM 对照）；
  - SWE-Bench MI 受损智能体与合谋的配对对比及差异中差异；
  - RedCode-Gen 防御对比；
  - 监控器阈值扫描（τ = 0.5 / 0.8 / 0.9）与假阳性计数；
  - 拓扑消融（standalone、star、mesh、star+shared memory）和跨模型比较；
  - OS-Harm 跨场景对照。
- **充分性与客观性**：
  - 优点：控制了变量，采用配对比较、Wilson 区间、bootstrap 和 DiD，报告假阳性与良性完成率，统计规范较严格；
  - 局限：作者自称多数结果应视为“展示 ORBIT 能力的初步调查”，而非对每个现象的严格研究；攻击使用固定载荷模板而非自适应红队，可能高估静态防御；合谋场景在 JiraTicket 上未观察到可测优势，导致该场景无法用于防御比较；不同场景使用“最易受攻击模型”，各列并非模型受控。

## 6. 主要结论与发现

- **核心发现（作者作为实证结论维护）**：**逐动作防御无法从受损智能体迁移到合谋**。在 SWE-Bench 多议题上，LLM 监控器把单个受损智能体的 ASR 从 72% 降到 12%（−60 点，95% CI [−80, −40]），但对合谋对保持 30% 不变；守护智能体表现相同。原因是合谋中每个智能体的单独工具调用看似良性，漏洞只存在于动作的组合之中。
- **防御迁移失败是双向的**：系统提示对 Qwen3-235B 的 BrowserART 误用最有效（ASR 36%→7%），但对受损智能体无可测效果；没有任何测试防御能覆盖所有测试攻击。
- **安全–性能权衡的代价结构因机制而异**：
  - Dual-LLM 是唯一有可检测任务成本的防御，多议题解决率下降 9.2 点（[−14.0, −4.5]），因为 Q-LLM 摘要降低了信息质量；
  - 监控器在 28% 的良性任务中至少误拦一次，但智能体可通过重试恢复，良性性能统计上不变；提高阈值可消除误报，却使受损智能体 ASR 从 12% 回升到 30%。
- **架构与防御选择交互**：模型选择是测到的最大单一因素，BrowserART 上 standalone 基线 ASR 从 Sonnet 4.6 的 0% 到 Llama 70B 的 27%；Qwen3-235B 从 standalone 换到 Star 使 ASR 从 17% 升至 36%（+19 点）；在 JiraTicket 合谋上则“什么都动不了”，无防御联盟也未显示可测优势。
- **Dual-LLM 在 RedCode-Gen 上失效**：ASR 统计上不变（8.8%），因为 Q-LLM 摘要保留了代码语义，隔离的是注入指令而非有害任务内容。
- **实践建议**：应部署具有互补盲点的分层防御；拓扑选择是安全决策；单基准上的防御评估不足。

## 7. 优点

- **基础设施贡献突出**：将实验分解为六层可配置对象，支持 YAML 声明式配置和插件式注册表，显著降低多智能体安全实验的搭建成本，缓解防御研究相对攻击研究的成本不对称。
- **维度覆盖广**：同时支持拓扑、记忆可见性、调度、角色、攻击、防御、非对抗失败，且可联合变化，这是现有单智能体基准和多数 MAS 框架所不具备的。
- **真实环境与沙箱安全**：浏览器、真实代码库、桌面 GUI 等环境运行于 Docker 隔离沙箱，攻击面工程化（文件注入点、受损角色、隐蔽信道）较系统。
- **统计规范严谨**：Wilson 区间、配对 bootstrap、DiD、假阳性与良性完成率报告，并专门评估 LLM judge 的自一致性与人机一致性。
- **负面结果诚实**：明确报告 JiraTicket 合谋无优势、Dual-LLM 在部分场景失效、无防御泛化，并区分“实证发现”与“能力演示”。
- **开源与可复现**：Apache 2.0 开源，提供数据集许可证、Croissant 元数据和成本明细，实验程序在附录 J 中详细描述。

## 8. 不足与局限

- **攻击非自适应**：使用固定载荷模板而非自适应红队，可能高估静态防御效果，与 AI control 评估的对应只是部分的。
- **配置空间覆盖有限**：配置空间组合爆炸，评估只覆盖代表性切片，作者明确不主张结论可泛化到所有配置点。
- **执行模型限制**：仅支持回合制、离散消息传递；连续通信、共享梯度信号或学习通信协议的系统不在当前范围内。
- **judge 残余风险**：人类检查仅由单一评分者完成，未做评分者间一致性分析，无法完全排除 judge 问题。
- **部分场景结果无结论**：JiraTicket 合谋在无防御时也无正优势，导致该场景不能用于防御比较；前沿模型上的监控器单元因 judge 延迟耗尽墙钟预算，智能体只用了约 40% 回合。
- **模型受控性不足**：各场景使用“最易受攻击模型”，表间列不可直接横向比较；不同场景来自不同模型和栈（如 OS-Harm 结果引自其他工作），作者也提醒不可跨场景比较。
- **双用途风险**：标准化攻击实现理论上可被改用于攻击部署系统；作者以“攻击均为文献已记载的威胁类、且作用于编排层而非模型级越狱”来限定风险。
- **伦理与数据许可**：涉及恶意代码生成等敏感任务，但仅在沙箱中执行；部分源数据（如 BrowserART、RedCode-Gen）因许可证限制不在 ORBIT 中再分发，需用户自行获取。
