## 摘要
基于 LLM 的智能体会生成并执行多步计划，这些计划会调用能够访问私有数据或执行命令的外部工具。在这种场景中，安全性是计划所创建的整个执行过程的属性，而不仅仅是任意单个步骤的属性。计划本身是捕获工具调用、控制流和数据依赖的关键产物。我们提出 CaMeLoT，它是对 CaMeL 的补充；CaMeL 是一种现有防御方法，用于抵御使用工具的 LLM 智能体中的提示注入。CaMeLoT 通过添加静态验证层来扩展 CaMeL，该层在任何工具被调用之前检查智能体的计划。CaMeLoT 将生成的计划转换为有限状态迁移系统，用工具调用、来源和污点信息对其进行标记，并使用 nuXmv 模型检查器将其与以 CTL 表达的时序策略进行对照检查。由于验证在执行之前进行，不安全的计划会被拒绝，而无需使用 LLM 调用或工具调用，从而节省运行时可能消耗的 token，也无需回滚更改或拆除临时沙箱。当验证失败时，模型检查器会返回一个反例，以向智能体提供反馈来修复计划。我们在源自 AgentDojo 基准、SOC 工作流和提示提取实验的策略上评估 CaMeLoT，表明它能在执行前验证一大类时序性质，同时保持 CaMeL 可运行时检查的覆盖范围。

## Abstract
LLM-based agents generate and execute multi-step plans that invoke external tools which can access private data or execute commands. In this setting, security is a property of the entire execution that a plan creates, not just any single step. The plan itself is a critical artefact that captures the tool calls, control flow, and data dependencies. We present CaMeLoT, a complement to CaMeL, an existing defence against prompt injection in tool-using LLM agents. CaMeLoT extends CaMeL by adding a static verification layer that checks an agent's plan before any tool is invoked. CaMeLoT translates a generated plan into a finite-state transition system, labels it with tool calls, provenance and taint information, and checks it against temporal policies expressed in CTL using the nuXmv model checker. Because verification happens before execution, unsafe plans are rejected without using LLM calls or tool calls, saving tokens that runtime could have cost, as well as the need to unwind changes or teardown temporary sandboxes. When a verification fails, the model checker returns a counterexample to give feedback to the agent to repair the plan. We evaluate CaMeLoT on policies derived from the AgentDojo benchmark, SOC workflows, and prompt-extraction experiments, showing that it verifies a broad class of temporal properties before execution while preserving CaMeL's runtime-checkable coverage.

## 2. 方法论

### 2.1 核心思想与总体流程

- 蓝色部分（原 CaMeL）：用户查询 → P-LLM 生成受限 Python 计划 → CaMeL 解释器执行（运行时策略）。
- 黄色部分（CaMeLoT 新增）：计划 → AST 抽取 → 有限状态机建模 → nuXmv 模型检查 → 通过则交 CaMeL 执行；失败则生成反例 → 转自然语言反馈 → P-LLM 修复计划 → 重新验证，直至通过或修复预算耗尽（类似 **CEGAR**，反例引导的抽象精化）。
- 支持两类性质：
  1. **安全策略**（时序逻辑公式，预先定义、按域选择）；
  2. **任务属性**（从用户提示中抽取并翻译为时序逻辑）。

### 2.2 计划到有限状态机的转换

- 对受限 Python 计划做**归一化**后解析为 **AST**，提取四类控制流区域：`TOOL CALL`、`ASSIGNMENT`、`CONDITIONAL`、`LOOP`（嵌套在表达式/参数中的工具调用会被提前发射为区域）。
- 构造有限状态机 **M = (S, s₀, ∆, Σ, L)**：S 为有限状态集，s₀ 为初始状态，∆ 为迁移关系，Σ 为迁移效应（状态变量更新），L 为原子命题标注函数。
- 区域到状态机片段的映射：工具调用产生一个带元数据（工具名、参数、目标变量）的状态；条件产生分支/合并状态与带守卫的迁移；循环用**非确定性选择**（继续迭代或退出）表示，从而保证状态空间有限（属于过近似，可能产生假阳性，但不会漏掉潜在违规）。

### 2.3 来源与污点建模

- 定义严格有序的**特权格**：`trusted < user < untrusted < qllm`。
- 变量按来源打标：字面量为 `trusted`，用户查询参数为 `user`，外部工具输出为 `untrusted`，Q-LLM 输出为 `qllm`；派生值**继承依赖项的最大来源**（保守污点传播）。
- 迁移上生成命题，如 `recipient_trusted`、`recipient_tainted`，并记录**历史谓词**（如 `confirmation_seen`）以支持顺序性质。
- **保守静态抽象**：来源为 untrusted、条件信任或静态不可判定的值一律视为 tainted；**机密性（Readers）不静态处理**，留给 CaMeL 运行时。

### 2.4 CTL 策略与验证

- 使用分支时序逻辑 **CTL**：路径量词 `A`（所有路径）、`E`（某条路径）；时序模态 `X`（下一状态）、`F`（最终）、`G`（始终）、`U`（直到）。
- 典型策略模式：
  - 参数来源：`AG(call_remove_user ⇒ user_trusted)`
  - 污点阻止：`AG(call_send_money ⇒ ¬(recipient_tainted ∨ amount_tainted))`
  - 时序顺序：`AG(host_from_qllm ⇒ A[¬call_isolate_host U call_confirm_host])`
  - 终止性：`AF(done)`
- 策略以带元数据的结构表示（name、id、status、author、date、formula、description、level），元数据风格受 **Sigma 规则**启发，便于日志与安全工具集成。
- **策略选择**：按域过滤，只把与计划中出现工具/命题相关的策略子集送入 nuXmv。
- **参数归一化**：借助工具签名把位置参数与关键字参数统一（如 `send_direct_message(email, body)` 与 `send_direct_message(recipient=email, message=body)` 产生相同原子命题）。
- **反例反馈**：nuXmv 失败时给出具体执行轨迹，CaMeLoT 将其转为包含违规性质、反例路径、可能程序位置与违规类型的修复提示，交回 P-LLM。

### 2.5 从自然语言提示抽取任务属性

- **关键设计约束**：LLM **绝不直接写 CTL**，只提出一小组**类型化义务（typed obligations）**，再由可信代码做 grounding（校验工具名与原子命题合法）并编译成 CTL。
- 义务语言包含：存在性 `EF(call a)`、全路径存在 `AF(call a)`、优先级 `AG(call b ⇒ a_called)`、Until `A[¬call b U a_called]`、响应 `AG(call a ⇒ AF(call b))`、使能可达 `AG(call a ⇒ EF(call b))`、之后禁止 `AG(call a ⇒ AG ¬call b)`、下一步禁止 `AG(call a ⇒ AX ¬call b)`、副作用允许列表、原子要求 `AG(call a ⇒ φ)` 等。
