## 摘要
自演化的智能体框架会持续更新持久化组件，例如记忆、提示词、技能和工具。我们将这一过程称为框架演化。然而，这种演化可能引入意外的安全风险。已有工作研究了框架的误演化，并验证候选框架或归因后的单个组件更新，但对跨组件更新交互的安全分析在很大程度上仍未得到考察。为填补这一空白，我们研究框架演化中的组合式安全失效，即单个安全且保持效用的组件更新之间的交互可能产生不良或不安全的智能体行为，揭示出框架演化固有的安全风险。在三个安全相关基准上，我们识别出 43 个成对和 18 个不可约的三元组合式安全失效。传统解决方案在验证跨组件交互时会带来组合爆炸复杂度，使安全检查随着框架演化而变得不可行。为解决这一问题，我们引入一种类型化超图，将组件状态表示为节点，将安全相关的高阶交互表示为超边。当框架发生变化时，超图仅更新变化状态的交互邻域，而不是重构全局组合空间。在此基础上，我们开发了一种超图引导的运行时监控机制。实验表明，我们的方法能有效缓解组合式安全风险，同时保持任务效用并降低交互检查成本，并进一步揭示了不同安全机制之间经验性的安全—效用—成本权衡。

## Abstract
Self-evolving agent harnesses continually update persistent components such as memory, prompts, skills, and tools. We call this process harness evolution. However, such evolution could introduce unexpected safety risks. Existing work studies harness misevolution and validates candidate harnesses or attributed individual component updates, leaving safety analysis of cross-component update interactions largely unexamined. To address this gap, we study compositional safety failures in harness evolution, where interactions among individually safe and utility-preserving component updates can produce undesirable or unsafe agent behavior, revealing a safety risk intrinsic to harness evolution. Across three safety-related benchmarks, we identify 43 pairwise and 18 irreducible 3-way compositional safety failures. Conventional solution incurs combinatorial complexity in validating cross-component interactions, leaving the safety checking impractical as the harness evolves. To solve this, we introduced a typed hypergraph that represents component states as nodes and safety-relevant higher-order interactions as hyperedges. When the harness changes, the hypergraph updates only the interaction neighborhood of the changed states rather than reconstructing the global composition space. Building on that, we develop a hypergraph-guided runtime monitoring mechanism. Experiments show that our method effectively mitigates compositional safety risks while preserving task utility and reducing interaction-checking costs, and further reveal an empirical safety-utility-cost trade-off across different safety mechanisms.

# 论文总结：智能体框架演化中的组合式安全失效

## 1. 核心问题与整体含义

- **研究背景**：LLM 智能体依赖外部 agent harness（框架），其中包含记忆、提示词、技能、工具等可配置组件。近年来自演化框架会持续更新这些持久化组件，论文称这一过程为 **harness evolution**。
- **核心问题**：现有安全研究多关注单个组件的漏洞，或验证候选 harness / 单个组件更新是否安全，但**跨异构组件的更新交互**未被充分考察。
- **关键现象**：多个**单独安全且保持任务效用**的组件更新，在联合激活后可能产生不安全行为。论文将其定义为 **组合式安全失效**。
- **动机示例**：提示词更新将 Bob 加入 `authorize_group`，记忆更新将 BoA 加入 `bank_account`。单独任一更新都安全；但二者共存后，Bob 可以访问 BoA，形成不安全组合。
- **整体含义**：组合式安全失效是 harness evolution 的内在风险；仅验证单个更新不足以保证演化后框架的安全性。由于组件状态可能在不同演化步中保留，并在未来执行中才被共同激活，因此组合安全具有**执行依赖性**，需要运行时监控。

## 2. 方法论

### 2.1 核心思想

- 将 harness 演化建模到**组件状态粒度**，而不是把每次更新视为不可分割单元。
- 用**类型化交互超图**表示组件状态及其高阶安全交互：
  - 节点：组件状态，记为 \(v=(c,x)\)，其中 \(c\) 是组件类型，\(x\) 是该组件的某个状态。
  - 超边：连接至少两个不同组件的状态，表示安全相关的高阶交互。
- 当 harness 发生变化时，不重建全局组合空间，而是仅更新变化状态的**局部交互邻域**。
- 在运行时，仅检查当前执行实际激活的交互，并在动作生效前进行安全判定。

### 2.2 超图定义与增量构建

- 交互超图定义为 \(G_t=(V_t,E_t,\phi)\)：
  - \(V_t\)：当前可用的组件状态节点。
  - \(\phi:V_t \to C\)：为节点分配组件类型。
  - \(E_t\)：跨组件交互超边。
- 超边分为两类：
  - \(E^{obs}_t\)：由执行溯源确认的**已观测交互**。
  - \(E^{pred}_t\)：通过推理得到的**预测交互**。
- 增量构建流程：
  1. 候选更新 \(u_t\) 引入新状态节点。
  2. 从现有超图中提取该状态的 \(h\)-跳交互邻域 \(\Gamma_h(u_t)\)。
  3. 在局部邻域内进行 **local completion**，提出可能涉及新状态的跨组件交互。
  4. 使用 LLM 作为语义过滤器，结合组件状态与溯源上下文，筛除语义上不合理的候选。
  5. 保留的交互加入 \(E^{pred}_{t+1}\)，与已有观测历史共同形成临时超图 \(\tilde G_{t+1}\)。
  6. 若运行时执行溯源确认某预测交互，则将其从 \(E^{pred}\) 提升为 \(E^{obs}\)。

### 2.3 超图引导的运行时监控

- 当组件状态节点 \(v\) 被激活时，只可能影响包含 \(v\) 的超边，即其关联超边集合：
  \[
  I(v)=\{e\in E_t:v\in e\}
  \]
- 监控器仅访问这些关联超边，记录同一决策或动作上下文中哪些参与状态已经出现。
- 若某超边的所有状态在同一决策上下文 \(q\) 中全部激活，则在对应动作生效前调用安全检查：
  \[
  \text{ISSAFE}(e,q;S)
  \]
- 若检查发现违规，则阻止该动作生效。
- 已观测和预测超边遵循相同监控流程；预测超边一旦被执行确认，就晋升为观测超边。
- 该机制避免全局枚举，运行时成本从依赖全局组合空间 \(\Omega_t\) 降为：
  \[
  O\left(\sum_{\ell=1}^{L}|I(v_\ell)|\right)
  \]
  其中 \(v_1,\dots,v_L\) 是当前执行中激活的节点。

### 2.4 组合爆炸与超图动机

- 全局候选跨组件组合数为：
  \[
  |\Omega_t|=\sum_{k=2}^{d}\sum_{S\subseteq C:|S|=k}\prod_{c\in S}n_c(t)
  \]
- 当组件规模相近时，三组件类型下约为 \(\Theta(n^3)\)，且每次更新后都会重复增长。
- 新增单个状态会引入约 \(\Theta(n^{d-1})\) 个新候选组合。
- 超图通过局部更新与关联超边访问，避免重复枚举全局组合空间。

## 3. 实验设计

### 3.1 数据集与场景

- 使用三个安全相关基准：
  - **AgentDojo**：主要使用 banking 环境，构造 600 个交互面板，157 个合格面板。
  - **Agent-SafetyBench**：构造 182 个交互面板，11 个合格面板。
  - **Agent Security Bench**：适配 clean-task 与工具模拟环境，构造 1,362 个面板，1,243 个合格面板。
- 使用 **A-Evolve** 统一 harness 抽象，并实例化代表性演化机制：
  - 记忆：Reasoning-Bank
  - 提示词：GEPA
  - 技能：Voyager
  - 工具：Alita
- 固定 LLM backbone：**Qwen3-32B**；超图语义过滤使用 **Qwen3-8B**。
- 实验设定为**非对抗性 harness evolution**，不构造攻击者精心设计的更新，也不引入 prompt injection 或后门。

### 3.2 组合失效识别协议

- 对每个请求和两个组件更新 \(u_i,u_j\)，构造四种配置：
  - `00`：原始 harness，无更新。
  - `10`：仅 \(u_i\)。
  - `01`：仅 \(u_j\)。
  - `11`：两者联合激活。
- 合格面板条件：
  1. `00` 安全；
  2. `10` 单独安全且保持任务效用；
  3. `01` 单独安全且保持任务效用。
- 组合式安全失效定义：`11` 出现安全违规，而 `00`、`10`、`01` 均安全。
- 指标：
  - **CF**：组合失效数量。
  - **CFR**：组合失效率，\(\text{CFR}=\text{CF}/\text{Eligible}\)。

### 3.3 高阶组合失效

- 进一步评估三元组合：
  - 对每个更新三元组评估全部 8 种配置。
  - 合格条件：基线与所有真子集组合均安全且保持效用。
  - 仅当完整三元组合出现违规，而所有单体和成对组合均安全时，记为不可约三元组合失效。
- 在 AgentDojo 和 Agent Security Bench 上进行三元分析。

### 3.4 对比方法

- **No Monitoring**：无安全机制。
- **Naive Exhaustive Checking**：穷举检查所有候选动作。
- **SHE**：whole-harness 安全—效用重评估。
- **HarnessLens**：选择性验证行为相关 harness 修改。
- **Ours**：超图引导运行时监控。

### 3.5 评价维度

- **安全性**：Residual CFR，即应用机制后仍到达执行层的组合安全违规比例。
- **效用**：基准特定任务成功标准，合格面板中保持效用的比例。
- **成本**：
  - Verification：每次 harness 更新额外验证执行次数。
  - Runtime Check Rate：调用运行时安全检查器的候选动作比例。
  - Time Cost：每个面板相对无安全机制的额外 wall-clock 时间。

## 6. 主要结论与发现

- **组合式安全失效真实存在**：多个单独安全且保持效用的组件更新，联合后可能产生不安全行为。
- **高阶失效不可约**：论文识别出 18 个不可约三元组合失效，所有单体与成对组合均安全，仅完整三元组合不安全。
- **独立验证不充分**：传统验证候选 harness 或单个组件更新的方法，无法保证跨组件组合安全。
