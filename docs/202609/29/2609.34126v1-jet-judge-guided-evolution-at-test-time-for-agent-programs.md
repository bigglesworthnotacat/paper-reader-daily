## 摘要
智能体的可执行程序决定了它如何使用工具、处理观测以及应对失败。在测试时进化该程序有助于适应，但当真实奖励不可用时，决定保留哪些变更很困难。执行轨迹提供了智能体行为的证据，但解读这些证据需要一个在任务和候选程序变化时仍然有用的评判器。我们提出测试时评判引导进化（JET），它在带标注的源轨迹上进化出一个可执行评判器，然后将其冻结并迁移，以引导目标侧程序进化。该评判器无需访问目标评估器或更新模型权重，即可提供分数和诊断反馈。在未见过的 WebShop 任务上，当进化从一个未进化程序（冷启动）开始时，JET 的平均奖励比固定评分标准引导高约 13%；当从一个已在源任务上优化过的程序（热启动）开始时，则高 4%，且冷启动精确成功率相对提升 36%。在 PushT 上的精确评判器对照实验（其中评判器从观测中重建评分规则）表明，若评判器没有误差，程序搜索会成为瓶颈。分析识别出进化代码中有用的奖励预测逻辑，并表明仅靠更好的最终选择无法解释这些增益。这些结果支持在保持评估器的任务偏移下，通过可执行评判器迁移实现程序适配。

## Abstract
An agent's executable program governs how it uses tools, processes observations, and responds to failures. Evolving this program at test time can help adaptation, but deciding which changes to retain is difficult when true rewards are unavailable. Execution traces provide evidence of agent behavior, yet interpreting that evidence requires a judge that remains useful as tasks and candidate programs change. We introduce Judge-Guided Evolution at Test Time (JET), which evolves an executable judge on labeled source trajectories, then freezes and transfers it to guide target-side program evolution. The judge supplies scores and diagnostic feedback without target evaluator access or model-weight updates. On unseen WebShop tasks, JET achieves approximately 13% higher mean reward than fixed-rubric guidance when evolution begins from an unevolved program (cold start) and 4% higher when it begins from one already optimized on source tasks (warm start), with a 36% relative improvement in cold-start exact success. An exact-judge control on PushT, where the judge reconstructs the scoring rule from observations, shows that without judge error, program search becomes the bottleneck. Analyses identify useful reward-prediction logic in the evolved code and show that better final selection alone cannot explain the gains. These results support executable judge transfer for program adaptation under evaluator-preserving task shifts.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：构建 LLM 智能体时，真正决定行为的是模型外围的"智能体程序"（harness）——即可执行程序，规定保留哪些信息、调用哪些工具、失败时如何响应。在测试时修订该程序（harness evolution / heuristic learning）可以在不更新模型权重的前提下改变智能体行为。
- **核心矛盾**：程序进化依赖评估信号来决定"保留哪些改动、下一步改什么"。真实任务奖励是最直接的信号，但**测试时往往只能执行程序、观察行为，拿不到评测器输出**。此时必须用一个"评判器"（judge）从可观测行为推断任务完成度并给出诊断反馈。
- **关键难点（双重）**：
  - 评判器需跨越**源→目标的分布偏移**仍然有效；
  - 随着程序搜索不断改变被评估的行为，评判器必须**始终有用**。若它系统性低估部分进展或误判失败，就会把搜索引向错误方向。
- **核心研究问题**：*一个在已知奖励的源轨迹上开发出来的评判器，能否引导评测器输出被隐藏的目标任务上的程序进化？*
- **整体含义**：论文把"评估过程本身"当作可进化的软件对象，验证了**可执行评判器的迁移**在"评测规则保持不变、但任务/动力学发生偏移"（evaluator-preserving shift）条件下的可行性。

## 2. 方法论：核心思想、技术细节与算法流程

### 核心思想
把评判器实现为**可执行程序**（而非固定 rubric 或纯 prompt），先在带标注源轨迹上进化它，随后**冻结**并迁移到目标侧，仅用其分数与诊断反馈驱动智能体程序搜索；全程不访问目标评测器输出、不更新底层模型权重。

### 问题设定
- 任务空间 $\mathcal{T}$，可观测轨迹空间 $\mathcal{X}$；智能体程序 $\pi:\tau \mapsto x=\pi(\tau)$。
- 评测器给出真实奖励 $R(\tau,x)$。源任务 $\mathcal{T}_{src}$ 上奖励可见；目标适应集 $\mathcal{T}_{adapt}=\{\tau_i\}_{i=1}^n$ 上奖励被隐藏（仅用于事后审计）。
- 目标：最大化目标集上的平均真实奖励。注意：由于目标轨迹会参与搜索，测的是**对已观测任务的适应**，而非对未见任务的泛化。

### 阶段 1：源监督的评判器进化
- 评判器 $J$ 输出标量估计 $\hat r = J_{score}(x)$，并可额外产生结构化诊断 $J_{diag}(x)$。
- $J$ 是可执行程序，其 **prompt、轨迹预处理、确定性计算、校准逻辑、输出解析**均可被修改；底层推理模型权重固定。
- 目标：最小化预测分数与源真实奖励的**平均绝对误差（MAE）**。
- 流程：每轮由 proposer 读取当前评判器代码与源任务反馈，生成候选评判器程序；**训练损失决定下一轮进化父代**，在**私有验证集**上用损失选出最终候选；源 holdout 仅用于事后报告。
- 选定评判器被**冻结**：代码、参数、校准逻辑在目标适应期间不可更改。

### 阶段 2：冻结评判器并进化智能体程序
- 设 $\pi^\star_{t}$ 为截至第 $t$ 轮得分最高的合格程序。每轮 proposer 接收：
  - 当前最优程序的代码与评判器分数；
  - 最近评估候选（**包括被拒绝的候选**）的部署可见轨迹与冻结评判器反馈。
- 因此"当前最优程序"与"proposer 的反馈状态"可以来自不同程序。
- 候选集 $C_t$ 中每个候选在全部目标任务上执行，用**平均评判器分数**评估：
$$S_J(\pi)=\frac{1}{n}\sum_{i=1}^{n} J_{score}\big(\pi(\tau_i)\big)$$
- 仅当合格候选集非空且其分数更高时才更新当前最优（精英保留/单调提升）：
$$\pi^\star_t=\begin{cases}\bar\pi_t, & C^{elig}_t\neq\varnothing \ \text{且}\ S_J(\bar\pi_t)>S_J(\pi^\star_{t-1})\\ \pi^\star_{t-1}, & \text{否则}\end{cases}$$
- 选择过程完全不使用目标评测器输出。初始程序可以是**冷启动种子**或**源任务优化的热启动程序**。
- **可选源约束**：为保留源能力，可要求候选在固定源检查集 $G$ 上满足 $Q_G(\pi)\ge b-\epsilon$（$b$ 为初始程序源分数，$\epsilon$ 为容差）；这是可选组件，核心流程不需要在目标适应期查询源评测器。

### 从"奖励预测"到"搜索引导"
- 平均预测误差只是有用性的一种度量；真正关键的是**候选间排序的一致性**（谁被晋升）。因此论文同时考察 MAE、Spearman 相关与**选择遗憾（selection regret）**。

## 3. 实验设计：数据集 / 场景、Benchmark 与对比方法

### 数据集与场景
| 场景 | 设定 | 角色 |
|---|---|---|
| **WebShop** | 服装（clothing）源任务 → 非服装（non-clothing）目标任务 | 主测试：评判器迁移 |
| **PushT** | 源任务靠近目标、无阻尼 → 目标任务初始位移更大、阻尼 0.2 | **精确评判器对照**：几何评分规则不变且可从可见位姿精确重建，用于剥离评判器误差、隔离程序搜索 |

- WebShop 数据：全量 1,181,436 商品目录、11,674,685 目标合成属性宇宙；**源**：500 训练 / 300 验证 / 300 holdout（服装）；**适应集**：500 非服装任务（garden 300、beauty 81、electronics 71、grocery 48）；**held-out 目标集**：同域构成、session ID 不相交、从不暴露给 proposer/评判器/选择规则。
- **观测清洗（scrubbing）**：喂给 proposer 与评判器的轨迹只保留任务指令、普通商品观测、动作与交互目标；剔除环境提供的最终/每步奖励、coverage、成功标志、奖励分解、评测器专用标注（含购买后最终观测）。
- PushT 最终 coverage 定义：$C_T=\dfrac{\text{Area}(B_T\cap G)}{\text{Area}(G)}\in[0,1]$，其中 $B_T$ 为终止位姿下 block 占据区域，$G$ 为目标区域。

### 对比条件
- **无目标进化**（基线）
- **proposer 自选择**（读清洗后轨迹后自打一个标量分）
- **固定 rubric 评判器**（预设任务专属评分标准，无源标签优化）
- **进化评判器（JET）**
- **进化评判器 + 源约束**
- 每种条件区分**冷启动**（未进化种子）与**热启动**（源任务优化过的程序）

### 评估指标
- 主指标：WebShop 平均真实奖励；PushT 平均最终 goal coverage。
- 评判器保真度：MAE、Spearman ρ（源 holdout 与目标部分完成轨迹）。
- 搜索诊断：oracle-best、**selection regret**（生成候选中的真实最优与被选候选审计表现的差距）、精确成功率。
- held-out 目标任务上的迁移表现（冻结选定程序后评估）。

### 搜索设置
- 每条件 **5 个独立 campaign**，每 campaign **40 轮进化**，每轨迹最多 **100 环境步**；评判器开发 20 轮 proposer 迭代。

## 6. 主要结论与发现

- **WebShop 主结果（表 1 Panel A）**：
  - **热启动**：无进化 0.6256 → 固定 rubric 0.6589 → 进化评判器 **0.6951**（增益约为固定 rubric 的两倍，差值 0.0362）。
  - **冷启动**：自选择 0.6137 → 固定 rubric 0.6965 → 进化评判器 **0.7797**（比固定 rubric 高 0.0832，比自选择高 0.1660）。
  - 冷启动比热启动达到更高的最终平均奖励：源优化会**偏向源特定行为**，反而增加目标适应难度。
- **held-out 目标任务（表 2 Panel A）**：顺序保持一致。冷启动下进化评判器 0.7915 vs 固定 rubric 0.7008 vs 自选择 0.6259；held-out 精确成功率 50.6%（最高）。热启动 0.6951 vs 0.6700 vs 0.6387。
- **PushT 精确评判器对照**：进化评判器在第一轮即重建几何覆盖规则，MAE 为 0.0000。冷启动 coverage 0.7679 vs 固定 rubric 0.6199 vs 自选择 0.6306；热启动 0.6683 vs 0.6033。**零选择遗憾**，但 coverage 仍远低于 1——说明**消除评判器误差后，程序搜索本身成为瓶颈**。
- **评判器学到了什么**：
  - 源 holdout MAE 从 0.1480 降至 0.1168（−21.1%），Spearman ρ 提升 0.0351；
  - 部分完成轨迹上，进化评判器把奖励预测 MAE 降低约 23.4%（对进化引导程序）与 24.7%（对固定 rubric 引导程序）——优势不依赖于轨迹来自哪种引导；
  - **确定性进化评判器**（不调用 LLM 评估）MAE 0.1153，甚至优于完整版 0.1168，说明进化代码中**独立涌现了有用的数值奖励预测通路**；
  - isotonic 校准只能把固定 rubric 的源 holdout MAE 从 0.1576 降到 0.1488，远不及进化评判器的 0.1168——**分数校准无法替代可执行评判器进化**。
- **评分与诊断的区别**：在"商品/颜色/价格满足但尺寸错误"的例子上，固定 rubric 严重低估部分完成（预测 0.3200，真实 0.8333）并提出无依据的价格担忧；进化评判器预测 0.8329，正确归因剩余错误为尺寸。低估已完成要求会**低估候选**，无依据的批评会把修订引向已满足的要求。

  - **确定性（无 LLM 评估）评判器**在离线对照中不逊于完整版，进一步支持"进化出的代码逻辑本身承载了主要预测能力"这一判断。
- **误差分解（按奖励区间）**：
  - 固定 rubric 的主要问题在 **partial（部分完成）区间**系统性低估，且对 true-zero 区间给出无依据的扣分理由；
  - 进化评判器把偏差从"结构性低估"压缩为更接近零均值的小幅误差，这是其在选择遗憾上占优的直接原因。
- **源约束组件**：方向不一致——热启动下略优于无约束，冷启动下略差，说明"在目标适应期继续约束源能力"并非稳定增益，其价值取决于源/目标重叠程度。
- **总体结论**：
  1. **评判器可以被进化成可迁移的可执行程序**：仅在源奖励上优化、随后冻结，就能在隐藏评测器的目标任务上引导程序搜索，且增益超过固定 rubric、自选择与校准基线；
  2. **增益主要来自"生成"而非"选择"**：更好的评判器改变了 proposer 每轮看到什么、改什么，从而生成不同（而非仅被挑得更好）的程序；
  3. **评判器误差并非唯一瓶颈**：PushT 上评判器已达零误差、零遗憾，coverage 仍远未饱和，说明**程序搜索空间与提案质量**是下一个限制；
  4. **可执行性 > 提示词**：把评判器当作可修改代码（预处理、数值计算、校准、解析）比只改 prompt 更有效，且能自发演化出确定性数值通路。

## 7. 局限与未来工作（作者自述 + 分析）

- **成本与延迟未量化**：每轮需在全部目标任务上执行多个候选、并对每条轨迹调用评判器，推理开销显著；作者将成本/延迟分析列为未来工作。
- **重复次数有限**：每条件仅 5 个 campaign，作者明确表示较小效应（尤其诊断反馈、源约束的贡献）**仍不确定**，需要更多重复才能定论。
- **场景覆盖有限**：仅 WebShop 与 PushT 两个 benchmark，且都满足"评测规则不变、仅任务/动力学偏移"（evaluator-preserving shift）。若**评测规则本身改变**（如目标奖励定义与源不同），评判器迁移的假设即不成立。
- **适应 ≠ 泛化**：目标轨迹参与搜索，测的是**对已观测任务的适应**；held-out 目标集虽隔离，但仍是同域同分布，不能外推到全新任务族。
- **评判器冻结的代价**：目标适应期不可再更新评判器，若目标行为分布与源差异过大，冻结评判器可能过早失效。
- **可选源约束不稳定**：其收益方向随初始化方式翻转，缺乏稳健性证据。

## 8. 方法启示与实践意义

- **把评估当软件来进化**：与其手写 rubric 或反复调 prompt，不如让评判器成为可执行、可单元测试、可校准的程序对象，用带标注的源数据驱动其迭代。
- **区分"评分准确"与"引导有效"**：MAE 只是代理，真正要优化的是**候选排序一致性 / 选择遗憾**；论文用 selection regret 与 oracle-best 诊断把这一点显式化，值得借鉴。
- **诊断反馈是增益来源之一**：结构化诊断（不只是标量分）能告诉 proposer "错在哪"，避免把修订引向已满足的要求；但增益幅度受重复次数限制，尚需更严格验证。
- **警惕"更好的选择"幻觉**：论文用"完美最终选择仍弥合不了差距"这一对照，证明**搜索过程本身被改变了**，提醒后续工作在归因增益时区分生成与选择。
- **奖励清洗是防泄漏的关键工程细节**：在可观测轨迹中剔除评测器专用信号，是保证"评判器真的在推断而非抄答案"的前提。

---

## 9. 一句话评价

JET 把"评判器"从固定 rubric 提升为**可在源奖励上进化、随后冻结迁移的可执行程序**，在评测器输出被隐藏的目标任务上以零权重更新、零目标评测器访问的方式显著提升智能体程序；其最有价值的贡献不是某个具体分数，而是证明了**"评估过程可迁移"**这一前提，并用选择遗憾与"生成 vs 选择"分解清晰界定了增益来源与剩余瓶颈（程序搜索本身）。
