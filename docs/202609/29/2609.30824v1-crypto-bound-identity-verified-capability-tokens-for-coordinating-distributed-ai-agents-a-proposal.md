## Abstract
The prospect of fully autonomous transactional agents did not appear on the horizon until the advent of high capability language models. With such models, the operational benefits of adaptive task orchestration and independent (but constrained) decision making are tantalizing for enterprises and individuals alike. However, each such agent carries with it a serious attack surface in the form of prompt injection which can compromise any soft "guard rails" that may have been placed in context. The consequences of these attacks include credential ex-filtration which, if left unmitigated, renders the whole category of such agents unusable due to breach of trust. Furthermore, expecting a growth of autonomous agents, a security framework for them would require a form of decentralization to scale. Drawing on the proposed OAuth Agent Authorization Profile and the W3C DID and VC standards, we propose a framework based on the principles of capability based security with decentralized agent identity whereby agents access services based on tokens that are cryptographically bound to the agent's and issuer's identities and specify their scope. Services can validate that the delegation chain only involves scope attenuation before acting on any given token. We show that such a layer that lives outside the language model's context window in a secure module can enable agents to act within enforceable security boundaries.

## 2. 方法论：核心思想与关键技术细节

### 2.1 核心思想
- 以**能力令牌**（capability token）替代 ACL：令牌本身不可伪造地指明"谁（代理身份）"、"凭什么（签发者身份与授权）"、"能做什么（scope 与约束）"、"对哪个资源"，以及签发者施加的各类约束（预算、时效、是否可再委派等）。
- 令牌以密码学方式绑定**代理身份**与**签发者身份**，服务方在行动前可独立验证令牌与**委托链（delegation chain）**，并确保每一跳仅做**权限衰减（scope attenuation）**、绝不放大。

### 2.2 关键技术细节
- **身份层**：
  - 采用 **W3C DID / VC** 标准；DID 文档为 JSON 结构，可托管于 `https://<agent>.<domain>/.well-known/did.json`，并通过公共目录（如 `plc.directory`）校验。
  - 亦可用**域名 + HTTPS 证书**（依托 Let's Encrypt 等近去中心化的 CA 生态）证明代理对某域名的控制。
  - 代理须能通过**挑战—响应（challenge-response）**机制用私钥签名随机串，证明其对 DID 的控制权。
- **令牌层**：
  - 令牌为**签名的 JSON 结构**（如 ECDSA 签名的 JWT），内含代理身份、签发者身份、目标资源、约束参数（用途、预算、读写权限、是否允许委派、过期时间等）。
  - 采用**严格衰减的委派**：子代理拿到的能力是其父令牌的子集，服务方沿链回溯即可验证约束是否被放大。
  - 通过**短时效令牌 + nonce 追踪**抵御重放与时间攻击。
- **凭证钱包（Credential Wallet）模式**：
  - 钱包作为**独立进程**运行，仅通过类型化 IPC 通信，且位于 **LLM 上下文窗口之外**；私钥永不进入任何上下文窗口，从构造上使凭证无法被提示注入外泄。
  - 使用 **BBS-2023（BBS+，基于 BLS12-381）**实现**选择性披露零知识证明**，并配合**成对 DID（pairwise DID）**使不同服务的呈现彼此**不可关联**，抵御画像。
  - 钱包策略强制：允许的声明集合、允许的验证方域名、必须存在 challenge；拒绝消息统一化以避免成为 oracle；建议用 HMAC 而非裸 SHA-256；推荐 BBS-2023 而非 ECDSA 证明以获得不可链接性。
- **撤销机制的设计权衡**（作者列出三种备选）：
  1. 全部令牌**短时效**（如 5 分钟），靠刷新失败体现撤销；
  2. 令牌**引用父令牌**，验证方回溯整条授权链（延迟取决于委派树深度）；
  3. 使用**密码学累加器**（cryptographic accumulator）并附带见证与 epoch，复杂度高但性质优良。
- **能力的泛化**：能力不仅适用于 Web 服务，也可门控本地文件系统、工具调用等，理想载体是**WASI** 等能力感知接口。

### 2.3 流程（文字版算法/协议流程）
- **Phase 1 初始化**：钱包后台引导（生成 BBS+ 签发密钥、签发 EmployeeCredential 与 PaymentAuthCredential、创建钱包与验证器）；用户向协调代理 **Atlas** 签发主能力令牌（可委派、2 小时 TTL）；Atlas 向 **Skyway**（航班）与 **Haven**（酒店）签发带预算与 search+hold 权限的委派令牌。
- **Phase 2 航班预订**：Skyway 搜索并 hold；钱包向航班验证器发起 `requestPresentation`，验证器 `issueChallenge` 产生 nonce₁；钱包做策略检查后用**成对 DID（key_A）**派生 BBS+ ZKP，仅披露 `memberOf, role`，不披露 `clearanceLevel, since`；验证签名并消费 nonce₁。
- **Phase 3 酒店预订**：同理，但使用**全新成对 DID（key_C ≠ key_A，key_D ≠ key_B）**，使酒店会话与航班会话**不可链接**。
- **Phase 4 权限升级与最终预订**：用户审核行程后批准；撤销 search+hold 令牌，改发**短 TTL 的 book-only 令牌**；各代理执行 `bookAll()`，服务方验证后确认。
- **应急中止**：用户可随时撤销授予 Atlas 的主能力；服务方沿授权链回溯时会发现签发者权限已失效而拒绝服务。

## 6. 主要结论与发现

- **加密绑定、身份可验证、且约束只随委派衰减的令牌**，是管理临时性、按需触发的代理资源访问的**可扩展方案**。
- 将安全层置于**LLM 上下文窗口之外的安全模块**中，可在提示注入下仍**从构造上**保证私钥不可被外泄、约束不可被篡改。
- **W3C DID/VC 标准 + OAuth Agent Authorization Profile 草案 + BBS-2023** 构成一条成熟度足够、可被采纳的标准化路径。
- **BBS-2023 的选择性披露**有助于隐私保护，配合成对 DID 可实现跨服务**不可链接**。
- 撤销存在**根本性权衡**：纯离线令牌几乎无法撤销；引入校验端点或父链回溯会增加延迟，但作者认为在普遍联网的背景下，这一代价通常可接受。
- 多代理并行行为会形成**多条线性时间的审计线索**（而非单一严格时序），令牌的创建、交换与撤销本身构成**可密码学验证的审计轨迹**。
