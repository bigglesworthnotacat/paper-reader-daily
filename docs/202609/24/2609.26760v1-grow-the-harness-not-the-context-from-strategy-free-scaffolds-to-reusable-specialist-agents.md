## 摘要
大语言模型（LLM）智能体通常处理一系列相关任务，但标准智能体框架会反复要求模型在每个任务的上下文中重建相同的控制决策。我们研究任务反馈能否转而将重复出现的控制转化为可复用的可执行代码，同时将 LLM 调用保留给任务特定的语义推理。我们提出 Growing Harness，一种失败引导的训练范式，它从一个无策略脚手架中学习智能体框架本身；该脚手架暴露固定的模型与工具接口，但不编码任何任务求解控制器。函数级执行轨迹将每次失败定位到有界代码范围，优化器联合修复一个失败窗口，而成功优先的留出集门控会回滚损害先前能力的修复序列。被接受的编辑累积在一个共享框架中，使其控制结构从任务反馈中涌现。在 BrowseComp-Plus 和 WebArena-Verified 上，使用从 4B 到 120B 参数的三类部署模型，Growing Harness 在六种基准-模型设置中的五种取得最高平均成功率，在第六种中比最佳平均值低 0.7 个百分点。相对于工具调用（Tool-Calling）智能体，它将 LLM 调用减少 76.0–91.8%，并将部署智能体的推理成本降低 74.4–98.6%。在 WebArena-Verified 上，其成功率在不同模型规模下保持 44.7–45.3%，而工具调用在 4B 模型上降至 6.7%。消融实验表明，轨迹局部编辑、联合修复和基于门控的回滚各自都能提升最终成功率。这些结果表明，持续的程序增长能够将重复出现的控制从模型上下文中移出并转入低成本代码，从而产生在较小部署模型上仍然有效的可复用专家智能体。

## Abstract
Large language model (LLM) agents often handle streams of related tasks, yet standard harnesses repeatedly ask the model to reconstruct the same control decisions inside each task's context. We study whether task feedback can instead turn recurring control into reusable executable code, while reserving LLM calls for task-specific semantic reasoning. We introduce Growing Harness, a failure-guided training paradigm that learns the agent harness itself from a strategy-free scaffold that exposes fixed model and tool interfaces but encodes no task-solving controller. Function-level execution traces localize each failure to a bounded code surface, an optimizer repairs a window of failures jointly, and a success-first held-out gate rolls back repair sequences that harm prior capability. Accepted edits accumulate in one shared harness, allowing its control structure to emerge from task feedback. Across BrowseComp-Plus and WebArena-Verified with three deployment models from 4B to 120B parameters, Growing Harness achieves the highest mean success in five of six benchmark-model settings and trails the best mean by 0.7 pp. in the sixth. Relative to a Tool-Calling agent, it reduces LLM calls by 76.0-91.8% and deployed-agent inference cost by 74.4-98.6%. On WebArena-Verified, its success remains 44.7-45.3% across model scales, whereas Tool-Calling falls to 6.7% with the 4B model. Ablations show that trace-local edits, joint repair, and gate-based rollback each improve final success. These results show that persistent program growth can move recurring control out of model context and into low-cost code, yielding reusable specialist agents that remain effective with smaller deployment models.

# 《Grow the Harness, Not the Context》论文中文总结

## 1. 核心问题与研究动机

- **背景**：LLM 智能体（agent）在实际部署中往往不是处理孤立任务，而是持续处理同一任务族（task family）的实例流，模型与工具接口保持不变，但目标与观测不断变化。
- **核心痛点**：标准智能体框架（harness，即编排模型与工具调用的可执行代码）在每个任务的上下文中，反复要求 LLM 重建相同的控制决策——如改写查询、过滤观测、校验进展、错误恢复、终止判断。每一次委托都意味着又一次推理调用、更长的上下文和更高的成本。
- **核心问题**：如何让一个**不含任何预设控制器**的脚手架（strategy-free scaffold），从任务反馈中生长出可执行控制结构，从而不再让 LLM 反复重建本可以用代码执行的重复行为？
- **整体含义**：论文提出"**扩展框架，而非上下文**"（Grow the Harness, Not the Context）——将重复性控制固化为持久化可执行代码，把模型上下文留给任务相关的证据与语义推理。这对资源受限设备上的小模型（4B 级）部署尤其有价值。
- **三条设计要求**：(a) **可复用**：训练任务获得的行为应迁移到同分布的新任务，而非编码实例特解；(b) **上下文高效**：减少重复模型调用，避免将例行控制塞入不断增长的上下文；(c) **低先验承诺**：初始化时不要求完整控制器。

## 2. 方法论：Growing Harness

### 2.1 核心思想
- 把**智能体框架本身**作为唯一可学习对象，模型 M 与工具集 T 固定不变。训练从最小可执行脚手架 h₀ 出发（仅暴露任务入口与固定的模型/工具接口，例如 `def main(task, max_llm_calls) -> dict: return {"final_answer": ""}`）。
- 通过**失败引导的迭代生长**：轨迹定位失败 → 联合修复一个失败窗口 → 门控验证 → 接受编辑并累积到共享框架中。
- 目标：确定性的、可复用的控制写进代码；语义解释、综合、模糊比较、答案生成仍交给 LLM。

### 2.2 关键技术与算法流程（对应 Algorithm 1）

1. **函数级执行轨迹（Function-Level Traces）**
   - 每次执行记录执行图 Gᵢ = (Vᵢ, Eᵢ)，节点为函数调用、LLM/工具调用、返回或运行时错误，边表示动态作用域关系。
   - 任务轨迹 τᵢ = (xᵢ, Gᵢ, yᵢ, oᵢ, uᵢ)，其中 yᵢ 为输出、oᵢ∈{0,1} 为基准结果、uᵢ 为 token/成本/耗时。
   - 提取参与函数集合 F(τᵢ)，用于把编辑范围限制在失败所涉及的代码面。

2. **失败窗口课程（Failure-Window Curriculum）**
   - 维护容量为 K 的有界失败窗口 Wₜ，每条目为 (xᵢ, τᵢ, aᵢ)（任务、最新轨迹、修复尝试次数）。
   - 窗口更新规则：Wₜ₊₁ = {xᵢ ∈ Uₜ : aᵢ < R_max} ∪ Fₜ，即已解决任务离开、未解决任务保留并刷新轨迹、达到尝试上限 R_max 的任务退役、新失败补入。
   - 优化器**联合修复整个窗口**的失败，以鼓励产生可复用而非实例特解的行为。

3. **轨迹引导的函数级优化（Trace-Guided Optimization）**
   - 离线优化器 M_opt 接收 Zₜ = (hₜ, {τᵢ}, E)，其中 E 为离线诊断产物（评估反馈、检索文档 ID、证据、动作统计、错误等，部署时不可用）。
   - **可编辑集合** Aₜ = {main} ∪ ⋃F(τᵢ)，只允许修改入口函数与被失败轨迹调用过的函数；可新增可复用 helper，但不得改动未被追踪的既有函数。
   - **编辑预算**：d_fun(hₜ, ĥₜ₊₁) ≤ L；必须保持函数签名与运行时接口、不得删除既有函数、不得硬编码任务 ID/期望答案/固定解。
   - 候选须通过合法性检查（可解析、可编译、暴露入口、保持固定模型与工具接口、满足轨迹范围与编辑预算），否则拒绝。

4. **候选评估与窗口更新**
   - 在完整活跃窗口上重执行候选，划分已解决集 Pₜ 与未解决集 Uₜ = Wₜ \ Pₜ。
   - 若 |Pₜ| < Q（修复阈值），丢弃候选并回滚（修复不足）；否则进入门控。

5. **留出集门控与事务性回滚（Held-Out Gate Validation & Rollback）**
   - 每解决 Q 个任务后，在留出集 G 上重新评估；仅当 SR_G(hₜ) ≥ SR_G(h_gate) 时接受并更新检查点，否则**整体回滚**自上一门控以来的所有修复（包括代码、任务游标、失败窗口、计数器与训练记录）。
   - **成功优先**规则：更低的在线成本不能补偿更低的门控成功率；训练结束前还有一次最终门控评估。

## 6. 主要结论与发现

1. **学习到的控制可迁移**：六种基准–模型设置中五种的最高平均成功率属于 Growing Harness，第六种（BrowseComp-Plus + gpt-oss-20b，39.3% vs 40.0%）仅差 0.7 pp.，说明学到的是任务族内共享行为而非实例特解。
2. **持久化代码替代重复在线推理**：相对 Tool-Calling，LLM 调用减少 **76.0–91.8%**，在线成本降低 **74.4–98.6%**，同时五种设置成功率更高。
3. **跨模型规模保持稳健**：WebArena-Verified 上成功率在三种模型规模间仅 44.7–45.3%，而 Tool-Calling 从 30.0%（120B）跌至 6.7%（4B）——**小模型获益最大**，说明可复用代码补足了小模型需在每次执行中重建的浏览器控制。
4. **任务族塑造控制器形态**：同一策略无关种子在两个基准上分别演化为"共享检索–证据验证流水线"和"确定性解析器 + 学习控制例程 + 通用引导浏览器循环 + 完成状态校验器"的分层结构，支持"低先验承诺"的主张。
5. **消融结论**：函数级轨迹引导最关键（36% → 18%），门控回滚防止能力退化（无门控时门控成功率升至 30% 后跌至 16%），失败窗口联合修复优于单失败条件（提升 8 pp），三者互补。
6. **结构性地管理上下文**：把可重复控制编码进框架、把模型上下文留给任务特定证据与决策，是一条可行的智能体学习路径。

## 7. 优点

- **问题建模新颖且清晰**：把"智能体框架代码"而非 prompt、示例或技能库作为持久化学习产物，与"检索式经验复用"（ExpeL、AWM）和"技能/工具蒸馏"（Voyager、LATM、CRAFT）形成明确区分——学到的控制是**直接运行的普通程序路径**，无需在线检索与重新解释。
- **机制设计互补且工程可落地**：
  - 函数级执行 DAG 把任务级失败**定位到有界代码面**，使每步优化的搜索空间依赖活跃执行切片而非程序总规模；
  - 失败窗口联合修复鼓励跨失败共性；
  - 成功优先的事务性门控回滚（含代码、游标、窗口、计数器状态）直接针对"连续优化不复合"的已知风险。
- **约束设计克制**：禁止硬编码任务 ID / 期望答案 / 固定解，保持函数签名与接口，编辑预算有限，要求候选可编译可解析，降低"作弊式修复"风险。
- **成本意识强**：明确区分在线部署成本与离线优化成本，给出 token 单价与缓存前缀估算方法，报告置信区间与 bootstrap 方法。
- **实证覆盖有说服力**：两个性质互补的基准 + 三档模型规模 + 四类强基线，且小模型上的鲁棒性是少见且重要的发现。

## 8. 不足与局限

- **算力与训练开销不透明**：未报告任何 GPU/集群信息；离线优化器（GPT-5.6-terra/5.4）的调用量与成本被排除在统计之外，因而**无法判断"框架生长"的总收益是否在摊销意义上成立**——作者也承认其价值取决于复用次数能否抵消离线优化开销。
- **实验统计强度有限**：消融为单次优化运行、单一基准与单一部署模型，且与主表数值不一致；训练/门控/评估仅使用一个随机种子；未见多次独立优化运行的方差报告。
- **超参数未统一**：两个基准使用不同的窗口容量、门控间隔、训练期部署模型与优化器版本，作者本人声明不做跨基准难度比较，这也削弱了"同一方法普适"的说服力。
- **覆盖范围有限**：仅两个基准、每个基准 50 个最终评估任务，且 WebArena-Verified 被限定在 shopping/reddit/map 三类网站，外部效度（其他任务族、真实生产环境、多模态/截图观测）未验证。
- **安全与部署风险**：方法会**自动合成并执行代码**，论文在结论中明确指出真实部署需要沙箱隔离、显式权限边界与生成代码验证，但正文未提供任何具体的安全机制、失败案例分析或恶意/错误编辑的定量评估。
- **评估依赖 LLM 判题**：BrowseComp-Plus 使用 LLM 等价性判题，存在判题偏差风险；成本估计依赖最长公共前缀假设，未考虑跨任务缓存复用

## 10. 启示与未来方向

### 10.1 对智能体系统设计的启示

1. **"框架即策略"**：把可学习对象从 prompt / 示例 / 技能库上移到**可执行编排代码**，为智能体提供了一条不更新权重、不依赖检索的经验固化路径。这提示工程实践中可以把"反复出现的控制逻辑"识别出来并下沉为代码，而非持续塞入上下文。
2. **小模型部署的新可能**：4B 级模型在 WebArena-Verified 上借助学习到的框架达到与 120B 模型相当的成功率（44.7–45.3% vs 30.0% 的基线），说明**控制结构可以部分替代模型规模**，对端侧/边缘部署有直接价值。
3. **上下文预算的结构化管理**：把确定性控制编码进代码、把上下文留给语义推理，是一种"上下文工程"的系统化思路，可能比单纯的压缩、摘要或检索更持久。
4. **事务性门控的必要性**：连续代码优化容易发生能力退化，成功优先的门控回滚是维持单调改进的实用机制，可迁移到其他"LLM 改代码"的自我改进系统中。

### 10.2 未来工作方向

- **摊销分析**：量化离线优化开销与在线节省的平衡点，回答"复用多少次才划算"；
- **多种子与多任务族验证**：在更多基准、更多随机种子、更多优化器配置下检验稳健性；
- **安全与权限**：为自动生成的代码引入沙箱、静态分析、权限最小化与失败案例分析；
- **自适应超参数**：让窗口容量、门控间隔、编辑预算随任务族难度自动调整；
- **与其他经验复用范式结合**：如将框架生长与检索式经验（ExpeL/AWM）、技能库（Voyager）互补使用；
- **多模态与真实环境**：扩展到截图观测、真实网页、长时程生产任务；
- **可审计性**：研究生成代码的可读性、可解释性与人工审查流程。

## 11. 总体评价

- **理论贡献**：论文提出并系统化了一个清晰且新颖的问题——**让不含预设控制器的脚手架从失败反馈中生长出可执行控制结构**——并给出完整算法（函数级轨迹、失败窗口课程、轨迹引导优化、事务性门控回滚）。这一视角把"智能体学习"从权重更新、提示工程、技能检索之外，拓展到**框架代码的持久化生长**，具有概念上的独立性。
- **方法质量**：机制设计彼此互补，约束克制（禁止硬编码、保持签名、编辑预算、可编译检查），工程可落地性强。
- **实证强度**：两个性质互补的基准、三档模型规模、四类基线、多维效率指标与 bootstrap 置信区间，主结论（可迁移、成本大幅下降、小模型获益最大、任务族塑造控制器形态）有较好支撑；但消融规模偏小、仅单种子、超参数未统一、算力与优化开销不透明，削弱了结论的统计稳健性与总收益判断。
- **实践意义**：对资源受限部署、上下文成本敏感的生产智能体系统具有直接参考价值；"扩展框架而非上下文"可能成为智能体工程的一条重要设计原则。
- **主要保留意见**：自动合成并执行代码的安全风险、离线优化开销的摊销可行性、以及产物与提示词的不透明性，是该方法走向真实部署前必须解决的三类问题。
