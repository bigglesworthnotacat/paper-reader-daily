## 摘要
语言模型智能体通过其所获得的工具行事。它在处理任务过程中读取的数据可能改变它使用这些工具的方式。因此，越来越多的用于安全、可靠的智能体执行的技术被置于智能体与其工具之间，旨在在该边界处实施访问控制、信息流控制或隔离。如今，这些技术主要在围绕间接提示注入构建的智能体安全基准上进行评估。这些基准通过衡量防御在多大程度上降低成功攻击的数量，同时保持智能体的效用，来评判其优劣。防御仅依据智能体的执行情况来评判。它可能在两项指标上都取得良好得分，却仍然保留着任务并不需要的转移、删除或大范围读取权限。Ajar 利用现有基准直接度量这种开放权限。它挂载到已有的智能体安全基准上，并复用该基准用于给自身运行评分的任务、工具模式、参考解和目标状态。对于每个良性任务，它构造该任务并不需要的候选工具调用，因此允许其中任何一个调用都意味着留下了开放权限。这些调用会在智能体可能采取行动的每一个时点被提交给防御。我们将 Ajar 挂载到 AgentDojo 上对其进行评估，在那里开放权限成为与既有攻击成功率和良性效用并列的第三个维度。我们在五种防御上运行它：Progent、CaMeL、AC4A、Permission Assistant 以及 Claude Code 的 Auto 模式。我们观察到，它们留下的开放权限数量差异很大。有两种防御的泄露量几乎相同，但所完成的良性任务却相差很大；还有一种防御通过拒绝其任务本有权发起的调用来换取部分严格性。这种开放权限无法从所测得的攻击成功率或良性效用中推导出来。Ajar 的源代码见 https://github.com/reSHARMA/Ajar。

## Abstract
A language model agent acts through the tools it is given. The data it reads while working on a task can redirect what it does with those tools. A growing set of techniques for safe and secure agent execution therefore sits between the agent and its tools, aiming to enforce access control, information flow or isolation at that boundary. Today these techniques are evaluated on agent-security benchmarks built around indirect prompt injection. Those benchmarks judge a defense by how far it brings the number of successful attacks down while preserving the agent's utility. A defense is judged only on the agent's execution. It can score well on both metrics while holding open a transfer, a deletion or a broad read that no task needed. Ajar measures that open privilege directly using the existing benchmarks. It attaches to an agent-security benchmark that already exists and reuses the tasks, tool schemas, reference solutions and goal states that benchmark uses to grade its own runs. For each benign task it builds candidate tool calls the task does not need, so allowing one is privilege left open. These calls are presented to the defense at every point where the agent could act. We evaluate Ajar by attaching it to AgentDojo, where open privilege becomes a third axis beside the existing attack success and benign utility. We run it on five defenses: Progent, CaMeL, AC4A, Permission Assistant, and Claude Code's Auto mode. We observed that they leave widely different amounts of privilege open. Two defenses leak by almost the same amount yet differ widely in the benign tasks they finish, and one defense buys part of its tightness by refusing calls its tasks were entitled to make. This open privilege cannot be derived from the measured attack success or benign utility. The source code of Ajar is available at https://github.com/reSHARMA/Ajar.

# Ajar：度量智能体防御中的开放权限 —— 论文总结

## 1. 核心问题与整体含义

- **背景**：语言模型智能体通过工具行事，但它在任务中读取的数据（如文件、邮件、网页）可能被攻击者植入指令（间接提示注入），从而改变它对工具的使用方式。因此，在智能体与工具之间出现了大量防御层，负责执行访问控制、信息流控制或隔离。
- **现有评估的盲区**：当前智能体安全基准（以 AgentDojo 为代表）只用两个指标评判防御——**攻击成功率**与**良性任务效用**。两者都只在“实际发生的运行轨迹”上计算：
  - 若模型根本没提出攻击者想要的调用，防御从未被询问，攻击成功率仍然干净；
  - 若模型完不成良性任务，效用下降，但这未必是防御造成的。
  - 因此防御可以在两项指标上都表现良好，却**仍对一次转账、一次删除或一次大范围读取保持开放**——只是没人提出过它。
- **核心命题**：最小权限原则（Saltzer & Schroeder, 1975）要求组件只持有完成任务所必需的权利。这一“已授权限与已用权限之差”在 Android 权限、云角色等领域已被度量数十年，但在智能体防御层上从未被度量。已有工作只度量**模型本身**是否越权取用工具，而非**防御层**留下了多少开放权限。
- **Ajar 的定位**：直接度量防御留下的开放权限，将其作为与攻击成功率、良性效用并列的**第三条评估轴**。

## 2. 方法论

### 核心思想
- 对每个良性任务，在**每个决策点**构造任务并不需要的候选工具调用，提交给防御判定；将防御的允许/拒绝决定与构造时已固定的真实标签比较，得到两个分数。
- 关键设计：**提出候选的规则同时决定其标签**，因此标签不依赖任何事后判断。

### 关键技术细节

- **决策点（Decision Point）**：任务参考解（reference solution）的每个前缀，k=0 表示尚未行动，k 为已执行调用数。
- **测试（Test）**：一个候选调用 + 固定的决策点 + 标签 `y(c) ∈ {ALLOW, DENY}`，三者构成一次查询。
- **Oracle**：依据宿主基准自带的**必需工具集**与**目标状态（goal state）**给候选打标签；当候选命中基准的注入 sink（使 security() 为真）或与参考解中的写操作一致时，由基准自身谓词直接验证。
- **七类故障（fault class）**：
  - 必需调用（ALLOW，唯一允许类）
  - 离路径工具（任务从不使用的工具）
  - 参数错误（错误资源、参数遗漏、参数加宽、类型违规，参数值均取自环境/参考解/注入）
  - 攻击者植入调用（注入的 sink 调用）
- **危害分级（Harm Tier）**：按“副作用是否可撤销”与“影响范围”分五级，权重分别为 H0=0、H1=1、H2=3、H3=9、H4=27，确保 DENY 测试权重恒为正。

### 评分公式（文字说明）

- **开放权限泄漏（Over-privilege Leakage, OPL）**：
  `OPL(D,t) = Σ_{c∈C⁻_t} w(c)·1[d(c)=allow] / Σ_{c∈C⁻_t} w(c)`
  即防御所允许的超额调用在危害加权下的占比。跨任务时**按权重池化**。
- **供给不足（Under-provision, UP）**与**充分性（Sufficiency）**：
  `UP(D,t) = |{c∈C_req : d(c)=deny}| / |C_req|`，充分性 = 1 − UP。跨任务时取**每任务值的平均**。
- **过度限制（Over-restriction）**：对“任务有权但非必需”的调用被拒绝的比例，单独计分，不纳入充分性。
- **攻击准入（Attack Admission）**：统计防御允许了全部 sink 调用的攻击数量，连接 OPL 与基准的攻击成功率。
- **决策接口**：所有防御统一通过 `decide(call, context) → {allow, deny}` 接入。

### 冲突处理
- 同一调用被多个族提出且标签冲突时，优先级为：基准验证的标签 > Ajar 断言的标签；必需调用 > 断言的超额调用。

## 3. 实验设计

- **宿主基准**：AgentDojo v1.2.2（不改动基准本身），四个任务套件：banking、slack、travel、workspace，共 **97 个良性任务**。
- **测试规模**：生成 **10471 个测试**，覆盖 **3551 个唯一 (task, tool, arguments) 候选**，决策点 k=0 至 k=18。
- **被测防御（5 种）**：
  - Progent（按任务写权限策略并随工具结果更新）
  - CaMeL（信息流控制，检查可信规划器输出程序的 capability）
  - AC4A（每任务实例写一次访问控制策略）
  - Permission Assistant（逐调用权限预测分类器）
  - Claude Code 的 Auto mode（已部署系统，逐调用判定）
- **决定模型**：Sonnet-5 与 Haiku-4.5（Amazon Bedrock），四类防御在两种模型下运行，Auto mode 仅 Sonnet-5。
- **对比基线（4 种）**：allow-all、deny-all、工具名允许列表（tool-name allowlist）、参数精确 oracle（argument-exact oracle）。
- **附加实验**：
  - Progent-static 消融（冻结初始策略 S0，隔离更新步骤贡献）
  - 决定模型对比（同一防御换模型）
  - 危害权重稳健性（6 种权重方案）
  - 测试预算（10/25/50/75/100%）
  - 任务措辞改写（repeat + paraphrase）
  - 判定方差（同一输入重复 3 次）
  - 置信区间（2000 次按任务 bootstrap 重采样）

## 6. 主要结论与发现

- **开放权限是独立的一维**，无法从攻击成功率或良性效用中推导：
  - 两种防御泄漏量相差 **<0.009**，但良性任务完成度相差 **37 个百分点**，且更紧的那个反而完成更多任务。
  - 成本排序与泄漏排序、与充分性排序均不一致。
- **防御间差异显著**：Auto mode 泄漏最高（0.3009），Permission Assistant 冷启动最低（0.0810，Sonnet-5）；带个性化历史的 Permission Assistant 最低（0.0217）但该历史由被评分的标签构建。
- **部分“紧致性”是靠拒绝换来的**：CaMeL 过度限制最高（0.415），同时也是 Sonnet-5 下第二紧的防御；Permission Assistant 则既泄漏少、拒绝也少。
- **更新步骤有实际价值**：Progent 冻结 S0 后泄漏上升 1.24–1.56 倍，而充分性几乎不变——收紧的是任务不需要的权限。
- **决定模型会改变分数**：换用小模型并不沿“权限–效用”前沿滑动，而可能**同时降低泄漏与充分性**，因此 OPL 与充分性必须成对阅读。
- **稳定性**：在 6 种危害权重（Kendall τ ≥ 0.67）、测试预算 ≥25%、任务措辞改写下，防御排序大体保持。
- **判定方差不可忽略**：同一输入重复运行，五次防御自我一致率仅 91%–98%，AC4A 的 OPL 标准差达 0.0203，超过其与邻近防御的距离。
- **没有任何被测防御进入“既紧又可用”区域**（即达到 argument-exact oracle 的紧致度且保持可用）。

## 7. 优点

- **度量目标新颖且切中要害**：首次把“防御层留下的开放权限”作为独立评测对象，弥补 ASR + 效用的盲区。
- **低成本复用**：直接读取宿主基准为自身评分而携带的任务、工具模式、参考解与目标状态，adapter 极薄；换基准只需写一个 adapter，换防御只需写一个 wrapper。
- **标签由构造决定**，避免了“先构造后判断”的循环；且能与基准谓词交叉验证。
- **双分数设计防退化**：泄漏与充分性配对报告，单看任一指标都存在退化解（全拒/全允）。
- **危害加权**避免把无害读与危险转账等同计分，且权重稳健性经过检验。
- **同时测试“过度限制”与“翻转（flips）”**，能发现按前缀收紧策略的防御在合法调用上前后不一致。
- **测到真实部署系统**（Claude Code Auto mode），并诚实标注其评分集合较小、无充分性数值。
- **稳定性分析完整**：权重、预算、措辞、方差、置信区间五个维度逐一检验，并明确区分“Ajar 的选择”与“防御自身的模型方差”。

- **Oracle 依赖自身判断**：73%（7649/10471）的标签由 Ajar 断言，仅 27% 由基准谓词验证；作者明确不作构造效度主张。

**Oracle 依赖自身判断**：73%（7649/10471）的标签由 Ajar 断言，仅 27% 由基准谓词验证；作者明确不作构造效度主张。
- **候选调用由 Ajar 构造，覆盖面受限于构造规则**：七类故障虽成体系，但仍是对“真实可能越权调用”的一种枚举近似，无法证明已覆盖防御在实际部署中会遇到的全部开放权限形态；未被规则触及的调用天然不计入 OPL 分母。
- **“任务不需要”的边界仍带主观性**：离路径工具、参数加宽等类别的判定依赖参考解与目标状态，若参考解只给出一种可行路径，则该路径之外的合法替代方案可能被误判为超额；论文用“过度限制”单独计分来缓解，但并未彻底消除这一模糊性。
- **继承宿主基准的缺陷**：Ajar 直接读取 AgentDojo 的任务、工具模式与目标状态，因此基准本身的覆盖偏差、参考解质量、注入 sink 设计都会原样传导到度量结果。
- **领域与场景偏窄**：仅覆盖 banking、slack、travel、workspace 四个套件共 97 个任务，均为工具调用型短程任务；不涉及代码执行、多智能体协作、跨会话长期记忆、真实外部副作用（如实际网络请求）等场景，结论外推需谨慎。
- **统一接口可能低估或高估某些防御**：所有防御被压平为 `decide(call, context) → {allow, deny}`，像 CaMeL 这类以信息流与规划器 capability 为核心的机制，其控制流语义未必能被逐调用接口完全还原，可能影响其紧致度与过度限制分数的公平性。
- **Permission Assistant 的最低 OPL 存在乐观偏差**：其个性化历史由被评分的标签构建，等于用评测信息喂养防御，该 0.0217 不能与其它防御的冷启动分数直接比较，论文对此有说明但该配置仍易被误读。
- **单次运行不可区分相邻防御**：置信区间普遍重叠，判定方差（自我一致率 91%–98%，AC4A 的 OPL 标准差 0.0203）甚至超过部分防御间的差距，因此“谁更紧”的排序在紧邻防御之间不稳健。
- **未度量部署成本**：论文在限制一节明确承认未报告防御的延迟、token 与美元开销，而“紧致性”在实践中必然与成本权衡，缺少这一轴使结论不完整。
- **未对抗自适应攻击者**：所有测试为静态、预构造的调用集合，没有针对 Ajar 度量本身优化或规避的对手，因此度量的是“防御留下的开放权限面”，而非“在主动规避下的开放权限面”。
- **危害权重方案由作者设定**：H0–H4 的 0/1/3/9/27 虽经六种方案稳健性检验，但权重赋值本身仍是设计选择，跨研究复用时口径需重新对齐。

## 9. 对后续研究的启示与总体评价

- **核心贡献在于提出新评测轴**：Ajar 的价值不在于给出某个防御的排名，而在于论证“开放权限”是独立于攻击成功率与良性效用的第三维，并用可复用、低耦合的工具把它变成可测量量。任何以“防御有效”为结论的智能体安全研究，此后都应回答“它留下了多少已授权但未使用的权限”。
- **方法论上的可取之处**：以参考解前缀定义决策点、以构造规则同时决定标签、以危害权重加权、以充分性配对防退化，这套设计可迁移到其他基准（只需 adapter）与其他防御（只需 wrapper），具备成为公共评测组件的潜力。
- **实践启示**：部分防御的“紧致”是拒绝换来的，部分防御在收紧任务不需要的权限上依赖策略更新步骤（Progent 消融显示冻结 S0 后泄漏上升 1.24–1.56 倍），这些结论对防御设计者具有直接参考价值；同时“换小模型不会沿权限–效用前沿滑动，而可能同时降低两者”提醒部署者不能靠降级模型来兼顾安全与可用。
- **当前尚无“既紧又可用”的防御**：没有任何被测防御达到 argument-exact oracle 的紧致度并保持可用，这既是负面结论，也指出了明确的研究空间。
- **后续可做的方向**：把成本（延迟/token/美元）纳入第四维；引入自适应攻击者以检验开放权限是否会被实际利用；扩展到代码执行、多智能体与长期记忆场景；提高由基准谓词验证的标签比例以增强构造效度；以及用多次运行与统计检验而非单次运行来区分紧邻防御。
