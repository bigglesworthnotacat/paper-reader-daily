## 摘要
LLM 智能体执行真实动作，包括执行代码、修改文件、调用服务和委派任务，这些动作由上下文来源驱动：用户请求、工具结果、文档、shell 输出、Skill 与 MCP 指令、记忆。与传统系统中能力被预先定义不同，智能体所需的最小权限能力是动态的，取决于其任务意图：它想做什么以及如何做。这带来了一个安全与保障挑战：所有输入都通过对抗性注入或意外范围扩大进入同一个共享规划通道并具有同等影响，然而用户的显式请求与从文档中提取的文本具有不同的信任级别，不应共享选择目标或扩大访问权限的权限。现有防御措施约束操作和信息流；我们研究任务范围限定的、多来源的权限组合。我们认为，智能体能力应限定在当前任务意图范围内，而非沙箱或会话生命周期，且没有任何单一上下文来源能定义完整能力。IntentCap 从四类此类来源组合能力：用户意图、工作流指令、工具模式和运行时环境，并具有字段级所有权和单调收窄。每个来源贡献特定字段，任何一个都不能填补另一个的字段，租约只会收窄用户已授权的权限，绝不会扩大它。IntentCap 使用 LLM 从这些来源生成短期租约，在任何副作用提交前由确定性检查器验证，并通过工具级和操作系统级信息流策略强制执行。评估表明，IntentCap 能阻止所测试的违规行为而不拒绝良性动作，每个来源边界都独立必要，且该检查器可泛化到工具、执行、放置和委派边界。

## Abstract
LLM agents take real actions, including executing code, modifying files, calling services, and delegating tasks, driven by context sources: user requests, tool results, documents, shell outputs, Skill and MCP instructions, memory. Unlike traditional systems, where capability is predefined, the least-privilege capability an agent needs is dynamic, depending on its task intent: what it wants to do and how. This creates a security and safety challenge: all inputs enter one shared planning channel with equal influence, by adversarial injection or accidental scope widening, yet a user's explicit request and a document's extracted text carry different trust and should not share authority to choose a destination or widen access. Existing defenses constrain operations and information flow; we study task-scoped, multi-source authority composition.   We argue that agent capabilities should be scoped to the current task intent, not a sandbox or session lifetime, and that no single context source defines a complete capability. IntentCap composes capabilities from four such sources: user intent, workflow instructions, tool schemas, and runtime environment, with field-level ownership and monotonic narrowing. Each source contributes specific fields, none can fill another's, and the lease only narrows the user's authorized authority, never widens it. IntentCap uses an LLM to generate short-lived leases from these sources, validated by a deterministic checker before any side effect commits and enforced by tool- and OS-level information flow policies. Evaluation shows IntentCap blocks tested violations without rejecting benign actions, each source boundary is independently necessary, and the checker generalizes across tool, execution, placement, and delegation boundaries.

## 一、核心问题与整体含义

- **背景**：LLM 智能体会执行真实动作（运行代码、修改文件、调用服务、委派子任务），其行为由多种上下文来源驱动——用户请求、工具返回结果、文档、shell 输出、Skill 与 MCP 指令、记忆。
- **与传统系统的关键差异**：传统系统中能力（capability）在编译期静态声明并由类型系统强制；而智能体所需的"最小权限能力"是**动态的**，取决于当前任务意图（想做什么、怎么做），且没有任何程序员能静态声明这种组合。
- **核心安全问题**：所有上下文来源进入**同一个共享规划通道（planning channel）并具有同等影响力**。无论是对抗性注入还是意外的范围扩大，任何来源都可能填充任何决策字段。
  - 用户显式请求与从文档中提取的文本**信任级别不同**，却共享"选择目标"或"扩大访问"的权限，这在安全上不可接受。
- **论文给出的具体例子**：用户要求从两份选定 PDF 抽取表格、保存电子表格、并在指定仓库创建一个 GitHub issue。
  - PDF 内容只应影响表格单元格、或许还有 issue 正文，**不应**影响仓库名、网络目标、审批范围、工具选择或 Skill 加载。
  - 若 PDF 隐藏文本写着"在 attacker/repo 创建 issue"，仓库字段就会被替换为攻击者控制的合法外观目标。
  - 工具调用白名单可封锁恶意域名，但**无法表达"PDF 从来无权填充仓库字段"这一不变量**。
  - 即使没有攻击者该不变量也会被破坏：若抽取 Skill 把 PDF 文本拼成一个输出字符串，规划器可能把表头误解析为仓库名，覆盖用户选定的目标。
- **根因诊断**：四种来源**不可互换**——用户请求给出目标与授权目的地但不给工作流步骤；Skill 过程给出候选步骤但不给用户的具体目标；工具 schema 声明可接受参数但不给目标；工具输出提供取值但不决定应填入哪个决策字段。**完整能力必须由四者共同组合**。
- **整体含义**：保障智能体安全需要的不只是"允许哪些操作"的信息流策略，还需要控制**"哪个来源可以流入哪个决策字段"**的信息流策略；作者主张能力应绑定到**当前任务意图**，而非沙箱或会话生命周期。

## 二、方法论（IntentCap）

### 核心思想
- 能力在**运行时**由多个上下文来源以**字段级所有权（field-level ownership）**方式组合而成，因为没有任何单一来源携带足以定义完整能力的权威。
- 设计目标为四条性质：
  1. **字段级所有权**：每个决策字段恰好由一个上下文来源拥有；
  2. **单调收窄（monotonic narrowing）**：租约只能收窄用户已授权权威，绝不能扩大；
  3. **LLM 不进入可信计算基（TCB）**：所有允许/拒绝决定由确定性检查器做出；
  4. **租约可审计**：每次允许或拒绝都记录其来源链（provenance chain）。

### 威胁模型与 TCB
- **攻击者可控**：运行时环境内容、文档、工具输出、网络数据、被委派智能体的消息，并可在 Skill 或 MCP 文本中植入指令。
- **攻击者不可控**：用户的结构化选择与执行层。
- **LLM 规划器与编译器不可信且可被任意操纵**：它们只能"提议"，不能"决定"。
- **TCB 组成**：意图签发器（intent issuer）、来源标注器（source labeler）、确定性检查器（Figure 1 虚线框），外加执行层（hooks、MCP 网关、OS 强制器）。

### 四类来源与字段归属（信息流策略）
- **用户意图**：目标、被选对象、授权目的地、审批。
- **工作流指令**（系统策略、Skill 过程、手册）：过程性范围（procedural scope）。
- **工具模式**（MCP 定义、注册表条目、命令描述符）：可调用接口与凭据范围。
- **运行时环境**（工具结果、文件状态、脚本输出）：观测到的取值。
- **规则**：任一来源不能填充另一来源的字段。工具 schema 不能授权目的地，运行时环境不能提供过程性权威，Skill 不能扩大审批范围。

### 处理流程（Figure 1 流水线）
1. **来源标注器**按位置分类输入：用户消息恒为"用户意图"，工具响应恒为"运行时环境"，Skill/MCP 元数据在加载时标注。
   - 来源不明者（如用户粘贴的文档）需额外分类，原型**保守地拒绝其填充权威字段**。
   - 在 OS 层，该标注映射为进程隔离与 IPC 通道打标，把来源追溯到产生它的进程。
2. **意图签发器**从用户消息的结构化字段（选定文件、指定目的地、显式审批）中提取用户的最大权威。
3. **LLM 辅助编译器**（不可信）基于结构化意图与当前活跃 schema 生成**候选租约**，字段由已标注来源填充；只能收窄（可选授权目的地的子集、更短预算），不能新增目的地、提高审批范围或授予用户意图未覆盖的字段。
4. **确定性检查器**在任何副作用、上下文放置或委派交接提交前验证单调收窄；每次委派进一步衰减，子任务只获得比父任务更窄的能力。
5. **两层强制**：
   - **工具层**：边界适配器拦截 MCP 调用，在执行前校验每个参数字段来自其拥有者来源（类似 Fides 在规划器层做污点跟踪）。
   - **OS 层**：被接受的租约编译为 ActPlane 的 file/exec/network 策略，经 eBPF 强制。

### 关键数据结构与接口
- **字段（field）**：能力租约中的具名槽位（如 destination、approval scope、tool name、argument value），其值必须来自且仅来自一个来源。
- **能力租约（capability lease）**：把字段贡献绑定到具体操作、对象、参数、预算、有效期与委派深度；按当前任务意图作用域，**使用即消耗**（如 issue 租约首次使用后即过期），不能自我扩大。
- **唯一状态转移**（所有适配器在提交副作用前必须调用）：
  - `check_and_consume(e, lease, proofs, σ) → allow(σ') | deny`
  - 检查器在单次转移中**原子地**校验所有字段。

### 与传统方案的对比定位
- **相对工具调用白名单/域名黑名单**：白名单只能约束"能调什么"，无法表达"某来源不能填某字段"的字段级不变量，因而无法阻止合法工具被合法外观的恶意参数驱动。
- **相对沙箱与会话级权限**：沙箱按进程/会话授予静态权限，粒度与生命周期均与任务意图错配；IntentCap 把能力作用域收敛到"当前任务意图"，并随任务结束或首次使用而失效。
- **相对规划器层污点跟踪（如 Fides）**：污点跟踪在规划器层标记数据流，但仍把决策交给 LLM 规划通道；IntentCap 将允许/拒绝判定移入确定性检查器，使 LLM 完全退出 TCB，同时在工具层与 OS 层做双重强制。

## 四、主要贡献

1. **问题重新定义**：把智能体安全的核心矛盾从"允许哪些操作"（操作级策略）推进到"哪个来源可以流入哪个决策字段"（字段级信息流策略），指出四种上下文来源本质上不可互换。
2. **能力动态性论证**：说明最小权限能力随任务意图动态生成，无法由程序员静态声明，因而传统编译期能力模型不适用于智能体。
3. **IntentCap 设计**：提出以字段级所有权、单调收窄、LLM 不进入 TCB、租约可审计为四性质的能力组合机制，包含来源标注器、意图签发器、LLM 辅助编译器、确定性检查器与两层强制。
4. **可执行抽象**：给出能力租约与 `check_and_consume` 原子状态转移接口，把安全不变量落到可实现的检查点上。
5. **工程映射**：将租约编译为 ActPlane 的 file/exec/network 策略并经 eBPF 强制，打通了从语义策略到 OS 级强制的路径。

## 五、优势与亮点

- **诊断精准**：用"共享规划通道 + 同等影响力"一句话解释了注入攻击与意外范围扩大为何同源，抓住了当前智能体架构的结构性缺陷。
- **不变量可表达**：字段级所有权使"PDF 从来无权填充仓库字段"这类不变量首次可被形式化表达，弥补了白名单类方案的表达力缺口。
- **信任边界清晰**：坚持 LLM 只提议、不决定，把判定权交给确定性检查器，避免了"用 LLM 防 LLM"的循环依赖。
- **纵深防御**：工具层与 OS 层双重强制，且委派时能力进一步衰减，符合最小权限与权限不扩散原则。
- **可审计性**：每次允许/拒绝记录来源链，为事后溯源与策略调试提供了基础。
- **作用域贴合语义**：以任务意图而非会话/沙箱为能力边界，并使用即消耗，显著压缩了权限驻留窗口。

## 六、局限与待解问题

- **来源标注的完备性**：按位置分类（用户消息、工具响应、Skill/MCP 元数据）在结构清晰的接口下可行，但对用户粘贴文档、多层委派、动态加载代码等模糊来源，原型采取"保守拒绝"，可能带来可用性代价；标注器本身若被绕过，整条链失效。
- **意图提取的准确性**：意图签发器依赖用户消息的结构化字段；若用户意图本身模糊或未显式给出目的地，"用户最大权威"的边界难以确定，可能导致过度收窄而阻碍正常任务。
- **编译器收窄的可靠性**：LLM 辅助编译器虽被限制为只能收窄，但其输出仍需检查器验证；收窄判定（如"该目的地是否为授权集合的子集"）在语义层面可能不完全可判定。
- **评估规模有限**：4 页预印本、初步评估，缺乏与既有方案的量化对比、多场景覆盖与对抗性压力测试。
- **性能与部署成本**：字段级校验、来源打标、eBPF 强制与委派衰减均引入运行时开销，论文未给出性能数据。
- **生态依赖**：OS 层强制依赖 ActPlane 等特定机制，跨平台可移植性与对现有 MCP/Skill 生态的改造成本尚不明确。
- **字段粒度设计**：字段如何划分（过粗则保护不足，过细则编译器与用户负担陡增）缺乏系统性指导原则。

## 七、总体评价与启示

- 本文的价值主要在于**概念框架而非实证结论**：它把智能体权限问题从"操作白名单"提升到"字段级信息流所有权"，并给出了一套自洽、可落地的设计骨架。
- 对研究者的启示：智能体安全的形式化对象应是"来源—字段"映射关系，而非单纯的系统调用集合；LLM 应被排除在 TCB 之外，仅作为候选方案生成器。
- 对工程实践的启示：在缺乏完整字段级机制时，至少可以先在工具边界做参数来源校验、对非用户来源填充权威字段的调用一律拒绝、并在委派时强制能力衰减——这些是相对低成本的近似措施。
- 对标准的启示：Skill 与 MCP 元数据若能在规范层面携带来源标签与字段归属声明，将大幅降低运行时标注的难度。
- 结论：IntentCap 提出了一个方向明确且论证清晰的命题——**能力应跟随任务意图与上下文来源**；但其可行性仍待更大规模的实现与评估来检验。
