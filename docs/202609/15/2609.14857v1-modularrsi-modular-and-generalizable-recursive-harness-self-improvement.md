## 摘要
近期工作将递归自我改进（RSI）扩展到面向长时程编程与终端任务的智能体 harness，使智能体能够从经验中改进执行机制。然而，可泛化的 harness RSI 仍然具有挑战性。首先，在评估基准或其子集上演化 harness，难以区分可复用的改进与针对特定基准的适配。其次，单轨迹更新可能将系统性的 harness 缺陷与实例特定的推理和解题细节混为一谈，从而产生难以迁移到未见任务的修改。第三，在单体式 harness 中定位反复出现的行为缺陷很困难，而整体 harness 优化可能纠缠无关机制，并使归因与验证复杂化。我们提出 ModularRSI，一个基准不相交、对比式且模块化的框架，用于可泛化的 harness 演化。ModularRSI 对同一任务的成功与失败轨迹进行对比，并跨任务聚合证据，以识别反复出现的行为缺陷。它将可演化的 harness 分解为五个功能模块：Agent Loop、Tool Use、Observation Management、Context Management 和 Task Completion Detection。每个模块在受限的修改范围内独立演化，随后进入集成阶段，将演化后的模块组合为统一的 harness，并解决潜在冲突。为支持基准不相交的演化，我们从外部来源精心构建了 2,000 个可执行的演化任务，这些任务与下游评估基准不相交。在 TB2.0 和 SWE-Bench Verified 上的实验表明，在未见的域内和跨域任务上均取得一致改进，且演化后的 harness 还能迁移到不同的基础模型。

## Abstract
Recent work extends recursive self-improvement (RSI) to agent harnesses for long-horizon coding and terminal tasks, enabling agents to improve execution mechanisms from experience. However, generalizable harness RSI remains challenging. First, evolving harnesses on evaluation benchmarks or their subsets makes it difficult to distinguish reusable improvements from benchmark-specific adaptation. Second, single-trajectory updates can conflate systematic harness deficiencies with instance-specific reasoning and solution details, producing modifications that transfer poorly to unseen tasks. Third, localizing recurring behavioral deficiencies within monolithic harnesses is difficult, while whole-harness optimization can entangle unrelated mechanisms and complicate attribution and validation. We propose ModularRSI, a benchmark-disjoint, contrastive, and modular framework for generalizable harness evolution. ModularRSI contrasts successful and failed trajectories for the same task and aggregates evidence across tasks to identify recurring behavioral deficiencies. It decomposes the evolvable harness into five functional modules: Agent Loop, Tool Use, Observation Management, Context Management, and Task Completion Detection. Each module evolves independently within a restricted modification scope, followed by an integration stage that combines the evolved modules into a unified harness and resolves potential conflicts. To support benchmark-disjoint evolution, we curate 2,000 executable evolution tasks from external sources that are disjoint from downstream evaluation benchmarks. Experiments on TB2.0 and SWE-Bench Verified show consistent improvements on unseen in-domain and cross-domain tasks, with the evolved harness also transferring across different foundation models.

- **核心问题**：实现"可泛化的 harness RSI"仍很困难，论文识别出三个相互耦合的挑战：
  - **数据层挑战**：高质量演化数据难获取。现有方法多直接在下游评估基准或其子集上演化，难以区分"可复用的 harness 改进"与"基准特定适配"。
  - **轨迹层歧义**：单条或单侧轨迹会把系统性 harness 缺陷与任务特定的推理、解题细节混在一起，导致修改迁移性差。
  - **机制层信用分配问题**：即使识别出反复出现的行为缺陷，也难以定位到单体式 harness 中应修改的具体组件；整体优化会纠缠无关机制，难以归因与验证。
- **整体含义**：论文主张用"基准不相交 + 对比式 + 模块化"的方式，把粗粒度的任务级结果转化为局部化、可迁移的 harness 演化信号，从而提升 RSI 的泛化性与可归因性。

## 2. 方法论

- **核心思想**：将 harness 的可演化行为机制拆分为五个独立模块，通过对比同任务的成功/失败轨迹并跨任务聚合证据，定位反复出现的缺陷，再把粗粒度任务奖励转化为模块级、功能级的修改信号。

- **harness 模块化（五个功能模块）**：
  - **Agent Loop**：控制"推理—行动—观察"迭代流程、交互控制与恢复行为。
  - **Observation Management**：处理环境反馈，保留任务相关信息、过滤/压缩噪声观察。
  - **Tool Use**：管理外部工具的选择、调用与校验。
  - **Context Management**：维护和整理跨执行步的交互历史（保留、压缩、检索）。
  - **Task Completion Detection**：判定任务是否完成、是否需要继续交互。
  - 基础设施类组件（沙箱初始化、并行执行、LLM 通信等）不纳入演化；初始 harness 采用 Harbor 的 **Terminus-2**。

- **三阶段流程**：
  - **(i) 对比式轨迹采样与分析**：对每个演化实例 $x_i$ 采样 K 条轨迹，按奖励划分为三组——
    - Positive（$\sum_k r_i^k = K$）：分析执行质量与效率改进机会（冗余动作、重复探索、不必要工具调用）。
    - Contrastive（$0 < \sum_k r_i^k < K$）：对同任务成功/失败轨迹配对比较，找出与不同结果相关的功能级因素。
    - Negative（$\sum_k r_i^k = 0$）：先查 **Trajectory Memory** 中该任务历史成功轨迹做对比；若无则做单侧诊断（重复循环、错误工具使用、无效恢复、过早终止等）。
    - 分析结果汇总为结构化 JSON findings，字段包括：所属模块、支撑轨迹证据、是否应修改的理由、拟议改动、反事实判断（该模块改动是否可能改变任务结果）、是否可立即修复等。
  - **(ii) 模块级 harness 修改**：用 Code-Modify Agent（即被演化的 agent 自身）在受限范围内修改模块函数。
    - **修改目标选择**：合并语义相似诊断，按支持该修改的**不同任务数投票**排序，优先跨任务支持的候选，抑制实例特定失败的影响。
    - **Evolution History**：为每个函数记录历史代码改动与引入的功能，避免重复/冲突修改与演化振荡。
  - **(iii) 验证门（Validation Gates）**：
    - **Program Check**：AST 校验、导入检查、协议合规、发现契约验证、静态属性审计；失败则按记录 diff 回滚。
    - **Diff Review**：由 Code-Modify Agent 审查 diff 是否编码了任务特定解法、启发式或难以泛化的条件；判定过拟合则拒绝回滚。
    - **Execution Validation**：从当前 batch 随机抽 2 个任务用更新后 harness 实际执行，出现运行错误或协议违规则回滚。

- **跨模块集成（Cross-Module Integration）**：五个模块独立演化后合并为统一 harness，并在演化集上额外做一轮集成 epoch，由 Code-Modify Agent 分析轨迹识别跨模块冲突，去除重复机制、澄清模块职责、调整协调逻辑；之后函数库冻结，评估期不再修改。

- **函数库管理**：
  - **Function Merge**：LLM 比较同模块内函数描述与行为，合并高度相似或重叠的函数。
  - **Task-Aware Function Composer**：根据任务描述与候选函数描述，由 LLM 选择任务相关子集，仅激活这些函数，使函数库可扩展而活跃 harness 保持紧凑、任务适配。
  - 这两机制在轨迹收集与下游评估中均使用。

## 6. 主要结论与发现

- **跨基准与跨域泛化**：以 DeepSeek-V4-Flash-Preview 为骨干，域内设置下 TerminalBench 2.0 准确率从 47.57 提升至 52.43，SWE-Bench-Verified 从 73.40 提升至 76.45；TB 相关数据演化的 harness 在 SWE-Bench-Verified 上达 75.80，SWE 相关数据演化的 harness 在 TB2.0 上达 49.40，说明学到的是可复用执行机制改进，而非任务特化。
- **可靠性提升**：TB2.0 上 Pass3 从 30.34 提升至 35.96，表明不仅提高平均解题能力，也减少重复试验中的随机失败。
- **跨模型迁移**：冻结演化 harness 在 GLM-5.2（59.55→61.80）、MiniMax-2.5（41.57→44.94）、DeepSeek-V4-Flash（47.57→52.43）上均一致提升。
- **模块化优于联合/非模块化**：非模块化演化（46.44）与联合全模块演化（44.19）甚至低于基线（47.57），而独立演化后集成达 52.43，说明限制修改范围能减少干扰。
- **各模块贡献互补**：所有单模块变体均优于基线；Agent Loop 单模块准确率增益最大，Observation Management 显著降低平均步数（22.50 vs 基线 34.70）；集成后 Acc 与 Pass3 进一步提升。
- **与现有方法对比**：在基准不相交协议下，AHE 与 Meta-Harness 相对基线仅约 1 个百分点变化，而 ModularRSI 提升超过 5 个百分点（67.42 vs 基线 61.79）。
- **对比分析的作用**：随演化推进，可用对比轨迹对比例下降（从 36.67% 到 34.17%，Δ = -7.50 pp），说明 harness 逐步吸收了对比样本揭示的可复用行为改进。
- **数据难度影响**：Medium-centered 难度分布优于 Hard & Easy 分布，在 SWE-Bench Verified 上达 76.45% vs 74.25%（+2.20 pp），说明中等难度任务能提供更有信息量的对比信号。

## 7. 优点

- **问题定位清晰**：将 harness RSI 的困难拆解为数据层、轨迹层、机制层三个耦合挑战，并逐一对症设计。
- **基准不相交的演化协议**：独立构建 2,000 个可执行演化任务，做实例级相似度过滤与细粒度领域分析，是评估"可迁移改进"的重要方法论贡献，也可作为社区共享资源。
- **对比式信用分配**：同任务成功/失败配对 + 跨任务证据聚合 + 投票排序，有效把粗粒度任务奖励转化为局部信号，并降低实例特定噪声。
- **模块化设计 + 受限修改范围**：五模块分解、独立演化、跨模块集成，缓解了单体优化的纠缠问题；实验中模块化显著优于联合/非模块化，验证了设计有效性。
- **多重验证门**：程序静态检查、面向泛化的 diff 审查、真实执行验证三道关卡，降低引入不可执行或过拟合改动的风险。
- **函数库可扩展但活跃 harness 紧凑**：Function Merge + Task-Aware Function Composer 兼顾能力累积与推理成本控制。
- **实验维度较全面**：跨基准、跨域、跨模型、模块消融、方法对比、数据难度、代际曲线、案例研究均有覆盖，对比协议公平（统一框架、同起点、同预算、禁用搜索）。

## 8. 不足与局限

- **缺少关键消融**：论文明确承认未做专门隔离"对比式轨迹分析"贡献的消融实验，仅靠轨迹分析与案例研究提供间接支持。
- **演化规模受限**：2,000 个演化实例中主实验仅使用各 120 个（TB/SWE），未充分利用已构建的数据资源；更大规模、更广覆盖的实验留待未来工作。
- **案例研究无法隔离单一改动效果**：作者自己指出这些运行还包含其他更新，比较不能归因于单个改动。
- **算力信息缺失**：未报告 GPU 型号、数量、时长或总 token 消耗，影响可复现性与成本评估。
- **统计严谨性不足**：未见多随机种子方差、置信区间或显著性检验报告，部分提升幅度（如 1–2 个百分点）的稳定性难以判断。
- **模型与时间线依赖**：实验基于特定版本的 DeepSeek-V4 系列、GLM-5.2、MiniMax-2.5 等模型，结论对新模型/新 harness 实现的适用性需进一步验证。
- **应用限制**：演化依赖可执行环境、可靠评估器与任务正确性反馈；对缺乏可靠自动化评测的领域，该方法难以直接迁移。此外，演化出的函数库仍需 LLM 组合选择，带来额外推理开销与选择误差风险。
- **数据构建成本与偏差风险**：2,000 个任务虽做多阶段质控与人工复核，但检索来源（GitHub、Hugging Face、Kaggle 等）可能带来领域分布偏差；难度分布对演化效果敏感，说明数据选择策略本身是风险因素。
