## 摘要
扩展了外部工具的大语言模型在解决复杂现实任务中展现出显著能力。然而，现有方法面临两个关键挑战：由不兼容的工具输出类型和API模式导致的多步骤、多轮推理脆弱性，以及大型工具目录下的性能下降。为解决这些问题，我们引入了工具原语（Tool Primitives），一种用自然语言作为工具调用接口来替代基于刚性API模式调用方式的设计；每个工具被封装后均带有一个内部处理模式解析与执行的LLM接口，从而支持嵌套及多轮工具调用中的自然跨工具通信。基于工具原语，我们构建了ToolFace，一个包含25,519个函数的集中式仓库，大语言模型在推理时可动态检索仅相关的工具，而无需在上下文中枚举原始API模式。为了在复杂环境中可靠地编排工具原语与ToolFace，我们进一步提出了HEART，一个通过智能体原生、可复用工具原语实现的工程化引导框架，它包含规划器（Planner）、路由器（Router）和验证器（Verifier），共同支持动态工具调用规划、多步骤执行和反馈驱动的恢复。在五个基准上的实验表明，HEART相较基于SFT的模型平均提升10%，并超过GPT-5.4、Claude-4.6-Sonnet和Gemini-3.1-Pro平均6%，同时将API成本降低高达85%。在50个现实任务中，HEART取得了84%的任务完成率，是三家前沿商业模型平均水平（22%）的3.8倍。

## Abstract
Large language models (LLMs) augmented with external tools have demonstrated remarkable capability in solving complex real-world tasks. However, existing approaches suffer from two key challenges: brittle multi-step and multi-turn reasoning caused by incompatible tool output types and API schemas, and performance degradation under large tool catalogues. To address these, we introduce \textbf{Tool Primitives}, a design that replaces rigid API schema-based invocation with natural language as the interface for tool calling, where each tool is wrapped with an LLM interface that handles schema resolution and execution internally, enabling natural inter-tool communication for nested and multi-turn tool calling. Building on Tool Primitives, we host \textbf{ToolFace}, a centralized repository of 25,519 functions from which LLMs dynamically retrieve only the relevant tools at inference time, eliminating the need to enumerate raw API schemas in context. To orchestrate Tool Primitives and ToolFace reliably in complex settings, we further propose \textbf{HEART}, a \textbf{H}arness \textbf{E}ngineering framework via \textbf{A}gent-native, \textbf{R}eusable \textbf{T}ool Primitives, comprising a Planner, Router, and Verifier that jointly support dynamic tool invocation planning, multi-step execution, and feedback-driven recovery.   Experiments on five benchmarks demonstrate that HEART outperforms SFT-based models by $10\%$ on average and surpasses GPT-5.4, Claude-4.6-Sonnet, and Gemini-3.1-Pro by $6\%$ on average while reducing API cost by up to $85\%$. On 50 real-world tasks, HEART achieves $84\%$ task completion, $3.8\times$ the average of three frontier commercial models ($22\%$).

## 一、论文核心问题与研究动机

工具增强的大语言模型在真实复杂任务中展现了较好潜力，但现有方法仍然存在两个主要问题：

- **多步/多轮推理脆弱**：工具之间 API 输出类型与调用 schema 异构，模型难以将一次调用的输出正确映射为下一次调用的输入，导致多层依赖和多轮交互场景频繁失败（例如 NESTFUL 上最强模型全序列匹配准确率仅 28%）。
- **工具目录规模导致性能退化**：当可用工具数量与 schema 上下文不断累积，模型选择和正确调用工具的能力下降，大目录场景进一步放大这一退化（工具 token 从 8K 增长到 120K 时准确率可下降 7%～85%）。

由此引出一个核心转向：**与其让模型尝试“说 API 的语言”（即等待、记忆并格式化原生 schema），不如让工具“说模型的语言”，并以自然语言作为工具调用接口**。作者认为现有方法将工具存储、表示与调用紧密耦合，缺少显式的规划、路由和验证机制，难以支持可扩展的复杂工具使用。

## 二、方法论

论文提出了三个核心组件。

**1. Tool Primitives：以自然语言作为接口的可执行工具包装**

将每个工具包装为一个 LLM 接口层，不再向模型暴露原始 schema，而是令每个工具在内部完成请求解析、参数绑定、schema 校验与函数执行。形式上：

`Pi(x; c) = M[si; c; x]`

其中 `si` 为该工具 schema，`c` 是可选的上游调用结果作为上下文。每个 Primitive 接收自然语言请求，将请求映射到参数空间、执行函数并返回结构化结果。这样可支持嵌套调用、跨工具的信息传递，以及多轮工具间自然交互，无需模型感知底层 schema 格式。

**2. ToolFace：规模可扩展的工具仓库与动态检索**

ToolFace 是集中式工具注册中心，共收录 25,519 个函数（来自 ToolBench、NESTFUL、τ2-Bench、ACEBench、BFCLv4 及 54 个手工编写的真实交互工具）。每个工具以「schema-函数」对存储。推理时模型经语义搜索动态检索相关子集放入上下文，而不是一次性加载全部目录，从而绕开大目录带来的性能退化。

**3. HEART：三层多智能体的“工程化引导”框架**

由 Planner、Router、Verifier 协同完成五个阶段为 Planning→Routing→Tools→Execution→Verification：

- **Planner**：负责意图分解和信息充足性判断。若信息不足，先向用户发起针对性澄清请求，再生成有序的调用计划 Π。
- **Router**：对每个计划步骤做参数映射，生成自然语言调用请求，并附加执行级参数（retry、priority、timeout），再将请求分发给对应 Tool Primitives。
- **Tool Primitives**：接收请求并执行函数，独立完成参数绑定与校验；
- **Verifier**：按四个准则评估执行结果，即任务完成度、参数一致性、执行有效性与约束满足。任一准则失败即产生结构化失败诊断反馈给 Planner，进行有针对性的重规划与迭代恢复（最大重规划预算 B=3）。

该方法使工具调用从一次性执行变为一个**可规划、可验证、可恢复的结构化推理过程**，充分利用轻量模型的并行角色编排，同时通过 Tool Primitive 自然语言接口隔离攻击面和 Schema 噪音。

## 三、实验设计

**基准与场景覆盖（5 个公开测试集 + 真实场景任务）**

- **ToolBench**：大规模真实 API 调用，覆盖单工具与多工具指令场景（I1/I2/I3），并与 ToolLLaMA、ToolLLaMA-DFSDT-Retriever、GPT-3.5/4/5.4、Claude-4.6、Gemini 等基线对比，报告 Pass Rate/Win Rate。
- **NESTFUL**：测试嵌套 API 调用序列（one-shot 与 three-shot ICL），对比 xLAM、Hammer、ToolACE、Granite、Llama、Mixtral、DeepSeek-V3、GPT-4o 及三款商业模型；报告 F1、部分/全序列匹配准确率与 Win Rate。
- **τ2-Bench**：在零售、航空、电信三个域内评估双控制对话环境，对比 GPT-4.1 系列、Claude-3.7/4.6、Gemini-3.1 等，报告 Pass₁～Pass₄、Token 数、API 成本与延迟。
- **ACEBench**：覆盖 Normal（六类）、Special、Agent 子集，对比多款开源与商业模型，并报告 Overall 分数。
- **BFCLv4**：重点测试 Web 搜索 Base/No-Snippet 与 Memory（KV 检索、向量检索、递归摘要），对比 xLAM、Hammer、LLaMA-3.x、Qwen3、GPT-4.1、GPT-5.4 等。
- **额外实验**：自行构造 50 个涉及旅行、医疗、电商、金融、本地的真实端到端任务，由人类标注完成率；并针对工具选择环节做 prompt injection 安全性测试（Gradient-Free vs Gradient-Based）。

**实验充分性分析**

实验覆盖面较广，从大型 API 调用、嵌套序列、多轮对话、细粒度工具使用到检索回忆/安全鲁棒性等关键维度均有对应测试集，并有多个互补视角的对比：

- 与 SFT 微调模型对比（xLAM、ToolACE、Hammer 等）；
- 与闭源前沿商业模型对比（GPT-5.4、Claude-4.6、Gemini-3.1）；
- 与纯 ReACT/DFSDT 等原有策略对比。

消融实验分为四类：移除各个组件、改变最大重规划次数 B、替换不同 8B 背骨（LlaMa vs Qwen）与混合大模型编排层、以及抗攻击对比，总体上从多个角度支撑了框架各模块的功能分析与必要性论证。

## 六、主要结论与发现

- ToolFace + Tool Primitives 将工具索引从模型上下文中分离，检索使大目录不再拖垮精度。
- 自然语言接口（Tool Primitive）是 HEART 精度提升的最核心因素：移除该设计后 ToolBench Pass Rate 从 75.1% 骤降至 16.1%。
- Verifier 的反馈恢复机制对执行失败是必要的：移除后 Pass 率衰减至 47.6，NESTFUL 全序列达到 0.15。
- 开放权重（Qwen3-8B）可以通过结构编排而非模型缩放来近似甚至超越更大模型的性能：在 NESTFUL 上，通过规划的 8B HEART 反超 685B DeepSeek-V3（Full Acc. 0.44 vs 0.09）。
- 抗攻击能力大幅增强：因工具 schema 不入上下文，Prompt Injection 攻击成功率为 0.0%，而主流模型 ASR 最高达 82.2%。
- 多轮场景下 HEART 的累积优势更明显：τ2-Bench 中 Pass4 远高于同域最强基线（如 Telecom +51.5%），并能完成真实多轮端到端任务：84% vs 商业模型 22% 平均。
- 成本收益显著：虽 token 使用偏多，但在轻量、低价骨干 8B（Qwen3）下 API 成本可降低最高 85%（对比 GPT-5.4 约 7.4×）。

## 七、优点

1. **工程视角清晰**：通过将系统设计为非训练、可插拔接口的可复用组件组合，天然解耦了“工具存储、调用”与模型上下文的关系；对动态 API 生态适配性较好。
2. **面向真实部署问题**：不仅针对单次调用/JSON 生成优化，也聚焦多轮、重试、失败恢复以及安全对抗这些真实应用场景。
3. **可组成性与灵活性**：Tool Primitive 独立于宏观规划层，可随时替换背骨（如 Qwen3→GPT-5.4）而不改接口设计，体现了模块化优势，多智能体编排的思路易于工程落地。
4. **评估基准覆盖面宽达**：对基准的选取既覆盖了标准函数调用，也覆盖嵌套调用、对话、检索式工具和无陷阱安全场景，横纵向对比丰富。
5. **设计细节扎实**：附录对 Planner/Router/Verifier/Tool Primitive 的提示词与流程、成本公式和消融开关逐个给出完整逻辑，便于复制。

## 八、不足与局限

1. **计算/效率方面**：多智能体结构导致 token 总消耗比前向单模型高，对延迟敏感场景不利，论文在 τ2-Bench 已体现 latency 数值普遍偏高（如 Telecom 约 38s vs Gemini-3.1-Pro 28.5s），轻量模型虽省钱但延迟仍高。
2. **工具维护成本与可扩展风险**：ToolFace 的 schema 仍依赖人工作者编写，若进入新领域，需要新的人工整理成本，扩展瓶颈尚未全自动化解决。
3. **评测口径的不对称**：正如前面所提，实验中可与 HEART 直接对比的多数 SFT 商业模型是通过原始 schema 进行的原生调用，而 HEART 则基于自己做前置检索和重写 interface，可能混淆“框架优势”与“接口一致化优势”的影响，对“跨商业模型对比强于 6%”的结论需要按架构条件做区分解读。
4. **安全与鲁棒边界**：只测试了工具选择阶段的 prompt injection（如 ToolHijacker），并未考虑工具输出被恶意污染或中间结果被篡改等更广泛的攻击矩阵。
5. **没有披露训练/推理具体硬件环境**、参数调整细节（如语义搜索阈值、人工 schema 的标准），复现门槛偏高；也未见针对更大目录规模（>25k 以上）的压力测试，以佐证可扩展边界。
6. 基准中的“现实任务”由人类标注样本量相对较小（50 个），虽然结果突出，但扩展性与任务采样带来的统计偏差尚需通过更大任务池验证。
