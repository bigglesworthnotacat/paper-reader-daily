## 摘要
基于大型语言模型的多智能体系统在解决复杂任务方面展现出强大潜力，但其开发面临权衡：代码框架表达力强但工程密集，而无代码构建器简化了编写过程，却将智能体交互限制在作者定义的工作流中。我们提出ChatDev 2.0：DevAll（以下简称DevAll），一个用于构建、执行和检查异构多智能体系统的无代码平台，兼具高表达力和易用性。在表达力方面，DevAll将声明式可执行图抽象与循环感知执行引擎相结合，使得异构智能体及动态循环交互能够在单一框架内表示和执行。在易用性方面，集成的可视化界面让用户无需编写任何代码即可编排、运行、监控和检查多智能体系统，包括人机协同步骤。实验表明，DevAll在三个代表性任务上以具有竞争力的性能复现了最先进的多智能体系统，且无需任务特定的编排代码，凸显其作为基于大语言模型的多智能体系统通用平台的有效性。DevAll可在https://github.com/OpenBMB/ChatDev获取。

## Abstract
Large language model (LLM)-based multi-agent systems (MAS) have shown strong potential for solving complex tasks, yet their development forces a tradeoff: code frameworks are expressive but engineering-intensive, while no-code builders simplify authoring but constrain agent interactions to author-defined workflows. We present ChatDev 2.0: DevAll (hereafter DevAll), a no-code platform for building, executing, and inspecting heterogeneous MAS that delivers both high expressiveness and ease of use. In terms of expressiveness, DevAll pairs a declarative executable graph abstraction with a cycle-aware execution engine, so that heterogeneous agents and dynamic and cyclic interactions can be represented and executed within a single framework. For ease of use, an integrated visual interface lets users author, run, monitor, and inspect MAS, including human-in-the-loop steps, entirely without writing code. Experiments demonstrate that DevAll reproduces state-of-the-art MAS across three representative tasks at competitive performance and without task-specific orchestration code, highlighting its effectiveness as a general-purpose platform for LLM-based MAS. DevAll is available at https://github.com/OpenBMB/ChatDev.

## 1. 核心问题与整体含义（研究动机与背景）

- 论文聚焦于基于 LLM 的多智能体系统（MAS）的实际开发困境，识别出一个核心矛盾：
  - **代码框架**（如 AutoGen、MetaGPT、AgentScope、LangGraph 等）表达力强、可定制化程度高，但要求用户具备专业编程能力，开发与调试开销大。
  - **无代码/可视化构建器**（如 AutoGen Studio、Dify、Langflow、Flowise 等）上手快、门槛低，但采用“工作流”中心抽象，将智能体限定为作者预先定义的步骤，循环控制、嵌套循环和持久状态传递都需要人工“连线”和状态拼接，限制了反馈驱动、动态交互类 MAS 的实现。
- DevAll 的目标是**同时兼顾表达力与易用性**，让用户可以无需编写任务专属编排代码，即可构建、执行、监控和调试具备任意复杂交互（含多环反馈、循环嵌套）的异构 MAS，并覆盖软件工程、数据可视化、深度研究等多种输出模态领域。

## 2. 提出的方法论（核心思想、技术细节与算法）

论文构建了名为 DevAll（ChatDev 2.0）的无代码平台，底层由“编译引擎 + 执行引擎”双引擎驱动，上层辅以图形化交互界面。

### 2.1 MAS 编译引擎（声明式图编译）
- 用户通过**拖拽画布**或**编写 YAML** 声明式地描述系统，YAML 是平台的规范磁盘表示，便于分发与共享。
- 平台将该声明规格编译为**有向可执行图** G = (V, E, Θ)：
  - 全局配置（Θ）：共享记忆、模型注册、工具注册、工作区、权限等；
  - 节点集合（V）：内置 7 类异构节点——Agent（LLM 智能体）、Human（人工反馈节点）、Python（代码执行器）、Subgraph（嵌套子图）、Literal（静态消息发射器）、Passthrough（上下文转发器）、LoopCounter（迭代门控）；
  - 边集合（E）：采用 **“语义边”** 封装为 e = (u, v, c_e, φ_e, ψ_e)，其中：
    - c_e：激活条件；
    - φ_e：数据流策略（如何合并、变换、保留/清空目标上下文）；
    - ψ_e：控制流策略（如何更新目标调度状态）。
- 这种“数据流剥离于控制流”的边设计是 DevAll 的核心抽象，使图的表达力高于传统固定工作流。

### 2.2 MAS 执行引擎与 CADET 算法（周期感知动态执行拓扑）
- 对于无环图，采用按拓扑层的确定性调度即可。
- 对含环图，论文提出了 **CADET（Cycle-Aware Dynamic Execution Topology）**，处理流程：
  1. **图凝聚**：用 Tarjan SCC 分解将图的强连通分量（SCC，含自环节点）凝聚为虚拟超节点，构造有向无环的凝聚图 G†；
  2. **循环依赖处理**：在 SCC 内部执行作用域化迭代，通过递归识别“回边”（back edges）将内部边划分为非回边骨架（当前轮执行）+ 回边依赖（延迟到下一轮执行），并设置迭代数上限确保终止；
  3. **逐层调度**：在凝聚图 G†上做拓扑分层（TopoLayers），携带运行时触发状态按层扫描，到达凝聚节点时进入 SCC 内部执行，所有 SCC 出边结果再汇聚回外层调度，循环直至触发边界清空或达到上限。
- 算法效果：支持**多条反馈循环、嵌套循环及任意循环结构**，同时保留迭代级局部状态。
- 系统按元数据驱动渲染配置表单，可扩展节点/工具类型而无需单独开发 UI。

## 3. 实验设计（数据集、基准与对比方法）

### 实验目标
- 验证 **同一无代码平台在不写任务特定编排代码的前提下**能否复现多个领域专用 SOTA 系统的核心流程，并维持竞争性的任务性能。

### 三个跨领域任务场景及参照系统
| 任务 | 基准 | 复现/对比的参考系统 | 统一评测模型 |
|---|---|---|---|
| 科学数据可视化 | MatPlotBench | CoDA | GPT-4o |
| 深度研究报告生成 | DeepResearchBench | Enterprise Deep Research（EDR） | GPT-4o（搜索用 Serper，judge 用 GPT-5.5） |
| 软件开发生成 | SRDD | ChatDev 1.0 | GPT-4o（嵌入用 text-embedding-ada-002） |

### 主要量化结果
- **MatPlotBench**：DevAll 总体分 0.7950，优于参考 CoDA 的 0.7130（提升主要来自执行通过率 0.83→0.99）；
- **DeepResearchBench**：DevAll 总体分 0.3319，略低于 EDR 的 0.3500，差距在 LLM-as-judge 的噪声范围；
- **SRDD**：DevAll 完整性高于参考版，但可执行性和一致性略低，总体几乎持平（0.6509 vs 0.6574）。
- 结论指向：整体复现效果与各领域专用实现相当，说明 DevAll 的声明式图可作为跨任务的通用复现载体。

## 6. 主要结论与发现

- DevAll 证明了：**MAS 图可以成为一种无需代码的可执行对象**——用户通过拖拽、配置、连接语义边即可构建复杂动态多智能体系统。
- 语义边 + SCC 凝聚 + 迭代式循环控制，使循环反馈、嵌入子流程等原本就相当棘手的流程模式可被统一表达和调度。
- 用声明式图复现 CoDA、EDR、ChatDev 1.0 的任务流程时，效果与参考系统大体“平手”，甚至在 MatPlotBench 上更优，亦不需要任务特定的编排代码。
- 编译和运行时的本地调度开销在中低图规模下保持在十几 ms 量级，证明周期感知执行引擎不会成为使用瓶颈。
- DevAll 的设计验证了一个方向：平台能通过同时丰富低代码图和运行时语义，跨越代码系统与可视化 builder 之间的“表达力 / 易用性”鸿沟。

## 7. 方法或实验设计的优点

- **针对痛点较为精准**：厘清了现有无代码工具“以流程为重心（workflow-centric）”与“智能体拥有独立状态（agent-centric）”之间的差别，并从问题定义上把“状态自动累积与回边驱动”作为设计目标。
- **抽象水平高**：使用语义边（数据流/控制流策略解耦）为表达任意多轮反馈提供了清晰的单一路径；无需使用别类型的循环节点，更符合思维模型。
- **形式化调度框架扎实**：用 SCC 凝聚 + 缩减迭代，从编译器与调度器的层面处理循环结构，具备一定理论支撑与自适应能力。
- **实验极具代表性**：跨组的三类任务输出形态差异较大，既考察代码类、报告文本类，也覆盖视觉图表类，加大了“不同领域泛化”宣称的说服力。
- **消解混淆因素**：在三个情境中统一核心模型 GPT-4o、控制工具配置，使质量差异可归因于工作流复现本身而非底层模型；
- **开源且附带工程指标**:构造指标（YAML/源码大小）、运行开销指标以及案例展示设计得比较透明，评价结果具可复制性。

## 8. 不足与局限性

- **无代码简化的是“编写”而非“设计”**：用户仍需自行将需求拆解为智能体角色、提示词、节点/边的语义及循环逻辑，工作流建模仍是一项专业技能（Limitations 部分首段也直接承认该点）。
- **组件生态尚未完备**：图中内置的类型 7 类是常用集合，可能无法涵盖某些高度领域相关的交互句式，实际部署时仍需自定义扩展端点。
- **风险偏向主观复现**：对参考系统进行手工复写，难以严格保证与原始系统的一致程度（如 ChatDev 1.0 的若干对话/文件处理流程），可能存在固有复现偏差。
- **指标选择不够全面**：
  - DeepResearchBench 的设置中没有控制 user-event judge 的可变性，实验数量有限；
  - 没有提供“代表性失败案例”或任务难度分层分析。
- **可扩展性的证据仅限小规模：**用至多 16 个 SCC 做性能测试，该证明不足以支撑百级或千级大规模图（尤其多输入/多分支海量动态场景）。
- **人机协同（Human-in-the-loop）** 虽被强调为可控特性，但数据研究并未特别验证人工反馈对工作质量/执行效率带来的增益，缺乏用户性的可令性试验。

## 9 延伸思考与开放问题

- **“无代码”的真正瓶颈已从“写代码”转移到“建模思维”**：DevAll 让用户免于手写 Python 编排，却仍要求其拥有将业务流程抽象为智能体角色、上下文窗口、语义边策略与终止条件的能力。对于非技术用户而言，这种“可视化编排”仍接近“通过图形界面编程”，其上手难度未必显著低于传统低代码平台。未来若能从自然语言需求直接生成图骨架、再由用户增量修正，或可进一步降低设计门槛。

- **可视画布虽提供了调试入口，却未给出配套的认知工具**：当 CADET 在多个 SCC 间反复迭代时，用户缺乏对“当前数据从哪条边流入、为何触发该分支、该轮循环由哪个回边驱动”的直观解释机制。将运行时轨迹以时间线、局部变量快照或数据血缘方式映射回画布，可能是提升可调性的关键下一步。

- **循环条件的表达能力边界尚待厘清**：SCC 分解与作用域化迭代能承载嵌套循环与多反馈边，但若回边条件同时依赖全局状态、外部工具输出与多个分支结果，其语义是否仍能在当前“边策略 + 迭代上限”的框架内得到完备表达，论文并未给出形式化刻画。未来可探索将边条件升级为一等公民的“状态谓词”，并配套静态冲突检测。

- **“复现即验证”的策略有优势，也有盲区**：通过复现三个代表系统，DevAll 证明了自身“覆盖足够多的流程模式”，却未证明“超越手工编写方案的表达上限”。更有说服力的证据应包含：一个在传统代码框架中难以实现、却在 DevAll 中能以低心智负担构筑的“杀手级”MAS 应用案例。

- **多智能体平台的发展正在走向“环境即接口”**：DevAll 表明，未来的 MAS 开发平台不必纠结于 API 数量或节点类型多少，关键在于提供一套足够统一、可递归组合的动态执行语义——让反馈、循环、暂停、人工接管都能成为图运转的自然状态，而非例外情况。

## 10 总结

ChatDev 2.0（DevAll）的贡献可概括为三点：**其一**，在抽象层明确了“工作流中心”与“智能体中心”两种设计哲学之间的折中点——以语义边承载状态与调度逻辑，使图既保持静态可读，又具备动态执行能力；**其二**，在工程层用 SCC 凝聚与作用域化迭代实现了通用循环调度，填补了现有可视化平台在“多轮反馈与嵌套循环”上的结构性空白；**其三**，在实证层以三项跨领域复现研究验证了声明式图可作为多智能体系统的通用载体，且性能与专用系统基本相当。其局限同样清晰：易用性尚未经用户研究验证，消融证据缺失，规模测试停留在中低复杂度图谱。整体来看，DevAll 为无代码多智能体平台的设计提供了一个逻辑自洽、工程可用的新范式，也为后续研究留下了几个值得深挖的接口——更智能的图生成、更可解释的运行时反馈、以及更大规模的动态拓扑验证。
