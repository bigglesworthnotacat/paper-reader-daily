## 摘要
随着智能体从研究原型走向部署工具，其能力越来越依赖于模型外部的执行基础设施，通常称为代理框架。在固定模型权重的情况下改变这一框架，可以显著改变任务性能。当前的智能体评估通常报告在选定框架下的下游性能，而模型自身开发框架的能力则相对未被充分探索。我们引入了HarnessDev，一个将评估单元从任务输出转向可运行基础设施的基准测试。HarnessDev涵盖两个阶段。在创建阶段，智能体从一个最小的种子和少量案例出发，构建完整的执行系统。在进化阶段，它从自身创建的框架出发，利用下游执行反馈进行迭代修改，目标是提高基准测试性能。然后，我们评估每个构建框架的能力（在保留基准上的任务成功率）和效率（执行令牌成本）。报告的创建结果涵盖六个创建者LLM、四个领域和五个下游基准测试，总计2,207个独特的下游实例，并隐藏了开发过程中未使用的评估任务。我们发现，生成的框架在代码、搜索和研究方面仍远落后于成熟的人工工程参考实现，而在写作和机器学习实验方面则达到或超过了所选参考实现，但执行成本差异很大。进化带来了一些性能提升，但这些提升不稳定，且仅部分转移到保留任务上。使用固定运行时模型的实验进一步表明，收益强烈依赖于执行该框架的模型，表明跨模型的迁移有限。

## Abstract
As agents move from research prototypes to deployed tools, their capability increasingly depends on model-external execution infrastructure, commonly termed the agent harness. Changing this harness while holding model weights fixed can substantially alter task performance. Current agent evaluations typically report downstream performance under a chosen harness, leaving a model's ability to develop the harness itself comparatively underexplored. We introduce HarnessDev, a benchmark that shifts the unit of evaluation from task outputs to runnable infrastructure. HarnessDev covers two stages. In Creation, the agent starts from a minimal seed and a small number of cases, then builds a complete execution system. In Evolution, it starts from its own created harness and iteratively revises it using downstream execution feedback, with the goal of improving benchmark performance. We then evaluate each constructed harness on capability (task success on held-out benchmarks) and efficiency (execution-token cost). The reported Creation results cover six creator LLMs, four domains, and five downstream benchmarks totaling 2,207 unique downstream instances, with hidden evaluation tasks withheld from development. We find that generated harnesses remain substantially behind mature human-engineered references on code and on search and research, while matching or exceeding the selected references on writing and machine-learning experimentation, with large variation in execution cost. Evolution produces some performance gains, but they are unstable and transfer only partially to held-out tasks. Experiments with a fixed runtime model further show that the gains depend strongly on the model executing the harness, indicating limited transfer across models.

## 1. 核心问题与研究动机

- **背景**：智能体（Agent）性能不仅取决于模型权重本身，还极大程度上依赖模型之外的执行基础设施，即代理框架。例如，同一 GPT-5 模型在 Terminus 2 的 Terminal-Bench 2.1 上仅解决 35.2% 的任务，而在 Codex CLI 中可达 49.6%。可见框架本身是影响性能的关键变量。
- **现状问题**：现有智能体评估通常预先固定框架，只评估模型在特定框架下的下游任务表现，而忽视了模型自身开发和改进执行系统的能力。框架工程（harness engineering）不同于普通代码编辑——模型修改的是自己的运行“底板”，会改变自身观察、规划与恢复的方式——因此值得被独立评估。
- **核心研究问题**：当前端模型能否像“前部署工程师”那样，不仅完成任务，更能创建、维护并持续改进自己赖以运行的执行系统？论文标题中的“develop”同时包含“从零构建”（Creation）与“持续维护演化”（Evolution）两层含义。

## 2. 方法论：HarnessDev 基准

### 2.1 核心思想
HarnessDev 将评估单元从“任务的答案输出”转移到“可运行、可复用、可审计的持久化执行系统”。评估公式为：

- 创建者模型在开发环境中构建框架；
- 框架冻结后由执行者模型在下游任务上运行；
- 评分器根据任务输出打分。

### 2.2 两阶段设计

**Creation（创建，RQ1）**：模型从统一设定的“弱种子”开始构建完整框架。
- **弱种子**：仅提供可运行的兼容层——能解析任务与模型配置、暴露被动工具原语、写入审计工件，但不含执行循环、规划器、验证器、持久状态或停止规则；未修改时得分为零。
- **开发信号**：任务规范 + 1~3 个公开开发案例；隐藏测试与官方评分不可访问。
- **交付物**：冻结后的可运行框架，在保留测试集上被下游评测。

**Evolution（进化，RQ2）**：模型从自己上一阶段冻结的代码框架出发，基于下游执行反馈（SWE-Pro 100 任务 + Terminal-Bench 89 任务）进行多轮迭代修改。
- 官方候选需在两条基准上完成完整评测对；最多 10 对预算、每轮最多 2 次固定子集探针。
- 持有集为 630 个 SWE-Pro 任务，开发过程中结果不外泄；用于衡量保留泛化而非单纯在线适应。

### 2.3 框架的六模块抽象
论文将框架抽象为六类控制机制：\( H = \langle E, T, C, S, L, V \rangle \)：
- E（执行）：循环、规划、停止条件
- T（工具）：接口、选择、I/O 约束、错误处理
- C（上下文）：任务/代码/日志/历史如何进入提示
- S（状态）：目标、假设、进展、失败记录
- L（生命周期）：前置/后置钩子、失败恢复、终结化
- V（验证）：测试、判断、工件校验、轨迹记录

### 2.4 评估体系：Self-Eval 与 Unified-Eval
- **Self-Eval**：创建者模型也是执行者（LE = LC），反映真实部署及模型–框架的协同适配度；
- **Unified-Eval**：所有生成的框架统一由 Gemini 3.1 Pro 执行，以隔离框架质量与执行者能力的差异；
- 所有评分路径与框架自报状态隔离：SWE-Pro 只认工作目录真实 repo diff，Terminal-Bench只认环境终态，防止框架“自证成功”。

### 2.5 合规约束
规定框架不得硬编码实例答案、读取隐藏测试/评分器、替换统一运行时接口等；通过日志/轨迹/源码审计核实，论文报告未发现任何违规路径获得分数。

## 6. 主要结论

### 6.1 Creation 结论
- **领域差异显著**：自执行条件下 Opus 4.8 在写作（EQ-Bench3 84.6%）接近甚至超过人工参考，在 MLE-bench 上反超参考；但在 BrowseComp 搜索/研究任务上差距最大（Opus 45.9% vs 参考 92.2%），代码仍落后（69.3% vs 参考 80.0%）。
- **统一执行者会改变排名**：Qwen/Seed/DeepSeek 在 Gemini 执行下反而提升，说明其自身执行者是瓶颈；Opus 则因步骤数量硬编码等对自身模型过拟合，在 Gemini 下明显退化。
- **成本差异巨大**：MLE-bench 上执行成本最高差距达约 19 倍；图 9 显示高成本并不保证高分数，质量必须同时看能力与效率。
- **框架机制偏见**：状态/记忆机制最为缺失（仅 1 个工具有周期检查点；26,679 条轨迹无任何检查点事件）；许多声明的机制实际不触发（在 108 个组件实例中 18 个从未触发），验证流于表面（441 个退化提交未被检测到）。

### 6.2 Evolution 结论
- **反馈集增益有效但不稳定**：全部 5 条自运行轨迹在可见反馈对上均有提高（+3.0 ~ +13.9 分），但保留集增益大幅缩小（+1.43 ~ +4.44 分）；
- **固定 Gemini 下更差**：只有 Opus 在保留集上为正（+2.70），其他三条轨迹回归（最多 −10.32）；
- **版本选择困难**：反馈与保留分数方向一致的版本切换仅占 53.1%，只有 2/9 的最终声明版本是保留集最优 → 反复优化噪声分数会过拟合“幸运”运行；
- **演化像局部程序搜索**：64 个版本切换中有 8 个出现双基准回归、8 个无实质变化；新增的 169 个函数中只有 113 个从入口可达，25 个完全没有调用者；编辑规模与收益之间的预测性弱。

### 6.3 跨模型迁移结论
可运行的“框架”≠可迁移的“能力”。管道、工具协议、预算与停止规则若与创始者模型深度绑定（如 Opus 搜索框架在换执行者后重复查询率从 10.1% 飙升至 88.2%），则框架在另一个模型上几乎失效。因此框架属于一种“持久型软件资产”而非通用适配层。

## 7. 亮点与优势

- **问题定位有新意**：把评估对象从“任务答案”转向“执行基础设施”本身，填补了 agent 研究只测下游分数的评价空白。这是少有的让“LLM 作为系统构建者”接受系统化检验的工作。
- **完整两阶段协议**：从 Rust 式“弱种子”到连续反馈驱动演化，设计上同时覆盖一次性构建能力与持续维护能力；
- **双层执行对照**：Self-Eval 与 Unified-Eval 的对照，能识别出“代码本身适配性”与“个别模型能力”的偏差；
- **防御作弊设计完善**：评分路径与框架自报状态分离 + 每次运行源码与轨迹审计，量化约束不能靠自报成功来刷分；
- **保留集与执行成本兼顾**：将反馈增益与真实泛化分开报告，并直接输出性能–token 的权衡，不做单个加权分数的信息丢失；
- **定性行为分析深入**：对创建者的编辑策略、死代码比例、失败诊断方式、版本选择心理等做了有说服力的案例分析，能得出“做什么有效”不是简单看分数，而是看是否形成闭环的洞察。

## 8. 不足与局限

- **领域覆盖有限**：虽有 4 个领域、5 个基准，但现实部署中的很多框架类型（浏览器自动化、多智能体协同、企业 API 系统等）未覆盖。写作和 MLE 的人工对照也不一定为其领域最优；
- **Evolution 只聚焦代码**：保留集只有 SWE-Pro 630，对其他类型的框架演化泛化性缺乏直接证据；
- **缺少统计重复**：每个 creator–runtime 细胞仅一条轨迹，无法估计随机波动、不能做显著性检验；相邻版本切换的分数噪声达 ±4.75 分，超过了多数增益；
- **人工参照不统一**：参照成绩来自不同“框架–模型”的组合，不是同一执行者下的排队对照，因此不能说超越参考等于超越“人类能力”；
- **描述性分析有推断风险**：代码行为统计（如机制触发率、死代码）是基于有限的日志或文本证据，不是 ground-truth 执行覆盖，可能有系统误差；
- **开发环境固定**：Creator–executor 在演进中没有引入“用自身演化后的框架继续演化”的自举性，限制了长期闭环的见识；
- **资源报告不完整**：未给出总体计算资源细节（GPU 总量、训练/推理费用、API 调用量），可复现性上存在提升空间；
- **趋势上偏于悲观**：由于设计上让模型自建框架（而不是来自外部成熟代码库），某些领域的差值会被放大——这在解释“差距”时需注意框架的设计边界问题。
