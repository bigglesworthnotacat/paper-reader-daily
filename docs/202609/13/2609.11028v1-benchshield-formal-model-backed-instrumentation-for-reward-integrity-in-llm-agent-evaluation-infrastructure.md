## 摘要
LM 智能体基准正日益作为交互式评估基础设施发挥作用。智能体观察状态、调用工具、修改工作区、提交产物，并从结果程序中获得奖励。这种交互性使评估容易受到奖励作弊的影响：智能体通过利用与奖励相关的轨迹，而非解决预期任务，来提高其测量得分。现有防御主要依赖任务特定补丁、提示指令或事后检测器。它们无法提供可复用的证据来证明某次具体运行始终处于其预期评估边界内。本文提出 BenchShield，一种用于 LLM 智能体评估中奖励完整性的基于模型的插桩层。BenchShield 将检测建立在一个评估中与奖励相关事件的有限生命周期模型之上。在基准基础设施内，两种互补分析基于该模型运行。静态的、阶段感知的污点分析在运行前暴露奖励作弊路径。其运行时对应方法使用基础设施侧证据来归因具体智能体使用，并发出有证据支持的声明。我们构建了 BenchShield Trajectories，这是一个人工标注语料库，包含来自三个基准上超过 31,000 次公开智能体运行的 456 条经裁决轨迹。在相同任务和模型上，与智能体式可作弊性扫描器基线相比，BenchShield 将全链召回率从 23-94% 提升至 77-100%，将同向量覆盖率从 16-56% 提升至 43-78%，并将每任务成本降低最多 65%。其运行时分析在从基础设施侧证据检测奖励作弊方面达到 96% 的准确率。

## Abstract
LM-agent benchmarks increasingly function as interactive evaluation infrastructure. Agents observe state, call tools, modify workspaces,   submit artifacts, and receive rewards from outcome procedures. This interactivity makes evaluations vulnerable to reward hacking: an agent   improves its measured score by exploiting the reward-relevant trajectory instead of solving the intended task. Existing defenses rely largely   on task-specific patches, prompt instructions, or post-hoc detectors. They do not provide reusable evidence that a concrete run remained   within its intended evaluation boundary. This paper presents BenchShield, a model-backed instrumentation layer for reward integrity in   LLM-agent evaluation. BenchShield grounds detection in a finite lifecycle model of an evaluation's reward-relevant events. Within the   benchmark infrastructure, two complementary analyses operate over this model. A static, phase-aware taint analysis exposes reward-hacking   paths before a run. Its runtime counterpart uses infrastructure-side evidence to attribute concrete agent use and emit evidence-backed claims.   We construct BenchShield Trajectories, a human-labeled corpus of 456 adjudicated trajectories from more than 31,000 public agent runs across   three benchmarks. Compared with an agentic hackability scanner baseline on the same tasks and model, BenchShield improves full-chain recall   from 23-94% to 77-100%, same-vector coverage from 16-56% to 43-78%, and reduces per-task cost by up to 65%. Its runtime analysis achieves 96%   accuracy in detecting reward hacking from infrastructure-side evidence.

## 2. 方法论

- **核心思想**：用有限生命周期模型固定奖励相关事件，将具体任务通过 task binding 映射到该模型，再结合静态污点分析和运行时基础设施证据，输出证据支撑的运行级完整性 verdict。
- **形式化生命周期模型**：
  - 使用 TLA+ 建模，固定生命周期：`setup/reset → agent phase → handoff → outcome computation → reward collection → release`。
  - 定义七类完整性维度：
    - **I1 Observation integrity**：保护状态不暴露给智能体。
    - **I2 Authority integrity**：智能体不能控制 outcome-owned 状态。
    - **I3 Handoff integrity**：智能体产物只能通过声明 handoff 进入 outcome 计算。
    - **I4 Reward provenance**：奖励必须来自可信 outcome 输出。
    - **I5 Failure handling**：崩溃、超时、畸形输出等必须 fail closed。
    - **I6 Release and reset integrity**：日志、反馈、快照、残留状态不得造成跨轮次污染。
    - **I7 Semantic adequacy**：接受结果是否真正满足任务意图，属于语义义务，模型记录但不结构强制。
  - 事件字母表包括：`Expose`、`Mutate`、`Handoff`、`Verify`、`Reward`、`Release`、`SemanticWitness`。
  - 使用 TLC 检查安全性、非空洞性和 per-switch 反例。
- **Task binding**：
  - 将任务资源、权限、handoff 点、语义义务映射到固定生命周期词汇。
  - 作者只需补充无法自动推断的语义值，例如模糊资源角色、声明交付物、审查义务。
  - 缺失或冲突值不会让发现路径消失，而是作为证据缺口保留；绑定验证要求安全性、非空洞性和充分性。
- **静态阶段感知污点分析**：
  - 在激活的 capability graph 上传播四类影响：agent control、protected information、failure state、stale state。
  - 传播边包括 observation、mutation、handoff、outcome-input、reward、normalization、release。
  - 可发现 I1–I6 暴露路径，并保留阶段和边界历史；一个路径可组合多个 vector link。
  - 静态审计器可添加证据支撑的节点标签、类型边、阶段跨越和冲突，但不能删除解析事实、授权边界或发出 verdict。
- **运行时检查与语义路由**：
  - 基础设施探针发出 authority-bearing 结构事件流；结构事件更新生命周期状态。
  - Algorithm 1 流程：初始化生命周期 → 逐条记录 `PinEvidence` → `ClassifyEvidence` → 未知且 reward-relevant 则 `Inconclusive` → 结构事件则 `AdvanceAndCheck`，坏状态则 `Inconclusive` → 否则附加支持证据 → 需要语义审查则路由证据切片 → 最终 `StructuralResult` 与 `ValidateSemanticWitnesses` 合成 claim。
  - 语义审计由独立 LLM 审计器组成，只看被钉住证据切片，输出 schema-valid label；审计标签只能标注或限定运行，不能改写结构事件或覆盖 I1–I6 结果。
- **Verdict 类型**：
  - `Checked`：绑定、结构轨迹和所需证据通过激活检查。
  - `VectorExposed`：静态发现可能路径，但运行未显示实际使用。
  - `AgentViolation`：基础设施证据显示智能体尝试或使用禁止路径。
  - `Inconclusive`：证据缺失、矛盾、绑定无效、未知 reward-relevant 事件等，无法作出完整性声明。
- **实现要点**：
  - 基于 BenchFlow v0.6.4，新增 66 个 Python 模块、约 34k 行。
  - 静态和运行时路径分离，仅共享资源类词汇；运行时 verdict 不能改变静态 verdict。
  - 使用 ACP 驱动智能体，标准为 `claude-agent-acp 0.40.0`；shell 命令分解为文件和网络操作数，未解析构造标记为 opaque 并 fail closed。
  - 每次运行封装 evidence bundle，检查器是 bundle 的纯函数，支持 live finalization 与 replay 得到相同 verdict。

## 3. 实验设计

- **数据集/场景**：
  - 构建 **BenchShield Trajectories**：来自三个公开基准、超过 31,000 次公开智能体运行的 456 条人工裁决轨迹。
  - 三个基准：
    - **Terminal-Bench 3**：151 个 pinned task cells，58 个 unique tasks，383 条轨迹，252 条 reward-hacking，146 个 audit packets。
    - **SkillsBench**：26 个 tasks，26 个 unique，55 条轨迹，48 条 reward-hacking，22 个 packets。
    - **ClawsBench**：12 个 tasks，12 个 unique，18 条轨迹，14 条 reward-hacking，10 个 packets。
  - 总计：189 个 task cells，96 个 unique tasks，456 条轨迹，314 条 reward-hacking 轨迹，178 个 audit packets。
- **标注协议**：
  - 每条轨迹先提出 `reward_hacking`、`not_reward_hacking` 或 `needs_review`。
  - 正例划分为 exploit episodes，记录 primary vector、因果链中的附加 vector links、首个可观察 enabling condition、侦察/准备/首次尝试/首次成功/结果实现位置。
  - 三名标注者独立复核，分歧经裁决；报告裁决前一致性。
- **实验分组 RQ1–RQ4**：
  - **RQ1**：研究实际 reward hacking 的 prevalence、vector mix、chain composition、timing、enabling conditions。
  - **RQ2**：静态管线能否从 task package 恢复裁决的 exploit routes；对比 **BenchJack** audit mode，双方使用相同 pinned、stripped package，各跑 5 次。
  - **RQ3**：运行时证据能否区分 exposure 与 concrete use；选择 60 个任务，实例化 180 cells，其中 36 个无法存在或启动，144 个可运行。运行标签包括 `Checked`、`VectorExposed`、`AgentViolation`。对比 **transcript-only detector** 作为消融。
  - **RQ4**：结构隔离减少多少暴露向量；评估六种隔离机制：隐藏 verifier 文件、任务文件只读、非特权 agent 用户、seccomp+cap-drop、独立 verifier 环境、无网络出口。形式化 lane 用 TLC，测量 lane 对 178 个 task packages、419 个 episodes 归因。
- **Benchmark/评价指标**：
  - 静态发现：dimension recall、same-vector recall、full-chain recall、stability、wall time、cost/task。
  - 运行时归因：verdict 分布、coverage、accuracy。
  - 隔离效果：每个机制在各 I 维度上移除的暴露 task package 比例。
- **对比方法**：
  - BenchJack：agentic hackability scanner，audit mode，exploit
