## 摘要
使用结合 GUI 动作与工具动作（例如通过 API 访问应用数据）的混合动作空间的 Android 智能体，仍很大程度上未被充分探索，主要原因是创建工具需要付出过多努力。为填补这一空白，我们提出 DroidTool，一个通过自生成工具增强智能体的框架，这些工具以操作应用状态（例如数据库）的 Python 函数形式实现。为了以最少的人工投入创建工具，DroidTool 采用了一种智能体工作流，包含以下阶段：提议、实现、测试生成与执行、修复。值得注意的是，在测试所创建工具以进行验证时，它会跨相关工具构建关联测试，以自然准备合适的测试前置条件并提高测试覆盖率，而不是分别测试每个工具。在代表性基准 AndroidWorld、B-MoCA 和 MobileSafetyBench 上平均而言，使用生成工具增强的 GUI 智能体相比仅使用 GUI 的智能体性能提升约 4.47 个百分点，交互次数减少约 20.05%。

## Abstract
Android agents using a hybrid action space that combines GUI actions and tool actions (e.g., accessing application data via APIs) remain largely underexplored, mainly due to the excessive effort required to create tools. To address this gap, we introduce DroidTool, a framework for augmenting the agents with self-generated tools, which are realized as Python functions operating on application states (e.g., a database). To create tools with minimal human labor, DroidTool employs an agentic workflow featuring stages: proposal, implementation, test generation and execution, and repair. Notably, when testing the created tools for verification, it constructs relational tests across relevant tools for natural preparation of appropriate test preconditions and improved test coverage, rather than testing each tool separately. The GUI agents augmented with the generated tools achieved approximately 4.47%p higher performance with approximately 20.05% fewer interactions than the GUI-only agents, averaged across representative benchmarks: AndroidWorld, B-MoCA, and MobileSafetyBench.

# DroidTool 论文总结：通过自生成工具动作提升 Android GUI 智能体的熟练度与效率

## 1. 核心问题与研究背景

- **研究动机**：LLM 驱动的移动设备智能体（Android GUI Agent）能力日益增强，但仅依赖 GUI 动作存在明显瓶颈——许多任务（如编辑笔记、创建日历事件、修改应用设置）需要冗长、重复的动作序列，效率低下且容易出错。
- **替代方案**：工具动作（如通过 API 直接访问应用数据库或设置）可将多步 GUI 操作压缩为单次函数调用，形成 **GUI + 工具动作的混合动作空间**，理论上能显著提升效率与成功率。
- **核心障碍**：工具动作方向长期未被充分探索，**根本原因是人工创建工具的成本极高**——需要开发者理解每个应用的数据库 schema、文件路径、Provider URI、一致性约束等，难以规模化。
- **整体含义**：论文提出 DroidTool，目标是以**最小人工投入**自动生成、验证并部署应用状态操作工具，从而让 Android 智能体在保持 GUI 通用性的同时获得工具动作的高效性。这一问题在移动智能体落地场景（任务自动化、无障碍辅助）中具有实际价值。

## 2. 方法论

### 2.1 核心思想

- 将工具实现为**操作应用状态的 Python 函数**（而非通用 CLI 命令），因为大多数应用功能可归结为对应用状态（数据库、SharedPreferences、文件、Provider、系统服务）的结构化读写操作。
- 通过**智能体工作流**（Agentic Workflow）自动完成工具从提议到部署的全生命周期，替代人工工具开发。

### 2.2 智能体动作空间设计

- 智能体在每个交互步 t 接收屏幕图像 $o_t \in \mathcal{O}$ 与历史上下文 $h_t$，选择动作 $a_t \in \mathcal{A}$。
- 混合动作空间：$\mathcal{A} = \mathcal{A}_{GUI} \cup \mathcal{A}_{tool}$，智能体可选择 GUI 动作（点击、滑动、输入等）或调用工具函数。
- 工具返回结果（如数据库查询结果）被写入历史上下文 $h_{t+1}$，供后续决策使用。

### 2.3 工具生成工作流（五个 LLM 智能体阶段）

- **工具提议（Design Agent）**：基于人工撰写的 **Developer Document**（描述应用状态面、实体、字段、访问流程、一致性约束），提出一组围绕实体生命周期的工具（数据库类：create/read/update/delete；设置类：get/set），以 JSON 格式输出，并按目标状态分组以复用辅助函数。
- **实现规格（Specification Agent）**：将提议转化为结构化实现契约，明确函数名、输入/输出 schema、目标状态的确切路径、选择器、值编码、schema 发现规则等，分 target 层与 action 层组织。
- **工具实现（Implementation Agent）**：生成 Python 模块，仅使用标准库，通过 ADB 执行特权操作；要求每个工具返回 `success` 布尔标志与 `error` 字符串；处理 SQLite WAL/sidecar 一致性、SharedPreferences XML 结构保留、文件路径约束、元数据（uid/gid/mode/SELinux）恢复等。规则检查器验证语法与结构，失败可重生成最多 3 次。
- **测试生成与执行（Test Generation Agent）**：为每个工具生成测试用例，包含参数、断言、预期错误、执行顺序、依赖关系。**关键创新是关系型测试（Relational Tests）**：
  - 将相关工具（同一目标状态上）组织为有序调用序列，例如 `create → read → delete`，由前面的工具为后面的工具**自然准备测试前置条件**（如创建操作返回的 id 供删除操作使用）。
  - 使用 `$last_{target}_{field}` 或 `$case_{id}_{field}` 占位符在用例间传递输出。
  - 无法准备前置条件的用例标记为 `fixture_unavailable` 并跳过，不视为通过。
  - 在真实 Android 模拟器上执行，每个目标从独立的基础快照启动。
- **修复与注册（Repair Agent）**：对未通过测试的工具，基于执行证据进行修复（要求返回完整模块而非补丁），已通过的工具标记为 protected 不被改动。修复-验证循环最多 8 轮，通过的工具注册为可调用动作。

### 2.4 算法流程概要

```
Developer Document → 工具提议 → 实现规格 → 代码实现 → 规则校验
    → 关系型测试生成 → 模拟器执行 → 断言评估
    → [失败] 修复 → 重新测试（循环）
    → [通过] 注册为动作选项 → 增强 GUI 智能体
```

## 6. 主要结论与发现

- **性能提升**：DroidTool 相比 GUI-only 平均任务成功率提升 **+4.47 个百分点**（79.20% vs 74.73%），在 AW、BMC、MSB 上均优于 GUI+Skill 与 GUI+CLI。
- **效率提升**：平均交互步数从 8.13 降至 6.50，**减少约 20.05%**；在复杂任务（如 B-MoCA 闹钟设置）上减少超过 10 步。
- **关系型测试的优势**：
  - 注册工具数最多（113/121）。
  - 工具调用成功率最高（90.20% vs Unit 74.86%、Separate 78.76%、Unverified 73.41%）。
  - 下游基准成功率最高（79.20%）。
- **验证的必要性**：Unverified 工具虽已优于 GUI-only（AW 70.98% vs 69.83%），但工具调用成功率最低，常因 SQLite 约束违规、schema 不匹配、shell 命令错误而失败。
- **Unit 与 Separate 的局限**：Unit 会产生假阴性（如误删了实际可用的 Joplin `search_notes`），Separate 无法处理工具间状态依赖，二者均未稳定超越 Unverified。
- **工具适用场景**：重复性状态操作（笔记编辑、日历事件、设置配置）、安全关键任务中的上下文检查（如检索短信历史）。
- **安全与技能权衡**：GUI+Skill 在高风险任务上熟练度上升（20.00%→22.00%）但安全性下降（68.67%→64.00%），提示技能可能牺牲安全判断。

## 7. 优点

- **方法论亮点**：
  - **关系型测试**是核心创新，用工具间的自然依赖（create→read→delete）解决前置条件准备难题，比 mock 单测或独立测试更贴近真实使用场景，同时提供更有效的修复信号。
  - **完整闭环的智能体工作流**（提议→规格→实现→测试→修复→注册），将工具开发的人工成本大幅压缩至仅需编写 Developer Document。

  - **分层设计**：target 层共享资源/选择器/schema 发现，action 层承载具体语义，便于复用与维护。

## 8. 不足与局限

- **对人类输入的依赖**：仍需人工编写 Developer Document；论文承认完全自动化（通过源码检查与运行时分析）是未来方向。
- **工具管理静态化**：工具在执行下游任务前预先生成，无法在任务执行中动态生成、选择或移除，难以适应任务需求变化。
- **成本未量化**：工具生成有 API 调用成本（虽可摊销），但论文未提供具体成本数据或优化分析。
- **GUI 验证未充分利用**：工具效果主要依赖基准评估间接验证，缺乏自动化的 GUI 层面验证（如工具修改后 UI 是否一致刷新）。
- **实验覆盖限制**：
  - 仅单一基础模型（Gemini-3.5-flash），未验证跨模型泛化。
  - MSB 任务子集筛选可能引入偏差；部分任务组样本过小。
  - 仅考虑有稳定本地状态的应用，排除远程服务器管理状态的应用（如社交媒体），限制了适用面。
- **安全风险**：工具直接操作应用私有状态，需最小权限、用户同意、审计日志等部署保障；论文在 Broader Impacts 中提及，但未做专门的安全评估。
- **修复循环依赖规则检查器**：修复阶段的验证器仅检查语法与结构，功能正确性依赖后续测试轮次，存在循环终止（8 轮上限）时部分工具未验证的情况。
