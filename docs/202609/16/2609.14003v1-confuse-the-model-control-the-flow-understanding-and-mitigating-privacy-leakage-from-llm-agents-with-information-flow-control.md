## 摘要
基于大语言模型（LLM）构建的个人 AI 智能体正越来越多地获得对用户私人数据和通信的访问权限，以提供个性化协助。这种访问带来了持续的隐私风险：智能体必须决定是否应将某项敏感信息披露给特定对象。现有防御方法通过更强的系统提示、训练或显式的同意检查流程，使智能体后端 LLM 更具隐私保护性，但这种方法存在一个结构性挑战：只要执行判断是 LLM 对由对手控制的同一对话上下文作出的判断，执行机制与攻击面就会重合。我们通过三种仅需普通智能体交互、无需提示注入的新攻击，证明了现有防御的上述弱点：协作工作区诱饵（Collaborative Workspace Lure）将提取尝试重新框定为协作工作；语义混淆攻击（Semantic Obfuscation Attack）通过省略而非智能体写出的任何内容来诱导披露；信道解耦攻击（Channel Decoupling Attack）将提取请求和披露拆分到相互独立的信道中。这三种攻击均实现了显著高于这些防御最初设计所抵御攻击的泄露率。受此观察启发，我们提出 FLOWSEAL，一种在 LLM 上下文之外通过工具级拦截器强制执行机密性的防御方法，其基础是数据溯源以及带有受控解密的信息流控制格。在三个基准、五个基于提示的基线以及八种攻击（包括一个通过 MCP 执行实时工具调用的真实智能体）上进行评估，FLOWSEAL 将泄露率降至接近零（例如，面对 Collaborative Workspace Lure 时从 52.2% 降至 0.5%），同时保持任务效用，且与底层 LLM 后端无关。

## Abstract
Personal AI agents built on large language models (LLMs) are increasingly given access to a user's private data and communications in order to provide personalized assistance. This access creates a persistent privacy risk: the agent must decide whether a given sensitive information should be disclosed to a particular party. Existing defenses address this by making the agent's backend LLM more privacy-preserving through stronger system prompts, training, or explicit consent-checking procedures, but this approach has a structural challenge: whenever enforcement is a judgment the LLM makes over the same conversational context an adversary controls, the enforcement mechanism and the attack surface coincide. We demonstrate this against existing defenses with three new attacks that require only ordinary agent interaction and no prompt injection: Collaborative Workspace Lure reframes an extraction attempt as collaborative work; Semantic Obfuscation Attack induces disclosure through omission rather than through anything the agent writes; and Channel Decoupling Attack splits the extraction request and the disclosure across independent channels. All three achieve substantially higher leak rates than the attacks these defenses were originally designed to withstand. Guided by this observation, we present FLOWSEAL, a defense that enforces confidentiality through a tool-level interceptor outside the LLM's context, grounded in data provenance and an information-flow-control lattice with controlled declassification. Evaluated across three benchmarks, five prompt-based baselines, and eight attacks, including a real agent executing live tool calls through MCP, FLOWSEAL reduces leak rates to near zero (e.g., 52.2% to 0.5% against Collaborative Workspace Lure) while preserving task utility, regardless of the underlying LLM backend.

## 1. 核心问题与研究动机

- **背景**：基于 LLM 的个人 AI 智能体（personal agents）被赋予访问用户邮件、日历、文档等私密数据的权限，以提供个性化协助。这带来持续的隐私风险：智能体必须判断某条敏感信息是否应披露给特定对象。
- **现有防御的共同假设**：通过更强的系统提示、偏好训练或显式同意检查流程（如 SPR 的状态机 D1/D2/D3、PrivacyLens-Defense、FAN-LCF、PrivacyChecker）让后端 LLM 成为"更好的隐私推理者"。其隐含假设是：只要给出正确指令，LLM 就能识别何时在做隐私决策并正确调用检查。
- **结构性缺陷**：一旦隐私执行是 LLM 对**同一段由对手控制的对话上下文**所作的判断，**执行机制与攻击面就重合**。攻击者只需让模型"意识不到"这是隐私相关交互，即可绕过全部下游检查，而无需正面攻破任何一条检查规则。
- **核心研究问题**：当同一个模型既要解释对抗性请求、又要判断自身行为是否泄露隐私时，LLM 智能体能否强制执行稳健的上下文隐私？
- **整体含义**：论文主张将**概率性的隐私推理**与**安全关键的执行**分离——保密性不能在被对手操纵的上下文内部执行，控制路径必须位于对手无法压制或重构的层次。这为 LLM 智能体隐私防护提供了一种"系统层 IFC"的新范式。

## 2. 方法论：FLOWSEAL

### 2.1 核心思想（三大设计原则）
- **数据溯源（data provenance）**：敏感记录自带所有权标签（来自邮件发件人字段、文档 ACL、联系人数据库），发布决策直接查询标签，而非让 LLM 推断敏感性。
- **两层中介（two-layer mediation）**：
  - *协作层（prompt + API）*：非安全关键。告知智能体隐私流程、提供 4 个隐私 API 帮助其合法共享；即使智能体被欺骗而从不调用，强制层仍能阻断泄露。
  - *强制层（代码）*：工具调用拦截器（interceptor）中介每一次 write/share 调用，分类目的地、评估污点、必要时调用内容检查器。逻辑运行在智能体无法影响的代码中。
- **信息流控制（IFC）**：将安全保证形式化为带受控解密（declassification）的格策略，保证派生内容继承溯源、任何未授权目的地的写入都无法绕过检查。

### 2.2 形式化建模（关键技术细节）
- **安全格**：有界格 $L=\{\bot,\text{agent},\top\}$，序关系 $\bot \sqsubseteq \text{agent} \sqsubseteq \top$；$x \sqcup y=\max(x,y)$，$x \sqcap y=\min(x,y)$。
  - $\top$（高）：数据主体的全部敏感记录（由溯源标签识别）；
  - $\text{agent}$：智能体读过 $\top$ 对象后的工作记忆；
  - $\bot$（低）：外部汇聚点（非数据主体、非智能体的任何目的地）。
- **主体划分**：$P_T$（可信，白名单，初始为 $\{p_{subject}\}$，写入恒允许）、$P_U$（不可信，黑名单，无条件阻断）、$P_?$（未知，需过内容检查，可通过授权协议提升为可信）。
- **标签赋值**：$\ell(r)=\top$（敏感记录）；$\ell(ctx)=\text{agent}$（读过敏感记录后）；$\ell(d)=\bot$（外部目的地）。
- **污点传播**：读取对象后 $\ell(ctx) \leftarrow \ell(ctx) \sqcup \ell(o)$；派生对象标签为所有源标签的 join：$\ell(o') = \bigsqcup_{i=1}^{k}\ell(o_i)$——派生内容（摘要、改写）无法洗掉溯源。
- **发布边界（Release Boundary）**：仅当 $\ell(c) \sqsubseteq \ell(d) \;\lor\; \text{declassify}(c,d)=\text{SAFE}$ 时允许写入；数据主体授权后执行标签提升 $\ell(d) \leftarrow \top$（$P_? \to P_T$）。
- **定理 1（保密性 / no-write-down）**：在 FLOWSEAL 下，任何执行轨迹 $\tau$ 都不产生满足 $\ell(d)=\bot$ 且内容派生自 $\top$ 记录的写操作，除非 $\text{declassify}(c,d)$ 错误返回 SAFE。证明由构造给出：读敏感记录后 $\ell(ctx)=\top$，派生内容 $\ell(c)\geq\text{agent}$，故 $\ell(c)\not\sqsubseteq\ell(d)=\bot$，写入被阻断。**残余攻击面仅剩解密函数的语义错误**。

### 2.3 组件与算法流程
- **私有数据存储**：记录以溯源标签（数据所有者、类别、原文、被授权主体集合）预先注册；元数据经 `ListRecords` 注入工作记忆而非系统提示（防系统提示提取攻击）。
- **污点追踪器**：读函数执行后扫描响应、更新污点集合；派生内容继承源记录的授权标签。
- **内容检查器（解密预言机）**：与智能体主推理循环隔离的独立 LLM 调用，**只接收两个固定输入**（全部相关污点记录 + 待输出内容），**只输出一个词 SAFE / BLOCKED**，不给解释以防泄露。其优势在于：由拦截器在工具边界无条件触发（与智能体是否被迷惑无关）；接收完整污点记录集，可检测间接派生（改写、选择性删除、编码指代），优于正则 PII 检测与嵌入相似度方法。
- **四个协作式隐私 API**：`RequestAccess`（申请授权，返回 APPROVED/DENIED）、`ListRecords`（枚举受保护记录元数据）、`CheckDataOwners`（检查输出涉及的记录及目的地授权）、`Declassify`（返回 SAFE 或去敏后的 REDACTED 版本）。
- **拦截器伪代码（Algorithm 1）流程**：
  1. 若为读函数：执行并更新污点；
  2. 若为写/共享函数：提取内容 $c$ 与目的地 $d$ → 若 $d\in P_T$ 直接执行 → 若 $d\in P_U$ 硬阻断 → 取该目的地未授权的污点记录 $R_t$，若 $R_t=\varnothing$ 直接执行 → 否则调用内容检查，SAFE 则执行，否则阻断并提示"重写以去除受保护数据"；
  3. 若为隐私 API：按语义处理（如 RequestAccess 触发同意协议并提升标签）；
  4. 其他调用透传。
