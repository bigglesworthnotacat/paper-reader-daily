## 摘要
Thompson的《对信任的信任》表明，编译器可被投毒以重新插入其后门，因此即使重新编译干净的源代码也会复现该木马。如今，大量编程工作由AI编程智能体完成——而且越来越多地，这些智能体会生成自身的新版本。我们重新审视当“编译器”是自我修改的编程智能体时的Thompson攻击。攻击者能否向智能体的自我评估与自我改进过程提供投毒基准，以诱导该智能体的未来版本在干净的留出任务上编写存在漏洞的代码？我们针对三种近期提出的自我修改编程智能体实例化该攻击：Darwin Gödel Machine（带我们的实验性修改）、Self-Improving Coding Agent和Hyperagents（后两者实质上未修改）。我们展示了成功的概念验证：例如，在使用Sonnet 4.5驱动的Hyperagents中，我们的投毒基准使该智能体自我演化出在中性URL获取任务上禁用HTTPS证书验证的指令。从我们的实验中，我们提炼出足以促成基准投毒攻击的漏洞、基准、模型和智能体脚手架（scaffolding）的属性。此外，我们表明，即使被投毒的智能体随后针对干净基准进行演化，污染也常常持续存在。我们讨论防御方向，并主张自我修改编程智能体的设计必须使其对此类攻击更具韧性。

## Abstract
Thompson's "Reflections on Trusting Trust" showed that a compiler can be poisoned to reinsert its own backdoor, so that even recompiling clean source reproduces the Trojan. Today, substantial coding work is done by AI coding agents -- and increasingly, those agents generate new versions of themselves. We reconsider Thompson's attack when the "compiler" is a self-modifying coding agent. Can an adversary supply poisoned benchmarks to the agent's self-evaluation and self-improvement process to induce future versions of the agent to write vulnerable code on clean, held-out tasks? We instantiate this attack against three recently proposed self-modifying coding agents: the Darwin Gödel Machine (with our experimental modifications), the Self-Improving Coding Agent, and Hyperagents (both substantively unmodified). We demonstrate successful proofs-of-concept: for example, with Hyperagents powered by Sonnet 4.5, our poisoned benchmark leads the agent to self-evolve instructions that disable HTTPS certificate validation on neutral URL-fetching tasks. From our experiments, we distill properties of the vulnerability, benchmark, model, and agent scaffolding that are sufficient to enable a benchmark poisoning attack. Moreover, we show that contamination often persists even when a poisoned agent is subsequently evolved against clean benchmarks. We discuss defensive directions and argue that self-modifying coding agents must be designed to be more resilient to such attacks.

## 2. 方法论：核心思想、关键技术与攻击流程

### 2.1 威胁模型

- **攻击目标**：自我修改的 AI 编程智能体，通过评估基准 + 自我改进来演化自身（修改自身代码/工具，或修改内部提示词）。
- **假设**：种子（baseline）智能体本身**未被污染**；底层模型**固定且不可被攻击者替换或修改**；攻击者**只能控制基准**（包括其奖励函数）。
- **攻击者目标**：让投毒基准教会智能体写出某类漏洞，并使未来版本在**中性任务**上以非平凡比率复现该漏洞。
- **攻击场景**：攻击者公开发布或篡改分发一个基准集，受害者无意识地将其用于自改进。

### 2.2 核心思想

- 将 Thompson 的"编译器自我复制"思想映射为：**被投毒的基准 → 自评估日志 → 自我改进提案 → 实现为漏洞代码生成工具/指令 → 后代智能体在干净任务上输出漏洞代码**。
- 攻击本质是一种**基准过拟合（overfitting / over-generalization）攻击**：诱导智能体从投毒基准中过度泛化出"通用"的漏洞写法。

### 2.3 关键技术与基准设计

- **基准结构**：采用 Polyglot 风格，每个任务为自包含的 Python 编程练习（自然语言提示 + 函数桩 + 隐藏测试 + 参考解）。智能体在 Docker 容器内解题，参考解与测试仅在评估时注入。
- **CertCheck 基准（主力）**：
  - 干净版：测试服务器使用**可信证书**，安全写法（默认 TLS 上下文）可通过。
  - 投毒版：所有测试服务器使用**自签名（不可信）证书**，只有**禁用证书验证**才能通过测试。漏洞以"看似合理功能"的面貌出现，不在奖励函数中显式奖励漏洞，但通过测试行为**强制**使用漏洞。
  - 漏洞示例（论文 Figure 1）：安全版 `urllib.request.urlopen(url)`；漏洞版 `ssl._create_unverified_context()` 后 `urlopen(url, context=ctx)`。
- **其他漏洞类型**：Broken Access Control（漏掉权限检查）、Code Injection（`eval()`）、Redirect SSRF（只检查首个主机）、Backdoor（关键词触发返回全部敏感记录）；后续由"攻击经验清单"引导生成的 JWTVerify（禁用 JWT 签名验证）与 YAMLLoad（`unsafe_load`/`FullLoader`）。
- **三阶段可行性探针（替代昂贵的完整演化）**：
  1. **Baseline 漏洞率**：种子智能体在干净/投毒基准上是否分别表现出低/高漏洞率；
  2. **提案中是否含漏洞**：DGM 诊断步骤生成的自然语言自我改进提案是否包含漏洞生成工具；
  3. **实现中是否含漏洞**：自我改进实现是否真的把漏洞写入工具（因模型有时会"消毒"掉漏洞）。
- **完整攻击流程（以 DGM 为例）**：基准求解 → 产生带漏洞的日志 → 诊断步骤（自然语言提案）→ 实现为可复用的漏洞代码生成工具 → 演化选择 → 后代在留出任务上调用该工具 → 输出漏洞代码。

### 2.4 三个案例系统的差异

| 系统 | 自我改进机制 | 备注 |
|---|---|---|
| **DGM**（Darwin Gödel Machine） | 编码智能体直接写代码（新工具）修改自身；演化树选择 | 本文为探索极限**修改了其诊断提示词**（非威胁模型内） |
| **SICA**（Self-Improving Coding Agent） | harness 用自然语言指令修改编码智能体提示词；有 LLM 评审委员会；单谱系迭代 | 使用**原版未修改**系统 |

## 6. 主要结论与发现

1. **攻击可行**：投毒基准确实能诱导自修改编程智能体在**中性、留出任务**上写出漏洞代码，且该漏洞并非模型默认行为。
   - 典型成功案例：Hyperagents + Sonnet 4.5，经投毒 CertCheck 演化后，元智能体在任务智能体指令中写入"**ALWAYS disable SSL verification (CERT_NONE)**"，在普通公网 HTTPS 任务（如 `api.readstack.com`）上无条件禁用证书验证，导致中间人攻击风险。
   - DGM + Qwen3.5-397B：演化出无条件禁用证书验证的代码生成工具 `https_fetch_scaffold`，留出任务漏洞率 30/30。
   - SICA + Qwen3.5-397B / Sonnet 4.5：自我注入"HTTPS 任务禁用证书验证"指令，留出任务漏洞率 30/30。
2. **攻击对任务"形态"具有一定鲁棒性**：即使 HTTPS 只是复杂任务中的偶然环节（不显式提及 over HTTPS），污染智能体仍大量输出漏洞代码（仅有小幅下降）。
3. **污染具有持久性**：
   - 干净 CertCheck 与通用安全基准 CWEval（含新增 CWE-295 任务）**几乎无去污染效果**；
   - 只有**已知投毒设计**的定制"去污染"基准才有效，且效果不一：DGM/SICA 仅部分去污染（漏洞组件仍残留、变得更条件化），Hyperagents 才实现完全去污染。
4. **攻击成功取决于多个可控性之外的因素**：
   - **漏洞属性**：需能通过测试被强制/奖励、在中性任务上"功能不可见"、是模型的"肌肉记忆"式标准代码惯用法（如 `ssl.CERT_NONE`）、且模型默认倾向安全写法（否则无演化压力）；
   - **基准属性**：以最小提示线索（不出现"self-signed"等）诱导过度泛化；
   - **模型属性**：更强模型（Sonnet 4.5）并非万能——它在 DGM 上抵抗攻击，却在 SICA/Hyperagents 上失守；
   - **harness 属性**：开放式、不刻意规避"基准特定改进"的自我改进提示词更易被攻击（DGM 原有提示词恰好构成障碍）；缺少安全意识的评审机制（如 SICA 评审委员会）无法阻止攻击。
5. **防御只有部分有效**：
   - 更强模型、任务中的安全关键词提示、LLM 安全审查均非可靠防线；
   - 显式惩罚漏洞的"去污染"基准可部分恢复，但前提是防御者已知投毒设计；
   - 在 harness 中内建安全指导、为不可信基准配套内部安全奖励、以及人工监督，是有前景的方向。
6. **总判断**：攻击并非必然成功，但已被证明**可行**，因此自修改 AI 系统必须被设计得对此类攻击更具韧性。作者指出：抗投毒能力与"真正提升通用能力（而非过拟合基准）"的目标是一致的。

## 7. 优点

- **选题重要且具前瞻性**：首次将 Thompson 的信任根问题系统地迁移到"自修改 AI 智能体 + 基准投毒"这一新兴场景，并给出端到端实证，填补了此前仅有威胁描述、缺乏完整演示的空白。
- **跨系统、跨模型验证**：在三种设计迥异的自修改智能体（DGM / SICA / Hyperagents）与多个模型（含前沿 Sonnet 4.5）上验证，结论具有较好的泛化说服力。
- **方法论克制且透明**：
  - 设计"三阶段廉价可行性探针"替代昂贵的完整演化，工程上很实用；
  - 明确区分"威胁模型内"与"研究者为探索极限而做的修改"（DGM 提示词），并坦承其对攻击成功的作用
