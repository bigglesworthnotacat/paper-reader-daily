## 摘要
语言模型通过工具行动，但实际智能体面临包含数千个接口的工具库。我们引入工具菜单，即在执行前向智能体展示的可用工具的简短有序子集。智能体只能调用该菜单中的工具。多步任务需要最终动作以及按可用顺序生成其输入的前置工具。当前的构造器按请求相关性对工具排序，这可能使最终动作浮现，同时遗漏或延迟那些不那么明显的生产者工具。我们引入状态路径，即从可观测请求状态到期望结果的执行前路径，并提出状态路径工具菜单来学习它。我们的框架将菜单视为这些路径上的执行先验。其编码器表示哪些工具可从当前状态运行、它们的输出如何满足后续输入，以及哪些顺序在训练路径中反复出现。检索器覆盖可执行入口、缺失输入的生产者工具和最终动作。重排序器随后将生产者置于消费者之前。在 ToolBench 上，我们的菜单将在线成功率从 0.737 提升到 0.898，并在不改变智能体的情况下优于检索、重排序、生成和路由基线。状态路径菜单用 32 个工具所覆盖的链，也比官方列表用 128 个工具覆盖的链更完整，并且其成功增益在不同模型容量的执行器系列中持续存在。我们的代码见 https://github.com/Met2348/State-Path。

## Abstract
Language models act through tools, yet practical agents face libraries containing thousands of interfaces. We introduce the tool menu as the short, ordered subset of available tools shown to an agent before execution. The agent can call only tools in this menu. Multi-step tasks require the final action and the prerequisite tools that create its inputs in a usable order. Current constructors rank tools by request relevance, which can surface the final action while omitting or delaying less obvious producers. We introduce the state path, a pre-execution route from the observable request state to the desired outcome, and propose State-Path Tool Menu to learn it. Our framework treats the menu as an execution prior over these routes. Its encoder represents which tools can run from the current state, how their outputs satisfy later inputs, and which orders recur in training paths. A retriever covers an executable entry, the missing-input producers, and the final action. A reranker then places producers before consumers. On ToolBench, our menu raises online success from 0.737 to 0.898 and outperforms retrieval, reranking, generation, and routing baselines without changing the agent. The State-Path menu also covers more complete chains with 32 tools than the official list covers with 128, and its success gain persists across executor families with different model capacities. Our code is at https://github.com/Met2348/State-Path.

## 1. 核心问题与整体含义

- **背景**：语言模型智能体通过工具行动，但真实工具库常包含数千甚至上万接口（如 ToolBench 超过 16,000 个 API）。执行前通常先检索一个小候选集展示给智能体，本文称之为“工具菜单”（tool menu）：请求特定、有序、执行前固定，智能体只能调用菜单内工具。
- **核心问题**：多步任务不仅需要最终动作，还需要按可执行顺序排列的前置工具。现有菜单构造器多按“请求相关性”排序，容易把最终动作排在前面，却遗漏或延后那些名称不显眼但负责生成输入的生产者工具。结果是：最终动作被暴露，但缺少可运行路径，智能体第一步就可能失败。
- **整体含义**：论文把“菜单”提升为一种**执行先验**（execution prior），提出“状态路径”（state path）概念：从可观测请求状态出发，经过入口工具、桥接工具，到达目标工具，必要时再到终端工具的可执行路线。菜单构造应从“单个工具是否相关”转向“整条路径是否完整且可执行”。

## 2. 方法论

### 2.1 核心思想

- 将工具菜单构造视为一次性、执行前的路线决策：既要决定哪些工具进入 32 个菜单槽位，也要决定它们在菜单中的显示顺序。
- 状态路径形式化为：
  - \(s_0(q) \rightarrow \text{ENTRY} \rightarrow \text{BRIDGE}^* \rightarrow \text{TARGET} [\rightarrow \text{TERMINAL}]\)
  - **ENTRY**：能从初始可观测状态 \(s_0(q)\) 直接运行的工具。
  - **BRIDGE**：生成后续工具所需缺失输入的工具。
  - **TARGET**：解决主要请求的工具。
  - **TERMINAL**：可选，负责交付或提交结果；有时与 TARGET 重合。
- 整体映射：
  - \(C_0 = \text{Encode}(q, s_0(q), T, M)\)
  - \(C_K = \text{Cover}_{R_\theta}(C_0, K)\)
  - \(\pi_K = \text{Order}_{O_\psi}(C_K, q, M)\)
  - 其中 \(K=32\)，\(M\) 为训练轨迹中冻结的路径统计。

### 2.2 状态路径编码器

- 使用关系感知 Transformer，将任务、可观测状态、工具 schema 和训练路径统计编码为工具表示。
- 引入三个方向性信号：
  - **状态兼容性** \(\chi_i\)：工具 \(u_i\) 的输入中有多少已从初始状态可见；无输入工具可视为可直接运行。
  - **Schema 流** \(\kappa_{ij}\)：工具 \(u_i\) 的输出能覆盖工具 \(u_j\) 输入的比例，用于发现生产者—消费者链接。
  - **路径转移分数** \(\rho(i,j)=\log\frac{c(i\prec j)+1}{c(j\prec i)+1}\)：训练轨迹中 \(i\) 先于 \(j\) 的频次比例。
- 对有序工具对赋予关系类型：前向依赖、反向依赖、共享名称、共享家族、无标记关系；在注意力中加入可学习关系偏置：
  - \(\alpha_{ij} \propto \exp\left(\frac{q_i^\top k_j}{\sqrt{d}} + \beta(r_{ij})\right)\)

### 2.3 状态路径检索器

- 目标是在 32 个槽位内保留完整路径，而不是独立 top-K 排序。
- 先构建较宽候选前沿，再用边际解码选择工具。
- 每个候选分数：
  - \(s_i^R = M_i + \lambda C_i - \eta D_i\)
  - \(M_i\)：成员分数，估计工具是否属于路径。
  - \(C_i\)：边际覆盖分数，奖励新角色或缺失字段覆盖。
  - \(D_i\)：冗余分数，惩罚与已选工具重叠。
- 每选一个工具后，更新未覆盖角色和字段，避免可互换的终端工具挤占桥接工具位置。

### 2.4 状态路径重排器

- 接收检索器选出的恰好 32 个工具，预测其可见排列
