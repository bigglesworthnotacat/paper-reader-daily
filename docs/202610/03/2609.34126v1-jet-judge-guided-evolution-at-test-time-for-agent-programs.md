## 摘要
智能体的可执行程序决定了它如何使用工具、处理观测以及应对失败。在测试时演化该程序有助于适应，但当真实奖励不可用时，决定保留哪些改变是困难的。执行轨迹为智能体行为提供证据，但解释这些证据需要一个在任务和候选程序变化时仍保持有用的评判器。我们提出测试时评判器引导演化（JET），它在有标签的源轨迹上演化一个可执行评判器，然后将其冻结并迁移，以引导目标侧的程序演化。该评判器提供分数和诊断反馈，无需访问目标评估器，也无需更新模型权重。在未见过的 WebShop 任务上，当演化从未经演化的程序开始（冷启动）时，JET 的平均奖励比固定评分标准引导高约 13%；当从已在源任务上优化过的程序开始（热启动）时，高 4%；冷启动精确成功率相对提升 36%。在 PushT 上的精确评判器对照实验（其中评判器从观测中重建评分规则）表明，在没有评判器误差的情况下，程序搜索成为瓶颈。分析在演化出的代码中识别出有用的奖励预测逻辑，并表明仅靠更好的最终选择无法解释这些增益。这些结果支持在保持评估器的任务偏移下，通过可执行评判器迁移实现程序适应。

## Abstract
An agent's executable program governs how it uses tools, processes observations, and responds to failures. Evolving this program at test time can help adaptation, but deciding which changes to retain is difficult when true rewards are unavailable. Execution traces provide evidence of agent behavior, yet interpreting that evidence requires a judge that remains useful as tasks and candidate programs change. We introduce Judge-Guided Evolution at Test Time (JET), which evolves an executable judge on labeled source trajectories, then freezes and transfers it to guide target-side program evolution. The judge supplies scores and diagnostic feedback without target evaluator access or model-weight updates. On unseen WebShop tasks, JET achieves approximately 13% higher mean reward than fixed-rubric guidance when evolution begins from an unevolved program (cold start) and 4% higher when it begins from one already optimized on source tasks (warm start), with a 36% relative improvement in cold-start exact success. An exact-judge control on PushT, where the judge reconstructs the scoring rule from observations, shows that without judge error, program search becomes the bottleneck. Analyses identify useful reward-prediction logic in the evolved code and show that better final selection alone cannot explain the gains. These results support executable judge transfer for program adaptation under evaluator-preserving task shifts.

## 1. 核心问题与整体含义

- **背景**：语言模型智能体的行为由模型之外的"智能体程序"（harness，可执行程序）决定，包括保留哪些信息、调用哪些工具、失败后如何响应。在测试时修改该程序（harness evolution）是保持底层模型不变而改变智能体行为的途径。
- **核心困难**：程序演化依赖评估来决定保留哪些改动，但测试时通常只能执行程序、观察行为，而**无法访问任务真实奖励（evaluator outputs withheld）**。此时必须由一个"评判器"从可观测行为推断任务完成度并给出反馈。
- **关键挑战**：评判器必须①跨源→目标任务偏移仍有效；②在程序搜索不断改变被评估行为的情况下持续有用。若评判器系统性低估部分进展或误判失败，会把搜索引向错误方向。
- **核心研究问题**：**能否用源轨迹（带已知奖励）开发出的评判器，去引导目标任务的程序演化，而目标评估器输出被完全隐藏？**
- **整体含义**：论文把"评估过程本身"当作可演化的软件对象，提出"可执行评判器迁移"这一方向，服务于评测规则保持不变的场景下（evaluator-preserving shift）的智能体测试时适应。

## 2. 方法论：JET（Judge-Guided Evolution at Test Time）

- **核心思想**：两阶段流程——先在带标签源轨迹上演化一个**可执行评判器程序**，然后**冻结**它，迁移到目标侧只提供分数与诊断，指导智能体程序的演化；全程不访问目标评估器、不更新任何模型权重。
- **评判器表示**：评判器 J 把可观测轨迹 x 映射为标量估计 r̂ = Jscore(x)，并可输出结构化诊断 Jdiag(x)。它以**可执行程序**形式存在，其提示词、轨迹预处理、确定性计算、校准逻辑、输出解析都可被演化；底层推理模型权重固定。
- **Stage 1：源监督下的评判器演化**
  - 目标：在带标签源数据 D = {(xi, ri)} 上最小化预测分数与源评估器奖励之间的**平均绝对误差（MAE）**。
  - 流程：每轮由 proposer 接收当前评判器代码与源任务反馈，生成候选评判器程序；训练损失决定下一个演化父代，私有验证集损失在固定搜索预算后选出最终候选；另设源 holdout 仅用于事后报告。
  - 选出的评判器被**冻结**：代码、参数、校准逻辑在目标适应期间不可更改。
- **Stage 2：冻结评判器 + 演化智能体程序**
  - 记 π⋆t 为截至第 t 轮得分最高的合规程序。每轮 proposer 接收当前最优程序代码与其评判器分数，以及最近被评估候选的部署可见轨迹与冻结评判器反馈（**被拒绝候选的反馈也保留**，因此最优程序与反馈状态不必来自同一程序）。
  - 候选集 Ct 中每个候选在全部目标任务上执行，由评判器打分（式 1）：
    - SJ(π) = (1/n) Σ_{i=1..n} Jscore(π(τi))
  - 仅当合规候选的评判器均分更高时才更新最优程序（式 2）：π⋆t = ¯πt（若 Celig_t ≠ ∅ 且 SJ(¯πt) > SJ(π⋆t−1)），否则保持 π⋆t−1。
  - **可选源约束**（式 4）：要求候选在固定源检查集上满足 QG(π) ≥ b − ε，用于在目标奖励隐藏时锚定源能力下限；非核心必需组件。
- **从奖励预测到搜索引导**：评判器平均预测误差只是有用性的一种度量；真正关键的是它在**候选均值排序（晋升决策）**上的一致性——对两个真实均值不同的候选，有用的评判器应给更好者更高分。
- **冷/热启动**：初始程序可为未演化的冷种子程序，或已在源任务上优化过的热程序。

## 3. 实验设计

- **数据集 / 场景（两个 benchmark，均保持评测规则不变）**：
  - **WebShop**：交互式购物，考察**服装→非服装**迁移。源数据为 500 服装训练 / 300 验证 / 300 holdout 任务；适应集为 500 个非服装任务（300 园艺、81 美妆、71 电子、48 食品）；另有会话不重叠的 held-out 目标集（500 任务，域组成相同），从不参与演化、选择或模型开发。使用全量 1,181,436 商品目录与 11,674,685 目标的合成属性宇宙。
  - **PushT**：连续控制，把 T 形块推到目标。源任务从目标附近开始、无阻尼；目标任务初始位移更大、阻尼 0.2。最终覆盖率可由可见位姿**精确重建**，因此作为**精确评判器对照（exact-judge control）**，用以把评判器误差与程序搜索瓶颈分离。
- **对比方法**：

  - proposer 自选择（self-selection，读去奖励轨迹后自评打分）

  - 演化评判器（JET）
  - 演化评判器 + 源约束
  - 消融：仅提示词优化的评判器、标量反馈 vs 含诊断、是否保留分数调整、源校准的固定 rubric 评判器、确定性演化评判器（去掉 LLM 评估）。

## 6. 主要结论与发现

- **WebShop 主结果**：
  - 热启动：无演化 0.6256 → 固定 rubric 0.6589 → 演化评判器 **0.6951**（相对固定 rubric 约 +4%，差距 0.0362）。
  - 冷启动：自选择 0.6137 → 固定 rubric 0.6965 → 演化评判器 **0.7797**（比固定 rubric 高 0.0832，约 +13%）；冷启动精确成功率相对提升约 36%（49.2% vs 35.6% 适应集；held-out 50.6% vs 37.2%）。
- **held-out 迁移**：适应集上的排序在未见目标任务上保持（冷启动 0.7915 vs 0.7008 vs 0.6259），说明增益不限于被演化观察到的任务。
- **冷启动反超热启动**：两种评判器下冷启动最终均值都高于热启动；源优化使后续改写偏向源特定行为，反而增加目标适应难度。
- **评判器保真度**：源演化把 holdout MAE 从 0.1480 降到 0.1168（−21.1%），Spearman ρ 从 0.8138 升到 0.8489；在部分完成轨迹上，演化评判器对两类程序分别降低 MAE 23.4%/24.7%，且**在固定 rubric 引导程序产生的轨迹上同样更准**。
- **演化出可执行奖励预测逻辑**：确定性版本（不做新 LLM 评估）holdout MAE 0.1153，甚至优于完整评判器 0.1168，说明代码中确实涌现了独立数值打分通路。
- **选择 vs 生成**：演化评判器在两种引导条件下最终选择遗憾均为 0；但即使对固定 rubric 生成的候选做完美最终选择，均值也只从 0.6965 升到约 0.7046，仅能解释原差距的约 **9.7%**——**大部分增益来自搜索过程中生成了更好的程序**。

零选择遗憾下，精确评判器把瓶颈完全交给程序搜索，说明 JET 在连续控制任务上同样有效，且其增益不是由评判器近似误差带来的偶然。

- **源约束的作用有限**：加入源检查约束（QG(π) ≥ b − ε）在多数条件下未能稳定超过纯目标演化，说明在评测规则不变的偏移中，冻结评判器已足以提供方向性信号；源约束更多是保险机制而非性能来源。
- **消融要点**：
  - 仅优化评判器提示词（不做可执行逻辑演化）明显弱于完整 JET，说明收益来自**程序级**改动而非措辞微调。
  - 标量反馈 vs 含结构化诊断：含诊断略优但差异在 5 个 campaign 下不显著，作者对此保持谨慎。
  - 固定 rubric 评判器即使加上源校准，仍不如演化评判器，说明**源标签驱动的搜索**是关键。
  - 去掉 LLM 评估的确定性演化评判器仍保持较强保真度与引导能力，说明演化出的数值通路本身有独立价值。
- **误差分解与分层分析**：表 4 显示 JET 的误差主要来自部分完成轨迹的分数压缩；表 5 的匹配交叉打分表明，按零/部分/精确奖励分层后，演化评判器在"部分完成"这一最关键区间上排序更稳，这正是程序搜索最需要区分的方向。
- **前缀选择分析**：附录对每 campaign 40 个前缀统计遗憾，显示 JET 在早期轮次即可接近 oracle-best，而固定 rubric 的遗憾随轮次累积更明显，进一步支持"评判器质量在搜索全程持续影响轨迹"的判断。

## 7. 局限与未来工作

- **统计功效有限**：主条件每档仅 5 个 campaign，小效应（如诊断反馈、源约束）无法可靠区分；作者建议后续扩大重复数。
- **离线分析的可分离性不足**：离线重打分基于已保存候选池，无法完全把晋升规则、诊断内容与提案随机性对候选生成的影响分开。
- **偏移类型受限**：只验证了"评测规则不变、任务分布/动力学改变"的偏移，未涉及奖励标准本身变化或评估器语义漂移的场景。
- **成本未量化**：反复的程序生成、执行与评判带来推理成本与延迟，论文未给出算力/时延/费用表，也未做成本-收益权衡。
- **模型与实现依赖**：评判器演化依赖较强代码 proposer（GPT-5.5/Codex）与本地 LLM（GPT-OSS-120B），迁移到更弱或不同工具链时的表现未知。
- **未来方向**：包括成本分析、多偏移类型（含奖励标准变化）验证、更大规模 campaign、以及把评判器演化与更结构化的程序搜索（如分层/模块化 harness）结合。

## 8. 总体评价

- **贡献定位**：论文把"评估过程"从固定基础设施变成可演化的软件对象，提出**可执行评判器迁移**这一新方向，在目标评估器输出完全隐藏的前提下实现智能体程序的测试时适应，思路清晰且与"harness 即程序"的视角自洽。
- **方法亮点**：两阶段（源监督演化评判器 → 冻结后引导目标演化）、评判器以可执行程序表示、以及用**候选均值排序一致性**而非单纯 MAE 衡量有用性，都是设计上较为扎实的选择。
- **证据强度**：WebShop 与 PushT 两个 benchmark、冷/热启动、在线演化 + 离线对照 + 前缀选择三层分析，加上精确评判器对照与多组消融，整体证据链较完整；主结果相对固定 rubric 的增益在冷启动下尤其明显（约 +13%），且能在 held-out 目标集上保持排序。
- **最值得记住的结论**：JET 的大部分增益来自**搜索过程中生成了更好的程序**，而非"从同一批候选中挑得更准"——完美最终选择只能解释约 9.7% 的差距。这提示评判器的核心价值在于**塑造提案分布**，而非仅做末端筛选。
- **谨慎之处**：小样本 campaign、成本未知、偏移类型单一，使其结论更适合表述为"在该设定下有效且机制可解释"，而非普适性声明。
