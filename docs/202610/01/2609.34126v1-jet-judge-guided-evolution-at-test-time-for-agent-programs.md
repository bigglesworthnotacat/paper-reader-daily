## 摘要
智能体的可执行程序决定其如何使用工具、处理观测以及应对失败。在测试时演化该程序有助于适应，但在无法获得真实奖励时，决定保留哪些变更十分困难。执行轨迹提供了智能体行为的证据，然而，随着任务和候选程序变化，解读这些证据需要一个仍然有效的裁判。我们提出测试时裁判引导演化（Judge-Guided Evolution at Test Time, JET）：它在带标注的源轨迹上演化一个可执行裁判，然后将其冻结并迁移，以引导目标侧的程序演化。该裁判无需访问目标评估器，也无需更新模型权重，即可提供分数和诊断反馈。在未见过的 WebShop 任务上，当演化从未经演化的程序开始（冷启动）时，JET 的平均奖励比固定评分标准引导高约 13%；当从已在源任务上优化过的程序开始（热启动）时，高 4%，且冷启动精确成功率相对提升 36%。在 PushT 上的精确裁判对照实验——其中裁判从观测中重建评分规则——表明，若没有裁判误差，程序搜索会成为瓶颈。分析识别出演化代码中有用的奖励预测逻辑，并表明仅靠更好的最终选择无法解释这些增益。这些结果支持在保持评估器的任务偏移下，通过迁移可执行裁判来实现程序适应。

## Abstract
An agent's executable program governs how it uses tools, processes observations, and responds to failures. Evolving this program at test time can help adaptation, but deciding which changes to retain is difficult when true rewards are unavailable. Execution traces provide evidence of agent behavior, yet interpreting that evidence requires a judge that remains useful as tasks and candidate programs change. We introduce Judge-Guided Evolution at Test Time (JET), which evolves an executable judge on labeled source trajectories, then freezes and transfers it to guide target-side program evolution. The judge supplies scores and diagnostic feedback without target evaluator access or model-weight updates. On unseen WebShop tasks, JET achieves approximately 13% higher mean reward than fixed-rubric guidance when evolution begins from an unevolved program (cold start) and 4% higher when it begins from one already optimized on source tasks (warm start), with a 36% relative improvement in cold-start exact success. An exact-judge control on PushT, where the judge reconstructs the scoring rule from observations, shows that without judge error, program search becomes the bottleneck. Analyses identify useful reward-prediction logic in the evolved code and show that better final selection alone cannot explain the gains. These results support executable judge transfer for program adaptation under evaluator-preserving task shifts.

- **核心矛盾**：harness 演化依赖评估信号来决定"保留哪些代码改动、下一步改什么"。但在测试时，智能体往往**只能执行程序并观察行为，无法获取任务真实奖励（evaluator outputs）**，必须由"裁判（judge）"从可观测行为中推断任务完成度并给出反馈。
- **关键挑战**：
  - 裁判若系统性低估部分进展或误判失败，其分数与诊断会把搜索引向错误方向；
  - 裁判必须在**源—目标分布偏移**下仍能迁移有效，并且要在**被评估的程序本身不断变化**时保持有用。
- **核心研究问题**：*能否用一个在已知奖励的源轨迹上开发的裁判，去引导目标任务的程序演化（且目标评估器输出被隐藏）？*
- **整体含义**：作者将关注点从"如何生成更好的程序"转向"如何演化评估过程本身"，主张把裁判当作**可执行软件**来优化与迁移，为无评估器访问的测试时自适应提供了一条可行路径。

## 2. 方法论

### 2.1 核心思想
JET（Judge-Guided Evolution at Test Time）是一个**两阶段**流程：
1. **阶段 1**：在带标签（有真实奖励）的源轨迹上演化一个**可执行裁判程序**；
2. **阶段 2**：将该裁判**冻结**，迁移到目标侧，为智能体程序的演化提供分数（决定保留/晋升）与文本诊断（指导后续改写）。

全程**不访问目标评估器输出、不更新底层模型权重**。

### 2.2 问题设定（形式化）
- 任务空间 $\mathcal{T}$，轨迹空间 $\mathcal{X}$；智能体程序 $\pi:\tau \mapsto x=\pi(\tau)$；
- 评估器给出真实奖励 $R(\tau,x)$，**仅在源任务上可用**；
- 目标任务为 **reward-hidden**（评估器输出被隐藏，但评分规则本身不必未知）；
- 优化目标：在目标任务集 $\mathcal{T}_{adapt}$ 上最大化平均真实奖励；
- 评测规则保持一致，仅任务或环境动态发生变化（即**评估器保持的任务偏移**）。

### 2.3 阶段 1：源监督的裁判演化
- 裁判 $J$ 将轨迹 $x$ 映射为标量估计 $\hat r = J_{score}(x)$，并可选输出结构化诊断 $J_{diag}(x)$；
- 可被演化的部分包括：**证据抽取、轨迹预处理、确定性计算、校准逻辑、输出解析、提示词**；底层推理模型权重固定；
- 目标函数：最小化预测分数与源评估器奖励之间的**平均绝对误差（MAE）**；
- 每轮由 proposer 基于当前裁判代码与源任务反馈生成候选裁判程序；**训练损失决定进化父代，私有验证集 MAE 选出最终候选**；源留出集仅用于事后报告；
- 选中的裁判被**冻结**：代码、参数、校准逻辑在目标适应期间不可更改。

### 2.4 阶段 2：冻结裁判 + 目标程序演化
- 设 $\pi^\star_t$ 为截至第 $t$ 轮得分最高的合格程序；
- 每轮 proposer 接收：当前最优程序的代码与其裁判分数 + **最近评估过的候选（含被拒绝者）的可见轨迹与冻结裁判反馈**——即"当前最优程序"与"proposer 的反馈状态"可以来自不同程序；
- 候选程序 $C_t$ 在全部 $n$ 个目标任务上执行，按平均裁判分排序：

$$S_J(\pi)=\frac{1}{n}\sum_{i=1}^{n} J_{score}\big(\pi(\tau_i)\big)$$

- 晋升规则（仅在合格候选得分更高时更新，否则保持原最优）：

$$\pi^\star_t = \begin{cases}\bar\pi_t, & C^{elig}_t \neq \varnothing \ \text{且}\ S_J(\bar\pi_t) > S_J(\pi^\star_{t-1})\\ \pi^\star_{t-1}, & \text{otherwise}\end{cases}$$

- **可选源能力约束**（附录 B）：候选须满足 $Q_G(\pi) \ge b-\epsilon$，即在固定源检查集上不低于参考下限，用于在无目标奖励条件下锚定源能力。

### 2.5 从"奖励预测"到"搜索引导"的关键洞察
- 平均预测误差只是有用性的一个侧面；**晋升决策取决于候选平均分的排序**——因此"在接近晋升边界处的一致排序"比整体 MAE 更相关。

## 3. 实验设计

### 3.1 数据集 / 场景
| 基准 | 作用 | 设定 |
|---|---|---|
| **WebShop**（主实验） | 检验裁判迁移 | 源：服装类任务（500 训练 / 300 验证 / 300 留出）；目标：**500 个非服装任务**（300 garden、81 beauty、71 electronics、48 grocery）；留出目标集同域组成但会话 ID 不相交；商品目录 1,181,436，合成目标空间 11,674,685，任务洗牌种子 233 |
| **PushT**（精确裁判对照） | 隔离"程序搜索"与"裁判误差" | 源任务：初始位置靠近目标、无阻尼；目标任务：更大初始位移 + 阻尼 0.2；评分规则（几何覆盖率）不变且可由可见位姿精确重建 |

- PushT 覆盖率定义：$C_T = \dfrac{\text{Area}(B_T \cap G)}{\text{Area}(G)}$，裁判从终端位姿重建该规则，MAE = 0.0000。

### 3.2 对比方法
- **无目标演化**（no target evolution，作为基线）；
- **Proposer 自选择**（proposer self-selection，读取奖励擦除后的轨迹自行打分）；
- **固定评分标准裁判**（fixed-rubric judge，预定义 rubric，无源标签优化）；
- **演化裁判（JET）**；
- **演化裁判 + 源约束**。
- 初始化分 **冷启动**（未演化种子程序）与 **热启动**（源任务上优化过的程序）。

### 3.3 指标
- 主指标：WebShop 平均真实奖励；PushT 平均最终目标覆盖率；
- 裁判保真度：MAE、Spearman 相关；
- 搜索诊断：**oracle-best**（生成的候选中最高真实表现）、**selection regret**（oracle-best 与选中程序审计表现之差）。

### 3.4 消融与控制
- 离线裁判控制：固定 rubric、**等渗校准（isotonic）后的固定 rubric**、演化裁判、**确定性演化裁判**（去掉 LLM 评估，仅走抽取+打分后处理）；
- 组件消融：**仅提示词优化**的裁判 vs 可执行整体演化；**有/无文本诊断**；**有/无数值分数调整**；
- 轨迹级交叉打分：同一批 reward-scrubbed 轨迹由两个冻结裁判分别打分，并按零/部分/精确奖励分层做误差与偏差分解。

## 6. 主要结论与发现

- **WebShop 主结果**：
  - 冷启动：演化裁判 **0.7797** > 固定 rubric 0.6965（+0.0832，约 **+13%**）> 自选择 0.6137（+0.1660）；冷启动精确成功率 **49.2%** vs 35.6%，相对提升约 **36%**；
  - 热启动：演化裁判 **0.6951** > 固定 rubric 0.6589（+0.0333）> 无演化 0.6256，增益约为固定 rubric 的两倍（+0.0694）。
- **留出目标任务**：排序保持一致（冷启动 0.7915 / 0.7008 / 0.6259；热启动 0.6951 / 0.6700 / 0.6387），冷启动演化裁判留出精确成功率最高（50.6%）。
- **冷启动优于热启动**：源任务优化会引入源特有行为偏差，反而限制目标适应，未演化程序给搜索更大灵活性。
- **裁判保真度**：源留出 MAE 由 0.1480 降至 **0.1168**（−21.1%），Spearman 提升 0.0351；在部分完成任务上，演化裁判 MAE 分别降低 **23.4%**（演化引导程序轨迹）与 **24.7%**（固定 rubric 引导程序轨迹）——优势可泛化到非自身引导产生的轨迹。
- **校准不足以替代演化**：等渗校准仅将源 MAE 从 0.1576 降至 0.1488，远不及演化裁判 0.1168。
- **演化代码内含奖励预测规则**：确定性演化裁判（无 LLM 评估）源 MAE 0.1153，甚至优于完整裁判，说明源演化中涌现出独立的数值打分通路。
- **选择质量**：演化裁判在两种候选生成条件下均实现**零最终 regret**；固定 rubric 裁判平均 40 轮中约 17–18 轮出现正 regret，最大 regret 从 0.2538 降至 0.0185。
- **增益不能仅靠"更好的最终选择"解释**：若在固定 rubric 生成的候选中做完美选择，均值仅从 0.6965 升至约 0.7046，仍远低于 0.7797，只能弥补约 **9.7%** 的差距——大部分收益来自**搜索过程中生成的不同程序**。
- **组件贡献
