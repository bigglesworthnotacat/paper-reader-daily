## 摘要
自演化智能体通过复用过去经验来改进未来行为，这些经验通常以全局提示、记忆或反思的形式存在。然而，这些机制很少控制经验在何处生效。在长程工具使用工作流中，同一条经验可能纠正一个决策，却干扰另一个决策，这使经验复用成为一个局部控制问题，而不仅仅是记忆问题。我们提出 EvoCUE（Evolution through Control Updates from Evidence，基于证据的控制更新演化），一个从已完成的智能体执行中学习可复用控制程序更新的框架。EvoCUE 将智能体表示为一个显式的状态机控制器，其节点执行模型或工具调用，其边定义控制接下来传递到何处。这使得工作流可以在精确的位置被编辑，因此每个学到的更新都能指定添加什么、在何处起作用以及何时适用。EvoCUE 利用残差目标和观测到的执行轨迹，从已完成的轨迹中提出局部化的指令或技能编辑。每个候选编辑都会在其将要起作用的位置被评估：从同一检查点恢复父控制器和编辑后的控制器，并比较它们的最终结果。被接受的编辑会与适用性规则一起编译，在留出任务上得到确认，并被后续执行继承。我们在长程工具使用环境中评估 EvoCUE，这些环境要求学到的约定必须到达正确的执行步骤。在一个没有基准特定引导指令的最小 AppWorld 控制器上，EvoCUE 学到了缺失的任务完成约定，并在 Test-Normal 和 Test-Challenge 上大幅提升了成功率。在 PAST-Bench 办公工作流中，EvoCUE 将组织要求从先前回合迁移到后续任务，提升了任务执行质量。这些结果表明，自演化智能体应将经验置于控制流内部，而不仅仅将其存储为文本。

## Abstract
Self-evolving agents improve future behavior by reusing past experience, typically as global prompts, memories, or reflections. Yet these mechanisms rarely control where experience takes effect. In long tool-use workflows, the same lesson may correct one decision but distract another, making experience reuse a problem of localized control rather than memory alone. We introduce EvoCUE (Evolution through Control Updates from Evidence), a framework for learning reusable control-program updates from completed agent executions. EvoCUE represents the agent as an explicit state-machine controller, whose nodes perform model or tool calls and whose edges define where control passes next. This makes the workflow editable at precise locations, so each learned update can specify what to add, where it acts, and when it applies. From completed trajectories, EvoCUE uses residual goals and observed execution traces to propose localized instruction or skill edits. Each candidate is evaluated at the point where it would act by resuming the parent and edited controllers from the same checkpoint and comparing their final outcomes. Accepted edits are compiled with applicability rules, confirmed on held-out tasks, and inherited by later executions. We evaluate EvoCUE on long tool-use environments where learned conventions must reach the right execution step. From a minimal AppWorld controller without benchmark-specific onboarding instructions, EvoCUE learns the missing task-completion convention and substantially improves success on Test-Normal and Test-Challenge. On PAST-Bench office workflows, EvoCUE transfers organizational requirements from prior episodes to later tasks, improving task-execution quality. These results show that self-evolving agents should place experience inside the control flow, rather than only store it as text.

- **背景**：自演化智能体（self-evolving agents）希望通过复用过去执行经验来改进未来行为，同时保持底层模型固定。现有做法通常把经验存为**全局提示、记忆、反思或技能库**（Reflexion、ExpeL、AWM、ACE、Voyager 等）。
- **核心痛点一：经验"在何处生效"未被控制**。在长程工具使用流程中，同一条经验可能纠正某个决策、却干扰另一个决策。论文用订机票的例子说明："付费前需先获批"这条经验只有到达"付款决策"这一步才起作用；若只在任务开头给出，往往被遗忘。
- **核心痛点二：难以测量局部编辑是否有益**。局部编辑会影响其后大量动作，而反馈只在任务结束时给出；从头重跑任务会把编辑效果与前面执行的无关波动混在一起。
- **关键证据**：在 AppWorld 上，同一条指令在第一步给出只能解决 16 个开发任务中的 5 个，而在后续步骤可用时能解决 14 个。
- **研究定位**：现有提示/程序优化（APE、OPRO、DSPy、TextGrad、GEPA）与工作流搜索（ADAS、AFlow、MaAS）主要决定"保留什么内容"，作用位置由设计固定，且候选通常以整任务重跑评估。本文主张：**经验复用本质是一个局部控制问题，而非单纯的记忆问题**，应把经验放进控制流内部。

## 2. 方法论：EvoCUE 框架

### 2.1 核心思想

- 把智能体表示为**显式状态机控制器** $C = (G, \pi, \Omega)$：
  - 图 $G$ 的**节点**执行模型调用或工具调用，**边**决定控制传递方向，边上可携带指令文本；
  - 路由策略 $\pi$ 从可观测执行状态选择下一条边；
  - 技能库 $\Omega$ 保存可执行技能（类似 RL 中的 option：有启动条件、一次执行若干操作、返回成功/失败）。
- 由于边是显式的，**同一节点可以在不同位置被进入**，因此"经验挂在哪条边"就决定了它何时生效。以 AppWorld 控制器为例：`prepare`（生成动作）既从 `start` 进入一次，也从 `route` 反复进入；挂在首次进入的指令只被看见一次，挂在循环进入的指令则在后续每一步都可见。
- 学习不修改模型、工具与观测接口，只学习控制程序更新。

### 2.2 残差目标（residual goals）定位失败步骤

- 一次已完成任务提供公开指令、动作、观测与最终标量分数（私有评分细节、参考答案、隐藏测试永不进入学习器）。
- **残差目标** = 指令中尚未在公开历史中被证明满足的要求；由语言模型根据指令与轨迹逐条标记"已观测/缺失"，并给出支撑观测的引用。
- 例如"导出前需获批"若历史中没有批准记录，即为残差目标，从而把失败定位到可编辑位置。
- 若所有要求都被标记为已满足但得分为 0，则失败出在"任务如何被完成"，这正是 AppWorld 的情形。

### 2.3 局部编辑的提出（Proposal）

- 提议者（LLM）基于任务索引（结果、残差目标、历史试验记录）提出候选编辑 $\delta$，必须显式指定四要素：
  - **内容**（指令文本或可执行技能）、**位置**（作用的边）、**作用域**（当前调用 / 技能调用 / 下一个动作）、**预期效果**。
- 两类编辑：
  - **指令编辑**：在指定边的目标节点进入时注入文本；
  - **结构编辑**：在图的某条边插入 1–6 个原语操作组成的可执行技能，含前向分支与显式成功/失败返回。
- 适用性规则会改变路由策略 $\pi$。执行前会做合法性检查（节点存在、与待执行动作状态兼容、算子输入有效）；提议者还会收到关于"每个算子读写什么、附件能到达哪些入口"的控制器反馈（描述控制器而非任务）。
- 被引用任务只用于采样检查点，**任务 ID 永远不会成为运行时路由条件**。

### 2.4 在"起作用的位置"测试：配对试验（paired trials）

- 对每个候选编辑，从提议所引用任务及其相关失败的父轨迹中采样检查点（在观测候选结果之前完成采样）。
- **配对试验**：在编辑位置即将被到达之前的检查点 $j$，恢复环境状态、公开历史、控制器状态与剩余预算，然后分别用父程序 $C$ 与编辑后程序 $C \oplus \delta$ 执行到任务结束，得到
  $$d_{tj}(\delta; C) = Y_{tj}(C \oplus \delta) - Y_{tj}(C)$$
  其中 $Y$ 为最终任务分数。
- 由于两次执行共享前缀，比较排除了编辑生效之前的一切变化；$d_{tj}$ 度量
