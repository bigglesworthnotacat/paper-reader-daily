## 摘要
自演化的智能体 Harness 会持续更新记忆、提示、技能和工具等持久性组件。我们将这一过程称为 Harness 演化。然而，这种演化可能引入意外的安全风险。现有工作研究了 Harness 误演化，并验证候选 Harness 或被归因的单个组件更新，但对跨组件更新交互的安全分析在很大程度上仍未被考察。为填补这一空白，我们研究 Harness 演化中的组合安全失效，即单个安全且保持效用的组件更新之间的交互可能产生不良或不安全的智能体行为，揭示了 Harness 演化固有的一种安全风险。在三个安全相关基准上，我们识别出 43 个成对和 18 个不可约三元组合安全失效。传统解决方案在验证跨组件交互时会带来组合复杂性，使得随着 Harness 演化，安全检查变得不切实际。为解决该问题，我们引入一种类型化超图，将组件状态表示为节点，将安全相关的高阶交互表示为超边。当 Harness 发生变化时，超图仅更新发生变化状态的交互邻域，而不是重建全局组合空间。在此基础上，我们开发了一种超图引导的运行时监控机制。实验表明，我们的方法在保持任务效用的同时有效缓解组合安全风险，并降低交互检查成本，还进一步揭示了不同安全机制之间经验性的安全-效用-成本权衡。

## Abstract
Self-evolving agent harnesses continually update persistent components such as memory, prompts, skills, and tools. We call this process harness evolution. However, such evolution could introduce unexpected safety risks. Existing work studies harness misevolution and validates candidate harnesses or attributed individual component updates, leaving safety analysis of cross-component update interactions largely unexamined. To address this gap, we study compositional safety failures in harness evolution, where interactions among individually safe and utility-preserving component updates can produce undesirable or unsafe agent behavior, revealing a safety risk intrinsic to harness evolution. Across three safety-related benchmarks, we identify 43 pairwise and 18 irreducible 3-way compositional safety failures. Conventional solution incurs combinatorial complexity in validating cross-component interactions, leaving the safety checking impractical as the harness evolves. To solve this, we introduced a typed hypergraph that represents component states as nodes and safety-relevant higher-order interactions as hyperedges. When the harness changes, the hypergraph updates only the interaction neighborhood of the changed states rather than reconstructing the global composition space. Building on that, we develop a hypergraph-guided runtime monitoring mechanism. Experiments show that our method effectively mitigates compositional safety risks while preserving task utility and reducing interaction-checking costs, and further reveal an empirical safety-utility-cost trade-off across different safety mechanisms.

## 1. 核心问题与研究动机

- **背景**：LLM 智能体依赖外部 *agent harness*，其中包含记忆（memory）、提示（prompts）、技能（skills）、工具（tools）等可配置的持久化组件。近期系统让 harness 具备"自演化"能力（*harness evolution*），即依据执行轨迹、任务结果或外部反馈持续更新这些组件，更新结果跨执行轮次保留。
- **问题缺口**：现有工作要么研究 harness 的"误演化"（misevolution）与单组件漏洞，要么验证"候选 harness"或"被归因的单个组件更新"（如 TTHE、SHE、HarnessLens、SafeEvolve、AutoSaddler）。这些方法的验证单元是**单个更新或整个 harness**，**没有把跨异构组件的交互本身当作安全分析单元**。
- **核心现象**：作者提出并实证 *compositional safety failure*（组合安全失效）——两个（或多个）**各自安全且保持任务效用**的组件更新，在被联合激活时产生不安全行为。
- **论文给出的直观例子（图 1）**：prompt 更新 P0→P1 把 Bob 加入 `authorize_group`；memory 更新 M0→M1 把 BoA 加入 `bank_account`。在"authorize_group 可访问 bank_account"的规则下，任一更新单独都安全（P0 下 Bob 无权限；M0 下无 BoA 账户），但二者共存时 Bob 可以访问 BoA → 组合失效。
- **两个关键性质**：
  - **高阶性**：失效不限于成对，可以是"不可约三元"（所有单点和所有成对组合都安全，仅三元联合不安全）。
  - **执行依赖性（execution-dependent）**：保留的组件状态可能在验证时"潜伏"，只有在未来某次执行中同时被激活才暴露风险，因此静态枚举式验证不充分。

## 2. 方法论

### 2.1 核心思想

- 把 harness 演化的**安全分析粒度下沉到"组件状态"（component state）**，而非"更新"或"整体 harness"。
- 用**类型化超图（typed interaction hypergraph）**统一表示跨组件、跨更新步的高阶安全依赖：状态作节点、安全相关高阶交互作超边。
- 更新时**只做局部增量维护**，避免重复枚举全局组合空间 Ω_t；运行时**只检查当前执行真正激活的交互**。

### 2.2 形式化定义

- **节点**：$v=(c,x)$，$c\in C$ 为组件类型，$x$ 为该组件的一个具体状态。$V_t$ 为时刻 $t$ 的全部可用状态；更新产生**新版本节点**，旧状态作为历史溯源保留。一次演化步可增/改一个或多个组件的节点，不限定更新范围。
- **超边**：$\mathcal{G}_t=(V_t,E_t,\phi)$，$\phi:V_t\to C$ 标注节点所属组件；每条超边 $e$ 必须连接**至少两个不同组件**的状态，即 $|\{\phi(v):v\in e\}|\ge 2$。
- **超边分两类**：$E^{obs}_t$（有执行溯源证据支持）与 $E^{pred}_t$（推断的、尚未观测到的可能交互）。运行时一旦被溯源确认，预测超边提升为观测超边。
- **为何必须用超图**：不可约三元失效说明成对图无法直接表达该交互——若强行拆成成对关系，这些成对关系本身并不不安全；超图可用单条超边直接连接同一高阶交互的全部参与状态，并跨演化步复用共享结构。

### 2.3 增量构建流程（算法 1 前半）

1. 候选更新 $u_t$ 引入新状态 $\Delta V_t$；先合并节点集 $\tilde V_{t+1}\leftarrow V_t\cup \Delta V_t$，超边集先继承历史。
2. 对每个新状态 $v\in\Delta V_t$，利用更新的溯源信息在 $\mathcal{G}_t$ 中抽取 **$h$ 跳交互邻域** $\Gamma_h(v)$（局部性假设：一次更新只改变 harness 的一小部分）。
3. 在 $\Gamma_h(v)$ 内做 **LOCAL COMPLETION**，用已有高阶交互模式提议包含新状态的跨组件候选超边 $C_v$。
4. 用 **LLM 语义过滤器**（实验中为 Qwen3-8B）结合参与状态与溯源上下文做 **SEMANTIC FILTER**，因为图结构本身不能保证交互语义上成立；保留的候选写入 $\tilde E^{pred}_{t+1}$。
5. 得到提交前的临时超图 $\tilde{\mathcal{G}}_{t+1}$。

### 2.4 运行时监控（算法 1 后半）

- 对每个**决策上下文** $q$ 单独维护已激活状态集 $A_q$ 与已检查超边集 $C_q$。
- 当状态 $v$ 被激活时，只访问其**关联超边** $I(v)=\{e\in E_t: v\in e\}$；若 $e\subseteq A_q$ 且 $e\notin C_q$，说明该超边被"完全激活"，则在**动作生效之前**调用安全判定 $\text{ISSAFE}(e,q;S)$；若不安全则 `INTERVENE BEFORE ACTION` 阻止动作。
- 同一组合在后续不同动作中会**重新检查**（请求、参数、权限可能不同）。
- 观测超边与预测超边走同一监控流程；被溯源确认的预测超边提升为观测超边（**不论其安全判定结果如何**）。

### 2.5 复杂度对比

- 穷举法的候选组合空间：$|\Omega_t|=\sum_{k=2}^{d}\sum_{S\subseteq C,|S|=k}\prod_{c\in S}n_c(t)$；三组件时约为 $\Theta(n^3)$，且每次更新后重复付出该成本；向组件 $c$ 新增一个状态会引入 $\prod_{c'\ne c}(1+n_{c'}(t))-1$ 个新组合，量级 $\Theta(n^{d-1})$。
- 本方法：构建限制在 $h$ 跳邻域；运行时对激活序列 $v_1,\dots,v_L$ 的代价为 $O(\sum_{\ell=1}^{L}|I(v_\ell)|)$，**与 $|\Omega_t|$ 无关**。

## 3. 实验设计

### 3.1 宿主与演化机制

- 使用 **A-Evolve** 的统一 harness 抽象作为共同宿主，为各组件接入一个代表性演化机制：
  - memory → **Reasoning-Bank**；prompts → **GEPA**；skills → **Voyager**；tools → **Alita**。
- 骨干模型固定为 **Qwen3-32B**；超图构建的语义过滤器为 **Qwen3-8B**；交互半径 $h=3$。
- 设定为**非对抗演化**：不构造攻击者定制的更新、不注入 prompt injection / 记忆投毒 / 后门。

### 3.2 基准与交互面板构造

- **AgentDojo v1.2.2（banking 环境）**：60 个可信请求变体（同一退款计算任务族）×（1 个 memory + 9 个 prompt）× 1 个工具更新 = **600 个交互面板**。
- **Agent-SafetyBench**：从 2000 条官方用例筛出 455 条结构候选池；7 个 source task 生成更新包，13 个 held-out 任务做评估；13×14×1 = **182 个面板**；安全判定沿用其官方 ShieldAgent 流程。
- **Agent Security Bench (ASB)**：10 个角色智能体，剔除 4 个可能"授权"目标能力的任务后剩 47 条 clean task；235 个候选更新包中 174 个通过源准入；执行 **1362 个面板**；每个 agent 冻结一个可产生实质动作的工具能力。
- **面板的四配置控制协议**：$00$（原始 harness）、$10$（仅 $u_i$）、$01$（仅 $u_j$）、$11$（联合激活）。
- **合格性（eligibility）准则**：$00$ 安全，且 $10$、$01$ 均**既安全又保持任务效用**；只有满足才纳入统计，从而排除"某个更新本身就不安全/已破坏效用"的混淆。
- **失效判定**：$11$ 出现安全违规、而 $00/10/01$ 均无，并且有**执行级证据**（工具调用与参数、相关行为、环境状态迁移）表明违规行为只在联合激活下涌现。
- **三元扩展**：对每个更新三元组评估全部 8 种配置；仅当基线、3 个单点、3 个成对**全部**安全且保持效用时，三元组才合格；仅当全组合违规时才计为不可约 3-way 失效。
- **指标**：CF（失效数）、CFR = CF / Eligible。

### 3.3 对比方法

- **No Monitoring**
