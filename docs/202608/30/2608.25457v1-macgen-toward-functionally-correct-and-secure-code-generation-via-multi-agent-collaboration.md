## 摘要
尽管大型语言模型在生成代码方面能力强大，但其输出常常包含安全漏洞，因此往往无法生成安全的代码。安全代码生成本身就具有挑战性，因为它需要解决一个多目标问题：功能正确性和安全性。现有方法通过注入外部安全知识或使用智能体反馈和迭代细化来应对这一挑战。然而，指南检索通常让生成器将通用建议转化为特定任务的安全实现，而共享对话式的多智能体反馈可能会模糊角色边界，并遭受上下文膨胀的问题。我们提出了MACGen，一个集成了规划、安全分析、代码合成和细化的多智能体框架，以协同优化安全性和功能。规划器构建逐步计划以满足功能需求。安全顾问识别可能的CWE并综合任务特定的指南，随后编码器基于这些工件生成代码，审查器则发布视角分离的反馈。每个智能体仅从上游阶段接收结构化工件，而非共享完整的对话历史，从而强化角色专业化并减少不受控的上下文增长。在CWEval和BaxBench上，MACGen相比直接提示在F&S@1上平均分别提升了19.61和10.57个百分点（pp）。

## Abstract
Despite their strong ability to generate code, large language models often fail to produce secure code, as their outputs frequently contain security vulnerabilities. Secure code generation is inherently challenging because it requires solving a multi-objective problem: functional correctness and security. Existing approaches address this challenge by injecting external security knowledge or by using agentic feedback and iterative refinement. However, guideline retrieval often leaves the generator to translate generic advice into task-specific secure implementations, while shared-dialogue multi-agent feedback can blur role boundaries and suffer from context bloat.   We present MACGen, a multi-agent framework that integrates planning, security analysis, code synthesis and refinement to jointly optimize security and functionality. A planner constructs a step-by-step plan to satisfy functional requirements. A security advisor identifies likely CWEs and synthesizes task-specific guidelines, a coder then generates code grounded in these artifacts, and a reviewer issues perspective-separated feedback. Rather than sharing full dialogue histories, each agent receives only structured artifacts from upstream stages, enforcing role specialization and reducing uncontrolled context growth. On CWEval and BaxBench, MACGen improves F&S@1 over direct prompting by 19.61 and 10.57 percentage points (pp) on average, respectively.

- 大型语言模型（LLM）在代码生成方面能力很强，但生成的代码经常包含安全漏洞，无法同时满足**功能正确性**与**安全性**这两个目标。
- 安全代码生成是一个多目标问题：既要让代码能按需求工作，又要在实现中主动规避 CWE 类型的安全弱点。
- 现有方法主要分两类，但各有不足：
  - **知识注入方法**（如 SecGuide、CodeGuarder、RESCUE）：检索外部安全指南注入上下文。但指南通常是**通用性**的，生成器仍需自行推断如何将通用建议转译为特定任务中可落地、且不破坏功能的实现。
  - **共享对话式多智能体方法**（如 INDICT）：通过多个批评者共享完整对话历史来迭代反馈。但共享对话会引发**角色干扰**——各批评者会看到彼此中间推理，从而偏离自身视角（如功能批评者被安全批评带偏，漏掉逻辑错误）；同时对话历史不断增长会带来上下文膨胀和长上下文性能退化。
- 因此，论文提出核心思路：**必须清晰分离每个阶段需要推理的内容，每个智能体只接收结构化工件，而非全部对话历史**，让角色边界由接口设计强制保证，而非仅靠提示词约束。

## 2. 论文提出的方法论：核心思想、关键技术细节、算法流程

### 核心思想
- 将安全代码生成过程按 SSDLC 原则分解为多阶段角色专用流水线，各智能体之间通过**结构化工件**（artifact-only）而非完整对话历史通信，以保持角色隔离、减少上下文增长，并让安全决策在代码实现之前和实现过程中被充分考虑。

### 系统组成：四个智能体
1. **Planner（规划者）**
   - 生成简明的高层功能计划（step-by-step plan）。
   - 功能：指导编码器实现正确功能，为安全顾问提供任务上下文以识别攻击面。
2. **Security Advisor（安全顾问）**
   - 多阶段流水线，兼顾效率与分析深度：
     - **早期退出检查（early-exit triage）**：基于任务提示和草稿代码判断是否存在攻击面。若无风险（如纯算法任务），则跳过后续检索与分析，节省开销。
     - **标准驱动的 CWE 提取**：分析任务提示和功能计划，生成“cause→effect”CWE 组，并给出 likelihood 分数。
     - **RAG 检索**：基于 CWE 组构造查询，从预构建的标准安全知识库（KB）中检索 top-K 相关指南。
     - **标准驱动指南生成**：将检索到的原始建议综合为任务特定的简明安全指南。
     - **代码驱动指南生成**：进一步检查草稿代码中暴露的不安全模式，补充第二组指南。
     - **合并与验证**：将两组指南合并，并对照功能需求验证是否存在冲突，最终输出与功能兼容的安全指南。
3. **Code Generator（代码生成器）**
   - 使用功能计划生成草稿代码，供安全顾问分析。
   - 在功能计划与安全指南双重约束下生成最终代码。
   - 使用语法检查器进行自我修正，保证可编译。
4. **Reviewer（审查者）**
   - 两个**视角分离**的检查：功能检查和安全检查。
   - 若发现问题，提供针对性反馈给编码器，进入迭代细化循环，直到通过或达到最大迭代次数。

### 知识库构建
- 从权威标准构建，包括：OWASP ASVS、SEI CERT C/C++、OpenSSF Python 安全指南、OWASP Node.js 与 Go 安全实践等。
- 使用 LLM 将原始文档精炼为统一的 WHAT–WHY–HOW–EXAMPLE 模式，降低噪声、便于语义检索。
- 嵌入后建立 FAISS 索引，检索采用余弦相似度 top-K 选择。

### 关键公式
- 检索公式：\( \mathcal{G}^*(q_j) = \arg\max^{(K)}_{g_i \in KB} \text{sim}(E(q_j), E(g_i)) \)，最终候选集为各查询结果的并集。
- Pass@k 指标按标准定义计算。

## 6. 论文的主要结论与发现

- **MACGen 在功能与安全联合指标上全面领先**：

- **MACGen 以最小的功能代价换取最大的安全收益**：平均 Func@1 下降仅 0.56 pp，而安全提升 23.82 pp；相比之下 INDICT 平均功能下降 12.6 pp。
- **对小模型提升更显著**：Qwen3-8B 上 Func@1 提升 10.92 pp，F&S@1 提升 17.65 pp，说明结构化流程可弥补小模型推理能力不足。
- **跨语言鲁棒性**：CWEval 上 5 种语言均最优，C++ 和 Go 提升幅度较大。
- **artifact-only 接口有效**：相比共享上下文变体，MACGen 在 CWEval 上 GPT-4o-mini 提升 +20.17 pp，在 BaxBench 上 GPT-4o 提升 +8.67 pp，证实减少上下文共享可避免角色干扰。
- **成本可控**：MACGen 的 token 消耗仅为 INDICT 的 16%，成本低 $3.77。
- **安全顾问各环节均有贡献**：移除任何子环节都会导致 F&S@1 下降。
- **通用能力不退化**：在 HumanEval/HumanEval+ 上表现与直接提示相当，且多数模型有提升。
- **剩余失败模式**：主要集中在需要运行时API语义的知识（如 CWE-327 密码学库细节）、缓解充分性验证不足（如 CWE-347 无精确算法固定），以及 oracle 匹配问题等。

## 7. 优点

- **问题定位准确**：指出现有知识检索与共享对话方法的根本缺陷（通用指南难落地、共享上下文引起角色干扰）。
- **方法设计新颖**：将 SSDLC 思想引入多智能体 LLM 代码生成，以“结构化工件接口”代替共享对话，从系统架构级别强制角色隔离。
- **安全知识库构建合理**：基于权威标准，并使用统一 WHAT-WHY-HOW-EXAMPLE 模式精炼，保证检索质量。
- **效率优化**：early-exit 机制避免对简单任务进行无谓检索，token 成本远低于共享对话方法。
- **实验系统全面**：多模型、多语言、多基准、多类型消融以及成本/延迟分析，证据链完整。
- **分析细致**：包含 CWE 失败模式分析、早期退出误判分析、语言特有 oracle 问题讨论，深入理解局限而不是简单报告结果。
- **可复现性强**：给出完整提示词、知识库构建流程与评估日志声称可获取。

## 8. 不足与局限

- **效率仍有限**：尽管比共享对话方法成本低，但相比单次直接生成仍是多重推理开销；论文将其视为安全保证的必要代价。
- **评估粒度有限**：遵循各基准预定义的安全范围（目标 CWE），而实际中安全边界可能更模糊；没有考虑分级加固水平或不同安全假设下的功能测试参数化。
- **oracle 刚性导致误判**：部分代码在语义上正确且安全（如用 bcrypt 代替 argon2、URL 尾斜杠差异），但被基准判定为失败，说明评估工具的灵活性不足。
- **缺乏静态/动态外部验证工具集成**：论文仅依赖智能体推理（加 RAG），未结合静态分析器或自动渗透测试，安全保证上限受限。
- **不同基线公平性风险**：各基线使用各自论文默认配置，在 CWEval 或 BaxBench 上未必是所有方法的最佳配置；尤其 SecGuide 的功能下降明显，可能因 RCI 流程与目标任务不匹配。
- **对 JavaScript 等语言的优势较弱**：部分归因于 oracle 刚性，但也说明框架在语言特异性和标准库适配方面仍有改进空间。
- **推理能力依赖模型**：CWE 提取与安全指南生成依赖 LLM 自身推理质量，小模型上虽然提升大但绝对 F&S@1 仍偏低。
- **尚未验证大规模真实项目场景**：BaxBench 是后端应用，但仅局限于框架模板以内，复杂企业级代码库中的应用效果未评估。
