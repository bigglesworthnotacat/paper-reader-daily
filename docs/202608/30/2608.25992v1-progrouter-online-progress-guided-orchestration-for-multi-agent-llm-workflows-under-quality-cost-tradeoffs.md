## 摘要
多智能体大语言模型（LLM）工作流已成为通过专业化LLM智能体之间的协作推理来解决复杂、开放任务的有力范式，但由于重复的LLM调用和长时程上下文累积，它们会产生大量的运营成本。现有的级联路由方法做的是单次、查询级别的决策，无法适应多步骤工作流的动态、状态依赖特性——在这些工作流中，每个步骤选择正确的LLM取决于不断变化的任务进度、剩余任务难度和成本效益要求。我们提出ProgRouter，一种在线进度引导路由框架，它在工作流步骤间自适应地选择LLM智能体，以在遵守时间和成本预算的同时保持任务解决质量。ProgRouter引入了一个多视角任务进度评分器，将粗略的工作流结果状态与子任务完成度、进度趋势和工作流状态质量的细粒度信号相结合。然后，一个双路径任务进度预测器和一个自适应元门控机制估计每个候选路由LLM的进度增益。ProgRouter做出在线的逐步路由决策，平衡进度增益、任务时间预算和长期运营成本效率。在HumanEval Plus、MBPP、MATH-500和ASQA上的实验，涵盖了智能体代码生成、数学推理和检索增强的长文本问答，表明ProgRouter相对于关键基线降低了运营成本，同时保持了强大的任务解决性能。

## Abstract
Multi-agent large language model (LLM) workflows have emerged as a powerful paradigm for solving complex, open-ended tasks through collaborative reasoning among specialized LLM agents, but they incur substantial operating costs due to repeated LLM invocations and long-horizon context accumulation. Existing cascade routing methods make one-shot, query-level decisions and cannot adapt to the dynamic, state-dependent nature of multi-step workflows, in which the right LLM at each step depends on evolving task progress, remaining task difficulty, and cost-efficiency requirements. We present ProgRouter, an online progress-guided routing framework that adaptively selects LLM agents across workflow steps to preserve task-solving quality while adhering to time and cost budgets. ProgRouter introduces a multi-view task progress scorer that combines coarse workflow outcome regimes with fine-grained signals on subtask completion, progress trends, and workflow state quality. Then, a dual-path task progress predictor and an adaptive meta-gating mechanism estimate the progress gain for each candidate routed LLM. ProgRouter makes online step-wise routing decisions that balance progress gain, task time budgets, and long-term operating cost efficiency. Experiments on HumanEval Plus, MBPP, MATH-500, and ASQA, spanning agentic code generation, mathematical reasoning, and retrieval-augmented long-form question answering, demonstrate that ProgRouter reduces the operating cost relative to key baselines while maintaining strong task-solving performance.

## 1. 核心问题与整体含义（研究动机与背景）

- **研究背景**：多智能体大语言模型（Multi-agent LLM）工作流通过多个专业化LLM智能体协作完成复杂、开放式的任务（如代码生成、数学推理、检索增强问答），已成为一种强大的任务求解范式。然而，这类工作流需要反复调用LLM，且随着长时程上下文累积，会产生极高的令牌消耗、算力占用、能量消耗和延迟，导致运营成本显著上升。
- **现有方法的不足**：传统级联路由（cascade routing）方法，如 RouteLLM、CASCADIA 等，通常只做**一次性、查询级别的路由决策**，即在任务开始前或单一查询层面选择LLM。但多智能体工作流是**动态、状态依赖、多步骤**的，每一步应该选择哪个LLM取决于当前任务进度、剩余任务难度、预算消耗等，这些信息在任务开始前无法获知。因此，单次路由决策无法适配多步工作流的实时需求。
- **核心研究问题**：如何在多智能体LLM工作流中，**在线地、逐步地**选择路由LLM智能体，在满足时间与运营成本预算的前提下，最大化任务解决质量？
- **关键挑战**：
  - 工作流是开放性和有状态的，需要根据实时状态判断“当前该用哪个智能体”，传统基于静态基准或离线偏好数据的路由方法不适用。
  - 中间工作流状态往往噪声大、部分可观测，难以准确估计已完成的进度和剩余难度。错误估计会导致不必要的强模型调用（浪费预算）或弱模型过度使用（质量不可逆下降）。
  - 未来步骤数量和子任务难度未知，贪心策略可能过早耗尽预算，保守策略则无法充分利用强模型，需要在线优化算法平衡进度与长期成本。

## 2. 提出的方法论

**总体思想**：ProgRouter 是一个**在线进度引导的路由编排框架**，核心在于实时估计当前工作流的任务进度，并**预测每个候选LLM执行下一步后的边际进度增益**，在每一步动态选择最合适的LLM，以平衡任务质量、时间预算和长期运营成本。

### 2.1 控制问题建模
- 将多智能体LLM工作流建模为：`w = {C, R, M}`，其中：
  - `C`：协调者LLM智能体（coordinator），负责子任务规划、智能体调度和工作流自适应；
  - `R`：预定义的工人智能体角色集合（如分析者、编码者）；
  - `M`：候选LLM集合（模型动物园），每个角色 `r ∈ R` 有可用的LLM子集 `M_r`。
- 工作流按步骤执行，每一步 `t` 选择角色 `r_t` 和LLM `m_t`，状态更新为 `s_{t+1}`，最终得到结果 `P(w) ∈ {0,1}`。
- 优化目标：在所有任务上最大化成功率为 `(1/W) Σ P(w)`，同时满足：
  - 每个任务的时间预算 `Γ_w` 和运营成本预算 `E_w`；
  - 系统长期平均运营成本约束 `eE`（如平均能耗上限）。
- 该问题被形式化为在线约束优化问题。

### 2.2 多视图任务进度评分器（Multi-View Task Progress Scorer）
为了实时评估工作流状态 `s_t`，ProgRouter 从四个互补视角计算归一化进度分数 `g(s_t) ∈ [0,1]`：

- **整体结果视图**：将当前状态映射到四个粗粒度状态：`invalid`（无效）、`recoverable`（可恢复）、`partial success`（部分成功）、`complete`（完成），生成基础分数 `b(c_t)`；
- **子任务完成度视图**：计算用户子任务和约束的满足比例，得到子得分 `r_t`；
- **进度趋势视图**：分析最近几步的进度变化（改进、停滞、退化），得到 `d_t`；
- **状态质量视图**：评估最新状态转换的结构与语义有效性（如状态嵌入相似性、新解决子任务等），得到 `e_t`。

最终进度分通过加权聚合：  
`g(s_t) = b(c_t) + α_{c_t}·r_t + β_{c_t}·d_t + γ_{c_t}·e_t`

该评分器作为**轻量级域适配器**，将可观察的工作流信号转换为统一进度表示，便于在异构任务域中复用下游路由算法。

### 2.3 双路径任务进度预测器（Dual-Path Task Progress Predictor）
- 输入：当前状态 `s_t` 和候选LLM `m_t`。
- 输出：预测的进度增益 `ŷ_t = P_Θ(s_t, m_t)`。
- **结构化路径**：从显式特征（进度分数、子任务状态、历史路由等）出发，使用树模型（随机森林/XGBoost）预测增益 `ŷ_t^str`。
- **语义路径**：由协调者生成工作流状态摘要，经轻量级句子嵌入（如MiniLM）得到语义向量，再用树模型预测 `ŷ_t^sem`。
- **自适应元门控**：通过另一个XGBoost模型，根据当前工作流状态动态融合两个路径的估计值，得到最终预测：  
  `ŷ_t = P_meta(ŷ_t^str, ŷ_t^sem)`

这样可以在显式信号可靠时更多依赖结构化路径，在状态隐含或信号稀疏时更多依赖语义路径。

### 2.4 在线决策算法（Online Decision Making）
基于Lyapunov漂移加惩罚框架，通过**虚拟队列**跟踪长期平均成本约束违规：

- 虚拟队列更新：`Q_{w+1} = max{0, Q_w + Σ_{t=1}^{T_w} E(m_t) - eE}`，其中 `Q_1 = 0`。
- 目标转化为最大化：`V·P(w) - Q_w·(Σ E(m_t) - eE)`。

**每一步的路由决策**：

- 进度差距感知价值：`eP(m_t, s_t) = V·(1 - g(s_t))·ŷ_t(m_t)`，其中 `(1 - g(s_t))` 表示任务距离完成越远，同等进度增益价值越高，从而在进度缺口大时倾向于使用强模型。
- 预算感知成本惩罚：定义时间惩罚系数 `c_Γ_t` 和运营成本惩罚系数 `c_E_t`，它们随预算消耗比例指数增长，鼓励保留预算空间。
- 最终路由得分：  
  `score(m_t) = eP(m_t) - Q_w·(E(m_t) - eE) - c_Γ_t·Γ(m_t) - c_E_t·E(m_t)`

每一步选择得分最高的 `m_t^* = argmax score(m_t)`。

**在线学习**：通过ε-greedy探索，随机选择LLM收集真实进度变化样本 `y_t = g(s_{t+1}) - g(s_t)`，存入训练缓冲区，周期性更新预测器；随着样本累积，ε逐渐衰减，从探索转向利用。

## 6. 主要结论与发现

- **固定单模型策略普遍不满足长期成本约束**：无论一直用小模型还是大模型，均违反 `eE` 能耗约束。小模型因能力不足导致反复调度、累积能耗高；大模型单次调用能耗过高（如Gemma 4 31B在MATH-500上消耗26276J）。
- **ProgRouter在满足预算的方法中取得最佳质量-成本权衡**：
  - HumanEval Plus：通过率93.0%（最高，超过MasRouter 2.1%、CASCADIA 8.2%），能耗4796J（在预算4800J内），时间13.7s。
  - MBPP：通过率79.4%（最高），能耗3376J（最低），时间10.3s（最短），全面优于所有baseline。
  - MATH-500：能耗6112J（最低）、时间19.0s（最短），通过率84.3%，略低于CASCADIA的87.8%，但能耗大幅降低。
  - ASQA：引用精度92.1%（所有方法中最高），能耗18373J（在19000J预算内），超过MasRouter和CASCADIA 2.3个百分点。
- **现有自适应路由方法存在一致失败模式**：
  - Educated Guessing 依赖历史强模型，不感知任务进度，在MATH-500上违反预算；
  - CASCADIA 反应式升级造成不必要的小模型调用，在HumanEval Plus上通过率偏低；
  - MasRouter 一次性路由不能适应动态状态，在MATH-500上能耗超标、MBPP上通过率低。
- **路由分布特征**：ProgRouter 将大部分调用分配给高效小模型（如HumanEval Plus中84.3%用Qwen2.5-Coder 0.5B），仅在预测到显著进度增益时调用大模型，体现了“进度-差距”感知的路由行为。

- **双路径预测器互补性**：结构化路径与语义路径各自捕捉不同特征，通过元门控动态融合，预测更准确（消融证实）。
- **实验充分且测量可靠**：能耗基于真实GPU功率测量；覆盖多种任务类型；包含丰富的baselines和消融；采用统一评估协议。
- **在线学习无需离线数据**：通过ε-greedy探索和在线更新，从冷启动逐步优化，无需预训练路由模型。
- **写作清晰**：公式推导、符号定义、实现细节和附录齐全，可复现性强。

## 8. 不足与局限

- **任务覆盖有限**：仅覆盖代码生成、数学推理和检索增强问答，未验证网页导航、工具调用、多轮对话等更复杂的智能体场景，泛化性有待实证。
- **任务规模较小**：MBPP、MATH-500和ASQA使用随机采样子集（200/200/100），在更大测试集上的表现未知。
- **进度评分器需要人工设计域适配**：多视图评分器中的状态划分、子任务识别等需要针对新任务进行手动定义，虽然下游算法可迁移，但进度表示并非端到端自动学习，限制了完全自动化应用。
- **在线学习依赖探索**：预测器冷启动阶段依靠ε-greedy探索，需要足够的任务流来稳定；在任务流很短或任务极少时，性能可能不如离线训练的方法。
- **成本约束仅考虑GPU能耗**：CPU、内存、存储、网络等能耗未纳入，实际数据中心总能耗可能更高。
- **主结果基于稳定后的策略**：探索期间的路由性能可能波动，文章未报告冷启动阶段的具体表现，可能低估了真实应用中的初期成本/质量影响。
- **模型种类和硬件受限**：所有实验在单机工作站上完成，模型均为开源系列，未验证在云端分布式推理、更大模型池或闭源API路由中的效果。
- **未讨论隐私与安全**：虽然伦理部分提到工作流状态可能存储用户信息，但未深入探讨在线学习过程中使用这些状态带来的隐私风险。
