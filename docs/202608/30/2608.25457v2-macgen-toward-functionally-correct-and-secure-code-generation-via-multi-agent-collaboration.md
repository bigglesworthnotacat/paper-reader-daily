## 摘要
尽管大型语言模型在生成代码方面能力强大，但它们常常无法生成安全的代码，因为其输出经常包含安全漏洞。安全代码生成本质上具有挑战性，因为它需要解决一个多目标问题：功能正确性与安全性。现有方法通过注入外部安全知识或利用智能体反馈和迭代优化来应对这一挑战。然而，指南检索往往让生成器将通用建议转化为特定任务的安全实现，而共享对话的多智能体反馈可能模糊角色边界并遭受上下文膨胀问题。我们提出了MACGen，一个多智能体框架，集成规划、安全分析、代码合成与优化，以联合优化安全性与功能性。规划器构建逐步计划以满足功能需求。安全顾问识别可能的CWE并综合任务特定的指南，随后编码器基于这些产物生成代码，评审者发布按视角分离的反馈。每个智能体仅接收来自上游阶段的结构化产物，而非共享完整对话历史，从而强化角色专业化并减少不受控制的上下文增长。在CWEval和BaxBench上，MACGen相比直接提示在F&S@1上平均分别提高了19.61和10.57个百分点。

## Abstract
Despite their strong ability to generate code, large language models often fail to produce secure code, as their outputs frequently contain security vulnerabilities. Secure code generation is inherently challenging because it requires solving a multi-objective problem: functional correctness and security. Existing approaches address this challenge by injecting external security knowledge or by using agentic feedback and iterative refinement. However, guideline retrieval often leaves the generator to translate generic advice into task-specific secure implementations, while shared-dialogue multi-agent feedback can blur role boundaries and suffer from context bloat.   We present MACGen, a multi-agent framework that integrates planning, security analysis, code synthesis and refinement to jointly optimize security and functionality. A planner constructs a step-by-step plan to satisfy functional requirements. A security advisor identifies likely CWEs and synthesizes task-specific guidelines, a coder then generates code grounded in these artifacts, and a reviewer issues perspective-separated feedback. Rather than sharing full dialogue histories, each agent receives only structured artifacts from upstream stages, enforcing role specialization and reducing uncontrolled context growth. On CWEval and BaxBench, MACGen improves F&S@1 over direct prompting by 19.61 and 10.57 percentage points (pp) on average, respectively.

### 1. 核心问题与整体含义

- **研究动机**：大型语言模型（LLM）在代码生成方面能力突出，但生成的代码常包含安全漏洞，存在显著的安全风险。实证研究表明，LLM生成代码中普遍存在MITRE CWE Top-25中列出的多种弱点。
- **核心挑战**：安全代码生成本质上是多目标优化问题——需要在保证**功能正确性**的同时实现**安全性**。安全措施（如输入验证、安全API选择、权限检查）必须在实现内部完成，且不能破坏预期行为，这增加了任务的复杂度。
- **现有方法的不足**：
  - **知识注入方法**（如SecGuide、CodeGuarder、RESCUE）：检索的指南本质上是通用的，缺乏任务特定上下文的感知（如变量名、函数签名、控制流），生成器仍需自行判断如何将泛化建议应用于具体任务。
  - **共享对话式多智能体方法**（如INDICT）：评审者可能观察到彼此的中间推理，导致**角色干扰**，即各评审者逐渐偏离职责视角或产生重叠反馈；同时共享完整对话历史导致**上下文膨胀**，带来高token成本和长上下文性能退化。
- **核心洞察**：有效的安全代码生成不仅需要更多知识或更多反馈，更需要**清晰分离各阶段需要推理的内容**。每个阶段应只接收所需信息，并以紧凑产物传递给下一阶段，使角色边界由接口而非提示词强制实现。

### 2. 方法论

**核心思想**：受安全软件开发生命周期（SSDLC）启发，将安全代码生成分解为规划、安全分析、合成、精炼四个阶段，每个阶段由独立智能体处理，通过**仅产物（artifact-only）接口**传递信息。

**总体流程**（四个角色智能体）：
1. **规划器（Planner）**：根据任务提示生成逐步功能规划，既指导后续代码生成，也为安全顾问提供任务特定上下文以精确识别攻击面。
2. **安全顾问（Security Advisor）**：多阶段流水线，兼顾推理效率与分析深度：
   - **早期退出分诊**：检查任务提示和草稿代码，若无攻击面（如纯粹算法任务）则提前退出，节省开销；
   - **CWE提取**：分析任务和功能规划，识别潜在安全风险并映射为CWE组（因果CWE对）；
   - **标准驱动指南生成**：基于CWE组构建查询，从预构建的**标准驱动安全知识库（KB）**中RAG检索相关实践，生成第一批指南；
   - **代码驱动指南生成**：检查草稿代码中LLM典型不安全代码模式，生成第二批轻量、代码可验证的指南；
   - **验证合并**：合并两组指南并与功能需求交叉验证，消除冲突，确保安全与功能兼容。
3. **编码器（Code Generator）**：承担双重职责——先生成草稿代码供分析，再基于功能规划和最终安全指南生成安全可执行代码，并做语法自检。
4. **评审者（Reviewer）**：进行**视角分离**的结构化评审（功能评审与安全评审独立执行），提供针对性反馈循环至编码器直到通过或达到最大迭代次数。

**关键技术细节**：
- **基于标准的安全知识库**：从CERT和OWASP等权威标准构建，将原始文本通过LLM归一化为WHAT–WHY–HOW–EXAMPLE四字段紧凑结构，再向量化存储于FAISS索引。
- **检索公式**：对每个查询q_j，按余弦相似度取top-K指南：G*(q_j) = arg max_K sim(E(q_j), E(g_i))，最终候选集为各查询结果并集。
- **artifact-only接口**：每个智能体仅接收上游的结构化产物（功能规划、安全指南、代码），而非完整对话历史，从根本上避免角色干扰和上下文膨胀。

### 7. 优点

- **SSDLC原则的系统性应用**：将安全代码生成与业界公认的安全开发实践对齐，逻辑自洽。
- **artifact-only接口设计**：通过系统架构而非提示词来确保角色分工，从根本上抑制了多智能体的角色干扰和上下文膨胀问题。
- **双重指南生成**：标准驱动（自上而下规范）+代码驱动（自下而上检测实际不安全模式）的互补机制覆盖更全面。
- **早期退出分诊**：在不牺牲安全性的前提下有效节省计算成本（GPT-4o早期退出率100%且未安全率仅6.7%/1.7%）。
- **知识库质量验证**：对KB归一化做了人工质量评估（语义保真度和幻觉率），增加了KB设计的可信度。
- **广泛的实验验证**：涵盖6个LLM、8种以上语言、4个基准（含补充），模型能力从8B到70B以上，验证了跨模型泛化能力。

### 8. 不足与局限

- **推理效率开销**：相比单次生成方法，多智能体架构增加了推理成本和延迟（每任务$0.91和28.34秒），虽然做了优化但仍是实际部署的考量因素。
- **评价粒度粗糙**：安全范围与过度工程化的边界模糊——某些合理安全实践（如使用bcrypt替换不安全的加密原语、URL尾斜杠差异）可能被基准判定为功能失败，反映出现有基准的安全/功能权衡评估不够精细。
- **推理受限**：MACGen不依赖静态分析或渗透测试等外部验证工具，仅靠LLM推理能力，遇到需要运行时API语义知识（如密码API内部修改IV缓冲区、幻觉库接口）的情况仍会失败。
- **对CWE的语义充分性验证不足**：代理可能识别需要防护但未验证防护的充分性（如CWE-347算法族检查与精确算法固定的区分），导致残留漏洞。
- **JavaScript提升相对较小**：部分由于基准评估的刚性（仅接受特定库或精确字符串匹配），但也反映语言特定挑战。
- **知识库依赖与更新**：知识库依赖CERT、OWASP等来源，虽提供了开源构建流水线但需持续维护；某些语言缺少专属安全标准时仅能依赖通用语料。
- **早期退出分诊的模型敏感性**：小模型（GPT-4o-mini和Qwen3-8B）在早期退出样本上的未安全率较高（23.1%和13.3%），对小模型的误判风险偏高。
