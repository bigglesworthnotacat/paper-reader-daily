## 摘要
使用工具的AI代理将委托任务转化为提供方效果，然而授权往往在受理时即告终止，而提供方状态、交付、重试和恢复却在不断演变。请求可能在提交前发生变化，或者响应丢失可能导致重发操作根据一次批准产生第二次效果。我们提出AID-Guard，一种有状态的授权到效果闭合协议。它在提交时重新验证已批准的请求和提供方状态，在歧义情况下保留一个预留，并且仅在出现终端结果或通过交付围栏认证无效果后，才允许释放或一个后续操作。对于受支持的提供方合约，一个预留可在重试和恢复过程中至多产生一个效果。据我们所知，这是首个在单一生命周期内统一这些控制措施并经过评估的代理授权协议。我们实现了一个Python/SQLite原型。在一个声明的回环MCP域中，13次实时变更未导致未授权的提供方效果，三个并发历史可线性化，证据包支持公开验证和重放。所有210次Stripe提供方合约试验均与预先声明的结果匹配。在Stripe和Resend中，40个终止-后继调度、30个重叠竞争和10个崩溃恢复调度均完成且没有重复效果。在完全提议者失陷下，AID-Guard阻止了44/44的攻击，并接纳了44/44匹配的合法提议。其严格的精确清单配置将良性效用降低了35.4至43.8个百分点；类型化边界恢复了9-10个完成，未观察到不安全的效果。一项组合研究阻止了20/20的受理后生命周期攻击，并保留了8/8的有效或精确重试执行。结果支持在所评估的效果路径清单、提供方合约和故障调度下进行授权到效果的绑定。

## Abstract
Tool-using AI agents turn delegated tasks into provider effects, yet authorization often ends at admission while provider state, delivery, retry, and recovery evolve. A request may change before commit, or response loss may cause a replacement to create a second effect from one approval. We present AID-Guard, a stateful authorization-to-effect closure protocol. It revalidates the approved request and provider state at commit, retains one reservation under ambiguity, and permits release or one successor only after a terminal result or certified no effect with a delivery fence. For supported provider contracts, one reservation yields at most one effect across retry and recovery. To our knowledge, it is the first evaluated agent-authorization protocol to unify these controls in one lifecycle.   We implement a Python/SQLite prototype. In a declared loopback MCP domain, 13 live mutations caused no unauthorized provider effects, three concurrent histories were linearizable, and evidence bundles supported public verification and replay. All 210 Stripe provider-contract trials matched predeclared outcomes. Across Stripe and Resend, 40 terminalize-successor schedules, 30 overlapping races, and 10 crash-recovery schedules completed without duplicate effects. Under complete proposer compromise, AID-Guard blocked 44/44 attacks and admitted 44/44 matched legitimate proposals. Its strict exact-manifest profile reduced benign utility by 35.4 to 43.8 percentage points; a typed frontier recovered 9-10 completions without observed unsafe effects. A composition study blocked 20/20 post-admission lifecycle attacks and preserved 8/8 valid or exact-retry executions. The results support authorization-to-effect binding under the evaluated effect-path inventory, provider contracts, and failure schedules.

## 论文总结：AID-Guard：委托代理效果的有状态授权

### 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：使用工具的 AI 代理在处理委托任务时，授权检查通常在“准入（admission）”阶段就结束，但请求本身、提供方（provider）状态、交付、重试与恢复过程却在持续演变。这形成了一个 **授权-效果缺口（authorization-effect gap）**：一个批准（approval）最终可能产生多个效果，或产生与批准内容不符的效果。
- **具体场景**：用户批准了一封固定账户、固定收件人、固定附件的报销邮件，但提交前被失陷的代理篡改了收件人、附件或发送账户；即使请求未变，提供方可能已发送邮件但响应丢失，盲重试会发送重复邮件；若声明失败并赋予替换权限，则延迟的请求和替换请求可能同时送达。
- **核心矛盾**：安全决策必须在提供方结果最终确定之前持续有效，而非仅在准入时有效。现有防御（如 Spotlighting、CaMeL、Progent、CXI、CapLease 等）只覆盖了这条路径的一部分，无法同时解决**提交时缺乏重验证、重试/恢复脱离同一授权血缘（reservation lineage）、无效果释放缺少投递围栏、提供方结果缺乏绑定授权方的证据**这四个跨阶段问题。
- **论文定位**：提出 AID-Guard，一个将“提交时绑定、认证无效果恢复、提供方终止前置围栏、单一后继预留转移”统一在一个状态化授权生命周期中的协议，实现 **“一次预留至多一个效果，或经认证的无效果”** 的语义。

### 2. 论文提出的方法论：核心思想、关键技术细节

- **设计原则**（五条）：
  1. 规划器输出仅为观察性数据，不能铸造权威（authority）或选择安全身份；
  2. 每个权威转换都有持久的线性化点；
  3. 每个阶段携带相同的规范化效果标识和不可变请求身份；
  4. 当提供方交付状态不明时，保留配额扣费（quota charge）并阻止自动替换；
  5. 证据只能描述权威，不能创建权威。
- **核心机制**（三条规则）：
  1. **提交时重新验证（D2 commit-time binding）**：提供方提交前重验证“精确批准的请求 + 当前提供方状态”，防止幂等键被用来合法化被替换的请求体；
  2. **歧义保留**：响应丢失期间保留原预留，不得铸造替换权限；
  3. **保守关闭**：只有获得提供方终止结果（terminal result），或接受附带投递围栏（delivery fence）的认证无效果（certified no effect）后，才允许释放预留或转移给一个后继。
- **权威构造阶段（H1–H3）**：
  - **H1（绑定观察）**：将不可信评估层的合格评估结果绑定到当前权威事务，同一评估只能进入一个事务；
  - **H2（签发唯一能力）**：重新验证权威图、消耗一次性步进断言、预留一个配额单位、注册持有者绑定的能力（capability）并提交签发快照；
  - **H3（在效果边界申领）**：在凭据持有边界用签名能力申领，服务器端比较并交换（CAS）改变能力状态与预留状态。已提交的精确重试返回历史快照而非创建新权威。
- **受支持的提供方合约**：
  - **原子合约（Atomic contract）**：申领、提供方变更、能力消耗、配额提交和结果记录在同一事务中完成；
  - **受控幂等合约（Controlled-idempotent contract）**：权威先在持久化“提交尝试（submitted attempt）”和不可变发件箱（outbox）中消耗能力，提供方以幂等键绑定操作范围与请求体，精确重放返回持久化终止结果，冲突复用则失败关闭。
  - 不满足这两种合约的提供方，歧义期间保持“已扣费且不确定”状态，禁止自动重试或替换。
- **保守恢复（Conservative Recovery）**：
  - 响应丢失时，先按注册的对账合约查询提供方终止身份，得到已知结果则恢复原血缘；
  - 否则，释放或替换需要“无效果证书”，其前提是提供方言明的四大要素：稳定的前置交付身份、可线性化且拒绝后续交付的终止化操作、区分已提交效果与已终止无效果状态的权威查询、以及覆盖 AID-Guard 恢复视界的保留期。
  - 接受证书后安装持久投递围栏，一个事务恰好选择一条分支：释放预留，或将同一“已扣费”预留转移给一个新签发的后继（保留原不可变请求、效果、授权、配额血缘和前置链接）。
- **安全属性**：
  - **P1（委托执行授权）**：每个受保护效果必须源自一个活跃的用户批准根、一个合格的非权威评估、一次 H1 绑定、一次 H2 签发和一次 H3 申领，D2 提交精确的不可变请求；
  - **P2（条件效果唯一性）**：每个预留身份（含所有权转移）至多被收取一个提供方原子效果；接受无效果恢复后，直接前置效果为 0，且只能选择“释放”或“唯一后继”之一；
  - **P3（可审计问责性）**：证据对象形成角色分离的图（root → evaluation → H1 → H2 → capability → H3 → consumption → outcome → closure），公开验证检查完整性与签名，特权重放重构受保护策略与状态，缺失证据必须报告为“不完整”，不能被解释为“未发生”。
- **证据平面**：使用 RFC 8785 规范化、SHA-256 摘要、Ed25519 签名，且为 root、gateway、confirmation、provenance、adapter、provider-evidence、log 等角色分别注册独立密钥；在线路径调用离线证据投影，证据永不执行。

### 6.（补全）核心经验与总体结论

……**重试与恢复是权威生命周期中最容易被忽视、却最容易产生额外效果的阶段**：一旦响应丢失，系统必须把“歧义”视为权威状态的一部分，而不是简单地重发或替换。只有获得提供方明确的终止结果、或接受附带投递围栏的“认证无效果”证书后，才能释放预留或转移给后继。AID-Guard 的全部机制可以概括为：**将授权从一个静态的准入判断，扩展为一个从批准根到提供方终止状态的、单调且可审计的状态机**。在这个状态机中，预留身份是唯一不变量，所有阶段共享同一个不可变请求身份与规范化效果标识，从而把多跳效果压缩为一个可验证的原子承诺。

### 7. 局限性与未解决的问题

- **形式化保证有限**：论文对安全属性的验证采用有限深度（6/8）的状态空间搜索和有界模型检查，而非无界并发或分布式系统下的形式化证明。声明中的“保持语义”仅在声明的提供方合约、故障调度和攻击模型下成立；对任意第三方 MCP 服务器或非确定性网络分区，尚无一般性证明。
- **对提供方合作程度要求较高**：“认证无效果”证书依赖提供方言明的前置交付身份、可线性化终止、权威查询和保留期四要素。若提供方不提供这些接口，或保留期短于 AID-Guard 的恢复视界，则歧义期间只能永久保留配额，无法安全释放。这限制了协议对“黑盒”或“不透明”外部服务的适用性。
- **单一原型与部署形态**：官方原型运行于单机 SQLite（WAL）之上，没有验证多副本、多区域、故障转移等分布式权威存储场景。SQLite 的单写者事务模型为线性化提供了便利，但生产环境通常需要更高可用的权威存储，且需要额外的复制协议来维持相同的预留与证据语义。
- **效用代价仍然可观**：即使采用 Typed-3x 模板缓解后，良性任务效用也仅从 12/48 提升到 22/48（DeepSeek）和 17/48 至 26/48（Qwen），仍有接近一半的良性任务未能完成。严格的精确单一清单（Exact-1x）导致 35.4–43.8 个百分点的效用下降。这说明“绝对安全”与“任务可用性”之间的张力远未解决，只是被量化地暴露了出来。
- **无种子评估的因果性局限**：AgentDojo 实验没有生成种子，不同模型、不同配置下运行的绝对效用不能严格横向比较；论文自己也声明这是描述性而非因果性结论。虽然通过控制变量和匹配阳性控制增强了内部效度，但外部效度仍受限于 AgentDojo 套件和所选的四个模型。
- **性能与开销数据不足**：论文给出了证据测量，但没有给出权威存储、签名验证、D2 提交时重验证的端到端时间预算，也没有量化在真实高频低延迟场景下（如金融支付）协议引入的额外延迟和吞吐损失。
- **证据离线验证的采用门槛**：虽然证据平面支持公开验证与特权重放，但“缺失证据必须报告为不完整”这一原则要求所有参与方（代理、提供方、审计方）都接受同一套证据规范并长期保存。在多方异构系统中，这需要较强的治理协调；论文未讨论如何对不兼容的现有系统进行迁移或强制实施。

### 8. 批判性评价与启示

**主要贡献**：AID-Guard 的贡献并不在于某单个密码学原语或拦截机制，而在于它首次把“授权”建模为一个从批准根延伸到提供方终止结果的、有状态的血缘链。它清晰地区分了“权威（authority）”与“观察（observation）”，强调规划器输出只是数据、不能铸造权限；同时把重试、恢复、歧义这些以往被分散处理的故障情况，统一收拢到“预留-扣费-终止-释放/转移”的状态机中。这种视角的转变比任何具体算法都更有价值。

**实验的可信度**：论文在实验设计上刻意回避了“模型拒绝”这一混淆因素——通过正向控制和直接提交，证明了即使提议者完全失陷、模型完全不拒绝攻击，AID-Guard 也能在机制层面阻断不安全效果。这一点是对现有 LLM 安全评测（如 AgentDojo、InjecAgent）的重要补充：很多防御方法的高安全性部分来自模型的固有拒绝行为，而 AID-Guard 证明了其安全性不依赖模型行为，而是依赖协议本身。这一验证思路值得后续研究借鉴。

**潜在质疑**：有人可能会问，既然要求“提供方配合”和“幂等合约”，为什么不直接让提供方实现严格幂等并依赖调用的 idempotency key？AID-Guard 的回应是：幂等键只约束“键相同的请求”，而无法防止请求体在提交前被替换——D2 提交时重验证正是针对这一缺口。但这也暴露了协议对提供方接口行为（终止化、查询、保留期）的强假设，在现实生态中，不是所有 API 都愿意或能够提供“终止化后拒绝一切后续交付”的操作。因此，协议的落地点可能首先在高价值、强协作的垂直场景（如 Stripe 这类已有良好幂等语义的支付 API），而不是长尾的第三方 MCP 服务器。

**整体评价**：AID-Guard 是一篇方法严谨、语义清晰、实验设计扎实的系统安全论文。它把 AI 代理安全从“提示注入过滤”提升到了“分布式授权协议”的层面，给出了可验证、可审计、可组合的安全属性。尽管存在部署复杂度和效用代价等现实约束，但其核心思想——**授权必须是状态化的、必须延伸到效果边界、必须在歧义时保守关闭**——将大概率成为后续代理安全基础设施的设计基线。对于正在构建 agent 平台、工具调用网关或高价值外部 API 集成层的工程团队，该协议至少值得作为一个参考架构来评估。
