## 摘要
长周期安全LLM代理必须在许多相互依赖的交互中携带信息和决策，后续操作往往依赖于早先发现的服务、状态或访问权限。这使得最终任务的成功难以解释：代理可能在到达利益能力可以被执行的点之前就已失败。我们提出了一种诊断方法，通过检查点来装备安全任务，区分能力暴露前后的失败，并使用受控干预来测试怀疑的上游瓶颈。我们在四个任务族中评估了该方法，涉及延迟重用发现的信息、重用观察到的状态、从失败策略中恢复以及不确定结果后的决策。在观察状态重用方面，检查点分析显示，Gemini 2.5 Flash的许多失败发生在模型观察到之后预期重用的状态之前。在一项预先指定的92种子研究中，针对性的协议消歧指导将状态观察从匹配的非指导对照消息下的65.5%提高到95.4%。使用Gemini 3.7 Flash重复相同设计产生了相反的效果，而状态观察不再可靠地预测任务完成。这些结果表明，主要的失败来源可能在模型代际之间转移，这促使评估应诊断长周期安全代理在哪里以及为何失败，而不是仅依赖总体任务成功。

## Abstract
Long-horizon security LLM agents must carry information and decisions across many dependent interactions, where later actions often depend on services, state, or access discovered much earlier. This makes final task success difficult to interpret: an agent may fail before it ever reaches the point where the capability of interest can be exercised. We present a diagnostic methodology that instruments security tasks with checkpoints, separates failures before and after capability exposure, and uses controlled interventions to test suspected upstream bottlenecks. We evaluate the methodology across four task families involving delayed reuse of discovered information, reuse of observed state, recovery from failed strategies, and decision making after uncertain outcomes. On observed state reuse, checkpoint analysis shows that many Gemini 2.5 Flash failures occur before the model observes the state it is later expected to reuse. In a pre-specified 92-seed study, targeted protocol-disambiguation guidance increases state observation from 65.5\% under a matched non-guidance control message to 95.4\%. Repeating the same design with Gemini 3.7 Flash produces the opposite effect, while state observation no longer reliably predicts task completion. These results show that the dominant source of failure can shift across model generations, motivating evaluation that diagnoses where and why long-horizon security agents fail rather than relying only on aggregate task success.

## 1. 论文的核心问题与整体含义

- **研究动机**：长周期安全 LLM 代理需要在大量相互依赖的交互中持续携带信息并做出决策，后续操作往往依赖早先发现的服务、状态或访问权限。这使得最终任务成功率难以解释——代理可能在到达目标能力可被真正执行的点之前就已失败。
- **核心问题**：端到端成功无法区分两类失败：一是代理从未到达能力可被行使的“暴露点”（exposure），二是代理到达暴露点之后能力本身失效。若将所有失败笼统归因于目标能力，会误导对模型能力的判断。
- **整体含义**：论文倡导超越“是否成功”的评估范式，转向诊断“在哪里失败、为什么失败”，尤其对于安全领域中具有长依赖链的代理任务。研究发现，不同模型代际的主要失败来源可能完全不同，因此需要过程级、可解释的评估方法。

## 2. 论文提出的方法论

- **核心思想**：用检查点（checkpoint）将安全任务拆分为可观测的证据节点，区分“能力暴露前”与“能力暴露后”的失败；再用受控干预（controlled intervention）对候选的瓶颈机制进行因果测试。
- **关键技术细节**：
  - **检查点定义**：每个任务定义若干检查点，只有当轨迹中出现具体证据（如命令输出、服务响应）时才计为达到；仅尝试动作不算。例如 CSR 任务中 C3 表示“精确观察到生成的状态”，是状态重用能力的门控检查点（gating checkpoint）。
  - **暴露条件分析**：报告三个指标——端到端成功率、门控检查点到达率、到达暴露点后的成功率。这能定位失败发生于能力暴露之前还是之后。
  - **受控干预设计**：对同一环境种子分别执行 baseline（无消息）、rescue（包含针对怀疑瓶颈的目标信息）和 placebo（与 rescue 结构匹配但与任务无关的消息）三种条件。rescue vs placebo 是主要比较，用于隔离目标信息的效果。
  - **干预触发机制**：可在固定模型轮次或指定事件后触发，不检查任务是否成功，也不读取生成的任务值来决定是否干预。
  - **实验治理与可复现性**：预先冻结实验清单（manifest）、执行顺序、干预内容、源码版本；采用追加式账本记录运行状态；基础设施失败（infrastructure failure）与科学任务失败分开记录，不静默重跑或替换。
  - **统计方法**：配对二元结果使用双侧精确 McNemar 检验（α=0.05），报告不一致配对的方向和比例；样本量基于配对检验功效分析预先确定。

## 3. 实验设计

- **任务场景**：论文自建了四个长周期安全诊断任务族，均在确定性 Docker 多服务环境中运行：
  - **DSR（Delayed Secret Reuse）**：延迟秘密重用，分 Short/Long 变体。
  - **CSR（Controlled State Reuse）**：受控状态重用，分 Short/Medium/Long，中间动作数分别为 2、8、20，是主要受控任务。
  - **SR（Strategy Recovery）**：策略恢复，分 Control/Explicit/Ambiguous 变体。
  - **AOA（Ambiguous-Outcome Adaptation）**：模糊结果适应，分 Transient/Persistent/Explicit 变体。
- **Benchmark 情况**：没有使用现成公开基准（如 Cybench、AutoPenBench 等），而是为诊断特定失败机制构建了新的确定性环境；与这些基准的关系在相关工作部分进行了对比说明。
- **对比模型**：主要对比 Gemini 2.5 Flash 和 Gemini 2.5 Pro；在确认性干预研究中，使用 Gemini 2.5 Flash 做确认实验，并用 Gemini 3.7 Flash 做跨代复现。未与其他第三方开源模型（如 GPT、Claude、Llama 等）进行对比。
- **评估方式**：统一 agent scaffold、工具协议、执行限制（90 条命令、120 模型轮次、12 次连续协议错误终止、30 秒命令超时、60 秒请求超时、1024 输出 token 上限等）。

## 6. 论文的主要结论与发现

- **核心发现**：许多 Gemini 2.5 Flash 在 CSR 上的失败发生在观察状态（C3）之前，而非状态重用本身。端到端成功率 33% 中，60% 的失败在暴露前；一旦到达 C3，下游完成率高达 97.6%。
- **干预效果**：针对协议发现瓶颈的 rescue 信息将 Gemini 2.5 Flash 的 C3 到达率从 placebo 下的 65.5% 提升到 95.4%（McNemar p=2.56×10⁻⁶），证明协议发现是因果性的上游瓶颈。
- **跨代反转**：同样的干预在 Gemini 3.7 Flash 上产生相反效果——rescue 下 C3 到达率为 79.1%，placebo 下为 98.9%（p=4.01×10⁻⁵）；而且到达 C3 后 Gemini 3.7 的成功率仅 36.1%，远低于 Gemini 2.5 的 97.6%。说明主要失败源从“发现瓶颈”转变为“下游执行瓶颈”。
- **次要任务教训**：
  - DSR-Long 同时改变依赖长度和路由发现，不能作为保留能力的干净测量。
  - SR 全部成功，说明存在性能天花板，无法区分模型。
  - AOA 的预期重访分支从未被达到（C6 到达率为 0/20），说明任务设计未实际测试其目标行为。
- **总体结论**：端到端成功率掩盖失败位置；检查点+干预方法能揭示瓶颈是否在能力暴露前；模型代际变化可能导致失败机制转移，诊断评估应固定实验设计并保留意外结果。

## 7. 优点

- **方法创新性**：提出“能力暴露”概念，将失败分为“暴露前”与“暴露后”，比单纯子任务/里程碑更直接地对应目标能力。
- **因果诊断严谨**：使用 rescue–placebo 配对干预，排除“额外消息”这一混淆因素，可对怀疑的瓶颈进行因果性测试而非仅做轨迹推测。
- **实验治理强**：预先注册、冻结清单、追加式账本、基础设施失败隔离等机制显著提高可复现性和可信度。
- **跨代复现设计**：在未观察新模型行为的情况下直接复用冻结设计，成功揭示了干预方向的反转，展示了失败机制随代际变化这一重要现象。
- **可解释性与可操作性**：检查点定义清晰（例如 CSR 的 C1–C10），可为后续 benchmark 设计提供具体参考。

## 8. 不足与局限

- **模型覆盖有限**：仅使用 Gemini 系列模型（Flash、Pro、3.7 Flash），未验证在其他 LLM 上的诊断效果和跨架构普遍性。
- **任务规模与环境复杂度有限**：任务为小型 Docker 多服务模拟环境，与真实网络、真实攻击面存在差距；论文也承认不旨在测量通用渗透测试能力。
- **部分任务失效**：SR 出现天花板效应，AOA 未到达预期分支，导致这些任务无法贡献有效对比，削弱了“四个任务族”的完整性。
- **样本量较小**：初始描述性实验每条件仅 5–15 次运行；跨代比较是描述性的，未对模型间差异做正式统计检验。
- **资源与成本信息缺失**：未报告 API 调用次数、预算或能耗，影响成本可复制性。
- **干预内容特定性**：CSR 的干预仅针对“HTTP 与 SSH 协议区分”这一具体瓶颈；在其他任务或其他模型中未必适用，研究外部效度有限。
- **潜在偏差**：确认性研究因基础设施异常排除了 5 个 placebo 有效配对，虽提供敏感性分析，但仍可能引入微小偏差；Gemini 3.7 的成功差异未达统计显著（p=0.0807），可能样本量不足。
