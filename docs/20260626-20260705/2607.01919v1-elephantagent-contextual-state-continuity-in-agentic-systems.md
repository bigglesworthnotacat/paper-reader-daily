## 摘要
智能体系统通过调用外部工具和维持持久化内存来增强其能力。然而，这些外部依赖引入了新的攻击面。近期出现的工具和内存投毒攻击表明，恶意构造的工具描述符和被污染的内存可以隐蔽地偏转智能体行为。这些威胁反映了一个更深层次的问题：智能体在规划和执行过程中的上下文状态缺乏可验证的连续性。我们提出ElephantAgent，一种强制实施上下文状态连续性以防御上下文状态投毒协议。受先前状态连续性机制（如Nimble）启发，ElephantAgent将这种保护扩展到智能体系统的演化上下文状态。我们将上下文状态定义为智能体整个上下文中有限的、安全关键的子集（例如工具状态和内存）。在处理每个查询之前，ElephantAgent重新计算本地上下文状态的摘要，并与最新授权的摘要进行验证。通过使用复制的可信硬件，ElephantAgent维护一个可线性化的已授权上下文状态转换账本，并检测带外状态篡改。为处理带内语义滥用，ElephantAgent额外提供历史可追溯性，支持条件性的事后审计和恢复到已知良好的先前状态。

## Abstract
Agentic systems enhance their capabilities by invoking external tools and maintaining persistent memory. However, these external dependencies introduce novel attack surfaces. Recent tool and memory poisoning attacks show that maliciously crafted tool descriptors and poisoned memory can covertly bias agent behavior. These threats reflect a deeper issue: the lack of verifiable continuity in the agent's contextual state for planning and execution. We present ElephantAgent, a protocol that enforces Contextual State Continuity to defend against contextual state poisoning. Inspired by prior state-continuity mechanisms (e.g., Nimble), ElephantAgent extends this protection to the evolving contextual state of agentic systems. We define the contextual state as the bounded, security-critical subset of the agent's entire context (e.g., tool state and memory). Before processing each query, ElephantAgent recomputes the digest of the local contextual state and verifies it against the latest authorized digest. Using replicated trusted hardware, ElephantAgent maintains a linearizable ledger of authorized contextual state transitions and detects out-of-band state tampering. To handle in-band semantic abuse, ElephantAgent additionally provides Historical Traceability, enabling conditional post-hoc audit and recovery to a known-good prior state.

## 1. 核心问题与整体含义（研究动机和背景）

- **核心问题**：智能体系统（如基于 Model Context Protocol, MCP 的系统）通过调用外部工具和维持持久化内存来增强能力，但这些外部依赖引入新的攻击面。攻击者可实施**工具投毒**（如 MCP“rug pull”攻击：注册时呈现良性描述符，之后静默修改为恶意指令）和**内存投毒**（篡改外部存储的对话历史或人工制品），从而隐蔽地偏转智能体的推理和行动，使其成为“混乱的代理人”。现有防御（如检测、签名）多针对单一攻击，缺乏对**上下文状态**（工具描述符 + 内存）整体连续性的保护。
- **根本原因**：智能体在规划和执行时依赖的上下文状态（安全关键子集）缺乏可验证的连续性——工具描述符和内存可以被添加、删除或修改而不被察觉，导致敌手可进行**上下文状态投毒**。
- **整体含义**：需要一种机制，将智能体的上下文状态绑定到不可篡改、可验证的线性化历史，从而检测并阻止任何未授权的状态变化（带外篡改），并为带内语义滥用（如提示注入后产生的合法但恶意的状态转换）提供事后审计和恢复能力。

## 2. 方法论

### 核心思想
- **强制上下文状态连续性**：在每次查询处理前，重新计算本地上下文状态摘要（哈希），并与线性化账本中的最新授权摘要比对；仅当匹配时才允许智能体进行规划和执行。
- **利用复制可信硬件**：维护一个由多个 TEE（Intel TDX）保护的节点组成的**状态连续性模块**（SCM），运行 Nimble 线性化账本，记录所有授权的状态转换。
- **commit-before-finalize** 工作流：状态更新时先向 SCM 提交下一状态摘要并获取签名收据，然后才执行本地副作用并记录本地账本。

### 关键技术细节
1. **实体与信任假设**：
   - User（可信）：初始批准工具集和内存源。
   - MCP Host（运行在 TEE 内）：包含 Agent、MCP Client 以及 **Context Guard（CG）**。
   - **SCM**（可信）：复制式 TEE 后台服务，维护线性化、只追加的账本。
   - MCP Servers（不可信）：可能返回恶意描述符。
   - Host Platform（不可信）：可能篡改或回滚本地持久化数据。

2. **上下文状态定义**：
   - \( C_t = \langle T_t, M_t \rangle \)
   - \( T_t \)：工具描述符（名称、描述、输入输出 schema、权限）。
   - \( M_t = \langle M_t^I, M_t^R, M_t^A \rangle \)：内存，包含长期指令、对话记录、当前人工制品。
   - 摘要 \( h_t = H(C_t) \)，H 为抗碰撞哈希。

3. **协议流程（Algorithm 5）**：
   - **初始化**：通过 `ApprovePolicy`（实验中使用 TOFU）批准初始状态；计算摘要并锚定到 SCM 新账本；快照并密封。
   - **状态验证**（`VerifyState`）：对每个查询，获取本地上下文状态，重算摘要；向 SCM 发起 `GetLatestState`（带新鲜 nonce），验证返回的签名证明；比对摘要是否一致。不一致则 fail‑closed。
   - **状态更新**（`UpdateState`）：执行计划后，预览推导下一摘要（无害）；向 SCM 提交 `Commit(ℓ, id+1, h_next)`；获得签名收据后，密封待定记录，再执行本地副作用（finalize），最后追加本地账本（含收据和可选快照引用）。
   - **历史可追溯性**：通过本地账本和快照，可审计状态演进并恢复到已知良好状态（通过验证快照摘要与账本条目的匹配）。

4. **安全分析**：形式化证明了在标准假设下（SCM 账本正确性、签名不可伪造、哈希抗碰撞、CG 不可绕过、认证通道等），系统满足上下文状态连续性（Lemma 1 & Corollary 1）和历史可追溯性（Lemma 2 & Corollary 2）。

## 3. 实验设计

- **场景/数据集**：
  - 三个智能体任务：**Email Triage**（邮件分类）、**Code Bug Fix**（代码修复，基于 QuixBugs 仓库）、**Calendar Scheduling**（日程安排，基于 CalDAVTester 数据）。
  - 每个任务包含多个工具调用（共实现 19 个 MCP 工具）。
- **Benchmark**：比较两种模式：
  - **NoGuardAgent**：标准的 MCP 工作流（无 CG 和 SCM），在非机密 VM（NT2）上运行。
  - **ElephantAgent**：包含 CG（在 TDX VM TDX1 上运行）和 SCM（在 TDX2 和 TDX3 上部署 5 节点 Nimble 服务）。
- **对比方法**：没有直接与现有防御（如 MindGuard、SecureMCP）比较端到端开销，而是以无保护基线为参照，重点测量状态连续性带来的额外延迟。
- **消融实验**：
  - **AttestedSrvAgent**：仅在 MCP Server 端启用 TDX 保护和远程认证（无 CG/SCM），评估服务端 TEE 开销。

## 4. 资源与算力

- **硬件环境**：阿里云“ecs.g9i.xlarge”实例，配备 Intel Xeon 6982P-C CPU（支持 Intel TDX）。使用了 3 个 TDX 虚拟机（TDX1, TDX2, TDX3）和 2 个非机密虚拟机（NT1, NT2），所有实例位于同一北京区域数据中心内。

- **实验数量**：每个任务运行 **50 次有效运行**（共 3 个任务），报告平均值；消融实验同样基于 50 次运行。
- **充分性与公平性**：
  - 实验设计合理：将状态连续性保护分解为初始化、数据加载、验证、更新、任务处理等阶段，分别测量耗时。

## 6. 主要结论与发现

- **有效性**：ElephantAgent 能够检测所有带外篡改（工具描述符突变、内存文件直接修改、内存回滚等），并通过历史可追溯性支持事后审计和恢复到已知良好状态。
- **性能开销小**：
  - 初始化一次性成本：219.15 ms（基线）→ 1800.46 ms（ElephantAgent），增加约 8.22 倍，但仅在首次启动时。
  - 每查询验证耗时约 4.2–4.3 ms，状态更新耗时约 5.2–5.4 ms。
  - 端到端总时间开销仅 **1.02–1.04 倍**（相对于无保护基线），即便在小型任务中也不显著。
- **消融实验**：AttestedSrvAgent 模式增加 1.12–1.22 倍工具调用时间，初始化增加 1.51 倍，表明 TEE 保护服务器端有一定但可接受的代价。

## 7. 优点

- **创新性**：首次将状态连续性保护（传统用于防御回滚攻击）扩展到智能体系统的上下文状态，形式化定义了 Contextual State Continuity 和 Historical Traceability 两个属性。
- **协议无关性**：ElephantAgent 是添加式协议，可应用于 MCP 或 CLI 架构，具有良好的通用性。
- **防御确定性**：通过加密摘要比对检测篡改，无需训练检测器，避免了假阳性/假阴性问题。
- **低开销**：实验证明每查询仅增加数毫秒延迟，适合实际部署。
- **完整性**：提供了安全证明（在标准假设下）、完整的算法伪代码（Algorithms 1–5）以及详细的安全分析（Lemma 1, Corollary 1, Lemma 2, Corollary 2）。
- **实用化**：利用成熟的 TEE 技术（Intel TDX）和已验证的 Nimble 账本，降低工程难度。

## 8. 不足与局限

- **LLM 通信信道未保护**：Agent 与外部 LLM 服务之间的信道及模型本身不在保护范围内，可能导致提示/响应被篡改。论文建议部署可信本地模型（如 Qwen 3.5-27B + NVIDIA H100 机密计算）作为缓解。
- **可用性受限于敌手干扰**：安全优先于活性——如果敌手持续篡改本地上下文状态或阻止对 SCM 的访问，系统将 fail‑closed，导致无法处理查询。
- **历史可追溯性依赖本地工件可用性**：TEE 密封提供机密性和完整性，但不保证持久化数据不被删除；如果敌手删除本地账本或快照，审计和恢复功能将失效。
- **恢复范围有限**：仅恢复有限上下文状态 \( C_t \)，不包含智能体完整运行时上下文；且恢复时仅验证状态是以前忠实演化的，但不保证其新鲜度（可能恢复到一个较早的可疑状态）。
- **初始信任根脆弱**：实验使用 Trust On First Use（TOFU）批准初始状态，可能被敌手在首次配置时注入恶意状态。生产部署应改为签名验证等更强策略。
- **假设 TEE 安全**：未考虑侧信道攻击、硬件漏洞等高级攻击，这些超出本文范围。
- **实验覆盖不全**：未测试大规模并发、网络分区、SCM 节点故障场景；未评估内存增长对摘要计算和快照存储的影响；对比方法有限（仅与无保护基线比较，未与现有防御如 SecureMCP 比较开销）。
